---

| ---- | ---------------------------------------- |

## 2. 项目背景

在敏捷研发体系中，测试自动化能力逐步从：

```text
PRD → 测试点 → 测试用例
```

演进为：

```text
PRD → 需求知识模型（RKM）→ 测试点 → 测试用例 → 覆盖率与回归分析
```

当前问题主要集中在：

- 原始 PRD 难以稳定拆解为可测试的需求单元。
- 不同人员对功能点、业务规则、异常流程的拆解标准不一致。
- 测试点生成缺少统一、可追溯的语义输入。
- 需求之间的依赖、影响范围和回归风险缺少结构化表达。
- 需求变更后，结构化需求与测试资产之间缺少影响分析依据。

### 2.1 架构调整背景

V2.1 版本采用独立应用（FastAPI Service）方案进行开发，存在以下问题：

- **集成成本高**：独立服务需要额外的进程管理、网络通信和部署运维，增加 function_test 工作流的集成复杂度。
- **调用链路长**：function_test 需要通过 HTTP 请求调用 RKM 能力，引入序列化/反序列化开销和错误处理复杂度。
- **部署依赖强**：独立服务需要独立的运行环境、端口分配和健康监控，不利于在 CI/CD 流水线中轻量运行。
- **版本耦合难管理**：服务间版本兼容性需要额外维护，增加回归测试负担。

因此，V3.0 将 RKM 从独立应用调整为 **Python 库/模块**，以配置文件驱动方式运行，直接嵌入 function_test 工作流。

## 3. 项目目标

构建一个 RKM（Requirement Knowledge Model，需求知识模型）构建模块，以 Python 包形式提供需求结构化能力，将不同来源的需求材料转换为统一的结构化需求文档，为 function_test 工作流中的测试点与测试用例生成提供标准输入。

### 3.1 核心目标

1. 以 Python 模块形式提供 RKM 构建、校验、分析等核心能力，支持 function_test 直接 import 调用。
2. 支持将原始需求文档解析为统一的文档片段。
3. 支持按 Domain / Module / Feature / Requirement 四层结构组织需求。
4. 支持将复合需求拆解为单一、可验证、可测试的 Requirement。
5. 支持识别并表达功能点之间的依赖关系、数据关系、流程关系和状态关系。
6. 支持输出人类可读的 Markdown 需求知识文档（Obsidian Vault）。
7. 支持对 RKM 完整性、准确性、一致性、可测试性进行质量校验。
8. 支持为测试点和测试用例生成提供明确映射字段。
9. 支持通过 YAML/JSON 配置文件驱动 RKM 构建流程，无需编写代码即可完成配置。

### 3.2 非目标

以下能力不纳入当前版本范围：

- 不实现完整测试用例生成，只提供测试生成所需的结构化输入。
- 不建设复杂知识图谱数据库，当前使用 Obsidian Markdown Vault 作为知识层。
- 不实现多人协同审批流，仅保留需求状态和版本字段。
- 不实现所有文档格式的完美解析，优先支持文本可抽取的需求材料。
- 不提供独立运行的 Web 服务或 HTTP API，所有能力通过 Python 函数调用暴露。
- 不实现独立的用户界面或前端交互。

## 4. 术语定义

| 术语 | 定义 |
|---|---|
| RKM | Requirement Knowledge Model，需求知识模型，是结构化需求数据的统一表达。 |
| Domain | 业务域，表示较大的业务边界，例如订单、支付、账户。 |
| Module | 模块，表示 Domain 下的业务子系统或功能集合，例如订单状态管理。 |
| Feature | 功能，表示用户可感知的业务能力，例如取消订单。 |
| Requirement | 需求原子单元，表示一个单一、可验证、可测试的功能点或业务规则。 |
| Rule | 业务规则，表示约束、判断条件、计算规则或校验逻辑。 |
| Scenario | 场景，表示在特定角色、条件和触发动作下发生的业务过程。 |
| Dependency | 关联关系，表示 Requirement 与其他功能、规则、状态或数据之间的影响关系。 |
| Source Trace | 来源追溯信息，用于定位结构化需求来自原始文档的哪个位置。 |
| function_test | 集成测试工作流框架，RKM 模块作为其子模块嵌入运行。 |
| RKM Config | RKM 配置文件，YAML 或 JSON 格式，定义项目信息、来源路径、构建参数和输出选项。 |

## 5. 用户与使用场景

### 5.1 目标用户

| 用户角色 | 主要诉求 |
|---|---|
| 测试工程师（function_test 使用者） | 在 function_test 工作流中自动完成需求结构化，生成测试点输入，减少漏测。 |
| 产品经理 | 通过配置文件定义需求来源和构建参数，无需编写代码即可生成 RKM。 |
| 开发工程师 | 理解功能范围、业务规则、依赖关系和变更影响。 |
| 研发管理者 | 查看需求覆盖率、风险项和需求质量状态。 |
| CI/CD 流水线 | 在自动化流水线中作为 function_test 的一个步骤执行 RKM 构建。 |

### 5.2 核心使用场景

1. 用户在项目根目录编写 RKM 配置文件（`rkm_config.yaml`），指定需求来源文档路径和构建参数。
2. function_test 工作流启动，加载 RKM 模块并读取配置文件。
3. RKM 模块解析配置，读取并预处理需求来源文档。
4. RKM 模块执行需求结构化流程（解析 → 拆解 → 关联 → 校验）。
5. RKM 模块输出 RKM JSON 数据和 Markdown 知识文档到配置指定的输出目录。
6. RKM 模块输出质量报告，function_test 根据质量分数决定是否继续后续测试生成步骤。
7. function_test 后续步骤基于 RKM 结构化数据生成测试点和测试用例。

## 6. 总体流程

```text
Step 1  读取 RKM 配置文件
↓
Step 2  加载需求来源文档
↓
Step 3  文档预处理
↓
Step 4  业务层级识别
↓
Step 5  功能点拆解
↓
Step 6  关联关系识别
↓
Step 7  RKM 结构化生成
↓
Step 8  RKM 质量校验
↓
Step 9  输出 RKM JSON + Markdown 知识文档
↓
Step 10 输出质量报告与测试映射数据
↓
Step 11 function_test 消费 RKM 数据，进入测试生成阶段
```

### 6.1 流程输入输出

| 步骤 | 输入 | 输出 |
|---|---|---|
| 读取配置 | rkm_config.yaml | 配置对象（项目信息、来源列表、输出路径、构建参数） |
| 加载来源文档 | 配置中的 sources 路径列表 | 原始文档内容 |
| 文档预处理 | 原始文档内容 | 标准化文档片段 sections |
| 业务层级识别 | sections | domains、modules、features |
| 功能点拆解 | features、sections | requirements、rules、scenarios |
| 关联关系识别 | requirements、rules、scenarios | dependency_graph |
| RKM 结构化生成 | 上述全部结构 | RKM JSON |
| RKM 质量校验 | RKM JSON、原始文档片段 | 校验报告 |
| 输出知识文档 | RKM JSON | Obsidian Markdown 文档 |
| 输出测试映射 | 已确认 RKM | 测试映射数据（供 function_test 消费） |

## 7. 多来源需求处理策略

### 7.1 支持的来源类型

| 来源类型 | 当前版本处理方式 | 可信度默认值 |
|---|---|---|
| Markdown PRD | 按标题、列表、表格解析 | 高 |
| Word 文档 | 提取标题、段落、表格文本 | 高 |
| PDF 文本 | 提取可复制文本，保留页码 | 中 |
| Excel / 表格 | 按行列解析字段、规则、状态、权限 | 中 |
| 接口文档 | 提取接口名称、入参、出参、错误码、业务约束 | 中 |
| 原型说明 | 提取页面、控件、交互、状态变化 | 中 |
| 会议纪要 / 聊天记录 | 仅作为候选需求，必须标记待确认 | 低 |

### 7.2 来源处理规则

- 每个结构化 Requirement 必须记录 source_trace。
- 低可信度来源生成的 Requirement 默认状态为 draft。
- 当不同来源描述冲突时，系统不得自动合并为确定需求，应输出 conflict 标记。
- 无法解析的图片、扫描件、附件应记录为 unsupported_source，并提示人工补充。

## 8. RKM 数据结构

### 8.1 顶层结构

```json
{
  "project": {},
  "sources": [],
  "domains": [],
  "modules": [],
  "features": [],
  "requirements": [],
  "rules": [],
  "scenarios": [],
  "state_machines": [],
  "data_models": [],
  "permission_models": [],
  "dependency_graph": [],
  "risk_items": [],
  "quality_report": {},
  "version": {}
}
```

### 8.2 Requirement 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| requirement_id | string | 是 | 需求原子单元编号，例如 REQ-ORDER-001。 |
| title | string | 是 | 需求名称，应使用明确动作和对象。 |
| domain_id | string | 是 | 所属业务域编号。 |
| module_id | string | 是 | 所属模块编号。 |
| feature_id | string | 是 | 所属功能编号。 |
| source_trace | object | 是 | 来源文档、章节、页码、原文引用。 |
| description | string | 是 | 功能描述，说明该需求要实现什么。 |
| user_role | string | 否 | 适用用户角色。 |
| preconditions | array | 否 | 前置条件。 |
| trigger | string | 否 | 触发动作。 |
| main_flow | array | 否 | 正常流程步骤。 |
| exception_flows | array | 否 | 异常流程步骤。 |
| business_rules | array | 是 | 关联业务规则编号或规则描述。 |
| input_data | array | 否 | 输入数据、字段和约束。 |
| output_result | array | 否 | 输出结果、提示、数据变化。 |
| state_changes | array | 否 | 状态变化，例如 待支付 → 已取消。 |
| dependencies | array | 否 | 关联功能点或规则。 |
| acceptance_criteria | array | 是 | 可验证的验收标准。 |
| test_mapping_hints | array | 是 | 生成测试点时使用的提示。 |
| priority | enum | 否 | P0 / P1 / P2 / P3。 |
| status | enum | 是 | draft / confirmed / changed / deprecated。 |
| version | string | 是 | 当前需求版本号。 |

## 9. 需求分析与拆解规范

### 9.1 拆解流程

1. 识别业务域和模块边界。
2. 提取用户可感知的 Feature。
3. 从 Feature 中拆分 Requirement。
4. 提取业务规则、输入输出、状态变化和异常流程。
5. 补充来源追溯、验收标准和测试映射提示。
6. 标记不确定、冲突或缺失的信息。

### 9.2 Requirement 拆解标准

一个 Requirement 必须同时满足：

- 只描述一个明确的业务目标或业务规则。
- 只有一个主要触发动作或判断条件。
- 有明确的输入、处理条件或输出结果。
- 能独立形成至少一个测试点。
- 能用验收标准判断是否实现。

### 9.3 拆解充分标准

满足以下条件时，认为拆解充分：

- 正常流程、异常流程、边界条件均可被识别或明确标记缺失。
- 每个 Requirement 至少有一条 acceptance_criteria。
- 每个 Requirement 至少有一条 test_mapping_hints。
- 关键业务状态变化已被记录。
- 影响其他功能的依赖关系已被记录。

### 9.4 过度拆解判断

出现以下情况时，视为可能过度拆解：

- 拆分项无法独立验证。
- 仅按按钮、字段、文案机械拆分，未形成业务含义。
- 多个拆分项共享完全相同的触发条件、规则和验收标准。
- 拆分后不提升测试覆盖价值，反而增加维护成本。

### 9.5 不确定信息处理

- 原文缺少必要条件时，应保留缺失项并标记为 unresolved。
- 原文存在多种理解时，应生成 ambiguity_notes。
- 原文冲突时，应生成 conflict_items，不得直接选择其中一个结论。

## 10. 关联功能点识别规则

### 10.1 关联类型

| 关联类型 | 标识 | 说明 | 示例 |
|---|---|---|---|
| 前置依赖 | prerequisite | A 完成后才能执行 B | 登录后才能下单 |
| 数据依赖 | data_dependency | A 产生的数据被 B 使用 | 下单生成订单号，支付使用订单号 |
| 流程依赖 | flow_dependency | A 与 B 属于同一业务流程 | 下单、支付、发货 |
| 状态依赖 | state_dependency | A 改变状态后影响 B | 支付成功后不可取消 |
| 规则依赖 | rule_dependency | A 与 B 共用同一业务规则 | 会员折扣影响订单金额与退款金额 |
| 权限依赖 | permission_dependency | A 与 B 受同一角色或权限控制 | 管理员可审核退款 |
| 异常影响 | exception_impact | A 异常会影响 B 的结果 | 支付失败导致订单保持待支付 |

### 10.2 关联识别规则

当两个 Requirement 满足以下任一条件时，应建立 dependency：

- 一个 Requirement 的输出是另一个 Requirement 的输入。
- 一个 Requirement 的状态变化影响另一个 Requirement 是否可执行。
- 两个 Requirement 出现在同一主业务流程中。
- 两个 Requirement 共享相同业务规则、权限规则或数据对象。
- 一个 Requirement 的异常结果会改变另一个 Requirement 的预期结果。

### 10.3 关联结构

```json
{
  "source_id": "REQ-ORDER-001",
  "target_id": "REQ-PAY-001",
  "type": "state_dependency",
  "description": "支付成功后订单状态变为已支付，取消订单需求不可执行",
  "test_impact": "需要覆盖已支付订单取消失败场景"
}
```

## 11. Markdown 知识文档规范

### 11.1 文档生成原则

- Markdown 是知识阅读与人工修正层，不作为复杂数据库使用。
- 文件内容必须与 RKM JSON 保持字段一致。
- 每个 Requirement 生成一个 Markdown 文档。
- 关联关系使用 Obsidian 双链表达。

### 11.2 Requirement Markdown 模板

```markdown
# REQ-ORDER-001 - 待支付订单允许取消

## 基础信息

- Domain: [[DOM-ORDER]]
- Module: [[MOD-ORDER-STATUS]]
- Feature: [[FEA-CANCEL-ORDER]]
- Status: confirmed
- Version: 1.0.0
- Priority: P1

## 来源追溯

- Source: SRC-001
- Section: 3.2 取消订单
- Quote: 待支付订单允许用户取消

## 功能描述

用户可以取消处于待支付状态的订单。

## 前置条件

- 订单状态为待支付
- 用户为订单创建人

## 主流程

1. 校验订单状态
2. 执行取消操作
3. 订单状态更新为已取消

## 异常流程

- 订单不存在时返回错误提示
- 订单状态非待支付时拒绝取消

## 业务规则

- 仅待支付订单允许取消

## 关联功能点

- [[REQ-PAY-001]]: state_dependency，支付成功后订单不可取消

## 验收标准

- 给定待支付订单，当用户取消订单时，则订单状态变为已取消

## 测试映射提示

- 正常取消待支付订单
- 已支付订单取消失败
- 非本人订单取消失败
```

## 12. 需求变更与版本控制

### 12.1 需求状态

| 状态 | 说明 |
|---|---|
| draft | 系统生成或低可信来源提取，尚未确认。 |
| confirmed | 已经人工确认，可作为测试生成输入。 |
| changed | 需求内容发生变化，需要重新评估测试影响。 |
| deprecated | 需求已废弃，不再用于生成测试点。 |

### 12.2 变更字段

| 字段 | 说明 |
|---|---|
| change_id | 变更编号。 |
| requirement_id | 受影响需求编号。 |
| change_type | added / modified / deleted / deprecated。 |
| change_source | 变更来源。 |
| change_summary | 变更说明。 |
| affected_requirements | 受影响的关联需求。 |
| affected_test_assets | 受影响的测试点或测试用例。 |
| updated_at | 更新时间。 |
| confirmed_by | 确认人。 |

### 12.3 版本规则

- RKM 顶层版本表示本次结构化文档版本。
- Requirement 版本表示单个需求原子单元版本。
- 修改 Requirement 的核心字段时，必须更新 Requirement 版本。
- 删除或废弃 Requirement 时，不物理删除记录，应将 status 改为 deprecated。
- changed 和 deprecated 状态的 Requirement 不应直接进入测试生成，除非用户明确选择。

## 13. 测试点与测试用例映射规则

### 13.1 字段映射

| RKM 字段 | 测试资产映射 |
|---|---|
| description | 正向功能测试点 |
| preconditions | 测试前置条件 |
| trigger | 测试步骤中的触发动作 |
| main_flow | 正常流程测试步骤 |
| exception_flows | 异常测试点 |
| business_rules | 规则类测试点 |
| input_data | 输入校验、边界值、等价类测试点 |
| output_result | 预期结果 |
| state_changes | 状态流转测试点 |
| dependencies | 集成测试点、流程测试点、回归影响分析 |
| user_role | 权限测试点 |
| acceptance_criteria | 用例断言和通过标准 |

### 13.2 生成约束

- 每个 confirmed Requirement 至少生成一个测试点。
- 每条 business_rule 至少应映射到一个规则类测试点。
- 每条 exception_flow 至少应映射到一个异常测试点。
- 每条 state_change 至少应映射到一个状态流转测试点。
- 每条 dependency 应生成至少一个集成或回归测试提示。

### 13.3 映射输出示例

```json
  "test_points": [
    {
      "type": "positive",
      "title": "待支付订单可取消",

    },
    {
      "type": "exception",
      "title": "已支付订单取消失败",

    }
```

### 14.2 Config Loader（配置加载器）

功能说明：

- 读取并校验 YAML/JSON 格式的 RKM 配置文件。
- 将配置解析为结构化配置对象，供后续模块使用。
- 校验配置项的完整性和合法性。

核心接口：

```python
from rkm.config import load_config

# 加载配置文件
config = load_config("rkm_config.yaml")
```

### 14.3 Document Parser（文档解析器）

功能说明：

- 接收原始需求文档路径或内容。
- 提取标题、段落、列表、表格和页码信息。
- 输出标准化 sections。
- 支持多种来源类型，通过策略模式扩展。

核心接口：

```python
from rkm.parser import parse_document

# 解析单个文档
sections = parse_document(
    source_path="docs/prd.md",
    source_type="markdown"
)
```

输出示例：

```json
{
  "source_id": "SRC-001",
  "source_type": "markdown",
  "trust_level": "high",
  "sections": [
    {
      "section_id": "SEC-001",

      "level": 2,
      "content": "待支付订单允许用户取消",
      "location": "3.2"
    }
  ]
}
```

### 14.4 RKM Builder（构建引擎）

功能说明：

- 基于 sections 识别 Domain、Module、Feature。
- 将复合描述拆解为 Requirement。
- 提取 Rule、Scenario、State Change 和 Dependency。
- 生成 RKM JSON 数据结构。

核心接口：

```python
from rkm.builder import build_rkm

# 基于解析结果构建 RKM
rkm_data = build_rkm(
    sections=all_sections,
    project_config=config.project
)
```

### 14.5 RKM Validator（质量校验器）

功能说明：

- 校验字段完整性。
- 校验 Requirement 是否原子化。
- 校验来源是否可追溯。
- 校验验收标准与测试映射提示是否存在。
- 输出缺失、冲突、重复、低置信度需求。

核心接口：

```python
from rkm.validator import validate_rkm

# 校验 RKM 数据
quality_report = validate_rkm(rkm_data)
```

### 14.6 Obsidian Knowledge Generator（知识文档生成器）

功能说明：

- 将 RKM JSON 写入 Obsidian Markdown Vault。
- 生成 Requirement 文档和双链关系。
- 保持 Markdown 内容与 RKM 字段一致。

核心接口：

```python
from rkm.generator import generate_markdown_vault

# 生成 Obsidian Vault 文档
generate_markdown_vault(
    rkm_data=rkm_data,
    output_dir="output/vault"
)
```

### 14.7 Test Mapping Generator（测试映射生成器）

功能说明：

- 基于 RKM 结构化数据生成测试映射数据。
- 输出 function_test 可直接消费的测试点提示。

核心接口：

```python
from rkm.generator import generate_test_mapping

# 生成测试映射数据
test_mapping = generate_test_mapping(rkm_data)
```

### 14.8 Coverage Analyzer（覆盖率分析器）

功能说明：

- 基于 Requirement 粒度计算结构化覆盖率。
- 基于 Feature、Module、Domain 聚合覆盖情况。
- 输出未结构化、低质量、未确认需求清单。

核心接口：

```python
from rkm.analyzer import analyze_coverage

coverage_report = analyze_coverage(rkm_data)
```

### 14.9 Risk Analyzer（风险分析器）

功能说明：

- 基于规则、状态、权限、资金、并发、数据一致性识别风险。
- 为测试生成提供风险优先级提示。

核心接口：

```python
from rkm.analyzer import analyze_risk

risk_report = analyze_risk(rkm_data)
```

### 14.10 RKM Pipeline（构建流水线）

功能说明：

- 编排完整的 RKM 构建流程，从配置加载到最终输出。
- 作为 function_test 调用的主入口，一键执行完整流程。
- 支持选择性执行部分步骤（如仅校验、仅生成文档）。

核心接口：

```python
from rkm.pipeline import run_pipeline, run_validate_only

# 完整流水线执行
result = run_pipeline(config_path="rkm_config.yaml")

# 仅执行校验
quality_report = run_validate_only(rkm_data)
```

## 15. 配置文件规范与函数接口设计

### 15.1 RKM 配置文件格式（rkm_config.yaml）

RKM 模块通过配置文件驱动，不使用 HTTP API。以下为完整的配置文件规范：

```yaml

project:
  project_id: "PROJECT-001"
  project_name: "订单管理系统"
  version: "1.0.0"
  description: "订单管理系统需求知识模型"

  - source_id: "SRC-001"
    source_type: "markdown"          # markdown | word | pdf | excel | api_doc | prototype | notes
    path: "docs/prd/order_prd.md"    # 文件路径（相对于项目根目录）
    trust_level: "high"              # high | medium | low（可选，默认按 source_type 推断）

  - source_id: "SRC-002"
    source_type: "word"
    path: "docs/prd/payment_spec.docx"
    trust_level: "high"

  - source_id: "SRC-003"
    source_type: "excel"
    path: "docs/rules/business_rules.xlsx"
    trust_level: "medium"

# 构建参数
build:

    enabled: true                    # 是否启用 LLM 辅助拆解

  parsing:

    extract_images: false            # 是否提取图片描述
    keep_page_numbers: true          # 是否保留页码信息
  decomposition:
    max_depth: 4                     # 最大拆解层级（Domain/Module/Feature/Requirement）
    min_confidence: 0.7              # 最小置信度阈值
    auto_resolve_conflicts: false    # 是否自动解决冲突（建议关闭）

# 输出配置

  rkm_json:
    enabled: true

  markdown_vault:
    enabled: true
    path: "output/vault"                   # Obsidian Vault 输出目录

    enabled: true
    path: "output/rkm/quality_report.json" # 质量报告输出路径
  test_mapping:
    enabled: true
    path: "output/rkm/test_mapping.json"   # 测试映射数据输出路径

  min_quality_score: 0.90            # 最低质量分数
```

### 15.2 核心函数接口一览

以下为 RKM 模块对外暴露的核心函数接口，供 function_test 集成调用：

```python
# === 主入口 ===

# 一键执行完整 RKM 构建流水线

# result 包含: rkm_data, quality_report, test_mapping, coverage_report, risk_report

# 1. 加载配置

# 3. 构建 RKM

# 4. 质量校验
```

### 15.4 function_test 集成示例

```python
# 在 function_test 工作流中集成 RKM 模块的典型用法

from rkm import run_pipeline

def test_requirement_coverage():
    """function_test 中的一个测试步骤：验证需求覆盖率"""

    # 执行 RKM 构建
    result = run_pipeline(config_path="rkm_config.yaml")

    # 质量门禁检查
    assert result.quality_gate_passed, (
        f"RKM 质量门禁未通过: quality_score={result.quality_report['quality_score']}"
    )

    # 获取测试映射数据，用于后续测试点生成
    test_points = result.test_mapping

    # 验证每个 confirmed Requirement 都有对应的测试点
    confirmed_reqs = [
        r for r in result.rkm_data["requirements"]
        if r["status"] == "confirmed"
    ]
    mapped_req_ids = {tp["requirement_id"] for tp in test_points}

    for req in confirmed_reqs:
        assert req["requirement_id"] in mapped_req_ids, (
            f"Requirement {req['requirement_id']} 缺少测试映射"
        )
```

## 16. 质量评估指标

### 16.1 指标定义

| 指标 | 说明 | 合格标准 |
|---|---|---|
| 字段完整率 | 必填字段填写完整的 Requirement 占比 | >= 95% |
| 来源可追溯率 | 包含 source_trace 的 Requirement 占比 | 100% |
| 原子化合格率 | 满足单一需求标准的 Requirement 占比 | >= 90% |
| 验收标准覆盖率 | 包含 acceptance_criteria 的 Requirement 占比 | >= 95% |
| 测试映射覆盖率 | 包含 test_mapping_hints 的 Requirement 占比 | >= 95% |
| 关联识别覆盖率 | 关键流程中已识别 dependency 的 Feature 占比 | >= 90% |
| 冲突关闭率 | conflict_items 已处理或明确标记的占比 | 100% |

### 16.2 质量报告输出

```json
{
  "quality_score": 0.92,
  "field_completeness": 0.98,
  "traceability_rate": 1.0,
  "atomicity_rate": 0.91,
  "test_mapping_rate": 0.96,
  "quality_gate_passed": true,
  "issues": [
    {
      "type": "missing_acceptance_criteria",
      "requirement_id": "REQ-ORDER-003",
      "severity": "medium",
      "suggestion": "补充可验证的验收标准"
    }
  ]
}
```

### 16.3 开发阶段准入标准

RKM 文档进入下一阶段开发前，必须满足：

- 所有 Requirement 均有 requirement_id、title、source_trace、description、business_rules、acceptance_criteria、test_mapping_hints、status、version。
- confirmed 状态的 Requirement 不存在 unresolved 或 conflict 标记。
- 每个 Feature 至少包含一个 Requirement。
- 关键业务流程中的 dependency 已完成识别。
- quality_score 不低于 0.90。
- 质量门禁（quality_gates）配置中的所有条件均已满足。

## 17. 权限、异常与边界处理

### 17.1 权限规则

- RKM 模块的调用权限由 function_test 框架统一管理，模块本身不做独立鉴权。
- draft、changed、deprecated 状态的 Requirement 需要在测试生成前提示用户确认。
- 手动修改 Markdown 后，应触发 RKM 字段一致性校验。

### 17.2 异常处理

| 异常场景 | 处理方式 |
|---|---|
| 配置文件不存在或格式错误 | 抛出 `RKMConfigError`，中断流水线并输出错误详情。 |
| 来源文档路径不存在 | 抛出 `RKMSourceNotFoundError`，记录缺失文件路径。 |
| 文档为空 | 返回空 sections，在质量报告中标记 warning。 |
| 文档无法解析 | 返回 unsupported_source，在质量报告中记录失败原因。 |
| 需求描述冲突 | 生成 conflict_items，等待人工确认。 |
| 必填字段缺失 | 生成 validation issue，不允许进入 confirmed 状态。 |
| 关联对象不存在 | 标记 dangling_dependency，并在质量报告中提示修复。 |
| LLM 调用失败 | 降级为规则引擎模式，在报告中标记 llm_fallback。 |
| 质量门禁未通过 | `RKMPipelineResult.quality_gate_passed` 为 False，function_test 据此决定是否中断。 |

### 17.3 异常类定义

```python
class RKMError(Exception):
    """RKM 模块基础异常类"""
    pass

class RKMConfigError(RKMError):
    """配置文件错误"""
    pass

class RKMSourceNotFoundError(RKMError):
    """来源文档未找到"""
    pass

class RKMParseError(RKMError):
    """文档解析失败"""
    pass

class RKMValidationError(RKMError):
    """RKM 校验失败"""
    pass

class RKMQualityGateError(RKMError):
    """质量门禁未通过"""
    pass
```

## 18. 技术选型

### 18.1 核心语言与运行时

- **Python 3.10+**：模块开发语言，与 function_test 运行环境保持一致。
- **无需独立服务进程**：模块以库形式被 import，不占用独立端口或进程。

### 18.2 数据结构与校验

- **Pydantic V2**：数据模型定义与校验，确保 RKM 数据结构的类型安全和序列化能力。
- **PyYAML**：YAML 配置文件解析。

### 18.3 文档解析依赖

| 来源类型 | 解析库 | 说明 |
|---|---|---|
| Markdown | markdown-it-py / mistune | Markdown 结构化解析 |
| Word | python-docx | 提取标题、段落、表格 |
| PDF | PyMuPDF (fitz) | 提取文本和页码 |
| Excel | openpyxl | 解析行列数据 |

### 18.4 AI 与规则引擎

- **LLM SDK**（如 openai / langchain）：辅助需求抽取、拆解、补全和冲突识别。
- **Prompt Chain**：按解析、拆解、关联、校验分阶段处理。
- **Rule Check**：执行必填字段、状态、关联、质量指标校验。
- LLM 为可选依赖，未配置时降级为纯规则引擎模式。

### 18.5 知识存储层

当前版本使用 Obsidian Vault（Markdown 知识库），不引入 Neo4j。

用途：

- RKM 持久化（Markdown 文件形式）。
- 人类可读知识网络。
- 手动与 AI 双向编辑。
- 需求关系可视化（通过 Obsidian 图谱视图）。

### 18.6 存储结构

```text

  modules/
  features/
  requirements/
  rules/
  state_machines/
  graphs/
  risks/
```

### 18.7 测试与质量保障

- **pytest**：模块单元测试与集成测试。
- **mypy**：静态类型检查。
- **ruff**：代码风格检查。

### 18.8 包管理与分发

- **pyproject.toml**：项目元数据与依赖管理。
- **pip install**：安装方式，支持 `pip install rkm` 或从本地路径安装。
- 可选发布到内部 PyPI 仓库，供 function_test 项目引用。

### 19.3 与 function_test 的集成方式

RKM 模块通过以下方式集成到 function_test 工作流：

1. **依赖引用**：function_test 项目的 `pyproject.toml` 或 `requirements.txt` 中声明 `rkm` 依赖。
2. **配置文件**：在 function_test 项目根目录放置 `rkm_config.yaml`。
3. **函数调用**：function_test 的步骤/阶段中通过 `from rkm import run_pipeline` 调用。
4. **结果消费**：function_test 读取 `RKMPipelineResult` 中的 `test_mapping` 数据，驱动后续测试生成。
5. **质量门禁**：function_test 根据 `quality_gate_passed` 字段决定是否继续执行。

## 20. 验收标准

### 20.1 功能验收

- RKM 模块可通过 `pip install` 安装，并被 function_test 项目 import 使用。
- 模块可读取 YAML 配置文件并正确解析所有配置项。
- 模块可接收至少一种文本型需求来源并生成 RKM JSON。
- 模块可将复合需求拆解为多个 Requirement。
- 模块可识别至少 prerequisite、data_dependency、state_dependency 三类关联关系。
- 模块可输出 Obsidian Markdown 版本的 Requirement 文档。
- 模块可输出质量报告并列出缺失字段、冲突和未确认需求。
- 模块可输出测试映射数据，供 function_test 后续步骤消费。
- `run_pipeline()` 函数可一键完成完整构建流程。
- 质量门禁机制可正确判断并返回 `quality_gate_passed` 状态。

### 20.2 质量验收

- confirmed Requirement 的必填字段完整率达到 95% 以上。
- 所有 Requirement 均可追溯到来源文档。
- 每个 confirmed Requirement 至少能生成一个测试点。
- changed 和 deprecated Requirement 不会默认进入测试映射输出。
- 关键业务流程的关联关系可以在 Obsidian 双链中查看。

### 20.3 集成验收

- function_test 项目可通过 `from rkm import run_pipeline` 正常调用。
- 配置文件错误时抛出明确的 `RKMConfigError` 异常。
- 质量门禁未通过时，`RKMPipelineResult.quality_gate_passed` 为 False。
- 模块不启动任何独立进程或监听任何网络端口。
- 模块无外部服务依赖（LLM 为可选依赖，可降级运行）。

## 21. 轻量化设计原则

当前版本遵循以下原则：

- 字段少而必要，优先满足需求拆解、追溯、测试映射。
- 规则可判断，避免依赖不可解释的复杂推理。
- 流程短而明确，避免引入审批流、复杂知识图谱和多级元模型。
- 输出可人工修正，Markdown 作为可读知识层。
- 先保证结构化需求文档稳定可用，再逐步增强自动化生成能力。
- **无独立服务依赖**：模块以库形式运行，无需部署、运维和进程管理。
- **配置驱动**：通过 YAML 配置文件控制行为，无需编写代码即可使用。
- **可降级运行**：LLM 为可选依赖，未配置时自动降级为规则引擎模式。

## 22. 最终系统定位

本模块不是独立的测试用例生成应用，而是：

```text
function_test 工作流中的 AI 驱动需求知识建模模块
```

它的核心价值是将原始需求材料转换为统一、可追溯、可测试、可维护的 RKM，作为 function_test 工作流的基础数据层，为测试点、测试用例、覆盖率分析和回归影响分析提供可靠输入。

### V2.1 与 V2.1 的核心差异

| 维度 | V2.1（独立应用） | V3.0（Python 模块） |
|---|---|---|
| 部署形式 | 独立 FastAPI 服务 | Python 包，pip install 安装 |
| 调用方式 | HTTP API 请求 | Python 函数调用（import） |
| 接口驱动 | RESTful API | YAML/JSON 配置文件 |
| 运行环境 | 独立进程 + 端口 | 嵌入 function_test 进程 |
| 集成成本 | 高（网络通信、部署运维） | 低（依赖引用 + 配置文件） |
| CI/CD 适配 | 需额外启动服务 | 直接作为流水线步骤执行 |
| 存储方案 | Obsidian Vault | Obsidian Vault（保持不变） |
| LLM 依赖 | 必选 | 可选（可降级为规则引擎） |
