## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.3 |
| 日期 | 2026-07-26 |
| 依据 | `docs/接口自动化V1.3-PRD.md` |

## 2. 设计目标

V1.3 在保留 V1.2 已有执行能力的前提下，完成以下数据职责拆分：

1. `data/apis` 只定义接口身份和 Gateway 业务路由。
2. `data/cases` 只定义单接口测试场景，并支持一个接口配置多条 case。
3. `data/flows` 直接引用 API，不再引用单接口 case 文件。
4. `data/scenarios` 独立保存 Flow 各接口步骤的完整参数和断言。
5. 自动会话管理直接使用 API 定义，不再从单接口 case 获取创建、刷新会话配置。

本次设计不改变以下基础能力：

- 固定使用 Gateway HTTP 入口。
- `comm + requests[req_0]` 请求信封结构。
- requests HTTP 客户端。
- pytest 参数化执行。
- YAML 配置方式。
- 日志记录与敏感信息脱敏。
- RuntimeContext 变量替换和响应提取。
- Gateway 分层断言。
- Flow 固定等待、条件轮询和 COS PUT。

## 3. 设计原则

### 3.1 单向依赖

```text
                       ┌── CaseLoader ── 单接口测试入口
ApiLoader / APIs ──────┤
                       └── FlowLoader ── FlowRunner
```

- API 定义是单接口和 Flow 的共同基础。
- CaseLoader 不被 FlowLoader 或 FlowRunner 调用。
- FlowRunner 不读取 `data/cases`。
- API 定义不反向依赖测试数据。

### 3.2 精确数据来源

```text
单接口可执行请求 = API 路由 + 当前 case 完整 params + 当前 case assert
Flow 可执行请求   = API 路由 + 当前 step 完整 params + 当前 step assert
```

V1.3 不再合并 API 默认参数、case 默认参数和 Scenario 覆盖参数。请求参数只有一个明确来源，避免缺参用例被默认值补回，也避免 Flow 随单接口 case 修改而变化。

### 3.3 保持执行协议稳定

`GatewayApi` 当前接收以下内部对象：

```python
{
    "request": {
        "service_name": "...",
        "method_name": "...",
        "params": {},
    },
    "assert": {},
    "extract": {},
}
```

V1.3 的加载层负责把 API 定义与测试数据组装成该内部对象。`build_payload()`、HTTP 客户端和断言器无需理解 API YAML、case 集合或 Flow YAML，从而把改动控制在数据加载和编排层。

## 4. 当前实现分析

### 4.1 当前耦合点

| 位置 | 当前行为 | V1.3 问题 |
| --- | --- | --- |
| `data/cases/*.yaml` | 同时保存路由、参数、断言和提取 | 接口定义与用例未拆分 |
| `test_single_api.py` | 一个 YAML 收集为一条 pytest 用例 | 无法表达一个接口的多条 case |
| `flow_loader.py` | 校验 Flow 的 `call` 对应 case 文件 | Flow 依赖 Cases |
| `flow_runner.py` | 加载 case，并合并 Scenario 参数和断言 | Flow 行为受 case 默认值影响 |
| `conftest.py` | 从 case 顶层读取 tags | 无法读取嵌套 case tags |
| `conftest.py` | 从 case 文件加载会话用例 | Flow 运行仍间接依赖 Cases |

### 4.2 当前基线问题

当前 `data/cases` 文件带有 `01_`～`12_` 数字前缀，但 Flow、测试代码和会话 fixture 引用的是无前缀文件名。全量测试在收集阶段会因找不到 `CreateIntentTask.yaml` 失败，定向框架测试也会因找不到 `CreateAnonymousSession.yaml` 出现失败。

该问题不单独修改旧结构，而是在 V1.3 一次性数据迁移时消除。开发过程中应将其记录为迁移前基线，避免误判为 V1.3 新增回归。

## 6. 数据模型设计

### 6.1 API 定义

示例：

```yaml
id: GetTask
name: 获取搜索任务状态
request:
  service_name: tool.people_insight.SearchService
  method_name: GetTask
```

字段约束：

| 路径 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `id` | string | 是 | 非空；在全部 API 中唯一；与文件名 stem 一致 |
| `name` | string | 是 | 非空 |
| `request` | object | 是 | 必须为对象 |
| `request.service_name` | string | 是 | 非空 |
| `request.method_name` | string | 是 | 非空 |

API 文件禁止保存：

- `params`
- `assert`
- `extract`
- `tags`
- `cases`

加载结果：

```python
{
    "GetTask": {
        "id": "GetTask",
        "name": "获取搜索任务状态",
        "request": {
            "service_name": "tool.people_insight.SearchService",
            "method_name": "GetTask",
        },
        "_source": "data/apis/GetTask.yaml",
    }
}
```

`_source` 仅存在于内存加载结果，用于错误定位，不写回 YAML。

### 6.2 单接口 case 集合

示例：

```yaml
api: GetTask
cases:
  - id: get_task_success
    name: 获取任务状态成功
    tags: [smoke, search, positive]
    request:
      params:
        task_id: task_example
    assert:
      http_status: 200
      gateway:
        code: 0
        message: ok
      response:
        id: req_0
        success: true
        code: 0
        message: ok
      data_fields:
        - status
        - task_id

  - id: get_task_missing_task_id
    name: 缺少 task_id
    tags: [search, negative]
    request:
      params: {}
    assert:
      http_status: 200
      gateway:
        code: 0
      response:
        id: req_0
        success: false
```

文件级约束：

- `api` 必填，且必须引用已加载 API。
- 文件名 stem 必须等于 `api`，确保一个接口只有一个 case 集合。
- `cases` 必须为非空列表。
- 不再支持 V1.2 顶层 `name`、`tags`、`request`、`assert`、`extract` 和 `flow_only` 格式。

case 级约束：

| 路径 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 当前文件内唯一 |
| `name` | string | 是 | pytest 展示名称 |
| `tags` | list[string] | 否 | 默认空列表 |
| `request` | object | 是 | 当前 case 请求数据 |
| `request.params` | object | 是 | 完整参数；允许 `{}` |
| `assert` | object | 是 | 当前 case 的完整断言 |
| `extract` | object | 否 | 路径以业务响应 `data` 为根 |

加载后将每个 case 展开为独立对象：

```python
{
    "id": "GetTask::get_task_success",
    "api_id": "GetTask",
    "case_id": "get_task_success",
    "name": "获取任务状态成功",
    "tags": ["smoke", "search", "positive"],
    "execution_case": {
        "name": "获取任务状态成功",
        "request": {
            "service_name": "tool.people_insight.SearchService",
            "method_name": "GetTask",
            "params": {"task_id": "task_example"},
        },
        "assert": {},
        "extract": {},
    },
}
```

内部 `id` 使用 `API ID::case ID`，避免不同接口出现相同 case ID 时 pytest 显示冲突。

### 6.3 Flow

示例：

```yaml
name: 搜索流程
tags: [flow, media, search]
steps:
  - id: create_task
    api: CreateIntentTask
    extract:
      task_id: $.task_id

  - id: poll_task
    api: GetTask
    until:
      path: $.status
      equals: SUCCEEDED
      interval_seconds: 2
      timeout_seconds: 120

  - id: list_candidates
    api: ListTaskCandidates
    extract:
      candidate_id: $.items[0].candidate_id

  - id: candidate_detail
    api: GetTaskCandidateDetail
```

V1.3 主动作：

| 主动作 | 用途 | 可附加配置 |
| --- | --- | --- |
| `api` | 调用一个 API 定义 | `extract`、`until` |
| `wait` | 固定等待 | 无 |
| `action` | 执行已注册特殊动作 | V1.3 仅 `prepared_media_upload` |

一个步骤必须且只能配置 `api`、`wait`、`action` 中的一项。V1.2 的 `call` 不再识别。

### 6.4 Scenario

示例：

```yaml
name: 姓名搜索成功场景
variables: {}
step_data:
  create_task:
    params:
      client_request_id: "{{client_request_id}}"
      match_strategy: UNION
      clues:
        - type: FULL_NAME
          full_name_query:
            full_name: JOJO CCQQ MOCK
      additional_details: []
    assert:
      http_status: 200
      gateway:
        code: 0
        message: ok
      response:
        id: req_0
        success: true
        code: 0
        message: ok
      data_fields:
        - status
        - task_id
      data_equals:
        status: QUEUED

  poll_task:
    params:
      task_id: "{{task_id}}"
    assert:
      http_status: 200
      gateway:
        code: 0
        message: ok
      response:
        id: req_0
        success: true
        code: 0
        message: ok
      data_equals:
        status: SUCCEEDED
```

校验规则：

- 每个 `api` 步骤必须存在同名 `step_data`。
- `step_data.<step_id>.params` 必须显式存在且为对象，空参数使用 `{}`。
- `step_data.<step_id>.assert` 必须显式存在且为对象。
- `wait` 和 `action` 步骤不配置 `step_data`；所需动态值继续通过 `variables` 和 RuntimeContext 提供。
- Scenario 不允许引用 Flow 中不存在的 step ID。
- Scenario 的参数和断言不与单接口 case 合并。

## 7. 核心模块设计

### 7.1 `api_loader.py`

职责：

- 扫描 `data/apis/*.yaml`。
- 校验 API 文件格式、文件名和 ID。
- 检查重复 API ID。
- 返回以 API ID 为 key 的只读使用约定注册表。
- 根据 API 定义、参数、断言和提取规则组装 `GatewayApi` 可执行对象。

计划接口：

```python
class ApiConfigError(ValueError):
    """接口定义缺失、重复或格式错误。"""


def load_api_definitions(project_root: Path) -> dict[str, dict[str, Any]]:
    """加载并校验全部接口定义。"""


def build_execution_case(
    api_definition: dict[str, Any],
    params: dict[str, Any],
    assertions: dict[str, Any],
    extract: dict[str, str] | None = None,
    name: str | None = None,
) -> dict[str, Any]:
    """深拷贝输入并组装 GatewayApi 可执行 case。"""
```

`build_execution_case()` 必须深拷贝所有输入，防止一次测试中的变量解析或数据处理修改 API 注册表和原始 case。

异常示例：

```text
API 定义文件 GetTask.yaml 的 id 必须与文件名一致，实际为 QueryTask
API CreateIntentTask.request 缺少 method_name
API 定义包含禁止字段 params: CreateIntentTask.yaml
存在重复 API id: GetTask
```

### 7.2 `case_loader.py`

职责：

- 扫描 `data/cases/*.yaml`。
- 读取 API 注册表。
- 校验 case 集合和每条 case。
- 将一个 YAML 中的多条 case 展开为 pytest 可参数化对象。
- 使用 `build_execution_case()` 组合路由和测试数据。

计划接口：

```python
class CaseConfigError(ValueError):
    """单接口 case 集合或具体 case 配置错误。"""


def load_single_cases(
    project_root: Path,
    selected_case_ids: tuple[str, ...] = (),
) -> list[dict[str, Any]]:
    """加载、校验并展开单接口用例。"""
```

筛选规则：

- `selected_case_ids` 为空时加载全部 case。
- 非空时使用完整 ID `ApiId::case_id` 精确筛选。
- 指定 ID 不存在时直接报错，并列出可用 ID。
- 标签转换为 pytest marks 的行为仍由测试入口完成，加载器只返回字符串标签。

### 7.3 `gateway_api.py`

保留：

- `build_payload()`。
- `execute()`、`invoke()` 和 `_post()` 调用协议。
- 会话临期判断、刷新失败后重建。
- 会话数据写入 `.env`。

调整：

1. 构造参数由 `session_cases` 改为 `api_definitions`。
2. 自动会话通过 API ID 获取 `CreateAnonymousSession` 和 `RefreshSession` 路由。
3. 会话请求参数、成功响应规则和提取字段作为运行时协议策略保留在 `GatewayApi` 内，不从测试 case 读取。
4. 缺少会话 API 定义时抛出包含 API ID 的 `RuntimeContextError`。

会话运行策略：

```text
普通 API 调用
    ↓
检查 access token 是否需要刷新
    ↓
可刷新 ── 是 ──> 使用 RefreshSession API 定义组装内部请求
    │                       ↓
    │                  成功后更新上下文和 .env
    │
    └─ 否或刷新失败 ──> 使用 CreateAnonymousSession API 定义组装内部请求
                            ↓
                       成功后更新上下文和 .env
```

内部会话策略仅服务于框架鉴权生命周期，不作为单接口测试用例，也不从 Cases 获取数据，因此删除或修改单接口会话测试不会影响 Flow。

### 7.4 `flow_loader.py`

保留：

- Flow/Scenario 同名配对。
- `--flow` 筛选。
- step ID 唯一校验。
- 路径、等待、轮询和特殊 action 校验。
- 孤立 Scenario 检查。

调整：

- `cases_directory` 替换为 API 注册表。
- 步骤主动作由 `call` 改为 `api`。
- 校验 `step.api` 是否存在。
- 不再加载 case，也不校验 case extract。
- 校验每个 API step 对应 Scenario 数据完整。
- 校验 `extract` 只用于 API step。
- 校验 `until` 只用于 API step。
- 返回的 FlowCase 带上本次已校验的 API 注册表或引用子集，供 FlowRunner 使用。

返回结构：

```python
{
    "id": "AnonymousSessionMediaSearch",
    "name": "搜索流程",
    "tags": ["flow", "media", "search"],
    "flow": {},
    "scenario": {},
    "api_definitions": {
        "CreateIntentTask": {},
        "GetTask": {},
        "ListTaskCandidates": {},
        "GetTaskCandidateDetail": {},
    },
}
```

只携带当前 Flow 引用的 API 定义，减少无关数据并使依赖清晰。

### 7.5 `flow_runner.py`

保留：

- 每条 Flow 创建独立 RuntimeContext。
- `${ENV_NAME}` 环境变量解析。
- 固定等待。
- 条件轮询。
- `prepared_media_upload`。
- 步骤日志和失败即停止。

移除：

- 从 `data/cases` 读取 YAML。
- `_deep_merge()`。
- case 默认参数与 Scenario 参数合并。
- case extract 与 Flow extract 合并。

调整后的 API 步骤：

1. 从 `flow_case.api_definitions` 获取 `step.api`。
2. 从 `scenario.step_data.<step_id>` 获取完整 `params` 和 `assert`。
3. 使用当前 RuntimeContext 递归解析 params 和 assert。
4. 调用 `build_execution_case()` 组装可执行对象。
5. 普通步骤调用 `gateway.invoke()`，再执行基础断言。
6. 轮询步骤每次执行基础断言，直到 `until` 满足。
7. 条件满足后执行 `data_equals`。
8. 执行 Flow step 的 `extract` 并写入当前 Flow 上下文。

伪代码：

```python
api_definition = flow_case["api_definitions"][step["api"]]
params = context.resolve(step_data["params"])
assertions = context.resolve(step_data["assert"])
execution_case = build_execution_case(api_definition, params, assertions)

data = poll_or_invoke(step, execution_case)
assert_data_equals(data, assertions.get("data_equals", {}))
context.extract(data, step.get("extract", {}))
```

`data_equals` 仍以业务子响应 `data` 为根。轮询的 `until.path` 同样以 `data` 为根。

### 7.6 `test_single_api.py`

调整：

- `_load_case_params()` 改用 `load_single_cases()`。
- 一个 case 元素生成一个 `pytest.param`。
- pytest ID 使用 `ApiId::case_id`。
- marks 来自当前 case 的 tags。
- 测试函数执行 `single_case["execution_case"]`。
- 原 `flow_only` 分支删除。
- 调试筛选常量改为 `RUN_CASE_IDS`，使用稳定完整 ID。
- 直接执行文件时继续使用 `-s --log-cli-level=INFO`，请求和响应仍显示在终端。

示例：

```python
RUN_CASE_IDS: tuple[str, ...] = ()
```

需要临时调试 GetMe 时，可在本地改为 `("GetMe::get_me_success",)`。正式提交保持空元组，确保 pytest 默认收集全部独立单接口用例。

### 7.7 `test_gateway_flow.py`

保留参数化入口和 `--flow` 行为。

调整：

- FlowCase 已包含所需 API 定义。
- `gateway_factory` 创建的新 GatewayApi 传递 API 注册表，不再传递 session cases。
- Flow 环境缺失时继续按现有策略跳过真实流程。

### 7.8 `conftest.py`

调整：

- `pytest_configure()` 通过 CaseLoader 或轻量 case 扫描读取每条嵌套 case 的 tags。
- Flow tags 注册逻辑保持不变。
- `gateway_api` fixture 加载 API 注册表并传给 GatewayApi。
- 删除 CreateAnonymousSession、RefreshSession case 文件名硬编码。
- 现有 `--env`、`--flow`、日志初始化和 endpoint fixture 保持不变。

标签注册期间发生 YAML 配置错误时保持立即失败，不吞掉异常。

### 7.9 `runtest.py`

V1.3 不新增命令行参数：

- `--env`
- `--module`
- `--tag`
- `--flow`
- pytest 参数透传

以上行为保持不变。单接口精确调试继续通过 `test_single_api.py` 中的 `RUN_CASE_IDS` 控制，本版本不增加 `--case`，避免扩大范围。

## 8. 执行时序

### 8.1 单接口收集与执行

```text
pytest 收集
    ↓
ApiLoader 加载全部 API
    ↓
CaseLoader 扫描 case 集合
    ↓
逐条校验并展开 case
    ↓
API 路由 + case 参数/断言
    ↓
pytest.param(ApiId::case_id)
    ↓
GatewayApi.execute()
    ↓
HTTP 请求 → 分层断言 → 可选提取
```

### 8.2 Flow 收集与执行

```text
pytest 收集
    ↓
ApiLoader 加载全部 API
    ↓
FlowLoader 配对 Flow + Scenario
    ↓
校验 API 引用、step_data、断言和路径
    ↓
FlowRunner 创建独立 RuntimeContext
    ↓
按步骤读取 API 路由 + Scenario 完整数据
    ↓
调用 / 等待 / 轮询 / 上传
    ↓
断言 → 提取 → 后续步骤引用
```

## 9. 数据隔离

### 9.1 API 注册表

- 加载后只读使用。
- 构造可执行 case 时深拷贝。
- RuntimeContext 解析不得修改 API 注册表。

### 9.2 单接口 case

- 每条 case 使用独立的深拷贝可执行对象。
- 不允许通过 case 执行顺序传递业务变量。
- case 的 `extract` 只描述本次执行结果，不构成下一条 case 的前置条件。
- 会话 token 属于框架运行状态，不视为单接口业务用例间的数据依赖。

### 9.3 Flow

- 每个 Flow 创建新的 RuntimeContext。
- Flow 仅在自身步骤间传递业务变量。
- Flow 不读取、修改或执行任何单接口 case。

## 10. 断言处理

继续使用现有断言器：

| 断言 | 根对象 |
| --- | --- |
| `http_status` | HTTP response |
| `gateway` | Gateway 响应根对象 |
| `response` | `responses` 中目标子响应 |
| `data_fields` | 目标子响应的 `data` |
| `data_equals` | 目标子响应的 `data` |

处理顺序：

```text
HTTP 状态
  ↓
Gateway 顶层字段
  ↓
目标业务子响应
  ↓
data_fields
  ↓
data_equals
  ↓
extract
```

Scenario 中的整个 `assert` 对象应先经过 RuntimeContext 解析，使 `data_equals` 和其他断言字段都能使用 `{{变量名}}`，不再只解析 `data_equals`。

## 11. 错误与日志设计

### 11.1 配置错误

| 异常 | 场景 |
| --- | --- |
| `ApiConfigError` | API 缺字段、ID 重复、文件名不一致、包含禁止字段 |
| `CaseConfigError` | case 集合格式错误、API 引用不存在、case ID 重复 |
| `FlowConfigError` | Flow/Scenario 配对、step、API 引用、等待或路径错误 |

配置错误必须在网络请求前抛出。

### 11.2 运行错误

继续使用：

- `RuntimeContextError`
- `FlowExecutionError`
- `FlowEnvironmentError`
- `AssertionError`
- requests 网络异常

错误消息要求：

- API 错误包含 API ID 和来源文件。
- case 错误包含 API ID、case ID 和文件名。
- Flow 错误包含 Flow ID 和 step ID。
- 不记录真实 token、refresh token、Authorization 或签名参数。

### 11.3 日志上下文

单接口日志至少能从 pytest ID 定位：

```text
case=GetTask::get_task_success
```

Flow 保持现有日志字段：

```text
flow=AnonymousSessionMediaSearch
scenario=姓名搜索成功场景
step=poll_task (2/4)
api=GetTask
```

HTTP 请求和响应继续由 `HttpClient` 统一记录，不在加载器中重复输出。

## 12. 数据迁移设计

### 12.1 API 定义迁移

从现有 12 个 case 文件中提取：

- 中文接口名称。
- `request.service_name`。
- `request.method_name`。

生成 12 个无数字前缀的 API 文件：

```text
CreateAnonymousSession.yaml
RefreshSession.yaml
GetMe.yaml
GetSubscriptionStatus.yaml
GetEntitlement.yaml
GetMediaUploadConfig.yaml
PrepareMediaUpload.yaml
CompleteMediaUpload.yaml
CreateIntentTask.yaml
GetTask.yaml
ListTaskCandidates.yaml
GetTaskCandidateDetail.yaml
```

### 12.2 单接口 case 迁移

当前 12 个旧 case 文件需要先按实际职责分类：

| 类型 | 当前文件 | V1.3 去向 |
| --- | --- | --- |
| 可独立执行 | CreateAnonymousSession、GetMe、GetSubscriptionStatus、GetEntitlement、GetMediaUploadConfig | 迁移为 API 定义和单接口 case 集合 |
| `flow_only` 接口模板 | RefreshSession、PrepareMediaUpload、CompleteMediaUpload、CreateIntentTask、GetTask、ListTaskCandidates、GetTaskCandidateDetail | 迁移为 API 定义；流程数据移入 Scenario，会话数据移入内部会话策略 |

可独立执行的 5 个旧 case 转换为对应 case 集合中的第一条成功用例：

```text
原 name           → cases[0].name
原 tags           → cases[0].tags
原 request.params → cases[0].request.params
原 assert         → cases[0].assert
原 extract        → cases[0].extract
```

V1.3 不再使用 `flow_only`。原 flow-only 文件不生成不可独立执行的 case，也不通过 tags 或默认筛选隐藏。后续确实需要测试这些单接口时，再为其补充具备完整前置数据和独立断言的 case。

### 12.3 Flow 和 Scenario 迁移

Flow：

```text
call: CreateIntentTask.yaml
                ↓
api: CreateIntentTask
```

Scenario：

- 把原 case 的完整 `request.params` 作为基础。
- 按 V1.2 实际递归合并规则应用当前 Scenario 覆盖。
- 将合并后的最终参数写入对应 `step_data.<step_id>.params`。
- 把原 case 基础断言与当前 Scenario 断言合并后，写成完整 `assert`。
- Flow 使用的提取规则全部放在 Flow step。

迁移结果必须以“V1.2 实际最终请求”和“V1.3 Scenario 完整请求”对比，而不是仅人工观察 YAML。

### 12.4 文件替换

完成新加载器和临时目录单元测试后，一次性执行以下切换：

1. 创建 `data/apis`。
2. 将带数字前缀的旧 case 文件替换为无前缀 V1.3 case 集合。
3. 更新 Flow 和 Scenario。
4. 更新 pytest 入口和会话 fixture。
5. 全量运行配置校验和测试。

不保留重复的 V1.2 case 文件，避免同一接口被收集两次。

## 13. 测试设计

### 13.1 API Loader

- 正常加载多个 API。
- 文件名与 API ID 不一致。
- 重复 API ID。
- 缺少 `name`、`service_name` 或 `method_name`。
- 根节点不是对象。
- API 定义出现 `params`、`assert`、`extract` 等禁止字段。
- 构造可执行 case 后原 API、params 和 assertions 没有被修改。

### 13.2 Case Loader

- 一个接口文件展开多条 case。
- pytest ID 为 `ApiId::case_id`。
- 每条 case tags 独立。
- case ID 重复。
- API 引用不存在。
- case 文件名与 API ID 不一致。
- `cases` 为空或不是列表。
- `request.params` 缺失、不是对象或为合法空对象。
- 成功、缺参、多参数据保持原样，不发生默认参数合并。
- 精确筛选存在和不存在的 case ID。

### 13.3 Flow Loader

- Flow 使用 API 引用正常加载。
- Flow 引用不存在 API。
- V1.2 `call` 被明确拒绝。
- API step 缺少 Scenario step_data。
- params 或 assert 缺失、类型错误。
- wait/action 被错误配置 step_data。
- 重复 step ID、孤立 Scenario、非法路径和未知 action 回归。
- 返回的 API 定义仅包含当前 Flow 引用项。

### 13.4 Flow Runner

- API 路由与 Scenario 完整参数正确组装。
- 不访问 `data/cases` 也能执行 Flow。
- 修改或删除临时 case 文件不影响 Flow。
- params 中嵌套变量保持原类型。
- assert 中运行时变量可以解析。
- data_equals、extract 和后续步骤引用。
- 固定等待。
- 轮询成功和超时。
- 不同 Flow 上下文隔离。
- prepared_media_upload 回归。

### 13.5 会话管理

- 普通请求临期时使用 RefreshSession API 定义。
- refresh 失败后使用 CreateAnonymousSession API 定义。
- 删除所有单接口 case 后，会话单元测试仍可执行。
- 会话 API 定义缺失时错误清晰。
- 会话响应提取、上下文更新和 `.env` 持久化回归。

### 13.6 集成回归

- 全部 V1.3 YAML 可在无网络请求条件下完成收集。
- 单接口每个 case 都有唯一 pytest ID。
- `AnonymousSessionMediaSearch` 可被 `--flow` 收集。
- `--tag` 可以筛选嵌套 case tags。
- 直接运行 `test_single_api.py` 仍实时输出请求和响应。
- 全量框架测试通过。
- 有真实环境时，执行选定单接口和现有 Flow 验证请求行为。

## 15. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 数据迁移遗漏参数 | 请求行为变化 | 对比迁移前最终合并参数与迁移后完整参数 |
| Flow 仍间接读取 case | 解耦目标未达成 | 增加删除 `data/cases` 后 FlowRunner 仍能运行的隔离测试 |
| 会话管理继续依赖 case | Flow 被隐藏依赖影响 | 会话改用 API 定义和内部运行策略 |
| 多 case 标签未注册 | `--tag` 筛选失效 | conftest 嵌套 tags 测试 |
| 加载器修改原对象 | 用例之间数据污染 | 深拷贝测试 |
| 一次性切换导致收集失败 | 全量测试不可运行 | 先用临时目录完成加载器测试，再原子迁移真实 YAML |
| 旧 `call` 被静默忽略 | Flow 步骤不执行 | 明确抛出 FlowConfigError |
| 动态 case 依赖前序数据 | 单接口执行不稳定 | 用例必须自带完整前置数据，不依赖收集顺序 |

## 16. 完成定义

满足以下条件才视为 V1.3 设计实现完成：

1. `data/apis` 包含全部现有业务接口定义。
2. 现有 5 个可独立执行 case 使用 V1.3 多 case 结构，原 flow-only 模板不再作为 case 保留。
3. Flow 和会话管理均不读取 `data/cases`。
4. 单接口和 Flow 通过同一个 API 定义加载入口获取路由。
5. 一个接口配置多条 case 时可被 pytest 独立收集和运行。
6. 配置错误在请求前失败，并包含可定位上下文。
7. V1.2 的日志、会话、变量、断言、等待、轮询和上传测试无回归。
8. README 与最终 YAML 格式一致。
