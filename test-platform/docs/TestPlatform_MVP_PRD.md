# 测试开发平台 MVP 产品需求文档

> 文档版本：V1.0  
> 项目阶段：第一阶段 MVP  
> 创建日期：2026-07-21  
> 首批接入工具：`TrackEvents_tess`、`log_filter_tool`

---

## 1. 项目背景

当前测试工具以独立项目形式存在：

- `TrackEvents_tess`：埋点日志分析工具，已经具备独立 Web 页面、HTTP API 和 Docker 部署能力；
- `log_filter_tool`：日志筛选与接口统计工具，已经具备 Flask Web 页面和 Docker 部署能力；
- 后续还会增加测试 Agent、接口自动化、测试用例管理等模块。

随着工具数量增加，分别记忆访问地址、启动方式和使用入口的成本会越来越高。因此需要建设一个测试开发平台，作为所有测试工具的统一入口。

平台负责导航和聚合，各工具仍是独立项目、独立服务、独立部署单元。第一阶段不重构现有工具业务逻辑，先验证平台化接入模式。

---

## 2. 产品目标

### 2.1 MVP 目标

建设一个可运行的测试开发平台首页，将 `TrackEvents_tess` 和 `log_filter_tool` 聚合到同一个访问入口中，实现：

1. 用户通过一个平台地址访问测试工具；
2. 平台展示工具导航、名称、说明和运行状态；
3. 用户可以从平台进入两个现有工具；
4. 两个工具继续作为独立服务运行，平台不复制其业务代码；
5. 建立可复用的工具接入规范，为后续模块扩展提供基础。

### 2.2 成功标准

- 平台首页可以正常打开并展示两个工具；
- 点击“埋点测试工具”可以使用 `TrackEvents_tess` 的现有功能；
- 点击“日志分析工具”可以使用 `log_filter_tool` 的现有功能；
- 用户只需要记忆一个平台访问地址；
- 任一工具停止运行时，不影响平台首页和另一个工具；
- 两个现有项目仍可脱离平台独立启动和测试；
- 新工具可通过增加服务和导航配置的方式接入，不需要修改已有工具核心逻辑。

### 2.3 非目标

第一阶段不包含以下能力：

- 完整的用户注册、单点登录和组织架构；
- 细粒度角色权限控制；
- 跨工具任务中心和结果汇总；
- 公共数据库和统一文件存储；
- 对现有工具页面进行统一重写；
- 测试 Agent、接口自动化、测试用例管理等后续模块；
- Kubernetes、微服务治理、服务注册中心等复杂基础设施。

## 3. 用户与使用场景

### 3.1 目标用户

- 测试工程师；
- 测试开发工程师；
- 需要查看日志或验证埋点的研发人员。

### 3.2 核心使用场景

#### 场景一：进入埋点测试工具

1. 用户打开测试开发平台；
2. 在工具列表中找到“埋点测试”；
3. 点击进入；
4. 上传或粘贴日志并完成埋点分析；
5. 返回平台首页继续使用其他工具。

#### 场景二：进入日志分析工具

1. 用户打开测试开发平台；
2. 在工具列表中找到“日志分析”；
3. 点击进入；
4. 粘贴日志，筛选接口并查看统计结果；
5. 返回平台首页。

#### 场景三：工具暂时不可用

1. 平台探测工具运行状态；
2. 不可用的工具显示“服务异常”或“未启动”；
3. 其他工具仍可正常访问；
4. 平台不展示工具内部异常堆栈或敏感信息。

## 4. 总体方案

### 4.1 架构原则

- 平台是统一入口，不承载工具的具体分析逻辑；
- 每个工具继续使用自己的代码、依赖和容器；
- 平台通过反向代理提供统一域名和访问路径；
- 工具之间不直接互相依赖；
- 第一阶段以最小改动接入，后续再逐步统一登录、权限和任务协议。

### 4.2 MVP 架构

```text
浏览器
  │
  ▼
测试开发平台统一入口
  ├── /                  平台首页和工具导航
  ├── /trackevents/      埋点测试工具
  └── /log-filter/       日志分析工具
          │
          ▼
反向代理（Nginx）
  ├── platform-web       平台首页
  ├── trackevents-web    TrackEvents_tess 独立容器
  └── log-filter-tool    log_filter_tool 独立容器
```

### 4.3 首期技术选型

| 模块 | MVP 选择 | 选择理由 |
|---|---|---|
| 平台首页 | 静态 HTML/CSS/JavaScript | 首期只有导航和状态展示，开发成本最低 |
| 统一入口 | Nginx | 支持路径转发、静态页面和健康检查，配置简单 |
| 服务编排 | Docker Compose | 两个现有工具已经具备 Docker 基础 |
| 工具通信 | HTTP | 与现有 Web 服务保持一致 |
| 平台数据库 | 暂不引入 | 第一阶段没有必须持久化的业务数据 |

平台后续出现登录、权限、任务记录等需求时，再增加独立的 `platform-api` 服务和 PostgreSQL，不在 MVP 中提前引入。

## 5. 功能需求

### 5.1 平台首页

平台首页至少包含：

- 平台名称，例如“测试开发平台”；
- 简短的平台说明；
- 工具卡片列表；
- 每个工具的名称、图标、功能说明、状态和进入按钮；
- 预留“即将接入”区域，用于展示后续模块规划；
- 平台版本信息。

首批工具卡片：

| 工具 | 描述 | 入口路径 |
|---|---|---|
| 埋点测试 | 分析埋点日志、检查事件和公共参数 | `/trackevents/` |
| 日志分析 | 按接口筛选日志并统计请求、响应和状态码 | `/log-filter/` |

### 5.2 工具跳转与访问

- 点击工具卡片后，在当前窗口进入对应工具；
- 工具页面提供明确的“返回平台”入口；
- 浏览器刷新工具页面后仍可正常加载；
- 页面内 API 请求必须通过统一域名访问，避免跨域问题；
- 外部用户不能直接访问容器内部端口。

### 5.3 服务状态

平台首页展示工具状态：

- `正常`：工具健康检查返回成功；
- `异常`：工具不可连接或健康检查失败；
- `检测中`：页面尚未获得检测结果。

MVP 可以由 Nginx 或平台页面调用统一健康检查地址。健康检查只判断服务是否可访问，不检查外部业务接口和测试数据。

### 5.4 错误处理

- 工具未启动时显示统一的友好错误页；
- 错误页提供“返回平台首页”和“重新加载”操作；
- 不向浏览器暴露容器地址、服务器路径、环境变量或异常堆栈；
- 单个工具异常不应导致平台首页不可用。

## 6. 路由与接入约定

### 6.1 统一路由

| 路径 | 目标服务 | 说明 |
|---|---|---|
| `/` | `platform-web` | 平台首页 |
| `/trackevents/` | `trackevents-web:8000` | 埋点测试工具页面和接口 |
| `/log-filter/` | `log-filter-tool:5001` | 日志分析工具页面 |
| `/health/tools` | 平台状态接口或静态状态适配层 | 返回工具可用状态 |

### 6.2 子路径兼容风险

当前工具页面使用了根路径资源或接口：

- `TrackEvents_tess` 使用 `/favicon.svg` 和 `/api/analyze`；
- `log_filter_tool` 使用 `/`、`/sample`，表单也可能提交到当前路由。

如果直接代理到 `/trackevents/` 和 `/log-filter/`，根路径请求可能被错误发送到平台首页。因此 MVP 实施时必须二选一：

#### 推荐方案：让工具支持可配置的基础路径

- `TrackEvents_tess` 的基础路径设置为 `/trackevents`；
- `log_filter_tool` 的基础路径设置为 `/log-filter`；
- 页面中的静态资源、表单和 API 地址基于该路径生成；
- 工具独立运行时基础路径仍可配置为 `/`。

该方案需要对现有工具做少量修改，但路由清晰，适合后续长期维护。

#### 临时方案：Nginx 路径改写

由 Nginx 去除路径前缀后转发到工具，并为现有根路径接口增加定向规则。该方案改动较少，但工具增加接口后容易出现规则冲突，只适合短期验证。

本 PRD 推荐采用“工具支持可配置基础路径”的方案。

### 6.3 新工具接入规范

后续每个工具至少提供：

- 唯一工具标识，例如 `trackevents`；
- 工具名称和简介；
- 独立 Dockerfile；
- 独立服务端口；
- 首页入口；
- 健康检查地址；
- 可配置的 URL 基础路径；
- 环境变量说明；
- 数据目录和文件大小限制说明。

## 7. 文件与项目管理方案

### 7.1 推荐目录结构

测试开发平台项目应与其他工具项目保持同级，而不是放进某个工具内部。

```text
/Users/admin/Testproject/
├── test-platform/            # 测试开发平台：统一入口和编排
├── TrackEvents_tess/         # 埋点测试工具：独立项目
├── log_filter_tool/          # 日志分析工具：独立项目
├── Truthy_Search/            # 搜索工具：后续接入
├── Truthy_ApiAutoTest/       # 接口自动化：后续接入
└── ...                       # 其他测试工具
```

推荐同级的原因：

- 平台不会成为其他工具源码的父工程；
- 每个项目可以独立维护版本、依赖和测试；
- 平台只保存入口、反向代理和服务编排配置；
- 后续工具迁移到独立代码仓库时成本更低；
- 不会因为平台部署而复制或混合工具源码。

### 7.2 `test-platform` 的职责边界

平台项目建议只包含：

```text
test-platform/
├── web/                      # 平台首页资源
├── nginx/                    # 统一入口和反向代理配置
├── docker-compose.yml        # 平台及工具服务编排
├── .env.example              # 非敏感配置模板
├── README.md                 # 启动、接入和部署说明
└── docs/                     # 平台需求与设计文档
```

第一阶段不要把以下内容复制进平台项目：

- `TrackEvents_tess` 的分析代码；
- `log_filter_tool` 的日志解析代码；
- 工具运行结果和用户上传日志；
- 各工具的 Python 虚拟环境；
- Token、密码和测试账号。

### 7.3 代码仓库管理建议

当前阶段可以继续放在同一个父目录下开发，但各项目保持独立 Git 仓库更合适。平台的 Compose 可以通过以下两种方式引用工具：

1. 本地开发：使用同级目录作为 Docker build context；
2. 测试或生产环境：使用 CI 构建好的独立镜像版本。

不建议使用 Git Submodule 作为 MVP 的第一选择，因为它会增加拉取、分支和版本同步成本。等平台需要固定多个工具版本时，再评估是否使用统一仓库、Submodule 或镜像版本清单。

### 7.4 运行文件管理

平台代码与运行文件应分开管理：

```text
代码目录                    运行数据目录
TrackEvents_tess/           data/trackevents/
log_filter_tool/            data/log-filter/
test-platform/              data/platform/
```

MVP 中两个工具主要处理用户临时粘贴或上传的日志，建议默认不持久保存原始日志。确需保存时，应满足：

- 每个工具使用独立数据目录；
- 文件名使用系统生成的唯一 ID，不能直接信任上传文件名；
- 限制文件类型和大小；
- 设置自动清理周期；
- 日志中可能含有 Token、用户信息等敏感数据，下载和访问必须受控；
- 数据目录加入 `.gitignore`，禁止提交到代码仓库。

## 8. 非功能需求

### 8.1 可用性

- 平台和工具支持主流桌面浏览器；
- 首页在常用分辨率下正常显示；
- 工具入口名称和用途清晰；
- 页面加载失败时提供可理解的提示。

### 8.2 性能

- 平台首页在内网环境下应在 2 秒内完成主体内容加载；
- 平台首页不加载工具内部的大型资源；
- 工具分析性能维持现有水平，平台不增加业务处理链路。

### 8.3 安全

- 仅通过统一入口暴露服务；
- 工具容器端口只在 Docker 内部网络开放；
- 限制请求体和上传文件大小；
- 禁止在前端保存接口 Token 和测试账号；
- 错误响应不得包含环境变量、服务器路径和堆栈；
- 为后续统一登录预留鉴权层，但 MVP 可先部署在受控内网。

### 8.4 可维护性

- 工具版本在部署配置中明确；
- 新增工具不修改其他工具代码；
- 平台配置和工具业务代码职责分离；
- 每个服务均提供健康检查；
- Docker Compose 可一次启动和停止整个平台。

## 9. MVP 实施范围与文件影响

### 9.1 预计新增的平台文件

正式开发前，经确认后创建 `test-platform` 项目，预计包含：

- `test-platform/web/index.html`：平台首页；
- `test-platform/web/styles.css`：平台页面样式；
- `test-platform/web/app.js`：工具状态和页面交互；
- `test-platform/nginx/nginx.conf`：统一入口和路径转发；
- `test-platform/docker-compose.yml`：平台及两个工具的服务编排；
- `test-platform/.env.example`：端口等非敏感配置模板；
- `test-platform/README.md`：启动与工具接入说明。

### 9.2 预计修改的现有文件

为支持子路径访问，预计最小修改范围为：

- `TrackEvents_tess/trackevents_web.py`：支持基础路径配置，并调整页面资源及 API 地址；
- `TrackEvents_tess/docker-compose.yml`：增加基础路径环境变量或健康检查配置；
- `log_filter_tool/app.py`：支持代理前缀或应用基础路径；
- `log_filter_tool/templates/index.html`：使用框架生成的相对 URL；
- `log_filter_tool/docker-compose.yml`：增加基础路径环境变量或健康检查配置。

是否修改 Dockerfile，应在实施时根据健康检查和启动参数确认。不得为平台接入重构两个工具的分析逻辑。

### 9.3 潜在影响

- 修改 URL 基础路径可能影响现有工具的独立访问；
- 页面中硬编码的 `/api/analyze`、`/sample`、favicon 或表单地址可能在代理后失效；
- Flask 对代理头和脚本前缀的处理需要实际验证；
- `TrackEvents_tess` 使用标准库 HTTP Server，需要显式处理前缀路由；
- 浏览器缓存可能导致路由调整后仍加载旧资源。

缓解措施：保留默认基础路径 `/`，仅在平台容器环境中通过环境变量启用工具前缀，并为独立模式和平台模式分别执行测试。

## 11. 测试方案

### 11.1 自动化测试

- 运行 `TrackEvents_tess` 现有核心和 Web 测试；
- 运行 `log_filter_tool` 现有日志过滤测试；
- 为两个工具增加基础路径路由测试；
- 检查首页、工具入口和健康状态接口；
- 检查反向代理对 GET、POST 和错误响应的转发。

### 11.2 手工回归测试

- 分别验证两个工具的典型日志输入；
- 验证空输入、错误格式和超大请求；
- 验证页面刷新、浏览器后退和返回平台；
- 验证单个容器停止后的平台表现；
- 验证直接访问工具独立端口时的原有功能。

### 11.3 安全检查

- 检查浏览器开发者工具中是否暴露 Token；
- 检查错误页是否暴露服务器路径和堆栈；
- 检查容器端口是否仅在内部网络可见；
- 检查上传大小限制是否生效；
- 检查临时日志是否被提交到 Git。

## 12. 实施计划

### 阶段一：平台骨架

1. 创建与工具项目同级的 `test-platform`；
2. 实现平台静态首页和工具卡片；
3. 配置 Nginx 和 Docker Compose；
4. 配置两个工具的内部服务地址和健康检查。

### 阶段二：工具子路径适配

## 13. 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 页面使用根路径 API | 代理后接口 404 | 支持可配置基础路径并增加路由测试 |
| 工具代码被复制到平台 | 后续版本难以同步 | 平台只引用容器或同级 build context |
| 日志包含敏感信息 | 数据泄露 | 默认不持久化、限制访问、禁止提交 Git |
| 平台过早引入复杂后端 | MVP 周期变长 | 首期使用静态首页和 Nginx |
| 工具异常拖垮平台 | 统一入口不可用 | 工具独立容器、独立健康检查和超时配置 |
| 本地目录耦合部署 | 换环境后构建失败 | 生产环境逐步切换为版本化镜像 |

## 14. 后续演进方向

MVP 验证完成后，可按业务优先级逐步增加：

1. 平台后端 `platform-api`；
2. 用户登录与统一会话；
3. 角色、工具和操作级权限；
4. 统一任务模型与任务执行记录；
5. 跨工具结果汇总和报告中心；
6. 文件存储、保留周期和下载权限；
7. 测试 Agent 接入规范；
8. 接口自动化任务执行与报告展示；
9. 测试用例管理；
10. 通知、定时任务和审计日志。

后续平台统一的重点应是“身份、权限、任务元数据和结果索引”，而不是把每个工具的业务实现合并到平台代码中。
