> 文档版本：V2.0  
> 文档日期：2026-08-13  
> 文档状态：待 Review  
> 产品阶段：接口开发期测试与缺陷发现  
> 关联产品：功能测试智能体、Gateway 接口自动化工具、测试开发平台

---

## 1. 文档目的

本文档将 API 测试智能体当前的“文档解析与用例生成”能力扩展为可实施、可验收的端到端产品方案：

```text
接口文档导入
→ 接口契约解析
→ 人工确认契约
→ 测试设计与覆盖补齐
→ 人工确认测试用例
→ 可执行用例生成与静态验证
→ 执行风险确认
→ 隔离执行
→ 结果分析
→ 本地缺陷草稿生成、编辑与下载
```

本文档重点解决以下问题：

1. API 文档解析如何借鉴功能测试智能体的需求拆解能力。
2. API 测试智能体与现有 Gateway 接口自动化工具的产品边界。
3. API 测试智能体应从 Apifox、Postman 等成熟 API 工具学习哪些交互能力。
4. 将现状审计中的 P0、P1、P2 改进项转化为明确需求、状态、数据模型、安全门禁和验收标准。

## 2. 产品定位与边界

### 2.1 产品定位

API 测试智能体服务于接口刚开发或频繁变化阶段，核心任务是：

> 从不完整或不稳定的接口文档中识别接口契约，快速设计并执行探索性接口测试，帮助测试人员尽早发现、复现和提交接口缺陷。

它不是稳定回归执行平台的替代品，也不以长期维护大量固定自动化流程为首要目标。

### 2.2 三类产品的职责

| 产品 | 主要阶段 | 核心目标 | 资产特点 | 主要使用者 |
| --- | --- | --- | --- | --- |
| API 测试智能体 | 接口开发期、联调期 | 发现问题、补齐覆盖、验证契约 | AI 生成、允许快速变化、需要人工确认 | 测试工程师、测试开发 |
| Gateway 接口自动化工具 | 接口稳定后 | 稳定回归、流程验证、持续运行 | 显式 YAML、确定性强、适合版本管理 | 测试开发、CI/CD |
| Apifox/Postman 类工具 | 开发与调试全过程 | 请求调试、集合管理、环境与协作 | 可视化请求资产、手工操作友好 | 开发、测试、接口协作者 |

### 2.3 产品协作原则

1. API 测试智能体负责“从未知到已验证”。
2. Gateway 接口自动化工具负责“从已验证到持续回归”。
3. 当前版本不实现智能体资产向 Gateway 自动化工具发布；该能力已迁入《AI 测试智能体后续需求池》。
4. 当前版本仍优先复用 Gateway 自动化工具已验证的运行时变量、断言、轮询、日志和报告经验，避免形成不兼容的执行语义。
5. API 智能体可以学习 Apifox/Postman 的工作台体验，但不得复制其完整产品范围。

### 2.4 不在本期范围

- 替代现有 Gateway 自动化框架。
- 在线管理所有历史接口资产和完整 API 生命周期。
- 实现通用低代码流程编排器。
- 默认自动执行所有 AI 生成的脚本或写操作。
- 自动把未经人工确认的失败直接提交为正式 Bug。
- 接入任何外部缺陷管理平台；当前版本只生成、编辑和下载本地缺陷草稿。
- 将稳定接口或用例发布到 Gateway 自动化工具、Git、测试管理系统或 CI/CD。
- Postman Collection 导入。
- gRPC、WebSocket、GraphQL 测试。

## 3. 方案决策

### 3.1 是否参考功能测试智能体的解析方式

结论：参考其方法和质量体系，不直接复用其 Requirement Schema。

应复用的能力：

- 文档保留原文并按结构切片。
- 结构化事实抽取。
- 字段级原文证据绑定。
- 明确区分“文档事实”和“AI 测试建议”。
- Grounding Check 与防幻觉处理。
- `draft → confirmed_candidate → confirmed` 人工确认门禁。
- 未解决项、歧义项和冲突项的显式记录。
- 可解释质量评分和阻断原因。
- 固定补齐轮次，避免无限循环。

API 场景需要新增的专用能力：

- OpenAPI/Swagger 等结构化格式的确定性解析。
- HTTP 方法、路径、参数位置、Schema、鉴权、响应码等契约字段。
- 文档 Base URL 与目标执行环境分离。
- 多接口依赖关系与动态变量提取。
- 文档版本差异和接口变更识别。

### 3.2 主要学习对象的优先级

| 学习来源 | 优先学习内容 | 不建议直接照搬 |
| --- | --- | --- |
| 功能测试智能体 | 证据、质量门禁、人工 Review、状态模型 | 功能 Requirement 字段和 GWT 作为 API 契约主模型 |
| Gateway 自动化工具 | API/Case/Flow/Scenario 分层、运行时变量、断言、轮询、日志、报告、CI | 要求用户在探索期手工维护全部 YAML |
| Apifox/Postman | 请求编辑、环境变量、单接口调试、请求/响应查看、集合式组织 | 完整 API 管理平台、团队协作、Mock、文档门户等大范围功能 |

### 3.3 核心架构决策

系统内部新增中立的规范化资产模型，避免 AI Prompt 输出直接成为最终执行格式：

```text
ApiContract
  ├── BaseTestCase
  ├── ExecutableCase
  ├── ExecutionRun / CaseResult
  └── DefectDraft
```

## 5. 端到端用户流程

### 5.1 标准流程

1. 用户创建任务，选择项目、模块、文档、目标测试环境和运行模式。
2. 系统预检文件，并识别文档格式。
3. 系统按格式路由解析器，生成规范化接口契约。
4. 系统执行证据、完整性、冲突和质量门禁检查。
5. 用户在接口 Review 页面确认或修正契约。
6. 系统基于已确认契约生成基础测试用例和覆盖矩阵。
7. 用户 Review 用例，禁用危险项或补充测试数据。
8. 系统生成可执行用例，执行 Schema、脚本、变量和目标检查。
9. 用户进入执行确认页，确认真实目标、写操作和脚本风险。
10. 系统在隔离执行环境运行，并持续返回进度。
11. 系统生成测试报告、失败聚类和缺陷候选。
12. 用户确认缺陷候选，生成、编辑并下载本地缺陷草稿；当前版本不自动提交外部系统。

### 5.2 快速模式

对已确认且没有高风险用例的任务，允许用户选择“生成到可执行用例”，但仍不得跳过：

- 契约质量门禁。
- 用例 Schema 校验。
- 真实执行确认。
- 目标允许列表检查。

### 5.3 仅解析模式

用户可只执行文档解析和契约 Review，不生成测试用例。该模式输出 `api-contract.json` 和质量报告。

## 6. P0：完成可用闭环

P0 目标是在安全执行默认关闭的前提下，先建立可信解析、人工 Review、阶段产物、可操作错误和完整结果模型；执行能力只有通过安全门禁后才可启用。

### 6.1 P0-01 文档导入与预检

#### 功能要求

- 支持 `.md`、`.txt`、`.json`、`.yaml`、`.yml`。
- 单任务一个主文档，最大 5 MiB、最多 500,000 字符。
- JSON/YAML 在进入解析前完成语法校验。
- 自动识别 OpenAPI 2.0、OpenAPI 3.x 和非结构化文档；识别到 Postman Collection 时返回 `DOCUMENT_FORMAT_UNSUPPORTED`，不把普通 Collection JSON 误当 OpenAPI。
- 展示文件名、格式、大小、摘要哈希和预检结果。
- 文档中的 Server/Base URL 只作为契约元数据，不自动成为真实执行目标。

#### 异常处理

- 空文件：`DOCUMENT_EMPTY`。
- 语法错误：`DOCUMENT_SYNTAX_INVALID`，返回行号和列号。
- 不支持格式：`DOCUMENT_FORMAT_UNSUPPORTED`。
- 文档疑似包含 Secret：提示风险并在保存、展示、日志中脱敏。

#### 验收标准

- Given 用户上传合法 OpenAPI YAML，When 预检完成，Then 页面显示格式、版本和接口数量预估。
- Given JSON/YAML 存在语法错误，When 用户提交，Then 不创建解析 Runner，页面显示可定位的语法错误。
- Given 文档包含 URL，When 完成预检，Then 系统不得向该 URL 发送请求。

### 6.2 P0-02 接口契约解析

#### 解析策略

| 文档类型 | 第一解析器 | LLM 的职责 |
| --- | --- | --- |
| OpenAPI/Swagger | 标准解析器 | 补充缺失说明、识别歧义，不覆盖明确结构字段 |
| Markdown/TXT | 标题切片 + LLM | 抽取接口契约并绑定证据 |
| 普通 JSON/YAML | 结构探测 + LLM | 判断字段语义并生成候选契约 |

#### ApiContract 核心模型

| 字段 | 说明 |
| --- | --- |
| `contract_id` | 任务内稳定 ID |
| `name`、`summary` | 接口名称与描述 |
| `method`、`path` | HTTP 方法与相对路径 |
| `servers` | 文档声明的 Server 列表，仅作元数据 |
| `parameters` | Header/Path/Query/Cookie 参数 |
| `request_body` | Content-Type、Schema、示例 |
| `responses` | 状态码、Schema、示例和错误语义 |
| `security` | 鉴权方式及作用域，不保存 Secret |
| `dependencies` | 前置接口、变量来源和依赖说明 |
| `source_trace` | 文档和片段来源 |
| `field_evidence` | 关键字段的原文证据 |
| `unresolved` | 缺失但执行必需的信息 |
| `ambiguity_notes` | 存在多种解释的字段 |
| `conflict_items` | 文档内互相冲突的信息 |
| `test_design_suggestions` | AI 推断的测试建议，不作为契约事实 |
| `quality_report` | 完整性、可追溯性、冲突、Schema 等质量结果 |
| `status` | `draft/confirmed_candidate/confirmed/changed/deprecated` |

#### 防幻觉规则

1. `method`、`path`、必填性、数据类型、枚举、响应码等关键事实必须有原文或结构化节点证据。
2. 无证据字段不得进入契约事实，移动到测试建议或未解决项。
3. LLM 不得覆盖确定性解析器得到的明确字段；冲突时记录冲突并等待人工确认。
4. 页面必须明确区分“文档事实”“AI 推断”“人工修改”。
5. 人工修改形成新版本，保留修改人、时间和原值。

#### 契约质量门禁

单接口进入 `confirmed_candidate` 至少满足：

- `method` 和 `path` 存在且格式有效。
- 关键字段证据完整。
- Schema 校验通过。
- 不存在未处理的关键冲突。
- Grounding Check 通过。
- 接口可执行所需的动态字段已标记来源或未解决原因。

#### 验收标准

- Given 标准 OpenAPI，When 解析完成，Then method/path/参数位置与源文档一致。
- Given 文档没有描述某参数是否必填，When 解析完成，Then 该信息进入 `unresolved`，不得由 AI 默认为必填。
- Given 文档中同一接口出现两个不同路径，When 解析完成，Then 契约保持 `draft` 并展示冲突。

### 6.3 P0-03 接口契约 Review

#### 页面结构

- 左侧：接口列表、方法、路径、质量状态和问题数量。
- 中间：契约字段编辑区。
- 右侧：当前字段的原文证据、AI 建议和修改历史。
- 顶部：接口总数、候选确认数、草稿数、冲突数。

#### 用户操作

- 确认单个接口。
- 批量确认无阻断项接口。
- 修改字段并填写修改原因。
- 标记忽略、废弃或非本次测试范围。
- 退回重新解析。
- 下载当前契约 JSON 和质量报告。

#### 阻断规则

- 有关键冲突、缺少 method/path 或质量门禁失败时，不允许确认。
- 至少一个接口达到 `confirmed` 后才能进入用例生成。
- 被忽略接口不进入后续生成，但保留在解析报告中。

### 6.4 P0-04 阶段性产物保存

每个阶段成功后立即原子保存产物，后续失败不得删除或隐藏已有产物。

| 阶段 | 必须保存的产物 |
| --- | --- |
| 文档预检 | `document-profile.json` |
| 契约解析 | `api-contract.json`、`contract-quality-report.json` |
| 契约 Review | `api-contract-reviewed-v{n}.json` |
| 基础用例生成 | `base-cases.json`、`coverage-matrix.json` |
| 可执行用例生成 | `executable-cases.json`、`validation-report.json` |
| 执行 | `execution-results.json`、日志、附件 |
| 报告 | `test-report.json`，后续可增加 HTML/Allure |
| 缺陷草稿 | `defect-drafts.json` |

任务整体失败时，页面仍展示已经完成阶段的可下载产物。

### 6.5 P0-05 测试设计与覆盖矩阵

#### 基础用例模型

- `case_id`、名称、测试目的。
- 关联 `contract_id`。
- 覆盖维度和风险标签。
- 前置条件。
- 测试步骤。
- 预期结果。
- 来源：规则、文档事实、AI 建议或人工新增。
- 风险级别：低、中、高。
- 状态：草稿、候选确认、已确认、禁用。

#### 默认覆盖维度

- 正常请求。
- 必填参数缺失。
- 类型错误。
- 长度、范围、枚举边界。
- 空值、空字符串、空数组和重复值。
- 鉴权缺失、失效和权限不足。
- 典型业务异常。
- 幂等性与重复提交，适用于写接口。
- 文档明确要求的状态流转和依赖接口。
- 安全 Payload 只生成候选，默认禁止执行。

#### 覆盖矩阵规则

- 先由确定性规则生成可判定覆盖项。
- 仅将不确定项交给 LLM 判断。
- 每项覆盖结论关联一个或多个用例 ID。
- 覆盖补齐最多 3 轮。
- 达到轮次仍不满足时，任务进入 `partial_success`，展示缺口，不无限循环。
- 不再通过模型文本是否包含 `100%` 判断是否通过。

### 6.6 P0-06 用例 Review

#### 页面能力

- 按接口、覆盖维度、风险、状态筛选。
- 展示覆盖矩阵和未覆盖项。
- 展开查看步骤、请求数据来源和预期结果。
- 编辑用例、人工新增、禁用、批量确认。
- 高风险用例必须逐条确认。
- 展示本轮生成使用的契约版本、Prompt 版本和模型。

#### 进入可执行用例生成的条件

- 契约为 `confirmed`。
- 至少一条基础用例为 `confirmed`。
- 所有高风险用例均有人工决定。
- 未解决覆盖缺口被接受或补齐。

### 6.7 P0-07 错误分类、建议动作与重试

#### 错误类型

| 类别 | 示例错误码 | 页面建议动作 |
| --- | --- | --- |
| 文档 | `DOCUMENT_SYNTAX_INVALID` | 修正文档后重新上传 |
| 契约 | `CONTRACT_QUALITY_FAILED` | 进入 Review 解决冲突或缺失项 |
| 模型 | `LLM_RATE_LIMITED` | 稍后重试或联系管理员检查额度 |
| 模型 | `LLM_AUTH_FAILED` | 联系管理员检查模型 Secret |
| 生成 | `CASE_SCHEMA_INVALID` | 重新生成失败项或人工修正 |
| 配置 | `CONFIG_NOT_READY` | 展示缺失配置名称，不展示 Secret |
| 系统 | `WORKER_DEPENDENCY_MISSING` | 联系管理员检查部署依赖 |
| 执行 | `TARGET_NOT_ALLOWED` | 选择登记目标或申请配置 |
| 执行 | `ASSERTION_FAILED` | 查看预期和实际响应 |

#### 重试规则

- 支持“从失败阶段重试”，复用已确认的上游产物。
- 重试生成新 Attempt，不覆盖原结果。
- 模型限流使用有限退避，最多自动重试 2 次。
- 用户手工重试时必须展示复用的契约、配置 Release 和 Prompt 版本。

### 6.8 P0-08 执行安全门禁

真实执行默认关闭。只有以下条件全部满足时，才允许管理员发布启用执行的配置 Release：

- 每个 ExecutionRun 启动一个短生命周期、独立、非 root 的受限执行容器；禁止复用 API Web 容器或多个 Run 共用执行容器。
- 根文件系统只读，仅任务目录可写。
- 限制 CPU、内存、进程数和磁盘。
- 单脚本、单用例、整任务三级超时。
- 移除不必要的 Linux capabilities。
- 不挂载 Docker Socket、平台 KEK、平台数据库或其他工具数据目录。
- 目标必须命中 `ALLOWED_TARGETS`。
- 网络只允许必要 DNS 和登记目标。
- 请求、响应、异常和日志统一脱敏。
- 取消任务可终止完整进程组。
- 生成阶段只允许解析和静态检查脚本，不执行脚本。

任何一项未满足时，页面显示执行未就绪，不展示可用执行按钮。

### 6.9 P0-09 执行确认

执行确认页必须展示：

- 环境与实际 Base URL。
- 用例总数、写接口数量和高风险用例数量。
- 是否包含 setup/teardown 脚本。
- 将访问的 Host 列表。
- 配置 Release、契约版本和用例版本。
- 数据库连接配置名称，不显示密码。
- “执行将向目标环境发送真实请求”的明确说明。

用户必须主动勾选确认并点击“开始执行”。“生成后申请执行”不能绕过该页面。

### 6.10 P0-10 执行结果与缺陷草稿

#### 执行结果

- 总数、通过、失败、错误、跳过和通过率。
- 开始时间、结束时间、耗时、环境和目标。
- 失败用例列表，按错误签名聚类。
- 请求方法、脱敏 URL、请求体、响应状态码、响应体和耗时。
- 断言预期值与实际值。
- 前置步骤、主请求、后置步骤的独立状态。
- 单条重试和重试全部失败项；重试产生新 Run。

#### 缺陷候选规则

以下结果可生成缺陷候选：

- 断言失败。
- 接口返回非预期业务错误。
- 契约与真实响应 Schema 不一致。
- 稳定复现的 5xx。
- 满足“慢响应候选”规则的稳定超限请求。

连接失败、环境不可用、测试数据缺失、脚本错误默认归类为测试阻塞或用例问题，不直接视为接口 Bug。

#### DefectDraft 字段

- 标题、模块、接口、严重级别建议。
- 环境、版本、任务 ID、Run ID、Case ID。
- 前置条件和复现步骤。
- 脱敏请求。
- 预期结果和实际结果。
- 响应状态码、错误摘要和请求 ID。
- 日志、报告和附件链接。
- AI 分析结论、置信度和待人工确认项。

P0 只要求生成、编辑和下载缺陷草稿；测试人员下载后如何提交 Bug 不属于当前系统范围。

当前版本不提供外部提交按钮、Provider 配置或外部缺陷状态同步。下载格式至少支持 JSON 和 Markdown。

#### 慢响应候选规则

1. 接口文档明确声明 SLA 时，以该 SLA 作为判断阈值。
2. 文档未声明 SLA 时，使用项目/环境配置的软阈值；默认值为 3000ms。
3. 软阈值单次超限只显示警告，不直接生成缺陷草稿。
4. 同一用例在相同环境至少独立执行 3 次且均超限，才允许生成性能类缺陷草稿。
5. 压测、并发、吞吐量、P95/P99 分析不属于当前版本范围。

## 7. P1：提升可信度与协作效率

### 7.1 P1-01 文档版本差异解析

- 相同项目和模块再次上传文档时，可选择与已确认版本比较。
- 输出新增、删除、修改和疑似重命名的接口。
- 参数必填性、类型、枚举、响应 Schema、鉴权变化标记为高影响变更。
- 只对受影响接口重新生成用例，未变化接口复用已确认资产。
- 删除或变更接口不自动删除历史用例，标记为 `changed` 或 `deprecated`。

### 7.2 P1-02 可执行用例规范化与预验证

可执行用例必须通过：

- JSON Schema 校验。
- method、相对 path、目标映射校验。
- 参数引用和变量依赖校验。
- setup/teardown Python 语法校验。
- 禁止模块、危险内置函数和文件访问的静态策略检查。
- 前置接口依赖拓扑检查。
- 请求数据来源完整性检查。
- 断言可执行性检查。

校验失败的用例状态为 `disabled`，不得进入执行确认。

### 7.3 P1-03 学习成熟 API 工具的工作台体验

仅实现与开发期测试直接相关的能力：

- 请求构造器：方法、URL、Header、Query、Body 和鉴权预览。
- 环境变量与密文变量分离；Secret 不回显。
- 单接口手工试跑。
- 请求和响应并排查看。
- 请求历史与本次生成用例之间可互相转换。
- 用例按接口集合组织。
- 从响应中选择字段快速创建断言或提取变量。

不在 P1 实现完整 API 文档门户、Mock Server、团队评论或通用可视化流程编排器。

### 7.4 P1-04 失败分析与聚类

- 基于接口、状态码、异常类型、断言字段和错误签名聚类。
- 区分产品缺陷、环境问题、数据问题、用例问题和未知问题。
- 展示分类依据和置信度，允许人工修正。
- 同一错误聚类默认生成一个缺陷候选，关联多个失败 Case。
- 人工分类结果保留为后续规则输入，但不得自动改变历史报告。

## 8. P2：规模化与持续优化

### 8.1 P2-01 质量评估数据集

建立不包含真实 Secret 的黄金文档集，覆盖：

- 标准 OpenAPI 2.0/3.x。
- 多接口 Markdown。
- 字段缺失、冲突和歧义文档。
- 鉴权、上传、异步轮询和分页接口。
- 中英文混合文档。

持续衡量：

- method/path 精确率。
- 参数位置、类型和必填性准确率。
- 响应 Schema 准确率。
- 未支持事实率。
- 人工修订率。
- 用例有效率和缺陷发现率。

### 8.2 P2-02 成本和性能治理

- 结构化文档优先使用确定性解析，减少 LLM 调用。
- 文档哈希、契约版本和 Prompt 版本一致时复用缓存。
- 覆盖矩阵先本地判定，再调用 LLM。
- 配置单任务 Token 和模型调用预算。
- 并发生成为可配置上限，避免模型限流。
- 页面展示耗时、模型调用次数和 Token 使用量。

### 8.3 P2-03 变更影响与重测推荐

- 基于接口契约差异推荐需要重跑的用例。
- 基于历史失败和人工分类调整推荐优先级。
- 推荐结果必须解释关联的接口字段或历史缺陷。
- 推荐只影响默认选择，不自动执行。

### 8.4 P2-04 可观测性和运营指标

- 阶段耗时和成功率。
- 模型错误率、限流率和格式修复率。
- 契约人工修改率。
- 覆盖缺口和用例禁用原因。
- 执行通过率及失败分类分布。
- 缺陷草稿生成率、人工编辑率和下载率。

## 12. 非功能要求

### 12.1 安全

- Secret 永不写入任务记录、日志、报告和用例产物。
- URL、Header、Cookie、Query、请求体和响应体统一经过脱敏策略。
- AI 生成内容属于不可信输入，必须通过 Schema 和安全校验。
- 文档中出现的操作指令不得改变系统权限和执行策略。
- 执行和生成使用不同进程、权限与网络策略。

### 12.2 可靠性

- 阶段产物原子写入。
- Worker 中断后任务可识别为中断，不误报成功。
- 模型、数据库、执行容器和产物发布错误分别记录。
- 缺陷草稿生成或下载失败不得影响已完成的测试报告。

### 12.3 性能

- 5 MiB 文档预检目标 3 秒内完成，不包含 LLM 调用。
- 页面查询和筛选目标 P95 小于 2 秒。
- 日志增量加载，单次最多 256 KiB。
- 大量接口使用可控批次，批次大小由配置决定。
- 慢响应候选优先使用文档 SLA；无 SLA 时使用项目/环境软阈值，默认 3000ms。
- 单次软阈值超限只告警；相同环境连续 3 次超限后才允许生成性能类缺陷草稿。

### 12.4 可访问性

- 所有主要操作可用键盘完成。
- 焦点状态清晰。
- 状态不只依赖颜色。
- 表单错误与字段关联，并提供修复说明。
- 正文和背景满足 WCAG AA 对比度要求。

## 13. 数据保留与审计

- 任务摘要默认保留 180 天。
- 输入、日志和产物默认保留 90 天。
- 运行中和等待 Review 的任务不自动清理。
- 到期前 7 天提示。
- 契约确认、用例确认、执行确认、缺陷草稿生成、编辑和下载均写审计日志。
- 审计记录只保存必要元数据，不保存 Secret、完整请求体或完整响应体。

## 18. 最终产品原则

1. 文档事实必须可追溯，AI 建议必须明确标识。
2. 人工 Review 是开发期 API 测试的质量门禁，不是多余步骤。
3. 生成成功、保存失败、执行失败和缺陷草稿生成失败必须分别表达。
4. 任何阶段失败都不得丢失之前已成功的产物。
5. AI 负责扩大覆盖和降低编写成本，人负责确认契约、风险和缺陷结论。
6. API 智能体负责发现和验证，Gateway 自动化工具负责长期稳定回归；两个系统的资产发布留待后续专项。
7. 学习成熟 API 工具的高价值交互，不扩张成另一个全功能 API 管理平台。
