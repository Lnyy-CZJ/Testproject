# 测试开发平台框架升级方案、开发设计与计划

> 文档版本：V1.0  
> 创建日期：2026-07-31  
> 当前平台：原生 HTML/CSS/JavaScript + Nginx + Docker Compose  
> 目标技术栈：React + TypeScript + Vite / FastAPI + PostgreSQL / Nginx + Docker Compose

---

## 1. 文档目的

本文档用于指导测试开发平台从当前静态 MVP 平滑升级为具备统一登录、权限、任务记录和结果汇总能力的平台。

升级遵循以下原则：

- 现有 `TrackEvents_tess` 和 `log_filter_tool` 继续独立运行；
- 保留 `/trackevents/`、`/log-filter/` 等现有入口；
- 先替换平台外壳，再逐步增加平台后端能力；
- 不在框架迁移阶段重写工具业务逻辑；
- 每个阶段可以独立上线、验证和回滚；
- 未进入当前阶段的能力不提前实现。

## 2. 任务目标与成功标准

### 2.1 任务目标

将当前测试开发平台升级为：

```text
前端：React + TypeScript + Vite
后端：FastAPI
数据库：PostgreSQL
网关：Nginx
部署：Docker Compose
```

同时保持各测试工具作为独立服务，通过统一入口导航和标准接口接入平台。

### 2.2 总体成功标准

- 平台首页由 React 渲染，现有工具入口与状态展示不丢失；
- Nginx 继续提供唯一对外入口；
- `/trackevents/` 和 `/log-filter/` 地址保持兼容；
- FastAPI 通过 `/api/v1/` 提供平台公共接口；
- PostgreSQL 保存用户、权限、工具、任务和审计数据；
- 用户登录后只能看到有权访问的工具；
- 平台记录任务提交人、运行状态、摘要和结果索引；
- 任一工具异常不会导致平台和其他工具不可用；
- 现有两个工具仍可脱离平台独立运行；
- 每个迁移阶段都有自动化测试和明确回滚方式。

## 4. 方案选择

### 4.1 前端：React + TypeScript + Vite

### 选择理由

- React 适合拆分工具卡片、侧边栏、任务表格和权限菜单；
- TypeScript 可以约束后端响应和任务状态；
- Vite 开发和构建流程轻量；
- 构建结果仍是静态文件，可以继续由 Nginx 提供；
- 不需要引入服务端渲染或 Node.js 生产服务器。

### 暂不选择 Next.js

当前平台是内网工具平台，不依赖 SEO、服务端渲染或公开内容分发。使用 Next.js 会增加 Node.js 生产运行时和部署复杂度，MVP 升级阶段收益有限。

### 前端配套选择

| 能力 | 选择 |
|---|---|
| 页面路由 | React Router |
| HTTP 请求 | 原生 `fetch` 封装 |
| 全局状态 | React Context，仅保存登录用户和少量全局状态 |
| 表单 | 简单表单使用受控组件；复杂表单出现后再评估表单库 |
| 样式 | 保留普通 CSS，逐步组件化 |
| 测试 | Vitest + React Testing Library |

初期不引入 Redux、MobX、微前端框架或大型 UI 组件库。

### 4.2 后端：FastAPI

### 选择理由

- 与现有 Python 工具技术栈一致；
- 适合 API 驱动的平台；
- 支持类型校验和自动 OpenAPI 文档；
- 适合实现工具目录、用户权限、任务和结果接口；
- 可通过依赖注入统一处理登录用户和权限；
- 后续可以接入测试 Agent 和异步任务。

### 后端运行方式

开发环境：

```text
uvicorn
```

Docker 运行环境：

```text
uvicorn + 单容器合理 worker 数
```

任务执行逻辑不放在多个 Web worker 的进程内存中。需要持久运行的任务必须有数据库状态，重型任务后续交给独立 worker。

### 4.3 数据库：PostgreSQL

### 选择理由

- 适合用户、角色、工具、任务和审计等关系型数据；
- 支持事务和可靠约束；
- 后续可保存 JSON 格式的工具结果摘要；
- 适合多用户并发和长期演进。

### 数据访问

```text
SQLAlchemy 2.x
Alembic
```

- SQLAlchemy 负责模型和查询；
- Alembic 负责数据库版本迁移；
- 所有表结构变更必须通过迁移文件执行；
- 不允许应用启动时自动修改生产表结构。

### 4.4 网关与部署：保留 Nginx + Docker Compose

Nginx 和 Docker Compose 已经满足当前部署需求，没有更换必要。

Nginx 继续负责：

- 前端静态资源；
- `/api/v1/` 平台后端代理；
- 工具子路径代理；
- 请求体限制；
- 安全响应头；
- 统一错误页。

Docker Compose 继续负责：

- 平台前端构建产物；
- FastAPI；
- PostgreSQL；
- 两个现有工具；
- 后续独立 worker。

## 5. 目标架构

### 5.1 总体架构

```text
浏览器
  │
  ▼
Nginx
  ├── /                    → React 静态资源
  ├── /api/v1/             → platform-api / FastAPI
  ├── /trackevents/        → TrackEvents_tess
  └── /log-filter/         → log_filter_tool
                                │
                                ▼
                        PostgreSQL
```

后续增加异步任务后：

```text
React
  │
  ▼
FastAPI ─────────────── PostgreSQL
  │                         ▲
  │ 创建任务                │ 更新状态和结果
  ▼                         │
任务队列或任务表 ─────── platform-worker
                              │
                              ├── 调用测试 Agent
                              ├── 调用接口自动化
                              └── 调用标准化工具 API
```

### 5.2 服务边界

| 服务 | 职责 | 不负责 |
|---|---|---|
| `platform-web` | 页面、导航、任务和结果展示 | 执行测试任务 |
| `platform-api` | 用户、权限、工具、任务和审计接口 | 工具业务分析 |
| `platform-db` | 平台结构化数据 | 保存所有原始大文件 |
| `platform-worker` | 后续执行耗时任务 | 页面和用户会话 |
| `trackevents-web` | 埋点分析 | 平台权限和用户管理 |
| `log-filter-tool` | 日志筛选与导出 | 平台任务调度 |
| `platform-gateway` | 路由、安全头和统一入口 | 业务权限判断 |

### 5.3 兼容原则

- `/trackevents/` 保持不变；
- `/log-filter/` 保持不变；
- 工具健康检查路径保持不变；
- 工具仍可以独立启动；
- 新平台 API 统一使用 `/api/v1/`；
- 前端不直接连接 PostgreSQL；
- 平台后端不复制工具分析代码。

## 7. 前端开发设计

### 7.1 页面规划

第一阶段：

| 页面 | 路径 | 说明 |
|---|---|---|
| 平台首页 | `/` | 工具卡片和服务状态 |
| 登录页 | `/login` | 登录功能上线后启用 |
| 无权限页 | `/403` | 权限不足提示 |
| 未找到页 | `*` | 平台前端 404 |

任务功能上线后：

| 页面 | 路径 | 说明 |
|---|---|---|
| 任务列表 | `/tasks` | 查询本人或授权范围任务 |
| 任务详情 | `/tasks/:taskId` | 状态、参数摘要和结果 |
| 工具详情 | `/tools/:toolId` | 工具说明、状态和执行入口 |
| 用户管理 | `/admin/users` | 管理员功能 |
| 角色管理 | `/admin/roles` | 管理员功能 |
| 审计日志 | `/admin/audit-logs` | 管理员功能 |

### 7.2 组件规划

```text
AppShell
├── Header
├── Sidebar
├── UserMenu
├── ToolGrid
│   └── ToolCard
├── ServiceStatus
├── PermissionGuard
├── TaskTable
├── TaskStatusBadge
└── ResultSummary
```

### 7.3 前端状态

全局状态仅包含：

- 当前用户；
- 登录状态；
- 当前用户权限；
- 全局错误提示。

工具列表、任务列表和结果详情使用页面级请求状态，不在初期引入复杂全局状态管理。

### 7.4 HTTP 客户端

统一封装 `fetch`：

```text
功能：
- 自动添加 Accept 和 Content-Type；
- 同源携带 HttpOnly Cookie；
- 统一处理 401、403 和 5xx；
- 支持 AbortController 超时；
- 将错误转换为统一前端错误对象。
```

前端不得：

- 在 `localStorage` 保存密码；
- 在 JavaScript 可读存储中保存长期登录凭证；
- 直接拼接未经编码的用户输入 URL；
- 绕过平台权限接口展示管理员页面。

### 7.5 工具导航

工具列表由平台 API 返回，不再写死在 `app.js`：

```json
[
  {
    "id": "trackevents",
    "name": "埋点测试",
    "description": "解析 TrackEvents 日志并校验事件字段",
    "entry_url": "/trackevents/",
    "status": "healthy",
    "can_access": true
  }
]
```

前端只展示 `can_access=true` 的工具。

### 7.6 前端构建与部署

开发：

```text
Vite dev server
```

生产：

```text
vite build → frontend/dist → Nginx
```

React Router 使用浏览器路由时，Nginx 对平台前端路由回退到 `index.html`，但不得影响：

- `/api/`；
- `/trackevents/`；
- `/log-filter/`。

## 8. 后端开发设计

### 8.1 模块划分

| 模块 | 职责 |
|---|---|
| `auth` | 登录、退出、当前用户和会话 |
| `users` | 用户管理 |
| `roles` | 角色和权限 |
| `tools` | 工具注册、导航信息和状态 |
| `tasks` | 任务创建、状态、查询和取消 |
| `results` | 结果摘要和结果索引 |
| `audit` | 关键操作审计 |
| `health` | 平台 API 和数据库健康检查 |

### 8.2 API 版本

所有平台后端接口使用：

```text
/api/v1/
```

工具自身接口不强制改为该前缀。

### 8.3 统一响应原则

成功响应直接返回资源或列表：

```json
{
  "id": "tool-id",
  "name": "工具名称"
}
```

错误响应使用：

```json
{
  "code": "PERMISSION_DENIED",
  "message": "无权访问该工具",
  "request_id": "req_xxx"
}
```

错误字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 稳定的机器错误码 |
| `message` | string | 用户可理解的中文信息 |
| `request_id` | string | 服务端请求追踪标识 |

不得在响应中暴露：

- 数据库连接信息；
- 服务器绝对路径；
- 异常堆栈；
- 密码哈希；
- 内部服务凭证。

### 8.4 健康检查

| 接口 | 用途 |
|---|---|
| `GET /api/v1/health/live` | FastAPI 进程存活 |
| `GET /api/v1/health/ready` | 数据库和必要依赖可用 |

`live` 不访问数据库，`ready` 才执行轻量数据库检查。

## 9. 登录与会话设计

### 9.1 推荐方式

采用服务端可撤销会话：

1. 用户提交账号和密码；
2. 后端验证密码哈希；
3. 后端生成高强度随机会话 Token；
4. 数据库只保存 Token 哈希；
5. 浏览器通过 HttpOnly Cookie 保存原始 Token；
6. 每次请求由后端验证会话；
7. 退出、禁用用户或管理员操作可以立即撤销会话。

### 9.2 Cookie 属性

```text
HttpOnly=true
SameSite=Lax
Secure=true（HTTPS 环境）
Path=/
```

本地 HTTP 开发环境允许通过配置关闭 `Secure`，但生产或共享测试环境必须使用 HTTPS。

### 9.3 密码

- 使用成熟密码哈希算法；
- 不保存明文密码；
- 不在日志中记录密码；
- 登录失败返回统一提示，避免泄露账号是否存在；
- 增加基础登录失败频率限制；
- 管理员重置密码后撤销该用户全部会话。

### 9.4 登录接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/auth/login` | 登录并设置 Cookie |
| POST | `/api/v1/auth/logout` | 撤销当前会话 |
| GET | `/api/v1/auth/me` | 获取当前用户和权限 |

## 10. 权限设计

### 10.1 RBAC 模型

采用用户、角色、权限三层模型：

```text
用户 ←→ 角色 ←→ 权限
```

初始角色：

| 角色 | 权限范围 |
|---|---|
| `platform_admin` | 用户、角色、工具和全部任务管理 |
| `tester` | 使用授权工具，创建和查看自己的任务 |
| `viewer` | 查看授权工具和允许查看的结果 |

### 10.2 权限命名

```text
tool:view
tool:manage
task:create
task:view_own
task:view_all
task:cancel_own
task:cancel_all
user:manage
role:manage
audit:view
```

工具访问范围单独通过角色与工具关联表控制。

### 10.3 权限校验位置

- 前端权限只用于隐藏菜单和改善体验；
- 真正权限判断必须在 FastAPI；
- Nginx 不承担业务权限判断；
- 工具直接页面在统一登录阶段需要增加平台鉴权入口或网关鉴权；
- 在工具鉴权完成前，平台必须继续部署在受控内网。

### 10.4 工具鉴权演进

第一步：

- 平台 API 控制工具导航可见性；
- 保留现有工具直达路径；
- 仅用于受控内网。

第二步：

- Nginx 在访问工具前调用平台鉴权；
- 或工具支持平台签发的短期访问凭证；
- 未登录或无权限用户不能直接访问工具路径。

MVP 升级不应立即修改全部工具认证方式。

| `is_active` | boolean | 默认 true |
| `created_at` | timestamptz | 非空 |
| `updated_at` | timestamptz | 非空 |

### 11.3 `sessions`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `user_id` | UUID | 外键 |
| `token_hash` | varchar | 唯一、非空 |
| `expires_at` | timestamptz | 非空 |
| `revoked_at` | timestamptz | 可空 |
| `created_at` | timestamptz | 非空 |
| `last_seen_at` | timestamptz | 非空 |

### 11.4 `tools`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | varchar | 主键，例如 `trackevents` |
| `name` | varchar | 非空 |
| `description` | text | 非空 |
| `entry_url` | varchar | 非空 |
| `health_url` | varchar | 非空 |
| `icon_key` | varchar | 可空 |
| `sort_order` | integer | 默认 0 |
| `is_enabled` | boolean | 默认 true |
| `created_at` | timestamptz | 非空 |
| `updated_at` | timestamptz | 非空 |

工具表只保存平台需要的元数据，不保存工具业务配置和敏感凭证。

### 11.5 `tasks`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `tool_id` | varchar | 外键 |
| `created_by` | UUID | 用户外键 |
| `status` | varchar | 非空 |
| `input_summary` | jsonb | 脱敏后的输入摘要 |
| `progress` | integer | 0～100 |
| `error_code` | varchar | 可空 |
| `error_message` | text | 可空 |
| `created_at` | timestamptz | 非空 |
| `started_at` | timestamptz | 可空 |
| `finished_at` | timestamptz | 可空 |
| `cancel_requested_at` | timestamptz | 可空 |

任务状态：

```text
pending
running
succeeded
failed
cancelled
```

允许的主要流转：

```text
pending → running → succeeded
pending → running → failed
pending → cancelled
running → cancelled
```

### 11.6 `task_results`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `task_id` | UUID | 唯一外键 |
| `summary` | jsonb | 结果摘要 |
| `result_type` | varchar | JSON、Markdown、HTML、file |
| `storage_key` | varchar | 可空 |
| `size_bytes` | bigint | 可空 |
| `created_at` | timestamptz | 非空 |

PostgreSQL 只保存适合查询的摘要。大日志、压缩包和报告文件后续应放文件存储或对象存储，数据库只保存索引。

### 11.7 `audit_logs`

至少记录：

- 登录和退出；
- 登录失败；
- 用户启用或禁用；
- 角色和权限修改；
- 工具启用或禁用；
- 任务创建和取消；
- 结果下载；
- 管理员查看敏感数据。

审计日志不能记录密码、会话 Token、完整测试账号凭证或未脱敏原始日志。

## 13. 工具接入设计

### 13.1 工具分类

#### 页面型工具

已有独立 Web 页面，例如：

- `TrackEvents_tess`；
- `log_filter_tool`。

平台提供导航和权限入口，工具页面仍由自身服务渲染。

#### API 型工具

只有后端能力，平台 React 页面负责输入和结果展示。

#### 任务型工具

执行时间较长，需要：

- 提交任务；
- 查询状态；
- 取消任务；
- 获取结果。

测试 Agent 和接口自动化更适合任务型工具。

### 13.2 标准任务协议

后续任务型工具至少提供或通过适配层实现：

```text
提交
查询状态
取消
获取结果
健康检查
```

平台不要要求现有两个页面型工具在前端框架迁移阶段立即实现该协议。

### 13.3 工具适配层

任务中心阶段可以在 `platform-api` 或 `platform-worker` 中为不同工具提供轻量适配器：

```text
TrackEventsAdapter
ApiAutomationAdapter
AgentAdapter
```

适配器只转换统一任务协议与工具接口，不复制工具核心业务代码。

### 阶段 5：重型异步任务

#### 触发条件

- 任务执行超过普通 HTTP 请求时长；
- 需要并发控制；
- 需要失败重试；
- 需要跨进程或跨机器执行；
- Agent 或自动化任务需要排队。

#### 方案

增加独立 worker。是否引入 Redis + Celery/RQ，应根据真实任务量和重试需求决定，不在前期预置。

## 19. 风险评估

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 一次性开发全部能力 | 周期长、回归范围大 | 严格按阶段上线 |
| React 路由覆盖工具路径 | 工具 404 | Nginx 明确排除 `/api` 和工具路径 |
| 数据库引入后平台依赖增加 | API 无法启动 | 独立健康检查和迁移验证 |
| 登录只限制菜单不限制后端 | 越权 | FastAPI 强制校验权限 |
| 直接保护工具路径困难 | 已知 URL 可绕过导航 | 内网过渡，第二步增加网关鉴权 |
| 耗时任务运行在 Web 进程 | 重启丢任务 | 任务持久化，后续独立 worker |
| 原始日志写入数据库 | 数据库膨胀和敏感信息风险 | 只存摘要和文件索引 |
| 工具接口格式不统一 | 汇总困难 | 使用适配器，不强改工具核心 |
| 数据库迁移失败 | 平台不可用 | 备份、预演、可回滚迁移 |
| 宿主机固定文件路径 | 环境不可移植 | 后续配置化并使用数据卷或对象存储 |

## 20. 回滚方案

### 20.1 React 回滚

- 保留当前 `web/` 静态页面；
- Nginx 可切回原静态目录；
- 工具路由完全不变；
- 不需要回滚工具服务。

### 20.2 FastAPI 回滚

- 前端临时恢复静态工具配置；
- Nginx 移除或停用 `/api/v1/`；
- 两个工具仍直接访问；
- 数据库保留，不执行破坏性删除。

### 20.3 登录权限回滚

- 保留管理员应急开关，但只允许在受控环境启用；
- 回滚前记录原因和时间；
- 不删除用户、角色和审计数据；
- 修复后恢复鉴权并撤销临时会话。

### 20.4 数据库迁移回滚

- 上线前备份；
- 在测试数据库预演 upgrade 和 downgrade；
- 破坏性字段删除分两次发布；
- 先停止写入，再执行必要回滚；
- 不使用 `drop all` 或手工修改生产表。

## 24. 最终建议

当前最合适的下一步不是一次性实现完整平台，而是先完成：

```text
阶段 1：React + TypeScript + Vite 替换当前静态首页
阶段 2：FastAPI + PostgreSQL 建立工具目录 API
```

这两阶段完成后，平台具备稳定的前后端基础，同时保持现有两个工具完全独立。之后再基于真实用户和任务需求开发登录、权限和任务中心，可以避免提前设计错误的数据模型和任务协议。

建议将第一轮实际开发成功标准限定为：

- React 首页上线；
- 工具列表由 FastAPI 返回；
- PostgreSQL 保存工具元数据；
- 两个现有工具入口和健康检查不变；
- 不在第一轮开发用户、角色和任务模块。

这一范围预计 1～2 周，改动可控、价值明确，也为后续功能提供稳定基础。
