# 测试开发平台多人协作开发与工具接入操作指南

> 文档版本：V1.0
> 编写日期：2026-08-23
> 适用仓库：`/Users/admin/Testproject`
> 适用分支：`dev`、`main` 及从 `dev` 创建的功能分支
> 适用对象：平台维护者、工具负责人、测试开发工程师、代码评审者和发布负责人
> 文档状态：团队试运行；团队确认负责人和合并规则后转为正式规范

---

## 1. 文档目的

本指南用于回答并落实以下问题：

1. 测试开发平台如何支持多名测试开发工程师共同开发；
2. 新工具、测试 Agent 和自动化能力应放在哪里；
3. 平台公共数据库与工具业务数据如何划分；
4. 多人修改同一套 Web 平台时如何分支、评审、测试、发布和回滚；
5. 一个新工具从独立项目接入平台时，具体要修改什么、由谁审批、如何验收；
6. 当前仓库还需要补齐哪些工程治理能力，才能降低多人开发冲突。

本指南不是要求把六个现有工具合并成一个应用，也不要求立即拆分成多个 Git 仓库。当前推荐路线是：

> **保留一个 Git 仓库，将平台作为统一控制面，将每个工具作为独立组件开发、测试、构建和运行。**

## 2. 五分钟团队说明

如果只需要向新成员快速说明平台，可以直接使用以下内容：

### 2.1 平台是什么

测试开发平台不是把所有业务代码写进一个项目，而是统一提供：

- 登录和平台会话；
- 用户、角色与工具权限；
- 工具入口和运行状态；
- 配置、Secret、Credential 和 LLM 配置；
- 审计日志；
- 统一网关、版本状态和发布入口。

每个工具继续解决自己的问题，保留自己的页面、接口、任务、数据和报告。

### 2.2 新成员如何开发

- 修改某个工具内部功能：只修改该工具目录，运行该工具测试；
- 修改平台公共能力：修改 `test-platform/`，同时运行平台前后端测试；
- 新增独立工具：先独立完成，再按本指南接入 Nginx、Compose、工具目录、权限、版本和 CI；
- 涉及平台数据库、登录、权限、Secret、网关或生产发布：必须由平台维护者评审；
- 所有 Secret、Token、密码和真实数据都不能提交 Git 或粘贴到 PR、日志、截图中。

### 2.3 数据怎么分

- 用户、权限、平台会话、配置、Secret、审计、工具目录：归平台数据库；
- 工具任务、用例、运行记录、报告、附件：归工具自己；
- 工具不能直接读写平台 PostgreSQL，只能调用平台内部 API；
- 工具之间不能直接修改对方数据库；
- 跨工具展示以后通过 API、事件或平台只读索引实现，不通过跨库表连接实现。

### 2.4 当前仓库策略

- 现阶段继续使用一个 Git 仓库；
- 每个一级工具目录视为一个独立组件；
- 每个组件有自己的负责人、版本、镜像、测试和回滚方式；
- 当某个工具出现独立团队、独立发布节奏或独立访问控制需求时，再评估拆分仓库。

## 3. 术语与状态说明

| 术语 | 含义 |
|---|---|
| 平台控制面 | `test-platform` 中负责身份、权限、配置、Secret、审计、目录和版本的能力 |
| 工具 | 埋点分析、日志分析、检索评测、接口自动化等独立服务 |
| Agent | 功能测试智能体、API 测试智能体等具有任务流程的独立服务 |
| 平台模式 | 工具部署在统一网关后，使用平台身份、权限、配置和审计 |
| 独立模式 | 工具不依赖平台，从自己的环境变量或本地配置启动 |
| Tool Client | 工具调用平台内部 API 时使用的服务身份，不是用户登录 Session |
| 平台维护者 | 负责平台公共架构、数据库、网关、权限和生产发布的人 |
| 工具负责人 | 对某个工具的业务、数据、测试、版本和故障处理负责的人 |

本指南使用以下标记区分事实和计划：

- **当前已实现**：代码仓库中已经存在，可按现有方式使用；
- **团队规则**：多人协作开始后应立即遵守；
- **待补齐**：当前尚未完整实现，需要平台维护者安排工程改造。

## 4. 当前架构与职责边界

### 4.1 仓库结构

当前六个正式工具和平台位于同一个 Git 仓库：

```text
Testproject/
├── test-platform/           # 平台前端、后端、网关、Compose、迁移和文档
├── functional-test-agent/   # 功能测试智能体
├── api-test-agent/          # API 测试智能体
├── TrackEvents_tess/        # 埋点分析
├── log_filter_tool/         # 日志分析
├── Truthy_Search/           # 检索评测
└── api-autotest/     # 接口自动化
```

这些目录都属于 `/Users/admin/Testproject` 这一个 Git 仓库，不是七个彼此无关的 Git 仓库。

### 4.2 技术架构

```text
浏览器
  │
  ▼
Nginx 统一网关（宿主机仅暴露 8080）
  ├── React + TypeScript + Vite 平台前端
  ├── FastAPI 平台 API
  │     └── PostgreSQL：身份、权限、配置、Secret、审计、目录、版本
  ├── 功能测试智能体 ── 自有任务目录
  ├── API 测试智能体 ── 自有任务目录和受控执行组件
  ├── 接口自动化 ───── 自有任务与报告目录
  ├── 埋点分析 ─────── 独立分析服务
  ├── 日志分析 ─────── 独立分析与导出目录
  └── 检索评测 ─────── SQLite、输入、输出和报告目录
```

当前正式组件路由如下：

| 组件 | 平台入口 | Compose Service | 内部端口 | 主要业务数据 |
|---|---|---|---:|---|
| 平台 Web | `/` | `platform-gateway` | 80 | 无业务数据，静态资源 |
| 平台 API | `/api/v1/` | `platform-api` | 8000 | 平台 PostgreSQL |
| 埋点分析 | `/trackevents/` | `trackevents-web` | 8000 | 近似无状态 |
| 日志分析 | `/log-filter/` | `log-filter-tool` | 5001 | 导出文件 |
| 检索评测 | `/truthy-search/` | `truthy-search` | 5002 | SQLite、输入、输出、报告 |
| 接口自动化 | `/api-autotest/` | `api-autotest` | 5003 | 任务、日志、Allure 报告 |
| 功能测试智能体 | `/functional-test-agent/` | `functional-test-agent` | 5004 | 独立任务目录和产物 |
| API 测试智能体 | `/api-test-agent/` | `api-test-agent` | 5005 | 独立任务目录、产物和受控执行状态 |

端口只在容器网络中使用。宿主机统一只通过 `${PLATFORM_PORT:-8080}` 访问 Nginx，不应为新工具额外映射宿主机端口。

### 4.3 平台负责什么

以下能力属于平台公共控制面，只能由平台模块负责：

- 用户、角色、权限和平台 Session；
- 网关统一鉴权和可信身份头注入；
- 工具目录和健康状态；
- 普通配置的草稿、发布、激活与回滚；
- Secret 加密存储和 Credential 维护；
- LLM Profile 与工具绑定；
- 审计日志；
- dev/prod 环境隔离；
- 组件版本、镜像身份和发布清单；
- 平台级数据库迁移。

### 4.4 工具负责什么

每个工具负责自己的：

- 业务算法和任务流程；
- 页面和业务 API；
- 任务、用例、执行记录和报告；
- 业务数据库或文件目录；
- 独立模式配置；
- 单元测试、集成测试和工具回归；
- 工具镜像、工具版本和工具回滚；
- 平台模式适配层。

### 4.5 禁止跨越的边界

以下做法禁止进入正式实现：

- 工具直接使用平台 PostgreSQL 用户名和密码；
- 工具直接更新平台用户、权限、配置、Secret 或审计表；
- 一个工具的 Alembic 或建表脚本修改另一个工具的表；
- 一个工具直接写另一个工具的 SQLite、任务目录或报告目录；
- 浏览器自行构造并信任 `X-Platform-*` 身份头；
- 将用户 Cookie 当作工具内部服务凭证；
- 将真实 Token、密码、API Key、KEK 或 Client Token 写入 Git；
- 平台模式和独立模式同时写同一份 SQLite、任务或报告目录。

## 5. 多人协作组织方式

### 5.1 推荐角色

一个人可以兼任多个角色，但职责必须明确。

| 角色 | 主要职责 | 强制评审范围 |
|---|---|---|
| 平台维护者 | 平台架构、公共 API、PostgreSQL、Alembic、Nginx、Compose、RBAC、Secret、发布 | 平台核心、数据库、网关、安全和生产配置 |
| 工具负责人 | 工具需求、业务代码、数据、测试、镜像、运行手册和回滚 | 所负责工具目录及其平台接入信息 |
| 功能开发者 | 按需求实现、补测试、更新版本和文档 | 自己提交的改动 |
| 代码评审者 | 检查需求、边界、测试、兼容性和风险 | 被指定目录或专业领域 |
| 发布负责人 | 合并发布分支、创建标签、审批生产部署、保存发布记录 | `main`、Release Tag、生产环境 |

### 5.2 建议负责人表

团队第一次宣讲后，应填写真实姓名或 GitHub 账号。

| 组件 | 主负责人 | 备份负责人 | 平台接入评审人 |
|---|---|---|---|
| `test-platform` | 待填写 | 待填写 | 平台维护者 |
| `functional-test-agent` | 待填写 | 待填写 | 平台维护者 |
| `api-test-agent` | 待填写 | 待填写 | 平台维护者 |
| `api-autotest` | 待填写 | 待填写 | 平台维护者 |
| `TrackEvents_tess` | 待填写 | 待填写 | 平台维护者 |
| `log_filter_tool` | 待填写 | 待填写 | 平台维护者 |
| `Truthy_Search` | 待填写 | 待填写 | 平台维护者 |

### 5.3 评审规则

| 改动类型 | 最低审批要求 |
|---|---|
| 仅修改工具内部代码 | 一名工具负责人 |
| 工具页面与平台视觉衔接 | 工具负责人；涉及平台公共组件时增加平台维护者 |
| 新工具接入 | 工具负责人 + 平台维护者 |
| 平台前端公共导航或目录 | 平台维护者 |
| 平台后端公共 API | 平台维护者 |
| Alembic、RBAC、登录、Secret、Credential | 至少一名平台维护者强制审批 |
| Nginx、Compose、宿主机端口、Docker Socket | 至少一名平台维护者强制审批 |
| 生产发布 | 发布负责人 + 平台维护者 |

### 5.4 代码所有权原则

- 负责人拥有评审权，不等于只有负责人能开发；
- 任何成员都可以提交跨目录改动，但必须获得对应负责人审批；
- 公共文件不能采用“最后修改的人负责”的临时规则；
- 迁移、网关和权限属于高冲突文件，合并前必须同步最新 `dev`；
- 不允许为了赶进度绕过评审，之后再补数据库或安全检查。

## 6. 什么情况下创建独立工具项目

### 6.1 应创建独立项目的情况

满足下列任意两项时，通常应建立新的一级目录和独立服务：

- 有自己的 Web 页面或业务 API；
- 有任务生命周期或长时间运行过程；
- 有自己的数据库、任务、报告或附件；
- 需要独立构建、发布或回滚；
- 工具故障不应影响平台或其他工具；
- 由独立负责人长期维护；
- 未来可能有不同的扩容、资源或安全策略。

### 6.2 不应创建独立服务的情况

以下内容通常应继续放在 `test-platform`：

- 用户、角色、权限、登录和会话；
- 配置、Secret、Credential 和 LLM 管理页面；
- 工具目录、健康状态和版本状态；
- 平台导航、管理页面和审计查询；
- 只为平台服务且没有独立业务数据的简单管理能力。

### 6.3 应创建公共库而不是服务的情况

如果一段能力：

- 没有独立运行进程；
- 没有独立数据；
- 只是多个项目重复使用的纯函数、协议类型或测试辅助代码；

则优先评估公共库。但在至少两个正式调用方出现前，不提前抽象公共库。

### 6.4 新项目命名规则

- 目录名：英文、短横线或现有兼容名称，不使用空格；
- Tool ID：全局唯一、小写、短横线分隔，发布后保持稳定；
- Compose Service：与 Tool ID 尽量一致；
- 浏览器路径：`/<tool-id>/`；
- 健康地址：平台模式优先使用 `/<tool-id>/health`；
- 版本组件 ID：与 Compose Service 一致或有清晰映射。

Tool ID 一旦写入数据库、权限、审计和历史任务，不得仅因展示名称变化而修改。

## 7. 数据库与数据所有权规则

### 7.1 平台数据库允许保存的数据

当前平台 PostgreSQL 是控制面数据库，主要数据域包括：

- `tools`；
- 用户、角色、权限、授权和平台会话；
- 工具 Client；
- 审计日志；
- 环境、配置定义、Release、Release Item 和 Activation；
- Secret、Secret Version；
- Credential 和 Credential Item；
- LLM Profile 和工具 LLM Binding。

这些表由 `test-platform/backend/alembic` 中的平台迁移管理。

### 7.2 工具必须自己保存的数据

以下数据不能因为“方便查询”而直接放进平台公共表：

- 工具任务和任务状态；
- 测试点、测试用例和执行步骤；
- 请求、响应、日志明细；
- 工具报告和附件；
- 工具专属项目、基准、评测样本；
- 工具内部队列或重试状态。

### 7.3 新工具需要关系数据库时怎么选

优先顺序如下：

1. 工具已有稳定 SQLite 且并发量可控：继续使用自己的 SQLite；
2. 工具需要并发、事务或查询能力：使用工具自己的 PostgreSQL Database 和账号；
3. 运维资源有限时：可以与平台共用一个 PostgreSQL 实例，但必须使用独立 Database 或独立 Schema、独立账号和独立迁移；
4. 对隔离要求较高时：使用独立 PostgreSQL 服务。

无论采用哪种方式，都必须满足：

- 数据所有者明确；
- 连接凭证不与平台数据库账号相同；
- 工具迁移不进入平台 Alembic；
- 备份和恢复方式单独验证；
- 删除工具不能破坏平台公共数据；
- 平台不可用时，工具已有任务和历史结果的行为符合设计约定。

### 7.4 数据访问决策表

| 场景 | 正确方式 | 禁止方式 |
|---|---|---|
| 工具读取当前用户 | 使用网关注入的可信身份上下文 | 查询平台 `users` 表 |
| 工具读取运行配置 | 使用平台内部 runtime-config API | 查询配置和 Secret 表 |
| 工具上报操作记录 | 调用幂等审计内部 API | 直接插入 `audit_logs` |
| 平台展示工具任务摘要 | 调用工具只读 API或消费脱敏事件 | 跨库 Join 工具业务表 |
| 工具读取另一个工具结果 | 通过稳定、授权的 API | 读取对方 SQLite 或共享目录 |
| 管理员修改 Secret | 使用平台 Secret 管理页面/API | 修改 `.env` 或数据库密文 |

### 7.5 数据库迁移规则

#### 平台迁移

- 只能在 `test-platform/backend/alembic/versions/` 新增迁移；
- 不修改已经进入 `dev` 或发布过的旧迁移；
- 新迁移必须连接当前唯一 Head；
- 每次合并前重新检查是否出现多个 Head；
- 迁移必须支持空库升级和从上一正式版本升级；
- downgrade 不得静默删除真实业务数据；
- 涉及 Secret 时，迁移只创建结构和定义，不包含明文；
- 迁移由平台维护者审批。

#### 工具迁移

- 放在工具自己的迁移目录；
- 由工具负责人维护；
- 不引用平台 ORM 模型；
- 不修改平台表；
- 必须有独立备份、升级和回滚说明。

#### 当前需要关注的版本一致性

截至本文编写时，`versions.json` 中记录的 Alembic revision 为 `20260818_0016`，迁移目录已经存在 `20260821_0017_add_api_agent_v24_permissions.py`。这可能是尚未完成的开发改动，但合并或发布前必须确认并同步版本清单。后续应由 CI 自动阻止“迁移 Head 与版本清单不一致”。

## 8. Git 分支、提交与 Pull Request 流程

### 8.1 分支职责

| 分支 | 用途 | 是否允许直接开发 |
|---|---|---|
| `main` | 可发布主线，只接受经过验证的发布 PR | 否 |
| `dev` | 日常集成分支 | 平台维护者也应尽量通过 PR |
| `feat/*` | 新功能 | 是 |
| `fix/*` | 缺陷修复 | 是 |
| `docs/*` | 文档 | 是 |
| `chore/*` | CI、构建和非业务维护 | 是 |

推荐分支名称：

```text
feat/api-test-agent-executable-review
fix/truthy-search-health-timeout
docs/tool-onboarding-guide
chore/ci-trackevents-tests
```

### 8.2 开始开发

```bash
cd /Users/<你的用户名>/Testproject
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feat/<tool-id>-<简短主题>
```

开始前必须执行：

```bash
git status --short
```

如果工作区已有其他人的未提交修改，不得清理、覆盖、`reset --hard` 或替换文件，应先确认修改归属。

### 8.3 提交规范

建议使用以下前缀：

```text
feat: 新增能力
fix: 修复缺陷
test: 增加或调整测试
docs: 文档变更
refactor: 不改变行为的重构
chore: 构建、CI、版本或维护
```

示例：

```text
feat: add platform adapter for new quality tool
fix: preserve base path in search redirects
test: cover tool permission denial
docs: document tool data ownership
```

一次提交应只表达一个可以解释、测试和回滚的目的。

### 8.4 Pull Request 目标

推荐多人协作后的正式流程：

```text
功能分支 → PR 到 dev → dev 集成验证 → 发布 PR 到 main → Release Tag
```

**待补齐：** 当前 GitHub Actions 只在 `dev` push 和面向 `main` 的 PR 上触发。团队正式采用“功能分支 PR 到 dev”前，应先把 CI 的 PR 触发分支增加 `dev`，否则 PR 合并前缺少远端门禁。

在该 CI 调整完成前，PR 提交者必须在本地运行对应测试并把完整命令和结果写进 PR，平台维护者不得在没有验证证据时直接合并。

### 8.5 合并前同步

```bash
git fetch origin
git rebase origin/dev
```

如果改动涉及 Alembic、Nginx、Compose、`versions.json` 或权限种子，必须在同步最新 `dev` 后重新运行验证，不能只解决文本冲突。

### 8.6 禁止提交的内容

- `.env` 和生产环境变量文件；
- `.runtime-secrets/`；
- KEK、Bootstrap Token、Client Token；
- API Key、账号密码、Access Token、Refresh Token；
- 真实请求和响应中的隐私或凭证；
- 本地数据库、任务目录、报告和备份；
- 带有 Secret 的截图、测试日志和 HAR 文件。

## 9. 新成员本地开发环境

### 9.1 基础依赖

团队统一使用：

- Git；
- Docker 与 Docker Compose；
- Python 3.12；
- Node.js 24；
- npm 11；
- 可访问本机 `127.0.0.1:8080` 的桌面浏览器。

### 9.2 首次获取代码

```bash
git clone <团队仓库地址> Testproject
cd Testproject
git switch dev
cp test-platform/.env.example test-platform/.env
```

每个人修改自己的本地 `test-platform/.env`，不得把它提交到 Git。

至少检查并修改以下本机专属项：

```dotenv
PLATFORM_PORT=8080
APP_PUBLIC_URL=http://localhost:8080
PROD_VERSION_SNAPSHOT_URL=
API_AGENT_RUNTIME_HOST_ROOT=/你的绝对路径/Testproject/api-test-agent/runtime/dev/api
```

- 如果 8080 已被占用，给 `PLATFORM_PORT` 选择一个未占用端口，并同步修改 `APP_PUBLIC_URL`；
- 普通本地开发默认清空 `PROD_VERSION_SNAPSHOT_URL`，避免未经授权访问共享生产快照；
- `API_AGENT_RUNTIME_HOST_ROOT` 必须是当前电脑上的真实绝对路径，不能沿用其他开发者的 `/Users/...`；
- 真实业务 Token 不写入 `.env`，应由本机平台 Secret 页面或获授权的共享 dev 环境管理。

### 9.3 本地 Secret 初始化

`.runtime-secrets/` 被 Git 忽略，每位开发者必须使用自己的随机值，不能互相复制真实 dev/prod Secret。

在本地仓库根目录执行以下命令，可以生成只用于本机空数据库的开发凭证。命令不会在终端输出 Secret：

```bash
python3 - <<'PY'
import base64
import json
import secrets
from pathlib import Path

root = Path("test-platform/.runtime-secrets")
dev = root / "dev"
dev.mkdir(parents=True, exist_ok=True)

def write_secret(path: Path, value: str) -> None:
    path.write_text(value + "\n", encoding="utf-8")
    path.chmod(0o600)

kek = {
    "active": "v1",
    "keys": {"v1": base64.b64encode(secrets.token_bytes(32)).decode("ascii")},
}
kek_path = root / "dev-kek.json"
kek_path.write_text(json.dumps(kek) + "\n", encoding="utf-8")
kek_path.chmod(0o600)

for name in (
    "bootstrap-token",
    "version-peer-token",
    "functional-test-agent-client-token",
    "api-test-agent-client-token",
    "api-execution-controller-token",
):
    write_secret(dev / name, secrets.token_urlsafe(48))

for name in (
    "trackevents-client-token",
    "log-filter-client-token",
    "truthy-search-client-token",
    "api-autotest-client-token",
):
    write_secret(root / name, secrets.token_urlsafe(48))

# 仅保证旧只读挂载存在，不代表已经配置真实 LLM。
legacy_llm_key = root / "llm-api-key"
legacy_llm_key.write_text("", encoding="utf-8")
legacy_llm_key.chmod(0o600)
PY
```

注意：

- 这组值只能用于个人本机空数据库；
- 不要用它覆盖共享 dev 或 prod Secret；
- 不要把输出目录压缩后发给其他人；
- KEK 丢失后，本地已加密的 Secret 无法解密；需要保留数据时应单独备份；
- 共享 dev 和 prod 的 Secret 由平台维护者或发布负责人管理。

### 9.4 启动完整平台

```bash
cd test-platform
./scripts/dev-up.sh
docker compose ps -a
```

首次空库启动后访问：

```text

```

使用本机 `test-platform/.runtime-secrets/dev/bootstrap-token` 完成第一个管理员初始化。已有用户的数据库会关闭 `/setup`，后续账号应由平台“用户管理”创建，不能共享管理员密码。

### 9.5 只重建一个组件

`dev-up.sh` 支持传入组件 ID，例如：

```bash

```

涉及平台 React 或 Nginx 时使用：

```bash

```


### 9.7 同一台电脑多工作区限制

- 不同成员在各自电脑运行，不会相互影响；
- 同一台电脑默认只运行一套完整平台；

## 10. 日常开发操作流程

### 10.1 仅修改一个工具内部功能

1. 从最新 `dev` 创建功能分支；
2. 阅读该工具 `README.md`、`AGENTS.md`、相关实现和测试；
3. 先运行或补充能够覆盖目标行为的测试；
4. 只修改工具目录内必要文件；
5. 运行工具回归；
6. 更新该组件在 `test-platform/versions.json` 中的 PATCH 或 MINOR 版本；
7. 运行版本校验；
8. 提交 PR，由工具负责人审批。

如果工具对外路径、健康响应、平台配置、权限或审计没有变化，通常不需要修改平台数据库、Nginx 和 Compose。

### 10.2 修改工具的平台接入适配

除了工具回归，还必须检查：

- 平台子路径是否保留；
- 平台模式和独立模式是否都能启动；
- 网关鉴权是否仍然失败关闭；
- 写操作是否继续通过 CSRF 和权限校验；
- 身份头是否只在网关之后信任；
- runtime-config 是否只获取本工具和当前环境；
- 审计事件是否脱敏且具备幂等 `event_id`；
- 平台不可用时行为是否符合工具约定；
- Secret 是否未进入日志、任务 JSON、报告或错误响应。

这类 PR 需要工具负责人和平台维护者共同审批。

### 10.3 修改平台公共能力

1. 明确是否影响现有六个工具；
2. 先定义向后兼容的公共接口或迁移方案；
3. 修改平台后端时运行后端测试和数据库迁移测试；
4. 修改平台前端时运行组件测试和生产构建；
5. 修改权限时验证匿名、无权限、直接 URL 和伪造 Header；
6. 修改 Nginx/Compose 时验证六工具故障隔离和宿主机端口；
7. 更新 `platform-backend` 或 `platform-gateway` 组件版本；
8. 由平台维护者审批。

### 10.4 修改平台数据库

1. 获取最新 Alembic Head；
2. 创建一个新迁移，不修改历史迁移；
3. 检查 `down_revision`；
4. 验证空库 `upgrade head`；
5. 验证从上一发布 revision 升级；
6. 验证重复执行不会创建重复数据；
7. 验证 downgrade 的数据影响；
8. 更新 `versions.json.database.alembic_revision`；
9. 平台维护者评审后才能合并。

### 10.5 修复线上缺陷

1. 先保存错误时间、组件版本、请求 ID 和脱敏日志；
2. 在本地或测试环境稳定复现；
3. 确认根因属于平台还是某个工具；
4. 编写失败测试；
5. 做最小修复；
6. 运行对应组件和接入回归；
7. 增加 PATCH 版本；
8. 说明回滚镜像和是否涉及数据恢复。

## 11. 新工具接入标准流程

新工具接入不是只增加首页卡片。必须完成“业务独立可运行”和“平台模式可治理”两部分。

### 11.1 第一步：接入评审

开发前提交以下信息：

```text
工具名称：
Tool ID：
负责人：
所属能力域：AI 测试 / 自动化 / 质量分析 / 专项评测
解决的问题：
主要输入：
主要输出：
平台入口：
内部服务名和端口：
是否有任务：
是否有数据库或文件数据：
独立模式配置来源：
平台模式需要的普通配置：
平台模式需要的 Secret：
需要的 Tool Client 能力：
需要的用户权限：
是否调用外部接口或 LLM：
预计测试命令：
备份与回滚方式：
```

平台维护者在编码前确认：

- Tool ID、路径、端口没有冲突；
- 该能力确实应该是独立服务；
- 数据归属和备份方式明确；
- 权限粒度没有复用错误；
- Secret 不会退回 `.env` 作为平台真源；
- 外部请求、文件上传、真实执行等风险有边界；
- 本期接入范围不包含未承诺的平台聚合能力。

### 11.2 第二步：先完成独立模式

新工具在接入平台前必须能够独立运行，并具备：

- 独立入口；
- 独立依赖文件；
- 独立 Dockerfile；
- 独立测试；
- 健康接口；
- 明确的数据目录和备份方式；
- `.env.example` 只包含键名和安全示例；
- README 中包含启动、测试和故障排查；
- 不依赖平台数据库；
- 不占用平台宿主机 8080。

### 11.3 第三步：支持平台子路径

平台模式下必须：

- 使用 `/<tool-id>/` 作为浏览器入口；
- 静态资源、表单 action、重定向、下载和 API 都保留前缀；
- 不通过 Nginx HTML 替换修复硬编码 URL；
- 可以通过环境变量配置 Base Path；
- 独立模式 Base Path 为空或使用工具原路径；
- 页面提供“返回测试开发平台”入口；
- 非法 Base Path 返回明确错误或拒绝启动。

### 11.4 第四步：健康与版本协议

健康接口不执行真实任务，不读取大文件，不调用外部付费服务。推荐返回：

```json
{
  "service": "new-tool",
  "status": "ok",
  "version": "1.0.0",
  "revision": "git-sha",
  "dirty": false,
  "content_sha256": "source-content-sha256",
  "runtime_environment": "dev"
}
```

要求：

- 正常返回 200；
- 自身关键存储不可用时返回 503；
- 不返回数据库路径、异常堆栈、Token 或内部凭证；
- 使用 `APP_VERSION`、`APP_REVISION`、`APP_BUILD_DIRTY`、`APP_CONTENT_SHA256` 和 `PLATFORM_RUNTIME_ENV`；
- 平台模式的健康地址必须能从 `platform-api` 容器访问。

### 11.5 第五步：接入身份与权限

浏览器到工具的请求必须经过 Nginx `auth_request`：

- 页面和静态资源至少需要 `tool.view`；
- 创建、分析、导入、重试、取消、导出等写行为需要 `tool.execute` 或工具专属权限；
- 结果、Raw、报告和下载需要 `tool.result.view`；
- 管理配置需要 `tool.config.manage`；
- 管理 Secret 需要 `tool.secret.manage`；
- 工具专属流程可以新增更细权限，但不能用前端隐藏代替后端校验。

工具只能信任网关注入的身份头。Nginx 必须先清除客户端提供的同名 `X-Platform-*`，再注入平台授权结果。

### 11.6 第六步：申请最小 Tool Client 能力

当前内部能力包括：

| 能力 | 用途 |
|---|---|
| `config.read` | 读取本工具当前环境的运行配置快照 |
| `config.ack` | 确认配置已加载或生效 |
| `audit.write` | 上报幂等审计事件 |
| `credential.status.write` | 上报凭证状态 |
| `credential.session.write` | 原子写回受平台管理的 Session |

新工具只申请实际需要的能力。例如一个无平台配置、只上报分析审计的工具，不需要 `config.read` 和 Credential 能力。

Client Token 规则：

- 每个工具、每个环境独立；
- 文件至少 32 字符，推荐高强度随机值；
- 数据库只保存哈希；
- 只读挂载到对应工具；
- 不进入 Web 日常配置；
- 不与用户 Session、Bootstrap Token 或其他工具共用；
- 工具 A 的 Token 不能读取工具 B 的配置。

### 11.7 第七步：登记平台数据

使用新的平台 Alembic 迁移登记：

- `tools` 工具记录；
- 必要的权限定义和内置角色授权；
- 平台可编辑的普通配置定义；
- Secret 定义；
- 必要时登记 LLM Binding；
- dev 的安全默认值或关闭状态。

迁移中不得包含真实 Secret，不得修改已有迁移。

### 11.8 第八步：修改平台接入文件

当前新工具接入通常会涉及以下中心文件：

| 文件 | 需要做什么 | 负责人 |
|---|---|---|
| `test-platform/backend/alembic/versions/<new>.py` | 工具、权限和配置定义 | 平台维护者 |
| `test-platform/backend/app/bootstrap_clients.py` | 登记最小 Client 能力 | 平台维护者 |
| `test-platform/docker-compose.yml` | dev 服务、环境变量、只读 Secret、内部端口和数据卷 | 平台维护者 + 工具负责人 |
| `test-platform/docker-compose.prod.yml` | 生产不可变镜像覆盖 | 发布负责人 |
| `test-platform/nginx/nginx.conf` | 子路径、鉴权、代理和故障页 | 平台维护者 |
| `test-platform/frontend/src/data/capabilityCatalog.ts` | 使命、输入、输出、边界和能力域 | 平台前端负责人 |
| `test-platform/versions.json` | 组件版本、源码范围、镜像变量和配置作用域 | 工具负责人 + 发布负责人 |
| `.github/workflows/ci.yml` | 工具测试和镜像构建 | 平台维护者 |
| `.github/workflows/release.yml` | 生产镜像和发布清单 | 发布负责人 |
| `test-platform/README.md` | 启动、测试、备份和回滚 | 工具负责人 |

这些文件是当前多人接入时最容易冲突的热点。修改前必须同步最新 `dev`，同一个接入 PR 中由工具负责人和平台维护者共同完成。

### 11.9 第九步：配置和 Secret 接入

普通配置必须先在迁移中登记白名单键，再通过 Web 草稿、校验、发布和回滚。

Secret 必须满足：

- 保存后不回显；
- dev/prod 隔离；
- 由平台 KEK 加密；
- 工具只在内部 runtime-config 中按权限获取；
- 任务启动时获取不可变快照；
- 运行中任务不因管理员发布新配置而漂移；
- 报告和审计只记录 Secret ID、版本和结果，不记录明文。

工具独立模式可以继续使用自己的 `.env`，但平台模式不得在平台不可用时静默回退到旧 Secret 文件。

### 11.10 第十步：审计接入

至少上报：

- 任务或分析提交；
- 取消、重试和导出；
- 配置加载结果；
- 关键终态；
- 凭证刷新或登录结果；
- 权限或 CSRF 拒绝。

审计事件必须：

- 使用全局唯一、可重试的 `event_id`；
- 包含操作者、动作、资源、结果和非敏感元数据；
- 不包含请求原文、响应原文、密码、Token、API Key 或用户隐私；
- 上报失败时遵守工具已经定义的故障策略；
- 不能由普通业务 API 更新或删除。

### 11.11 第十一步：版本和镜像

当前机器真源是 `test-platform/versions.json`，采用无前导零的 Semantic Versioning：

- PATCH：兼容的缺陷修复和小改动；
- MINOR：向后兼容的新能力；
- MAJOR：不兼容变更。

每个独立组件只在自身源码范围变化时升级版本。验证命令：

```bash
python3 test-platform/scripts/version_tool.py validate
python3 test-platform/scripts/version_tool.py check-bump --base origin/dev
```

新组件还必须登记：

- `source_paths`；
- `image_envs`；
- `compatible_product_major`；
- 如果使用平台配置，登记 `config_scopes`。

### 11.12 第十二步：自动化和集成验收

新工具至少通过：

- 工具独立模式测试；
- 平台模式测试；
- Base Path、静态资源、重定向和下载测试；
- 健康接口和故障测试；
- 匿名、无权限、直接 URL 和伪造身份头测试；
- Tool Client 跨工具和跨环境拒绝测试；
- Secret 哨兵扫描；
- Nginx 配置检查；
- Compose 配置检查；
- 平台首页目录和健康状态测试；
- 单工具停止时的故障隔离；
- 版本清单和镜像构建；
- 回滚演练。

### 11.13 新工具完成定义

以下项目全部满足，才可以宣布接入完成：

## 15. 发布流程

### 15.1 dev 集成

1. 功能分支 PR 合并到 `dev`；
2. CI 运行组件测试、版本检查和镜像构建；
3. 使用 `scripts/dev-up.sh` 构建对应组件；
4. 在共享 dev 或获授权的本地环境进行集成验证；
5. 记录组件版本、Git SHA 和验证结果；
6. 验证 `/system/versions` 中运行版本与目标一致。

### 15.2 main 和生产

当前发布约定：

```text
dev 验证完成
→ 发布 PR 合并 main
→ 创建 release-YYYY.MM.DD.N 标签
→ GitHub Actions 构建 linux/amd64 镜像
→ production Environment 审批
→ 服务器拉取不可变镜像 digest
→ 迁移、启动、健康检查和发布记录
```

生产服务器不执行 `git pull` 和 `docker compose build`。

### 15.3 发布前门禁

- [ ] PR 已由正确负责人审批；
- [ ] 组件版本已升级；
- [ ] Release 组合可追溯到 Git SHA 和 digest；
- [ ] Alembic revision 正确；
- [ ] 平台与工具测试通过；
- [ ] Nginx 和生产 Compose 校验通过；
- [ ] 备份已完成并可恢复；
- [ ] 没有正在运行且会受迁移影响的任务；
- [ ] dev/prod Secret 和 KEK 未混用；
- [ ] 回滚镜像和操作顺序已经确认。

## 16. 回滚与故障归属

### 16.1 工具内部发布失败

1. 暂停该工具的新任务；
2. 保留数据库、任务和报告；
3. 恢复该工具上一镜像；
4. 不回滚平台和其他工具；
5. 验证平台入口和其他五个工具；
6. 记录失败版本和请求 ID。

### 16.2 平台网关发布失败

1. 恢复上一 `platform-gateway` 镜像；
2. 不回滚工具数据库和任务；
3. 验证登录、权限、六个入口和 8080；
4. 确认无匿名绕过。

### 16.3 平台后端或数据库迁移失败

1. 暂停新任务和配置发布；
2. 停止 Credential Agent；
3. 保存数据库、KEK 和发布记录；
4. 优先恢复兼容的新后端或上一镜像；
5. 只有旧代码确实不能使用新 Schema 时才 downgrade；
6. Secret 表降级前禁止导出明文；
7. 验证身份、权限、配置、Secret、审计和工具访问。

### 16.4 故障归属原则

| 现象 | 首要负责人 |
|---|---|
| 只有一个工具业务失败 | 工具负责人 |
| 工具入口 502/504，但其他工具正常 | 工具负责人，平台维护者协助代理排查 |
| 所有工具都无法通过鉴权 | 平台维护者 |
| 登录、权限或 Session 异常 | 平台维护者 |
| 配置或 Secret 无法读取 | 平台维护者 + 对应工具负责人 |
| 某工具数据损坏 | 工具负责人 |
| PostgreSQL、Alembic、网关或生产 Compose 异常 | 平台维护者 / 发布负责人 |

## 18. 常见问题

### Q1：每个人都要理解整个平台吗？

不需要。工具开发者必须理解自己工具、平台接入契约和安全边界；平台维护者需要理解身份、权限、配置、数据库、网关和发布。

### Q2：所有人都可以修改平台数据库吗？

可以提出和实现迁移，但必须由平台维护者评审，且只能通过新 Alembic 迁移修改。

### Q3：新工具一定要使用 PostgreSQL 吗？

不需要。按业务并发、事务和查询需求选择。SQLite 或文件存储可以继续使用，但数据必须归工具管理。

### Q4：工具可以调用另一个工具吗？

可以，但必须先定义稳定 API、鉴权、超时、失败策略和数据边界。不能直接读写对方数据库或目录。

### Q5：是否应该马上把每个工具拆成单独 Git 仓库？

暂时不建议。当前接入修改经常同时涉及工具和平台，单仓库更容易做原子 PR、统一 CI 和版本组合。出现独立团队、独立发布节奏或访问控制需求后再拆。

### Q6：公共表大家一起用，工具表各自用，可以吗？

可以，但“公共表”仅限真正跨工具的控制面数据，而且只能由平台 API 管理。工具业务表即使位于同一 PostgreSQL 实例，也必须有独立所有者、账号和迁移。

### Q7：为什么不能让工具直接查询用户或配置表？

因为这会绕过 RBAC、环境隔离、Secret 解密、审计和接口兼容性。一旦平台表变化，所有工具都会被迫同步修改。

### Q8：工具服务异常时平台应该怎样？

只将该工具标记为不可用，平台和其他工具保持运行。平台身份服务异常时必须鉴权失败关闭，不能恢复匿名访问。

### Q9：一个功能改动需要升级哪个版本？

只升级实际发布内容变化的组件。平台整体向后兼容能力升级时再升级产品 MINOR；普通兼容修复升级对应组件 PATCH。以 `versions.json` 和版本校验脚本为机器真源。

### Q10：团队可以共享一个管理员账号吗？

不可以。每个人使用自己的平台账号和角色，才能撤销权限并通过审计追溯操作。

## 20. 最终原则

多人开发后，平台仍应保持以下结构：

> **平台统一治理，工具独立负责；公共契约稳定，业务数据隔离；所有改动可测试、可追踪、可发布、可回滚。**

团队扩大的第一步不是更换框架，也不是增加复杂基础设施，而是先把负责人、数据边界、接入契约、PR 门禁、版本规则和测试流程落实。当前 React、FastAPI、PostgreSQL、Nginx 和 Docker Compose 架构可以继续支撑下一阶段协作开发。
