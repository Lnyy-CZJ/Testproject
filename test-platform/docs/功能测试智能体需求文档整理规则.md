# 功能测试智能体需求文档整理规则

> 文档版本：V1.0
> 适用对象：Codex、需求人员、产品经理、测试人员
> 下游系统：功能测试智能体的需求拆解、测试点生成、测试点 Review 和测试用例生成流程
> 推荐输出格式：UTF-8 编码的 Markdown（`.md`）文件

## 1. 文档目的

本规则用于指导 Codex 将原始需求、会议记录、产品说明、接口说明或已有 PRD，整理为适合功能测试智能体分析的结构化需求文档。

整理后的文档应帮助智能体准确识别：

- 业务模块、功能和场景；
- 测试对象及其取值；
- 输入、业务、权限和状态约束；
- 正向流程、反向流程和异常处理；
- 状态流转及非法流转；
- Given / When / Then 验收条件；
- 边界、并发、幂等、数据一致性、安全、性能和兼容性风险；
- 未确认、存在歧义或相互冲突的需求。

本规则只负责整理和结构化原始需求，不允许补写未经原文支持的业务事实。

## 2. Codex 使用指令

以后需要 Codex 整理需求文档时，可以直接使用以下指令：

```text
请严格按照《功能测试智能体需求文档整理规则.md》整理我提供的原始需求。

要求：
1. 不得编造原文中不存在的业务规则、默认值、错误提示、权限或状态。
2. 保留原始需求中的所有有效信息，不得因结构调整而遗漏内容。
3. 将确定需求、测试设计建议、未确认项、歧义项和冲突项分开记录。
4. 输出 UTF-8 Markdown 文档。
5. 按规则执行整理后的自检，并在文档末尾输出“整理结果检查”。
6. 如果原始资料不足，不要停下来猜测；将问题写入“未确认项”。
```

如果还需要 Codex 直接保存文件，可以追加：

```text
请将整理结果保存为：{目标文件绝对路径}.md
```

## 3. 核心整理原则

### 3.1 只基于原始资料

Codex 必须遵守以下事实边界：

- 不得把行业惯例、常见做法或模型推测写成已确认需求；
- 不得自行补充字段长度、次数、超时时间、金额、错误提示或默认值；
- 不得自行增加角色、权限、状态、外部依赖或页面跳转；
- 可以指出可能缺失的信息，但必须写入“未确认项”；
- 可以提出测试设计建议，但必须放入“测试设计建议”，不能混入正式需求；
- 原始资料之间存在不同说法时，不得自行选择一个结论，必须写入“冲突项”。

### 3.2 一个条目表达一个可验证规则

每条规则应尽量满足：

- 有明确测试对象；
- 有触发条件或输入；
- 有明确行为或限制；
- 有可观察的预期结果。

推荐写法：

```text
REQ-LOGIN-003：手机号必须为 11 位数字；格式不正确时禁止提交，并显示原文规定的错误提示。
```

不推荐写法：

```text
手机号需要合法，登录相关异常要正常处理。
```

如果一个原始段落包含多个独立规则，应拆分为多个规则编号。

### 3.3 确定需求与建议分离

以下内容属于需求事实，可以进入正式需求章节：

- 原文明确规定的行为；
- 原文明确规定的数值和边界；
- 原文明确规定的角色、权限和状态；
- 原文明确规定的成功或失败结果。

以下内容只能进入“测试设计建议”：

- 原文未规定，但测试时通常需要考虑的边界；
- 性能、安全、并发、兼容性等可能风险；
- 建议补充的异常流程；
- 建议确认的数据一致性规则。

### 3.4 保持可追溯性

- 原文已有需求 ID 时必须保留；
- 原文没有 ID 时，按模块和功能生成稳定 ID；
- 推荐格式：`REQ-{模块缩写}-{三位序号}`；
- 同一份文档内的 ID 不得重复；
- 不要因为重新排序而随意改变已经生成的 ID；
- 对重要规则可增加“来源”字段，记录原始章节、文件或会议记录位置。

### 3.5 使用具体值替代模糊表达

原文存在具体值时必须完整保留，例如：

- 长度：8～32 个字符；
- 次数：连续失败 5 次；
- 时间：锁定 30 分钟；
- 金额：不得超过当前可退款金额；
- 状态：待支付、已支付、已取消；
- 提示：原文规定的完整提示语。

如果原文只有“合理范围”“多次失败”“一段时间”等模糊说法，必须保留原意并记录为歧义或未确认项，不得自行填写数值。

## 4. 文件和 Markdown 格式要求

### 4.1 文件格式

- 首选 `.md`；
- 可以整理为 `.txt`，但内容仍建议使用 Markdown 标题语法；
- 编码必须为 UTF-8；
- 当前功能智能体主需求文档不应直接使用 `.docx` 或 `.pdf`；
- Word、PDF、图片或设计稿中的有效规则，应先转换为文字；
- 不得只保留截图而不描述截图表达的规则；
- 推荐单文件不超过 5 MiB，解码后不超过 500,000 字符。

### 4.2 标题层级

推荐层级固定为：

```text
# 需求名称
## 模块
### 功能
#### 业务场景或规则类别
##### 必要时使用的细分场景
```

标题层级应连续，不建议从二级标题直接跳到五级标题。

功能测试智能体会按 Markdown 标题切分需求章节，因此：

- 不要把整份需求全部放在一个标题下；
- 不要使用只有标题但没有正文的空章节；
- 不要用加粗文本代替真正的 Markdown 标题；
- 同一业务场景的规则应放在对应场景标题下；
- UI 文字、图标、颜色、间距等展示要求可以合并到一个“页面展示”章节，不必拆成大量微小章节。

### 4.3 表格使用

以下内容优先使用 Markdown 表格：

- 角色与权限；
- 字段定义；
- 输入和边界规则；
- 状态流转；
- 错误码和错误提示；
- 外部依赖和失败策略；
- 示例数据。

表格中的每一列必须有清晰含义，避免把多项规则塞入同一个超长单元格。

## 5. 标准文档结构

整理结果原则上按以下顺序输出。原始资料不涉及的章节可以写“原始资料未说明”，也可以省略，但不得编造内容补齐章节。

### 5.1 文档信息

记录：

- 项目名称；
- 需求名称；
- 需求版本；
- 原始资料来源；
- 产品负责人或确认人；
- 整理日期；
- 适用系统或端；
- 关联模块。

### 5.2 背景与目标

只保留理解需求所必需的背景，重点说明：

- 当前存在什么问题；
- 本期希望实现什么结果；
- 如何判断目标已经达成。

不要把长篇项目汇报、会议讨论过程或与本期无关的历史信息放入正文。

### 5.3 需求范围

必须尽可能区分：

- 本期包含；
- 本期不包含；
- 后续规划；
- 受影响的已有功能；
- 明确保持不变的功能。

“本期不包含”有助于避免智能体生成范围外测试点。

### 5.4 名词与业务对象

对容易混淆的名词、实体和对象进行定义，例如：

| 名词 | 定义 | 备注 |
|---|---|---|
| 当前可退款金额 | 订单已支付金额减去已成功退款金额 | 不包含处理中退款时需另行确认 |

同一个对象在整份文档中应使用同一个名称。

### 5.5 角色与权限

明确每个角色能做什么、不能做什么，以及权限不足时的结果。

推荐格式：

| 角色 | 允许操作 | 禁止操作 | 权限不足时的行为 |
|---|---|---|---|
| 普通用户 | 查看自己的订单 | 查看其他用户订单 | 返回原文规定的提示或状态 |

不得用“有权限的人”代替明确角色。

### 5.6 功能规则

每个功能建议包含：

1. 功能说明；
2. 前置条件；
3. 触发入口；
4. 测试对象；
5. 输入和边界；
6. 正常流程；
7. 异常流程；
8. 状态变化；
9. 数据处理；
10. 验收标准。

规则编号示例：

```markdown
- REQ-LOGIN-001：用户输入已注册手机号和正确密码后，可以登录系统。
- REQ-LOGIN-002：手机号为空时禁止提交。
- REQ-LOGIN-003：连续输入错误密码达到 5 次后，账号锁定 30 分钟。
```

### 5.7 测试对象与字段规则

推荐格式：

| 对象/字段 | 类型 | 是否必填 | 取值或格式 | 边界 | 默认值 | 空格/大小写处理 | 说明 |
|---|---|---:|---|---|---|---|---|
| 手机号 | 字符串 | 是 | 11位数字 | 原文规定 | 无 | 去除首尾空格 | 登录账号 |

原文未说明的单元格填写“未说明”，不要自行推测。

### 5.8 正常流程

正常流程应使用有序步骤，并单独列出前置条件和预期结果。

```markdown
前置条件：

- 用户账号状态为“正常”；
- 用户已经设置密码。

操作步骤：

1. 用户进入登录页。
2. 用户输入手机号和密码。
3. 用户点击登录。

预期结果：

- 登录成功；
- 页面跳转到首页；
- 系统创建有效登录会话。
```

### 5.9 异常和反向流程

每个异常场景单独描述，不要把所有异常合成一句“异常时提示失败”。

建议至少检查原文是否包含：

- 输入为空；
- 格式错误；
- 超出边界；
- 数据不存在；
- 重复提交；
- 权限不足；
- 状态不允许；
- 外部服务超时或失败；
- 保存部分成功；
- 网络中断；
- 并发操作。

原文没有说明时，应写入“未确认项”或“测试设计建议”，不得写成确定需求。

### 5.10 状态流转

涉及订单、审批、账号、任务、支付、退款等状态时，必须优先整理为状态表。

| 当前状态 | 触发条件 | 下一状态 | 系统行为 | 是否允许 | 失败行为 |
|---|---|---|---|---:|---|
| 正常 | 连续密码错误达到5次 | 锁定 | 禁止继续登录 | 是 | 原文未说明 |

还应记录：

- 初始状态；
- 终态；
- 是否允许回退；
- 非法状态转换的处理；
- 超时自动转换；
- 状态变化后的关联数据处理。

### 5.11 数据、一致性、并发和幂等

原文涉及数据写入或多个系统协作时，应整理：

- 哪些数据需要新增、修改或删除；
- 多项写入是否必须同时成功；
- 部分失败如何处理；
- 重复请求是否会重复创建数据；
- 多个用户或设备同时操作时如何处理；
- 缓存、数据库和页面数据何时保持一致；
- 是否需要操作记录、审计或日志。

### 5.12 外部依赖和失败策略

| 依赖 | 调用目的 | 正常结果 | 超时结果 | 失败结果 | 是否重试 |
|---|---|---|---|---|---:|
| 用户中心 | 查询账号状态 | 返回账号状态 | 原文未说明 | 原文未说明 | 原文未说明 |

不要默认增加重试、降级或补偿机制。

### 5.13 非功能要求

按原始资料整理：

- 性能；
- 安全；
- 兼容性；
- 可用性；
- 日志和审计；
- 数据隐私；
- 可访问性；
- 国际化和时区。

没有明确指标时，不得自行填写响应时间、并发量或成功率。

### 5.14 验收标准

优先转换为 Given / When / Then：

```markdown
#### AC-LOGIN-001 正常登录

Given 用户账号存在、状态正常且密码正确
When 用户提交手机号和密码
Then 系统登录成功并跳转到首页
```

每条验收标准只验证一个主要行为。复杂流程可以拆成多条验收标准。

### 5.15 未确认项、歧义项和冲突项

三类问题必须分开记录。

#### 未确认项

原始资料没有给出答案的问题：

```text
Q-001：登录会话有效期未说明，需要产品确认。
```

#### 歧义项

同一句话可能存在多种解释：

```text
A-001：“多次失败后锁定”未说明“多次”的具体次数。
```

#### 冲突项

不同资料对同一规则描述不一致：

```text
C-001：产品文档规定锁定30分钟，安全规范规定锁定60分钟，尚未确认最终值。
```

### 5.16 测试设计建议

测试设计建议不得混入正式需求，例如：

- 建议补充最大长度边界；
- 建议确认重复提交的幂等行为；
- 建议覆盖依赖服务超时；
- 建议确认多设备并发操作规则；
- 建议补充敏感数据日志脱敏要求。

建议必须明确标注“非已确认需求”。

## 7. 原始资料整理步骤

Codex 应按以下顺序整理，不应直接对原文进行表面格式转换。

### 步骤一：识别资料类型和事实来源

列出所有输入资料及其性质：

- 已确认 PRD；
- 产品说明；
- 设计稿文字；
- 接口文档；
- 会议记录；
- 聊天记录；
- 测试反馈；
- 技术设计。

如果资料可信等级不同，应优先保留来源标识，不自行决定冲突答案。

### 步骤二：提取范围、角色、对象和状态

先建立需求骨架：

- 有哪些模块和功能；
- 谁使用；
- 操作什么对象；
- 对象有哪些状态；
- 本期包含和排除什么。

### 步骤三：拆分原子规则

将包含多个逻辑关系的长句拆分为独立规则，但不得改变原意。

例如：

```text
原文：手机号为空或格式错误时不能登录，连续错误5次锁定30分钟。
```

应拆分为：

```text
REQ-LOGIN-001：手机号为空时禁止登录。
REQ-LOGIN-002：手机号格式错误时禁止登录。
REQ-LOGIN-003：连续登录失败5次后账号锁定30分钟。
```

### 步骤四：整理正常、异常和状态流程

把散落在不同位置的同一功能规则归入对应章节，避免同一规则在多个章节重复出现。

### 步骤五：标记缺口和冲突

所有无法确定的内容进入：

- 未确认项；
- 歧义项；
- 冲突项。

不得通过“合理推断”消除这些问题。

### 步骤六：生成验收条件

原文能够支持时，将规则转换为 Given / When / Then。转换不得增加原文未规定的结果。

### 步骤七：执行完整性检查

使用第 9 章检查清单逐项检查，发现问题后先修正文档再交付。

## 8. 转换示例

### 8.1 原始需求

```text
登录页支持手机号密码登录。手机号要正确，密码不能太短。密码错了提示错误，错多次要锁一段时间。登录成功进入首页。禁用的用户不能登录。
```

### 8.2 错误整理方式

```markdown
## 登录

- 用户可以登录。
- 输入错误时正常提示。
- 多次错误后进行账号限制。
```

问题：

- “手机号要正确”没有明确格式；
- “密码不能太短”没有最小长度；
- “错多次”没有次数；
- “锁一段时间”没有时长；
- 没有区分确定规则和未确认信息。

### 8.3 推荐整理方式

```markdown
# 手机号密码登录需求

## 账号与认证

### 密码登录

#### 功能说明

系统支持用户使用手机号和密码登录。

#### 正常流程

Given 用户账号未被禁用，且输入的手机号和密码正确
When 用户提交登录
Then 系统登录成功并进入首页

#### 输入校验

- REQ-LOGIN-001：手机号必须符合系统要求的正确格式。
- REQ-LOGIN-002：密码不得短于系统要求的最小长度。

#### 登录失败

- REQ-LOGIN-003：密码错误时，系统拒绝登录并显示错误提示。
- REQ-LOGIN-004：连续密码错误达到规定次数后，系统锁定账号一段时间。

#### 禁用账号

- REQ-LOGIN-005：账号状态为“禁用”时不允许登录。

## 未确认项

- Q-001：手机号的具体合法格式未说明。
- Q-002：密码最小长度未说明。
- Q-003：触发账号锁定的连续错误次数未说明。
- Q-004：账号锁定时长未说明。
- Q-005：登录失败时的具体错误提示未说明。
```

该整理方式没有补写具体数值，同时把可确定规则与信息缺口清楚分开。

## 9. 整理质量检查清单

Codex 在输出前必须检查：

### 9.1 事实准确性

- [ ] 没有新增原文不存在的业务事实；
- [ ] 原始规则、数值、提示语和状态没有被改变；
- [ ] 推测内容已经移入测试设计建议；
- [ ] 未确认内容没有伪装成确定需求；
- [ ] 冲突内容没有被擅自合并或裁决。

### 9.2 结构完整性

- [ ] 使用了连续的 Markdown 标题；
- [ ] 模块、功能和场景边界清楚；
- [ ] 每个有正文的功能都形成独立章节；
- [ ] 没有把整份需求堆在一个大段落中；
- [ ] 表格和列表可以被纯文本方式理解。

### 9.3 可测试性

- [ ] 每个业务规则尽量只表达一个可验证行为；
- [ ] 输入、触发条件和预期结果尽量明确；
- [ ] 已知边界值和枚举值已经保留；
- [ ] 权限主体和允许操作已经明确；
- [ ] 状态变化和非法流转已经整理；
- [ ] 正常、异常和反向流程已经区分；
- [ ] 可以转换的规则已经整理为 Given / When / Then。

### 9.4 测试点生成适配

- [ ] 文档能够识别模块、功能、场景和具体规则；
- [ ] 测试对象和字段具有明确名称；
- [ ] 约束、权限、状态和验收标准没有混在背景说明中；
- [ ] UI 展示要求没有被过度拆成大量碎片；
- [ ] 测试建议与需求事实已经隔离；
- [ ] 未确认、歧义和冲突项有独立编号。

### 9.5 文件安全和可用性

- [ ] 输出为 UTF-8 Markdown；
- [ ] 文件名能反映需求名称和版本；
- [ ] 文档没有依赖本地绝对路径才能理解；
- [ ] 图片中的关键规则已经转换为文字；
- [ ] 文档大小满足功能智能体上传限制。

## 10. 禁止事项

整理需求时禁止：

- 仅修改排版，不分析规则结构；
- 为了让文档看起来完整而编造缺失信息；
- 把测试建议写成产品已经确认的需求；
- 删除看似重复但来源或上下文不同的规则；
- 隐藏原始资料之间的冲突；
- 把会议中的提问或假设直接变成需求；
- 把多个模块、多个流程和多个结果写进同一个规则；
- 用“正常处理”“合理提示”“视情况而定”等词替代原文中的具体规则；
- 只引用图片、原型或外部链接，不转写关键业务含义；
- 擅自改变原有需求 ID；
- 为同一需求生成重复 ID；
- 输出 Markdown 之外无法被功能智能体读取的主文档格式。

## 11. 与功能测试智能体的对应关系

整理后的内容与测试点标准字段通常按以下关系对应：

| 需求文档内容 | 测试点字段或生成依据 |
|---|---|
| 模块标题 | `module` |
| 功能标题 | `feature` |
| 正常、异常、权限、状态等场景 | `scenario` |
| 原子业务规则和验收条件 | `test_point` |
| 业务重要性及安全、金额、状态等风险 | `risk_level` 的判断依据 |
| 规则编号 | 测试点追溯依据 |
| Given / When / Then | 正向和异常测试设计依据 |
| 未确认、歧义、冲突项 | Review 阶段的人工确认依据 |

该映射是生成指导，不代表标题文字一定机械复制到测试点字段。最终结果仍应在测试点 Review 页面进行人工检查和修正。

## 12. 最终交付要求

Codex 整理完成后，应交付：

1. 一份 UTF-8 Markdown 需求文档；
2. 文档内明确区分正式需求和测试设计建议；
3. 未确认项、歧义项和冲突项清单；
4. 文档末尾的整理结果检查；
5. 如用户要求，额外给出原始章节到新章节的映射摘要，但不得把映射摘要混入功能需求正文。

整理完成的需求文档应满足以下最终标准：

> 不需要依靠整理者的口头解释，产品、开发、测试和功能测试智能体都能从文档中识别需求范围、业务规则、测试对象、约束、状态、权限、异常行为和待确认问题。
