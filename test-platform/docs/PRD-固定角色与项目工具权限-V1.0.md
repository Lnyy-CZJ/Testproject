# 固定角色、项目范围与额外工具授权 PRD

> 文档版本：V1.1（修订草案）
> 创建日期：2026-08-24
> 文档状态：待评审
> 适用平台：test-platform
> 产品方案：方案一——固定角色 + 项目范围 + 额外工具授权

---

## 1. 文档摘要

平台当前采用“角色直接绑定细粒度权限”的 RBAC 模型：系统内置 5 个角色，用户可同时拥有多个角色，角色再通过 RoleGrant 获得平台或工具级权限。部分测试角色使用资源通配符，可查看或操作全部工具。工具只有业务分类 category，没有“公共工具 / 项目工具”属性，也没有项目归属；/tools 当前只依据工具是否启用以及用户是否拥有 tool.view 决定展示。

本期将权限模型调整为：

    工具可访问范围
      = 公共工具
      + 用户所属或负责项目的工具
      + 平台管理员额外授予的单个项目工具

账号只保留三种固定全局角色：

1. 平台管理员；
2. 管理员；
3. 测试人员。

角色只决定管理级别，不再通过可编辑角色组合决定工具范围。项目关系决定成组工具范围，额外授权只处理少量跨项目例外。权限分为“工具/Agent 使用权”和“任务、结果、报告等业务资源的数据操作权”两层：测试人员即使能使用同一工具，也只能查看和操作自己创建的任务及其结果；项目负责人可在所负责项目内进行运维管理；平台管理员保留全局运维和审计能力。工具配置、Secret、用户、项目、部署和平台安全等控制面仍按角色及项目范围严格隔离。

本 PRD 定义产品目标、角色边界、项目与工具规则、有效权限算法、注册和账号生命周期、管理页面、审计、迁移、发布及验收标准。数据库表、接口路径、服务拆分和具体迁移脚本在后续开发设计与实施计划中确定。

## 2. 背景与现状

### 2.1 当前实现

当前平台已具备：

- 本地用户、服务端 Session、登录限流、密码修改和会话撤销；
- Role、Permission、UserRole、RoleGrant 组成的 RBAC；
- 一个用户关联多个角色的能力；
- 平台权限与工具权限两类稳定权限代码；
- 工具目录、工具启停、健康检查和网关统一鉴权；
- 配置、Secret、Credential、LLM、审计和发布管理能力。

当前 5 个内置角色为：

| 角色 ID | 当前名称 | 当前主要能力 |
|---|---|---|
| role_platform_admin | 平台管理员 | 管理平台、配置及全部工具 |
| role_test_developer | 测试开发 | 执行全部工具并维护普通工具配置 |
| role_test_executor | 测试执行者 | 执行全部工具并查看结果 |
| role_readonly | 只读查看者 | 查看全部工具和结果 |
| role_auditor | 审计查看者 | 查看和导出平台审计 |

当前测试类角色的工具授权使用资源 ID 通配符，导致新增工具通常会自动落入已有角色的全部工具范围。当前权限解析会聚合用户所有角色授权，因此多角色用户获得各角色权限并集。

当前 Tool 数据仅包含名称、入口、健康地址、category、features、排序和启用状态等字段，不包含：

- 访问范围类型；
- 所属项目；
- 公共工具标识；
- 项目工具标识；
- 用户额外工具授权。

当前 /tools 的核心逻辑为：

1. 查询 is_enabled 为真的工具；
2. 对每个工具判断用户是否拥有 tool.view；
3. 仅返回通过判断的工具。

平台当前没有自助注册接口，账号主要由首次 setup 或平台管理员创建。

### 2.2 当前问题

现有模型产生以下产品和管理问题：

1. **角色数量会随业务膨胀**：若继续使用角色表达项目范围，每增加一个项目就需要新增项目管理员、执行者、只读者等角色组合。
2. **多角色难以解释**：同一用户的最终能力来自多个角色并集，管理页面难以直接回答“为什么能访问这个工具”。
3. **工具新增容易越权**：通配符授权使新工具可能自动暴露给不应访问的用户。
4. **缺少项目边界**：无法表达“某管理员只负责两个项目”“某测试人员自动获得所属项目的全部工具”。
5. **逐工具授权成本高**：若不用项目继承，每新增工具或成员都要重复勾选，容易漏配。
6. **业务使用与平台管理混杂**：能使用工具的用户可能同时获得配置或 Secret 权限，难以建立清晰安全边界。
7. **目录与真实接口可能不一致**：/tools 只判断 tool.view，不能保证执行、结果、Review、下载等后续接口使用同一范围算法。
8. **缺少可审计的授权来源**：系统不能稳定区分一次访问来自公共范围、项目继承还是额外单工具授权。

### 2.3 目标权限模型

本期采用固定角色、项目继承和例外加权模型：

    账号管理级别 = 单一固定全局角色

    工具业务范围 = 公共范围
                 ∪ 项目范围
                 ∪ 额外单工具授权

    工具管理能力 = 全局角色
                 ∩ 项目管理关系
                 ∩ 工具归属范围

    业务资源访问 = 当前账号有效性
                 ∩ 资源归属快照
                 ∩ 用户的数据操作范围

该模型不引入拒绝授权，不支持用额外授权覆盖项目规则，也不允许通过角色编辑重新制造逐工具权限矩阵。

## 3. 产品目标与成功标准

### 3.1 产品目标

#### G1：固定账号管理级别

每个用户只能拥有平台管理员、管理员、测试人员中的一个全局角色。角色名称、语义和核心边界由系统固定，不允许创建自定义角色或叠加多个角色。

#### G2：通过项目自动继承工具范围

管理员可负责多个项目，测试人员可加入多个项目。项目新增工具或成员后，范围自动生效，不需要逐用户补授权。

#### G3：公共能力开箱即用

所有 active 用户无需额外分配即可使用全部已启用公共工具。新注册测试人员可在注册完成后立即进入公共工具。

#### G4：支持少量跨项目例外

平台管理员可给 active 的管理员或测试人员额外授予单个项目工具。额外授权只增加该工具的使用权和本人业务资源操作能力，不增加他人数据、项目、配置、Secret 或用户管理能力。

#### G5：分离业务使用与管理控制面

工具/Agent 使用权只允许用户进入并发起业务操作，不等于读取或控制该工具下所有任务、结果和报告。测试人员只能查看、Review、取消、重试、下载和导出自己创建的业务资源；项目负责人可管理所负责项目内的业务资源；平台管理员可管理全平台业务资源。平台配置、项目工具配置、Secret、Credential、用户、项目、工具归属、部署、安全和发布等控制面继续按角色严格隔离。

#### G6：统一目录、网关和工具接口鉴权

/tools、工具详情、健康检查和网关代理必须使用统一的有效工具访问结论；任务、结果、Review、取消、重试、下载和导出还必须对目标业务资源执行对象级授权。禁止只在前端隐藏入口，也禁止用工具访问权替代业务资源访问权。

#### G7：安全迁移现有账号与工具

迁移不得把存量工具默认公开，不得把旧只读或审计账号静默提升为可执行项目成员，并且必须提供可复核、可回滚、不包含 Secret 的迁移报告。

### 3.2 可衡量成功标准

- 数据层和接口层均保证每个用户恰好一个全局角色；
- 所有工具均明确标记为公共工具或项目工具；
- 每个项目工具恰好归属一个项目，公共工具不关联项目；
- 任意 active 用户访问工具时，系统能返回唯一且可解释的授权来源；
- 任意任务、结果或报告访问均能解释资源所有者、项目快照及调用者允许的数据操作范围；
- 两个同项目且均可使用同一工具的测试人员，不能查看、枚举或操作对方的任务、结果和报告；
- 用户退出项目或额外授权被撤销后，下一次请求立即按新权限处理；
- inactive 用户不能登录、续用现有会话、查看工具或调用任何业务与管理接口；
- 普通管理员不能查看或管理自己负责项目之外的成员、工具配置和 Secret；
- 测试人员无法修改配置、Secret、项目、工具归属、用户角色或平台发布；
- /tools 返回集合与直接访问工具业务接口的鉴权结果一致；
- 迁移后不存在仍依赖旧多角色并集或资源通配符决定业务访问的请求链路；
- 所有角色、项目、成员、工具归属和额外授权变更均产生可追溯审计记录；
- 在生产等量数据副本上，/tools 的 P95 响应时间不高于迁移前基线 100 毫秒以上；
- 权限单元测试、接口测试、迁移演练、双用户越权测试和端到端验收全部通过。

## 4. 范围与边界

### 4.1 本期包含

1. 三种固定全局角色及单角色约束；
2. 用户自助注册并默认成为 active 测试人员；
3. 项目创建、编辑、启用、停用和详情管理；
4. 管理员负责项目、测试人员加入项目的关系管理；
5. 公共工具与项目工具两种访问范围；
6. 项目工具单项目归属；
7. 平台管理员授予和撤销用户额外单工具访问；
8. 统一有效工具访问计算；
9. 工具使用权、业务资源数据操作权与控制面管理能力三层分离；
10. 用户、项目、工具和授权管理页面调整；
11. /tools、工具路由和网关鉴权调整；
12. 权限变更即时失效、会话收敛和审计；
13. 现有 5 角色、多角色、通配符授权及存量工具迁移；
14. 灰度发布、迁移校验和回滚要求。

### 4.2 本期不包含

1. 自定义角色、角色复制或角色市场；
2. 同一工具同时归属多个项目；
3. 项目层级、子项目、项目组或组织树；
4. 对单个用户设置拒绝规则；
5. 对项目成员逐工具减权；
6. 公共工具对单个用户关闭；
7. 额外授权的自动审批、定时审批或多级审批流；
8. 项目硬删除和历史数据物理清理；
9. 面向单条任务或结果的人工 ACL、共享名单或逐条授权；业务资源所有者和项目快照仍是本期强制鉴权属性；
10. 调整个人 Credential、个人 LLM 等已有用户私有数据的所有权规则；
11. 取消 API 真实执行开关、目标地址白名单、速率限制等运行安全门禁；
12. 改造工具自身的内部业务角色体系；平台只向工具提供可信访问结论和必要上下文。

### 4.3 V1 强约束

- 一个用户只有一个全局角色；
- 一个项目工具只有一个所属项目；
- 额外授权只能指向项目工具；
- 额外授权必须设置有效期，只增加工具使用权，不提供拒绝、他人数据访问或管理权限；
- 公共工具对所有 active 用户开放；
- 项目和工具均采用停用而非硬删除；
- 权限判定默认拒绝，数据不完整或状态未知时不得放行；
- 平台管理员可管理停用资源，但任何角色都不能业务执行已停用工具或已停用项目中的工具。

## 5. 核心概念与数据关系

### 5.1 全局角色

全局角色表示账号在平台上的最高管理级别。角色固定为：

- platform_admin：平台管理员；
- admin：管理员；
- tester：测试人员。

全局角色不表达具体项目或工具范围。

### 5.2 项目

项目是工具和人员的授权边界。项目至少包含：

- 稳定唯一标识；
- 唯一项目编码；
- 项目名称；
- 项目描述；
- active / inactive 状态；
- 创建人、创建时间、更新人、更新时间。

项目编码创建后不可修改，用于接口、审计和迁移引用。项目名称可修改。

### 5.3 项目关系

项目关系分为两种语义：

| 关系 | 允许的全局角色 | 含义 |
|---|---|---|
| 项目负责人 | 管理员 | 可使用并管理该项目的工具和测试成员 |
| 项目成员 | 测试人员 | 可使用该项目的全部工具 |

平台管理员天然拥有全平台管理范围，不要求创建项目关系记录。

管理员可负责零个或多个项目。测试人员可加入零个或多个项目。零项目用户仍可使用公共工具。

### 5.4 工具访问范围

每个工具必须且只能选择一种范围：

| 范围 | 项目要求 | 默认访问人群 |
|---|---|---|
| 公共工具 | 不允许关联项目 | 全部 active 用户 |
| 项目工具 | 必须关联一个 active 项目 | 项目负责人、项目成员、平台管理员及额外授权用户 |

Agent 在本权限模型中视为工具，使用相同的范围和归属规则。

### 5.5 额外工具授权

额外工具授权是“用户—项目工具”的直接允许关系，只用于少量跨项目业务使用场景。

每条授权至少记录：

- 用户；
- 工具；
- 授权原因；
- 授权人；
- 授权时间；
- 到期时间；
- 当前状态或撤销时间；
- 撤销人和撤销原因。

同一用户与工具同时只能存在一条有效额外授权。

授权默认有效期为 7 天，平台可配置最大有效期，但 V1 最大不得超过 90 天。授权到期立即失效；续期必须由平台管理员显式操作、填写原因并产生审计，不允许无期限授权。

### 5.6 业务能力与管理能力

**工具业务使用能力**指用户可在授权工具内开展正常测试和质量工作，但所有涉及既有业务资源的操作还必须通过对象级授权，包括：

- 查看工具页面与能力说明；
- 创建并执行任务；
- 查看自己有权访问的任务、结果和报告；
- 对自己有权操作的任务执行 Review、确认、取消和重试；
- 下载、导出自己有权访问的报告；
- 调用工具对外提供的其他标准业务操作。

**管理能力**指改变平台或工具控制面的操作，包括：

- 修改工具普通配置；
- 修改 Secret、Credential 或公共 LLM 配置；
- 修改工具公共 / 项目属性或所属项目；
- 管理用户、项目和额外授权；
- 修改平台部署、安全、数据库和发布配置。

获得业务能力不自动获得任何管理能力。

### 5.7 业务资源与数据操作范围

业务资源至少包括任务、任务步骤、结果、Review 记录、报告、导出文件和与任务绑定的运行日志。每条根业务资源创建时必须固化以下不可变授权快照，并由派生资源继承：

- tool_id；
- created_by_user_id；
- access_scope_snapshot（public 或 project）；
- project_id_snapshot（公共范围为 null）；
- authorization_source_snapshot；
- created_at。

数据操作范围如下：

| 调用者 | 可查看和操作的业务资源 |
|---|---|
| 测试人员 | 仅本人创建的资源 |
| 管理员 | 本人资源，以及所负责项目快照下的全部资源 |
| 平台管理员 | 全平台资源 |

管理员或测试人员仅凭额外工具授权访问其他项目工具时，仍只能访问本人创建的资源，不获得该项目其他用户的数据访问权。公共工具的业务资源默认仅创建者本人和平台管理员可见。

## 6. 有效权限规则

### 6.1 工具业务访问公式

工具业务访问必须同时满足运行状态和范围条件：

    可业务访问 =
        用户状态为 active
        AND 工具状态为 enabled
        AND (
            工具为公共工具
            OR (
                工具为项目工具
                AND 所属项目状态为 active
                AND (
                    用户为平台管理员
                    OR 用户是该项目负责人
                    OR 用户是该项目成员
                    OR 用户拥有该工具的有效额外授权
                )
            )
        )

任何缺失、冲突或未知字段均按不允许处理。

工具业务访问公式只决定“能否使用工具”，不得直接用于任务、结果或报告接口的放行。业务资源请求还必须满足：

    可读取业务资源 =
        当前用户状态为 active
        AND 资源及其授权快照完整
        AND (
            用户为平台管理员
            OR (
                资源为公共范围
                AND 用户为资源创建者
            )
            OR (
                资源为项目范围
                AND project_id_snapshot 对应项目当前为 active
                AND (
                    用户为管理员且当前仍是 project_id_snapshot 的项目负责人
                    OR (
                        用户为资源创建者
                        AND (
                            用户当前仍是 project_id_snapshot 的项目负责人或成员
                            OR 用户仍持有与资源 tool_id、project_id_snapshot 匹配的有效额外授权
                        )
                    )
                )
            )
        )

取消、重试、Review、下载、导出等具体操作还必须通过对应动作权限；“可读取”不自动等于“可执行所有动作”。

### 6.2 授权来源优先级

授权来源不用于扩大权限，只用于解释和审计。若用户同时命中多个来源，按以下顺序返回一个主要来源：

1. platform_admin；
2. public；
3. project_manager；
4. project_member；
5. extra_grant。

系统可同时保留全部命中来源供内部审计，但前端只需展示主要来源。

### 6.3 额外授权的加权规则

- 额外授权只增加访问，不减少访问；
- 公共工具不得创建额外授权；
- 用户已经通过项目继承访问时，不需要也不允许重复创建额外授权；
- 撤销额外授权后，若用户仍通过项目关系获得访问，则访问继续有效；
- 用户、工具或项目停用时，额外授权不能绕过停用状态；
- 工具从项目 A 移动到项目 B、从项目改为公共或从公共改为项目时，原有额外授权全部撤销；
- 额外授权不授予所属项目的其他工具；
- 额外授权不授予配置、Secret、成员或项目管理能力。
- 额外授权不授予同一工具内其他用户的任务、结果或报告访问权；
- 有效额外授权必须未撤销且 expires_at 晚于当前时间，并同时满足用户、工具和项目均为 active；
- 项目恢复时只恢复尚未过期且未撤销授权的可用性，已经到期的授权不得自动复活。

### 6.4 历史业务资源规则

- 工具从项目 A 移动到项目 B 时，历史资源仍绑定创建时的项目 A 快照，不随工具迁移；A 项目负责人仍可按当前负责人关系管理该历史资源，B 项目用户不能因此看到历史资源；
- 测试人员只可查看自己的历史资源，且项目资源要求其当前仍通过该项目关系或该工具的有效额外授权具备相应历史访问资格；被移出项目或授权失效后，不再访问该项目历史资源；
- 公共工具创建的历史资源保持创建者本人可读。工具后来改为项目工具，不得据此把历史公共资源暴露给项目成员；
- 查看历史资源与基于当前工具重新执行是两个独立授权动作。用户可以保留历史读取权，但重试或重新执行时仍须满足当前工具访问、状态和运行安全策略；
- 工具或项目停用不删除历史资源；平台管理员仍可审计，其他用户是否可读按上述规则和当前账号状态判定。

### 6.5 管理权限规则

| 管理对象 | 平台管理员 | 管理员 | 测试人员 |
|---|---|---|---|
| 公共工具配置与 Secret | 可管理 | 不可管理 | 不可管理 |
| 自己负责项目的工具配置与 Secret | 可管理 | 可管理 | 不可管理 |
| 其他项目工具配置与 Secret | 可管理 | 不可管理 | 不可管理 |
| 工具范围与所属项目 | 可管理 | 不可管理 | 不可管理 |
| 项目创建、停用、恢复 | 可管理 | 不可管理 | 不可管理 |
| 项目负责人分配 | 可管理 | 不可管理 | 不可管理 |
| 自己负责项目的测试成员 | 可管理 | 可管理 | 不可管理 |
| 其他项目的测试成员 | 可管理 | 不可管理 | 不可管理 |
| 额外单工具授权 | 可管理 | 不可管理 | 不可管理 |
| 平台配置、系统 Secret、数据库、安全、发布 | 可管理 | 不可管理 | 不可管理 |
| 审计查看与导出 | 可管理 | 不可管理 | 不可管理 |

项目工具 Secret 仅指该工具控制面中明确标记为项目可管理的共享 Secret。用户私有 Credential、个人 LLM API Key 等数据仍遵守其自身所有权规则，普通管理员不得查看或修改其他用户的私有值。

### 6.6 权限变更生效时机

以下变更必须在事务提交后立即影响下一次请求：

- 用户角色或状态变化；
- 项目状态变化；
- 项目负责人或成员变化；
- 工具启用状态、范围或归属项目变化；
- 额外工具授权创建或撤销。

前端缓存、Session 内旧权限声明和工具侧历史上下文不得继续作为放行依据。用户角色和状态使用用户 permission_version 或等效机制失效；项目、工具和公共范围变更使用对应资源 revision / authorization_epoch 失效。缓存键必须包含所有相关版本，不要求通过批量更新全体用户版本来传播公共范围变更。

### 6.7 运行中任务与执行租约

- 权限撤销后禁止用户发起新任务、控制任务或读取结果；
- 已经交给后台执行器的任务默认不自动取消，以避免产生不一致的半完成状态；执行器只能持有创建任务时签发的窄范围、不可扩权执行租约；
- 执行租约必须绑定 task_id、tool_id、项目快照、允许的环境和配置/凭据引用及明确到期时间，只允许完成既有任务，不能创建新任务、浏览其他结果或扩大目标范围；
- 后台任务可以完成并保留审计，但失去访问权的用户不得继续查看或操作；
- 如需终止运行中任务，由仍有权限的管理员或平台管理员显式取消；
- 项目或工具停用后同样禁止新执行，不把停用动作隐式等同于批量取消。
- 普通交互权限版本变化不撤销已派发任务的执行租约；用户禁用、工具禁用、项目停用等是否紧急终止租约必须由明确的运行安全策略决定并记录审计，默认仍按“不自动批量取消”处理。

## 7. 固定角色定义

### 7.1 平台管理员

平台管理员拥有全平台控制面权限：

- 创建管理员和测试人员账号；
- 将现有账号切换为管理员或测试人员；
- 在满足“至少保留一个 active 平台管理员”的前提下管理其他平台管理员；
- 创建、编辑、停用和恢复项目；
- 为管理员分配或移除负责项目；
- 为测试人员分配或移除任意项目；
- 设置工具为公共工具或项目工具；
- 修改项目工具所属项目；
- 管理所有公共及项目工具；
- 授予和撤销单个额外项目工具；
- 禁用账号、恢复账号、重置密码、强制退出；
- 管理平台配置、系统 Secret、公共 LLM、数据库、安全、审计和发布；
- 查看和管理全部项目、用户、工具，以及全平台任务、结果、报告和权限来源；
- 查看固定角色规则及权限矩阵。

固定角色不允许通过管理页面新增、删除、重命名或任意绑定细粒度工具权限。“角色管理”在本期仅表示分配固定角色、查看固定规则和执行受保护的角色切换。

### 7.2 管理员

管理员可负责多个项目：

- 自动使用全部公共工具；
- 使用自己负责项目的全部工具；
- 管理自己负责项目工具的普通配置、项目级共享 Secret、运行状态，以及该项目快照下的任务、结果和报告；
- 查看自己负责项目的测试人员；
- 创建全局角色固定为测试人员的账号；
- 将 active 测试人员加入或移出自己负责的项目；
- 通过精确用户名查找可加入的 active 测试人员；
- 查看自己的项目清单、成员、工具及状态。

管理员不得：

- 创建、修改、禁用或删除管理员；
- 修改任何用户的全局角色；
- 禁用账号、重置密码或强制全局退出；
- 创建、停用或恢复项目；
- 为项目分配其他管理员；
- 修改工具公共 / 项目属性或所属项目；
- 管理公共工具配置和 Secret；
- 管理其他项目工具；
- 授予额外单工具访问；
- 管理平台级安全、数据库、公共 LLM 和发布配置；
- 查看平台审计或其他项目的成员清单。

通过额外工具授权访问其他项目工具时，管理员只获得该工具业务能力，不成为该项目负责人。因此其数据操作范围与测试人员相同，只能查看和操作本人创建的任务、结果和报告。

### 7.3 测试人员

测试人员：

- 自助注册后默认获得此角色；
- active 后立即使用全部公共工具；
- 可加入多个项目并自动使用各项目全部工具；
- 可获得平台管理员授予的其他项目单个工具；
- 能访问工具时可创建任务，并仅查看和操作本人创建的任务、结果和报告；
- 可查看自己的角色、项目、额外授权和每个工具的主要授权来源。

测试人员不得：

- 管理用户或项目；
- 修改工具范围、所属项目或启用状态；
- 修改工具控制面配置、Secret、Credential 或公共 LLM；
- 管理其他用户的权限；
- 修改平台部署、安全、数据库和发布策略；
- 查看平台审计。
- 查看、枚举、Review、取消、重试、下载或导出其他测试人员的任务、结果和报告，即使双方属于同一项目且使用同一工具。

## 8. 账号与注册规则

### 8.1 自助注册

注册流程固定为：

    用户提交注册信息
      → 校验用户名、密码及必填字段
      → 创建单一角色为 tester 的用户
      → 状态设为 active
      → 创建登录会话
      → 返回全部公共工具
      → 默认没有项目关系
      → 默认没有额外工具授权

注册接口不得接受 role、role_ids、project_ids、tool_ids、status 等提权字段。所有写接口请求模型必须拒绝未知字段，不得静默忽略或通过批量赋值进入数据模型。

自助注册保持“注册后立即 active”，但必须同时具备：

- 按来源 IP、规范化用户名及可用设备信号组合限流；
- 全局注册熔断和异常速率告警；
- 部署级 open / invite / disabled 模式，当前默认 open；
- 不泄露用户名是否存在、内部限流阈值或账号状态的安全错误响应；
- 公共工具的每用户执行配额、成本预算和运行安全门禁，防止新注册账号滥用外部 API 或高成本 Agent。

### 8.2 管理员创建测试账号

- 普通管理员只能创建 tester；
- 新账号状态为 active；
- 普通管理员可在同一流程中把账号加入自己负责的一个或多个项目；
- 未选择项目时，账号仍可创建并仅使用公共工具；
- 普通管理员不能选择其他管理员负责的项目；
- 平台管理员可创建 admin 或 tester，并完成对应项目分配；
- 新建账号可沿用现有“首次登录必须修改密码”安全能力。

### 8.3 单角色约束

- 任一用户必须且只能有一个全局角色；
- 创建、注册和迁移均不得产生无角色或多角色用户；
- 平台管理员切换用户角色时，必须原子提交切换后的项目关系；
- tester 切换为 admin 时，必须明确选择其负责项目，不自动把成员关系提升为负责人；
- admin 切换为 tester 时，必须明确选择保留为成员的项目，不自动转换；
- 任何全局角色变化都清除现有额外工具授权，避免形成角色降级后的潜伏权限；
- 系统必须阻止禁用、降级或删除最后一个 active 平台管理员。

### 8.4 用户停用与恢复

停用用户时：

- 立即撤销全部服务端 Session；
- 使现有权限快照失效；
- 禁止登录和所有业务、管理访问；
- 保留项目关系、额外授权和审计记录，便于恢复和追踪；
- 不自动取消已在后台执行的任务。

恢复用户时：

- 恢复为 active；
- 原项目关系和仍有效的额外授权重新参与权限计算；
- 必须重新登录；
- 如恢复前发生工具归属变化，按当前工具和项目状态计算，不恢复历史范围。

## 9. 项目生命周期

### 9.1 创建项目

仅平台管理员可创建项目。创建时必须填写：

- 唯一项目编码；
- 项目名称；
- 项目描述；
- 初始状态，默认 active。

项目创建后可暂时没有负责人、成员或工具。

### 9.2 编辑项目

仅平台管理员可修改名称和描述。项目编码创建后不可修改。

普通管理员只能查看自己负责项目的基础信息，不可编辑项目定义。

### 9.3 停用项目

仅平台管理员可停用项目。停用前页面必须展示：

- 受影响的项目负责人数量；
- 受影响的测试成员数量；
- 项目工具数量；
- 有效额外授权数量；
- 当前运行中任务数量。

影响预览必须返回项目 revision 和签名 impact_token。确认请求必须携带预期 revision / token；服务端加锁后重新计算影响范围，预览已过期时返回 409 STALE_IMPACT，且不得执行变更。运行中任务数量必须来自权威任务状态源；无法准确获得时显示 unknown，并默认阻止操作，只有平台管理员显式提交 force_unknown_impact、填写原因并再次确认后才可继续。

停用后：

- 项目工具从普通用户 /tools 中消失；
- 项目负责人、成员和额外授权用户均不能业务访问项目工具；
- 普通管理员不能继续修改项目工具配置或成员；
- 平台管理员仍可在管理页面查看和调整项目、工具及人员；
- 项目关系和额外授权保留但不生效；
- 项目恢复 active 后按当前关系重新生效。

### 9.4 项目删除

V1 不支持项目硬删除。无继续使用需求的项目必须停用，以保留任务、结果、工具、成员和审计引用。

### 9.5 项目负责人管理

- 仅平台管理员可把 admin 分配为项目负责人；
- 一个项目可有零个或多个负责人；
- 一个管理员可负责零个或多个项目；
- 不能把 tester 设置为项目负责人；
- 不能把 platform_admin 作为项目负责人，因为其天然拥有全局范围；
- 停用项目保留负责人关系但关系不生效。

### 9.6 项目成员管理

平台管理员可管理任意项目成员。普通管理员只能管理自己负责项目中的 tester：

- 可加入 active tester；
- 可移除 tester；
- 不可修改用户全局角色或状态；
- 不可把 admin 当作普通项目成员；
- 不可操作其他项目；
- 同一测试人员与同一项目不能重复关联。

成员移出后，若没有公共范围、其他项目关系或额外授权，下一次请求即失去对应工具访问。

## 10. 工具归属与生命周期

### 10.1 创建和接入工具

新增工具或 Agent 时必须明确选择：

- 公共工具；或
- 项目工具，并选择一个 active 项目。

不允许创建“未分类但已启用”的工具。范围信息不完整时，工具必须保持 disabled。

### 10.2 公共工具

- 全部 active 用户自动获得业务访问；
- 不允许关联项目；
- 不允许创建额外单工具授权；
- 仅平台管理员可管理其配置、Secret、启停和发布；
- 公共工具不能对单个用户关闭。

工具只有通过公共开放安全策略后才能设为公共，包括每用户调用配额、速率限制、成本预算、外部目标地址白名单及 API 真实执行门禁。范围变更前必须展示影响预览并由平台管理员确认；公共范围不代表放宽任何运行安全策略。

V1.1 的公共资格进一步限定为“业务能力可在平台本地完整完成、无需访问真实外部目标”的工具。当前第一方工具中仅 `log-filter` 满足该条件；`functional-test-agent`、`api-test-agent`、`Truthy_Search` 与 `Truthy_ApiAutoTest2` 在统一公共沙箱及出口代理接入前只能配置为项目工具。管理端必须隐藏不可用的公共选项，服务端仍以 `PUBLIC_SANDBOX_UNAVAILABLE` 失败关闭，避免出现目录声称可执行但创建任务必然失败的伪授权。

### 10.3 项目工具

- 必须关联一个项目；
- 项目 active 且工具 enabled 时才能业务使用；
- 项目负责人、项目成员、平台管理员和额外授权用户可访问；
- 项目负责人可管理其项目级配置与共享 Secret；
- 测试人员和额外授权用户只能在各自的数据操作范围内使用业务能力，不能访问同工具其他用户的任务和结果。

### 10.4 修改范围或项目

仅平台管理员可执行：

- 公共工具改为项目工具；
- 项目工具改为公共工具；
- 项目工具从项目 A 移至项目 B。

变更前必须展示受影响用户、历史资源范围、运行中任务和额外授权数量，并要求二次确认。影响预览必须返回工具 revision 和签名 impact_token，提交时按 9.3 的相同规则在锁内重算，防止确认后状态漂移。变更提交时：

- 原有额外授权全部撤销；
- 权限版本立即更新；
- /tools 与直接接口从下一次请求起使用新范围；
- 记录变更前后范围、项目、影响数量和操作原因；
- 不修改或删除历史任务和结果。

### 10.5 工具停用与恢复

工具停用后：

- 从普通用户工具目录中隐藏；
- 拒绝所有新业务请求；
- 平台管理员仍可在管理页面查看和恢复；
- 项目负责人不得绕过停用状态；
- 项目关系与额外授权保留但不生效。

恢复后按当前范围、项目状态和用户关系重新计算。

---

## 11. 额外工具授权

### 11.1 授权条件

只有平台管理员可以创建额外授权，且必须同时满足：

- 目标用户为 active admin 或 active tester；
- 目标工具为 enabled 项目工具；
- 所属项目为 active；
- 用户不属于该项目且不是项目负责人；
- 用户当前不通过其他来源获得该工具；
- 授权原因非空。

不满足条件时不得创建冗余或无效授权。

### 11.2 授权结果

授权成功后：

- 用户可在 /tools 看到该工具；
- access_source 显示为 extra_grant；
- 用户可创建并完整处理本人业务资源；
- 用户看不到所属项目其他工具；
- 用户不获得项目成员列表、配置或 Secret 管理入口；
- 用户不自动成为项目成员。

### 11.3 撤销

平台管理员可随时撤销。撤销原因必须记录。

撤销后：

- 若用户没有其他访问来源，下一次请求立即拒绝并从 /tools 隐藏；
- 若用户已经通过项目关系获得访问，业务访问继续有效，授权来源切换为项目关系；
- 历史任务和审计保留。

撤销工具访问不删除历史资源，也不把历史资源转交给其他用户。撤销后的读取和控制按 6.4 重新判定。

### 11.4 自动撤销

以下情况自动撤销对应额外授权：

- 用户全局角色变化；
- 工具范围或所属项目变化；
- 工具改为公共工具。

用户、工具或项目停用只使授权暂时不生效，不自动删除记录。

### 11.5 到期与续期

- 创建授权必须指定 expires_at；默认 7 天，且不得超过平台配置的 90 天上限；
- 到期后授权立即不参与任何工具或历史资源访问计算，并记录到期安全审计；
- 续期必须由平台管理员显式确认、填写原因并产生审计，不得静默延长；
- 项目、工具或用户恢复时，已过期授权不得重新生效。

## 12. 用户故事

### US-1：新用户立即使用公共工具

作为新注册用户，我希望注册后直接进入平台并看到全部公共工具，不需要等待人工审批。

### US-2：测试人员通过项目获得工具

作为测试人员，我希望加入项目后自动看到项目全部工具，项目新增工具时无需再次申请。

### US-3：管理员管理多个项目

作为管理员，我希望在“我的项目”中分别查看各项目的成员和工具，并只能管理我负责的范围。

### US-4：管理员创建测试账号

作为管理员，我希望创建测试人员账号并把其加入我负责的项目，但不能创建管理员或改变全局角色。

### US-5：平台管理员分类工具

作为平台管理员，我希望把工具设为公共或归属某个项目，并在变更前看到影响范围。

### US-6：跨项目临时使用单个工具

作为测试人员，我希望在不加入整个项目的情况下，经平台管理员授权使用该项目的某个工具。

### US-7：理解访问来源

作为用户，我希望知道某个工具来自公共范围、项目继承还是额外授权，以便权限变化时能够理解原因。

### US-8：项目停用立即收敛

作为平台管理员，我希望停用项目后所有普通用户立即失去项目工具访问，同时保留历史数据和审计。

### US-9：工具可用但他人数据隔离

作为测试人员，只要我能访问某工具，我希望能够创建任务并完整处理自己的任务和结果，但不能看到、枚举或操作其他测试人员的数据，即使我们属于同一项目。

### US-10：管理面继续最小授权

作为安全负责人，我希望测试人员处理本人业务资源的能力不会扩展到他人业务数据、工具配置、Secret、用户或平台发布。

## 13. 功能需求

### FR-1：固定角色与单角色

1. 系统仅提供 platform_admin、admin、tester 三种全局角色；
2. 用户创建、更新、查询和登录响应均使用单值 role；
3. 服务端拒绝空角色、多角色和未知角色；
4. 角色规则不可由普通管理页面任意编辑；
5. 角色切换必须同时处理项目关系、额外授权和权限版本；
6. 最后一个 active 平台管理员受保护。

### FR-2：自助注册

1. 提供未登录用户可访问的注册能力；
2. 用户名规范化后全局唯一；
3. 密码继续使用现有密码策略和安全哈希；
4. 注册角色固定 tester，状态固定 active；
5. 默认无项目、无额外授权；
6. 注册成功建立会话并返回公共工具访问；
7. 记录注册安全事件和审计信息。
8. 注册接口执行组合限流、全局熔断和安全错误响应；
9. open / invite / disabled 模式由部署配置控制；
10. 注册用户使用公共工具时继续受每用户配额、成本预算和运行安全门禁约束。

### FR-3：项目管理

1. 平台管理员可创建、编辑、停用和恢复项目；
2. 项目编码唯一且不可修改；
3. 项目不支持硬删除；
4. 停用项目使项目业务访问整体失效；
5. 管理页面显示负责人、成员、工具和额外授权汇总；
6. 项目状态变更必须二次确认并审计。
7. 状态变更使用 revision / impact_token，提交时重新计算影响；过期预览返回 409；
8. 运行中任务统计来自权威任务状态源，未知状态不得伪装为 0。

### FR-4：项目人员关系

1. 平台管理员可分配项目负责人和成员；
2. 普通管理员仅可维护自己负责项目的测试成员；
3. 关系必须符合全局角色；
4. 重复加入为幂等成功或明确冲突，不得生成重复记录；
5. 关系变化立即影响有效工具范围；
6. 普通管理员跨项目请求必须被服务端拒绝。

### FR-5：工具范围与归属

1. 工具必须为 public 或 project；
2. public 工具 project_id 必须为空；
3. project 工具 project_id 必须指向一个存在的项目；
4. 启用项目工具前，所属项目必须 active；
5. 只有平台管理员可修改范围和归属；
6. 范围变更自动撤销额外授权并更新权限版本；
7. category 继续作为业务展示分类，不承担权限语义。
8. 工具设为 public 前必须通过公共开放安全策略校验，并保留每用户配额、成本预算、目标白名单和真实执行门禁；
9. 范围或归属变更使用 revision / impact_token，服务端在锁内重算影响，过期预览拒绝提交；
10. 业务资源历史授权快照不随工具范围或项目变化而改写。

### FR-6：有效工具访问服务

1. 后端提供单一权限判定入口；
2. 判定同时考虑用户、工具、项目、项目关系和额外授权状态；
3. 返回 allow / deny、主要授权来源和必要的拒绝原因；
4. /tools、工具详情和网关复用工具访问结论；任务、结果、报告等直接业务接口在此基础上继续执行对象级授权；
5. 不允许前端、自报角色或工具侧自报项目决定权限；
6. 查询失败、数据冲突和未知状态全部拒绝；
7. 判定结果可被测试并具有稳定审计字段。
8. 工具访问、业务资源 own / project-manage / global 范围和控制面权限必须分别判定，不得相互推导。

### FR-7：工具目录

/tools 只返回当前用户可业务访问的 enabled 工具。每项至少返回：

- 现有工具展示字段；
- access_scope；
- access_source；
- 项目工具的项目 ID、项目编码和项目名称；
- 用户是否拥有该工具管理能力。

目录不得返回其他项目成员、额外授权明细、内部健康地址或 Secret。

### FR-8：业务资源对象级授权

用户通过任一有效来源访问工具后，可创建新的本人任务。查看或操作既有任务、结果、报告时，必须同时校验资源所有者、创建时项目快照和调用者当前数据操作范围：

- view；
- execute；
- own task/result/report view；
- own Review / confirm；
- own cancel / retry；
- own download / export / report；
- project manager scoped view/control；
- platform administrator global view/control。

测试人员不得拥有 task.view.all、result.view.all、task.cancel.any 等跨所有者能力。普通管理员只在当前负责项目的资源快照范围内拥有项目级查看和控制能力；仅凭额外工具授权时仍为 own 范围。旧兼容权限不得通过工具 ID 前缀或命名规则自动推断；每个权限必须在显式权限注册表中分类为 own 业务权限、项目管理业务权限或控制面权限，未分类的新权限默认拒绝。

### FR-9：工具管理能力

1. 平台管理员可管理所有工具；
2. 普通管理员只可管理自己负责项目的项目工具；
3. 普通管理员不能管理公共工具；
4. 额外授权不产生管理能力；
5. 测试人员没有工具控制面管理能力；
6. 个人私有 Credential 和 LLM 配置不因项目管理关系而暴露；
7. 所有 Secret 响应继续只返回掩码或就绪状态。

### FR-10：额外工具授权

1. 仅平台管理员可创建和撤销；
2. 仅支持单用户、单项目工具；
3. 授权和撤销原因必填；
4. 重复和冗余授权被拒绝；
5. 工具范围或项目变化时自动撤销；
6. 列表需展示当前状态、授权人、时间和原因；
7. 用户可查看自己的额外授权来源，但不能查看其他用户授权。
8. 授权必须包含 expires_at，默认 7 天且最长 90 天；
9. 授权到期立即失效，续期需平台管理员填写原因并审计；
10. 额外授权不提供所属工具内其他用户的数据访问权。

### FR-11：账号安全管理

1. 平台管理员可禁用、恢复、重置密码和撤销用户全部会话；
2. 普通管理员只能创建测试账号和维护项目成员；
3. 用户停用立即撤销会话；
4. 角色和范围变化使旧权限快照失效；
5. 最后一个 active 平台管理员不可被禁用、降级或删除；
6. 所有高风险操作必须 CSRF 防护、二次确认并审计。

### FR-12：错误和提示

至少提供稳定错误语义：

| 场景 | HTTP 语义 | 用户提示 |
|---|---|---|
| 未登录或 Session 失效 | 401 | 请重新登录 |
| 用户已停用 | 401 | 账号已停用，请联系平台管理员 |
| 工具范围不允许 | 403 | 你无权访问该工具 |
| 可见对象但缺少具体管理动作 | 403 | 你无权执行该操作 |
| 项目或工具已停用 | 409 或业务不可用 | 项目或工具当前已停用 |
| 范围与项目字段冲突 | 422 | 工具范围配置不合法 |
| 重复成员或额外授权 | 409 | 关系已存在 |
| 操作最后一个平台管理员 | 409 | 必须至少保留一个有效平台管理员 |
| 业务资源不存在或不在调用者可见范围 | 404 | 资源不存在 |
| 影响预览已过期 | 409 | 资源状态已变化，请重新确认影响范围 |

前端不得把权限拒绝统一显示为网络错误，也不得在错误信息中泄露其他项目、用户或 Secret。
对调用者不可见的任务、结果、报告、用户或项目对象必须与真实不存在对象返回一致的 404 响应，避免形成 ID 枚举信号；403 只用于调用者可见对象但缺少某一具体动作权限的场景。

### FR-13：审计

以下操作必须记录成功和失败审计：

- 用户注册、创建、角色切换、停用、恢复、密码重置、会话撤销；
- 项目创建、编辑、停用、恢复；
- 项目负责人和成员加入、移除；
- 工具范围、所属项目和启用状态变化；
- 额外授权创建、撤销和自动撤销；
- 额外授权到期和续期；
- 工具配置、Secret、发布等既有高风险操作。

审计至少包含：

- actor；
- action；
- resource_type 和 resource_id；
- outcome；
- 操作时间；
- 变更前后非敏感摘要；
- 原因；
- 请求关联 ID；
- 必要的客户端和会话摘要。

Secret、密码、Token、Cookie 和完整 Credential 不得进入审计。

成功的高风险业务变更与成功审计必须在同一事务内原子提交；成功审计写入失败时业务变更失败关闭。授权拒绝、校验失败等失败事件不得依赖随后回滚的业务事务，必须通过独立审计事务、可靠安全日志或事务外安全事件通道持久化。失败事件通道应限流和聚合以抵抗审计型拒绝服务，但不得丢失最后平台管理员保护、跨项目越权、Secret 写入等高风险失败。

操作原因 reason 属于不可信输入：限制长度和允许字段，不记录原始请求体，写入前执行 Secret / Token 模式检测与脱敏。审计测试必须覆盖原因字段中包含疑似密钥的情况。

### 14.2 工具工作台

- 公共工具标签；或

项目详情分为：

1. 概览；
2. 项目负责人；

4. 项目工具；

普通管理员看到相同信息的受限版本，不显示负责人编辑、项目状态、工具归属和额外授权管理操作。

### 14.4 用户管理页

平台管理员用户列表展示：

- 用户基本信息；

### 14.5 工具管理页

- 工具启用状态；
- access_scope；
- 所属项目；
- 现有展示与运行字段。

普通管理员只能进入自己负责项目的工具控制面，不显示范围、所属项目、公共工具和平台级配置。

### 14.6 状态、确认和无障碍

- 停用项目、停用工具、角色切换、移除成员、撤销授权必须二次确认；
- 高风险确认框明确展示对象名称、影响数量和不可见后果；
- 不只用颜色表达角色、状态和授权来源；
- 表格、弹窗、表单和错误提示支持键盘操作、焦点管理和可读标签；
- 空项目、无工具、无额外授权和无可管理权限均提供明确空状态。

## 15. 概念数据要求

后续数据库设计必须表达以下对象和约束，但本 PRD 不锁定具体表名：

### 15.1 用户角色

- 用户与固定角色为一对一；
- 角色值仅允许 platform_admin、admin、tester；
- 不允许无角色或多角色；
- 角色变化可追溯。

### 15.2 项目

- 项目编码唯一；
- 状态仅 active / inactive；
- 不物理删除；
- 保留创建和更新主体。

### 15.3 项目关系

- 用户、项目、关系类型唯一；
- manager 仅允许 admin；
- member 仅允许 tester；
- 平台管理员不依赖关系；
- 关系删除或失效可审计。

### 15.4 工具范围

- access_scope 仅 public / project；
- public 与 project_id 互斥；
- project 必须有 project_id；
- category 保持原业务分类含义；
- 范围和归属变化有审计。

### 15.5 额外授权

- 用户与工具的有效授权唯一；
- 只允许项目工具；
- 记录授权和撤销主体、时间、原因；
- expires_at 必填，默认 7 天且最长 90 天；
- 支持保留历史而不物理覆盖；
- 状态变化可参与权限版本失效。

### 15.6 业务资源授权快照

- 根任务创建时固化 tool_id、created_by_user_id、access_scope_snapshot、project_id_snapshot、authorization_source_snapshot 和 created_at；
- 结果、报告、导出和运行日志必须能追溯至根任务并继承其授权快照；
- 快照不得因工具改范围、改项目或用户角色变化而改写；
- 当前关系和快照共同决定历史资源访问，具体规则见 6.4；
- 对 owner、project snapshot、tool 和创建时间建立支持对象级授权的查询约束与索引。

### 15.7 授权版本与变更并发

- 用户、项目和工具具备独立 revision / authorization_epoch 或等效版本；
- 影响预览使用可验证 impact_token 绑定资源版本和预览摘要；
- 并发写入必须能保护最后一个 active 平台管理员及跨对象不变量；
- 运行任务的执行租约与交互权限版本分离。

### 15.8 旧 RBAC 数据

旧 Role、UserRole、RoleGrant 在回滚窗口内必须保留为只读迁移依据，不得继续作为新业务访问的最终授权源。验收及回滚窗口结束后，再由独立清理步骤决定是否删除。

## 16. API 与鉴权行为要求

### 16.1 身份响应

当前用户身份响应必须提供：

- 单一 role；
- status；
- 负责或所属项目摘要；
- 自己的额外授权摘要；
- permission_version 或等效版本；
- 与现有 Session、CSRF 和首次改密状态兼容的信息。

不得继续把 role_ids 作为新前端的权威来源。

### 16.2 工具目录与详情

- /tools 复用统一有效访问服务；
- 工具详情和健康检查重复校验，不能信任目录访问历史；
- 无权工具不出现在列表；
- 直接构造工具 ID 仍必须拒绝；
- 项目及工具停用后，缓存不得继续展示或放行。

### 16.3 业务资源接口

- 任务、结果、Review、报告、下载和导出接口必须先按可见范围查询对象，再校验具体动作；
- 测试人员查询条件必须包含 created_by_user_id = current_user.id，不得先全量查询后在应用层过滤；
- 普通管理员的项目级查询必须限制在当前负责项目和资源 project_id_snapshot 内；
- 仅有额外工具授权的管理员按本人资源范围查询；
- 平台管理员可使用全局运维查询，但仍须记录审计；
- 不可见对象与不存在对象统一返回 404；可见但不允许特定动作时才返回 403；
- 列表计数、分页、搜索、导出和批量操作必须使用相同数据范围，不能通过总数、状态筛选或错误信息旁路枚举。

### 16.4 网关与独立工具

- 网关代理每次请求校验当前有效工具访问；
- 可信头由网关覆盖，忽略浏览器自报角色、项目和权限；
- 工具侧只能接受平台签发的用户、工具和业务权限上下文；
- 工具不得通过收到旧 tool.view 就自行推断配置或 Secret 管理能力；
- 平台独立模式已有安全策略保持不变，不因本期改造自动放宽。
- 所有业务权限必须来自显式权限注册表；禁止根据 tool_id 或权限代码前缀自动推断 own、项目管理或控制面能力；
- 未注册权限默认拒绝；所有写请求模型拒绝未知字段。

### 16.5 并发与幂等

- 重复加入成员、重复撤销和重复停用应返回可预测结果；
- 角色、项目关系、工具归属和额外授权写入必须使用事务；
- 并发变更不得产生双角色、重复关系、公共工具带 project_id 等非法状态；
- 权限版本更新与授权变更必须在同一事务中提交。
- 涉及相同授权域的变更必须采用事务级串行化、行锁或等效互斥，并在取得锁后重新读取和校验状态；
- 锁定顺序必须全局一致：全局角色保护资源 → 按 ID 排序的项目 → 按 ID 排序的工具 → 按 ID 排序的用户 → 成员/授权关系，避免死锁；
- 必须原子保护以下不变量：至少一个 active 平台管理员、角色与项目关系兼容、公共工具不存在额外授权、项目停用后关系不参与授权；
- 两个并发管理员同时降级或禁用最后两名平台管理员时，最多一个事务成功，另一个返回 409；
- 角色切换与成员变更、授权创建与工具范围变化、项目停用与成员/授权变化的并发结果必须落入合法最终状态，不得产生短暂放宽窗口。

## 17. 审计与可观测性

### 17.1 授权解释

管理端应能回答：

- 用户当前是什么角色；
- 用户负责或属于哪些项目；
- 用户有哪些额外授权；
- 用户为什么能访问某个工具；
- 用户为什么能或不能访问某条任务、结果或报告；
- 某次变更后哪些用户失去或获得访问。

### 17.2 指标

至少监控：

- active 用户数量及角色分布；
- active 项目数量；
- 公共 / 项目工具数量；
- 项目负责人和成员关系数量；
- 有效额外授权数量；
- 权限拒绝次数，按原因分类；
- 业务资源 404 隔离拒绝、额外授权到期和执行租约使用次数；
- /tools 响应时间和错误率；
- 权限缓存命中率与版本失效次数；
- 迁移前后可访问工具数量差异。

### 17.3 日志安全

日志只记录稳定 ID、角色、范围、授权来源和拒绝原因。不得记录：

- 密码；
- Session Cookie；
- CSRF Token；
- API Key；
- Secret 明文；
- Credential 明文；
- 完整下游 Token。

原因字段、错误消息和请求摘要同样按不可信输入处理，不得原样写入日志；疑似敏感值必须拒绝或脱敏。

## 18. 非功能与安全要求

### 18.1 安全

- 默认拒绝，禁止因查询异常、关联缺失或缓存失败而放行；
- 服务端是唯一权限真相来源；
- 所有写操作保留现有 CSRF、会话、登录限流和审计保护；
- 普通管理员所有查询必须包含项目范围约束；
- 对资源 ID 构造、参数篡改和水平越权提供自动化测试；
- 工具配置与 Secret 写操作必须再次校验管理能力；
- 权限缓存键必须包含用户权限版本，或使用等效即时失效机制；
- 权限缓存还必须包含相关项目和工具 authorization_epoch；
- 测试人员的任务、结果和报告查询必须在数据访问层限制所有者；
- 所有写请求模型拒绝未知字段，所有未登记业务权限默认拒绝；
- 禁止在浏览器本地存储长期权限真相。

### 18.2 性能

- /tools 不得按工具逐条发起独立数据库查询；
- 权限计算应支持一次查询获得用户可访问工具集合；
- 在生产等量数据副本上进行迁移前后基线对比；
- P95 增量超过 100 毫秒时不得全量发布；
- 管理页计数可分页或聚合，但必须与真实权限一致。

### 18.3 可用性

- 授权变更提交后下一次请求生效；
- 成功审计写入失败时，高风险授权变更必须失败关闭；失败尝试通过独立可靠安全事件通道留痕；
- 管理页面刷新后必须从服务端重新读取权限，不只更新本地状态；
- 项目或工具停用不删除历史任务、结果和审计。

### 18.4 兼容性

- 保留现有 category 展示分类；
- 保留现有工具 ID、入口、健康检查和业务路由；
- 保留现有 Session、CSRF 和 permission_version 能力；
- 旧角色及授权数据在回滚窗口内只读保留；
- 旧前端 role_ids 和细权限展示在灰度期可兼容读取，但不得继续作为新业务决策源。

## 19. 存量迁移

### 19.1 迁移原则

1. 最小权限；
2. 不默认公开存量工具；
3. 不把旧只读或审计账号静默提升为执行用户；
4. 不自动创建普通管理员；
5. 迁移前可预演；
6. 迁移报告不包含敏感值；
7. 数据清理晚于回滚窗口。
8. 未知角色、无角色、非法多角色或无法解释的权限数据必须在任何角色回填前被预检阻断，不得兜底为 tester；
9. 迁移采用 expand / compatibility / backfill / cutover / contract，旧版本应用在扩展阶段仍可运行；
10. 新权限模型开始接受写入后，不允许用旧 RBAC 快照覆盖新数据。

### 19.2 默认项目与工具迁移

迁移创建一个 active 的“存量工具项目”，项目编码固定且唯一。

存量工具分类规则：

1. 迁移清单明确标记为 public 的工具迁移为公共工具；
2. 迁移清单明确指定项目的工具归入指定项目；
3. 未在清单中明确分类的现有工具全部归入“存量工具项目”；
4. 不存在默认公开行为；
5. disabled 工具保持 disabled，但仍必须补齐合法范围；
6. 范围无法确定或数据冲突时迁移失败，不以公共工具兜底。

### 19.3 用户角色迁移

角色映射采用以下确定规则：

| 旧角色组合 | 新全局角色 | 默认项目处理 |
|---|---|---|
| 包含 role_platform_admin | platform_admin | 无需项目关系 |
| 不含平台管理员，但包含 role_test_developer | tester | 加入存量工具项目 |
| 不含以上角色，但包含 role_test_executor | tester | 加入存量工具项目 |
| 仅含 role_readonly | tester | 不自动加入项目 |
| 仅含 role_auditor | tester | 不自动加入项目 |
| role_readonly 与 role_auditor 组合 | tester | 不自动加入项目 |
| 无角色或未知角色 | 不自动迁移 | 阻断迁移并要求修复 |

补充规则：

- 多角色按上表从上到下匹配；
- 旧测试开发用户不自动升级为 admin，避免新增项目成员管理权限；
- 旧测试开发用户在迁移后失去工具配置管理，平台管理员可在评审后显式提升并分配项目；
- 旧只读和审计型账号不自动加入项目，避免获得执行以及对本人业务资源进行 Review、取消和导出等新增能力；
- 旧只读 / 审计用户仍可使用被明确迁移为公共的工具，这是新模型的统一公共规则；
- 原用户 active / inactive 状态原样保留；
- 不迁移旧通配符 RoleGrant 为额外单工具授权。

### 19.4 迁移报告

预演和正式迁移均输出：

- 用户总数及各新角色数量；
- 每个用户的旧角色组合、新角色和项目关系变化；
- 项目创建数量；
- 公共 / 项目 / disabled 工具数量；
- 每个工具的新范围和项目；
- 未自动恢复访问的只读 / 审计账号；
- 配置管理权限被收敛的旧测试开发账号；
- 数据冲突、未知角色、非法工具和阻断项；
- 迁移前后每个用户可访问工具数量差异；
- 校验结果和迁移版本。

报告只包含稳定标识和非敏感元数据。

### 19.5 迁移校验

正式切换前必须满足：

- 所有用户恰好一个新角色；
- 所有 enabled 工具范围合法；
- 所有项目工具存在所属项目；
- 公共工具 project_id 为空；
- 项目关系与用户角色一致；
- 额外授权无重复、无公共工具、无非法用户；
- 至少一个 active 平台管理员；
- 迁移前后差异报告已由平台管理员复核；
- 旧只读 / 审计账号未被自动加入项目；
- /tools 与直接访问矩阵测试一致。
- 所有存量任务、结果和报告已补齐可验证的所有者与项目快照；无法可靠确定所有者或项目范围的数据必须作为阻断项处理，不得默认公开或归属任意测试人员；
- 新旧权限影子计算差异中不存在未审批的权限放宽；
- 未知角色和无角色预检结果为零。

## 20. 发布与回滚

### 20.1 上线顺序

1. 在旧系统上执行只读预检，识别未知/无角色、非法关系、无法确定所有者的历史业务资源和其他阻断项；预检未清零不得执行回填；
2. 备份数据库并生成迁移前权限快照；
3. 执行扩展迁移：增加可空新字段、新表、索引和非破坏性约束；此阶段不添加会使旧应用无法运行的 NOT NULL 或收缩约束；
4. 部署兼容后端：继续兼容旧读路径，同时对新字段双写、执行新权限影子计算，但仍不使用新模型放行；
5. 执行迁移预演、历史业务资源授权快照回填和差异比对，修复全部阻断项；
6. 平台管理员审核用户、工具、历史资源和访问差异报告；
7. 在最终回填和切换窗口，短暂停止用户角色、项目关系、工具范围和额外授权等权限管理写入；业务任务是否暂停按环境切换方案决定；
8. 执行增量回填并再次校验不变量和影子计算差异；
9. 启用新有效工具访问、业务资源对象级授权和执行租约，随后恢复新权限模型管理写入；旧 RBAC 转为只读；
10. 灰度切换 /tools、工具详情、网关、任务、结果、Review、取消、重试和导出；
11. 发布新管理页面，完成双用户、跨项目、停用、并发和越权验收；
12. 全量切换并观察指标；
13. 验证稳定后执行收缩迁移：为已验证字段添加 NOT NULL、最终 CHECK / UNIQUE 等约束；
14. 回滚窗口结束后再独立规划旧 RBAC 清理。

### 20.2 灰度要求

- 灰度期间同时计算旧、新权限但只使用指定模型放行；
- 对旧、新结论差异进行非敏感统计；
- 任何新模型比预期更宽的差异必须阻断全量；
- 不允许通过“旧模型允许”兜底新模型拒绝；
- 所有环境分别预演，禁止用 dev 迁移结果替代 prod。

### 20.3 回滚原则

- 回滚窗口内不删除旧 Role、UserRole、RoleGrant；
- 新模型管理写入切换前，可恢复旧鉴权读取路径和旧前端，保留已新增的可空结构与影子数据；
- 新模型开始接受角色、项目、工具范围、授权或业务资源快照写入后，不得恢复可能过期的旧 RBAC 作为授权真相，也不得直接删除新表或回滚数据；
- 切换后回滚应回到“兼容读取新模型”的稳定版本，关闭新管理页面和相关写入，再以前向修复恢复服务；只有确认切换后不存在任何新模型写入时，才允许执行数据库降级；
- 新增注册用户、项目和工具在回滚时不得强行映射回旧通配符授权；必要时暂停权限管理写入并由兼容版本继续读取新模型；
- 回滚不得丢失迁移后产生的审计；
- 回滚不得输出或重新生成 Secret 明文；
- 扩展迁移、应用切换和网关切换需具备独立恢复路径；收缩迁移只在回滚窗口结束或明确评审后执行；
- 回滚后重新执行权限差异校验。

## 21. 验收场景

| 编号 | 场景 | 前置条件 | 预期结果 |
|---|---|---|---|
| AC-01 | 自助注册 | 用户名未占用 | 创建 active tester，立即登录 |
| AC-02 | 注册字段篡改 | 注册请求携带 admin、项目或任意未知字段 | 服务端以 422 拒绝，数据库不产生用户或关系 |
| AC-03 | 公共工具 | active tester 无项目 | /tools 展示全部 enabled 公共工具 |
| AC-04 | 默认无项目 | 新注册 tester | 不展示任何项目工具 |
| AC-05 | 加入项目 | tester 加入 active 项目 | 下一次请求展示并可使用项目全部 enabled 工具 |
| AC-06 | 项目新增工具 | tester 已是项目成员 | 新工具启用后自动可见，无需逐工具授权 |
| AC-07 | 移出项目 | tester 无其他访问来源 | 下一次请求隐藏并拒绝项目工具 |
| AC-08 | 多项目成员 | tester 属于 A、B | 可使用 A、B 工具，不能使用 C |
| AC-09 | 管理多个项目 | admin 负责 A、B | 可管理 A、B 成员和项目工具 |
| AC-10 | 管理员跨项目 | admin 不负责 C | 列表不泄露 C 成员，构造 C 的对象读取请求与不存在对象一致返回 404 |
| AC-11 | 创建测试账号 | admin 创建账号 | 角色固定 tester，不能提交 admin |
| AC-12 | 管理员管理用户状态 | admin 尝试禁用或重置 tester | 服务端拒绝 |

| AC-16 | 额外授权管理边界 | admin 通过额外授权访问工具 | 可创建并处理本人任务，不可查看他人任务、配置 Secret 或管理成员 |
| AC-17 | 重复额外授权 | 用户已有项目继承 | 创建额外授权被拒绝为冗余 |
| AC-18 | 撤销额外授权 | 用户无其他来源 | 下一次请求立即隐藏并拒绝工具 |
| AC-19 | 撤销但仍继承 | 用户同时是项目成员 | 访问继续，来源变为 project_member |

| AC-21 | 项目工具改公共 | 平台管理员确认 | 全部 active 用户获得访问，旧额外授权自动撤销 |
| AC-22 | 工具跨项目移动 | 工具从 A 移到 B | A 用户失去新任务访问，B 用户获得，旧额外授权撤销；历史资源保持 A 快照 |

| AC-24 | 项目恢复 | A 恢复 active | 按当前成员和授权重新生效 |
| AC-25 | 工具停用 | 工具 enabled | 所有用户目录隐藏且新执行被拒绝 |
| AC-26 | 用户停用 | 用户有项目和额外授权 | Session 撤销，所有请求 401，关系保留 |
| AC-27 | 用户恢复 | 用户重新 active | 重新登录后按当前关系恢复访问 |
| AC-28 | 本人业务资源 | tester 可访问工具并创建任务 | 可查看、Review、取消、重试和导出自己的任务及结果 |
| AC-29 | 配置隔离 | tester 可访问工具 | 修改配置、Secret、归属和用户权限均被拒绝 |
| AC-30 | 公共工具配置 | 普通 admin | 即使可使用公共工具，也不能管理其配置 |

| AC-32 | 私有 Credential | admin 管理项目 | 不能查看或修改其他用户个人凭证明文 |
| AC-33 | 目录与直达一致 | 工具不在用户 /tools | 构造入口、健康、任务或结果请求均被拒绝 |

| AC-37 | 审计 | 成员、范围、授权发生变化 | 审计包含 actor、前后摘要、原因且无 Secret |
| AC-38 | 迁移默认范围 | 存量工具未在清单分类 | 归入存量工具项目，不成为公共工具 |
| AC-39 | 旧执行角色迁移 | 旧测试开发 / 执行者 | 迁移为 tester 并加入存量工具项目 |
| AC-40 | 旧只读迁移 | 仅有 readonly / auditor | 迁移为 tester 但不自动加入项目 |
| AC-41 | 迁移未知角色 | 用户存在未知或无角色 | 迁移被阻断并输出修复项 |

| AC-43 | 同项目测试人员隔离 | tester A、B 同属项目且可用同一工具 | A 的列表、计数、搜索、直达、导出和批量接口均无法发现或操作 B 的任务，返回与不存在一致的 404 |
| AC-44 | 项目负责人业务范围 | admin 负责项目 A | 可管理 A 快照下所有成员任务，但不能查看项目 B 或仅额外授权工具中的他人任务 |
| AC-45 | 公共工具数据隔离 | tester A、B 均可使用公共工具 | 两人只能查看自己的任务；平台管理员可全局运维 |

| AC-49 | 最后管理员并发保护 | 两名管理员并发降级/禁用最后两个 active 平台管理员 | 至多一个成功，另一个 409，系统始终保留至少一个 active 平台管理员 |
| AC-50 | 执行租约 | 任务派发后用户权限被撤销 | 交互读取和控制立即拒绝；既有任务只能在窄租约内完成，不能扩权或创建新任务 |

| AC-52 | 注册与公共工具防滥用 | 匿名来源批量注册并调用公共高成本 Agent | 组合限流/熔断生效，单用户配额和运行安全门禁不因公共范围绕过 |

## 22. 测试要求

### 22.1 单元测试

- 三角色和单角色约束；
- 有效工具访问公式各分支；
- public / project 字段互斥；
- 项目负责人、成员角色约束；
- 额外授权创建、冗余、撤销和自动撤销；
- 额外授权默认/最大有效期、到期、续期和恢复不复活；
- 项目、工具、用户停用；
- 最后一个平台管理员保护；
- 权限版本更新和缓存失效；
- 业务资源 own / project-manager / platform-admin 数据范围；
- 工具迁移前后的历史资源快照规则；
- 显式权限注册表未分类权限默认拒绝；
- 执行租约不可扩大任务、工具、环境和凭据范围。

### 22.2 接口测试

- 注册提权字段篡改；
- 普通管理员跨项目水平越权；
- 测试人员修改配置和 Secret；

- 不可见对象与不存在对象的 404 响应体和明显时序特征一致；
- /tools 与工具健康、网关和业务接口一致性；
- 并发角色切换和成员变更；
- 最后平台管理员、角色/成员、授权/工具范围、项目停用/关系变更的并发竞争；
- 影响预览 revision / impact_token 过期；
- 注册组合限流、熔断及公共工具配额；
- 审计成功原子性、失败事件持久化和原因字段 Secret 脱敏；
- 重复请求幂等；
- 401、403、409、422 稳定错误语义。

### 22.3 迁移测试

- 空数据库全量升级；
- 含 5 种角色和多角色用户的升级；
- active / inactive 用户；
- enabled / disabled 工具；
- 显式公共清单、指定项目和默认项目；
- 只读 / 审计账号不自动提权；
- 未知角色和非法工具阻断；
- 重复执行迁移结果一致；
- 迁移失败事务回滚；

## 23. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 旧只读角色在新模型中没有等价角色 | 可能静默获得执行能力 | 默认不加入项目，由平台管理员显式决定 |
| 旧测试开发自动升级为管理员 | 新增成员管理能力 | 默认迁移为 tester，不自动创建 admin |
| 存量工具默认公开 | 新注册用户立即越权 | 未分类工具统一进入存量工具项目 |
| 仅修改 /tools | 可通过直达接口绕过 | 目录、网关和业务接口统一权限服务 |
| 把工具使用权等同于工具内全部数据权 | 同项目测试人员可互看、取消或导出他人任务 | 工具访问与业务资源对象级授权分层，测试人员查询强制 owner 条件 |
| 权限缓存未失效 | 撤权后仍可访问 | 权限版本和事务内失效 |
| 项目管理员查询缺少范围条件 | 泄露其他项目成员或 Secret | 服务端强制项目作用域和越权测试 |
| 工具范围切换保留旧额外授权 | 产生跨项目潜伏权限 | 范围或项目变化自动撤销 |
| 项目停用自动取消任务 | 产生半完成状态和数据不一致 | 只禁止新访问，任务取消独立处理 |
| 项目管理暴露个人 Credential | 泄露用户私密配置 | 明确区分项目共享控制面和个人所有权 |
| 回滚过早删除旧 RBAC | 无法恢复 | 回滚窗口后独立清理 |
| 权限查询产生 N+1 | /tools 性能下降 | 集合查询、索引和生产等量基线 |
| 额外授权长期不回收 | 跨项目权限永久残留 | 强制 expires_at，默认 7 天、最长 90 天，续期需原因和审计 |
| 影响预览与提交间状态漂移 | 停用或迁移影响超出确认范围 | revision / impact_token、加锁后重算、过期返回 409 |
| 权限并发写破坏不变量 | 无平台管理员、非法关系或潜伏授权 | 统一锁序、事务内重读和竞争条件测试 |
| 失败审计随事务回滚 | 越权尝试无痕 | 成功审计原子提交，失败事件使用独立可靠安全通道 |
| 自助注册滥用公共高成本工具 | 资源耗尽或外部调用风险 | 注册组合限流/熔断、公共工具资格策略、每用户配额与安全门禁 |
| 旧权限按命名前缀自动归类 | 新权限被意外授予 | 显式权限注册表，未分类权限默认拒绝 |
| 切换后恢复旧 RBAC | 新写入丢失或权限回退错误 | 回滚到兼容新模型版本并前向修复，存在新写入时禁止数据库降级 |

## 24. 已锁定产品决策

1. 采用“固定角色 + 项目范围 + 额外工具授权”；
2. 固定角色只有平台管理员、管理员、测试人员；
3. 每个用户恰好一个全局角色；
4. 不支持自定义角色和多角色叠加；
5. 公共工具对全部 active 用户开放；
6. 项目工具首期只归属一个项目；
7. 管理员可负责多个项目，测试人员可加入多个项目；
8. 额外授权只由平台管理员操作；
9. 额外授权只增加单个项目工具使用权，不增加项目内他人数据访问权；
10. 不提供拒绝授权；
11. 项目成员默认继承项目全部工具；
12. 工具/Agent 使用权与任务、结果、报告的数据操作权严格分离；
13. 测试人员只能查看和操作本人创建的任务、结果及报告；
14. 普通管理员可管理所负责项目快照下的业务资源；仅凭额外授权时只能管理本人资源；
15. 平台管理员可执行全平台业务资源运维和审计；
16. 工具业务能力不包含配置、Secret、用户、项目和平台管理；
17. 普通管理员只能管理自己负责项目的测试成员和项目工具控制面；
18. 公共工具控制面只由平台管理员管理；
19. 注册用户默认 tester、active、无项目、无额外授权，同时受注册防滥用和公共工具配额约束；
20. 项目和工具采用停用，不做硬删除；
21. 项目或工具停用时，平台管理员保留管理能力，但所有角色均不能发起新业务执行；既有任务按执行租约策略处理；
22. 工具范围或所属项目变化时撤销全部额外授权，历史业务资源仍绑定创建时快照；
23. 额外授权必须到期，默认 7 天、最长 90 天，续期需显式理由和审计；
24. 存量工具不默认公开，未分类时进入存量工具项目；
25. 旧测试开发和测试执行者默认迁移为 tester 并加入存量工具项目；
26. 旧只读和审计型账号默认不加入项目，避免静默提权；
27. 旧测试开发不自动升级为新管理员；
28. 未知角色、无角色和无法确定所有者的历史资源阻断迁移，不得兜底；
29. 迁移采用 expand / compatibility / backfill / cutover / contract；
30. 新模型开始写入后只允许回滚到兼容新模型版本，不恢复陈旧旧 RBAC；
31. 不可见业务对象与不存在对象统一返回 404，避免枚举；
32. 权限必须显式分类，未登记的新权限默认拒绝；
33. 成功高风险变更与审计原子提交，失败尝试通过独立可靠安全通道留痕；
34. 旧 RBAC 数据在回滚窗口内保留，只是不再作为新业务访问的最终授权源。
