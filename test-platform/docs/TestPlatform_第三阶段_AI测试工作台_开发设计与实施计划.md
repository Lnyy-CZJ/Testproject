## 1. 文档目标

本文把第三阶段 PRD 与已确认 Figma 概念稿转化为可以直接执行的开发设计和实施计划，回答以下问题：

1. 如何把当前“工具入口集合”重组为使命驱动的 AI 测试工作台；
2. 如何在不合并工具任务、不改造核心算法的前提下形成统一平台体验；
3. 首页、能力域页面、导航、状态和权限如何落到现有 React 应用；
4. 哪些现有 API、数据表和权限可以直接复用；
5. 哪些文件需要修改或新增；
6. 如何测试、发布和回滚；
7. 如何判断本阶段真正完成，而不只是完成一次视觉换肤。

本文是开发设计与实施计划，不是最终逐条执行命令。后续可以基于本文再生成最终执行计划。

## 2. 输入基线

### 2.1 产品输入

本阶段已经确认以下产品判断：

- 平台定位为“AI 测试与质量工程工作台”；
- 平台围绕用户测试使命组织能力，而不是围绕项目目录或技术栈组织；
- 功能测试智能体和 API 测试智能体都是独立产品能力；
- 接口自动化、埋点分析、日志分析和检索评测继续承担各自独立使命；
- API 测试智能体与接口自动化可以表达使用顺序，但不传递任务数据；
- 平台统一入口、登录、权限、配置、Secret、凭证、审计和基础状态；
- 各工具继续独立运行、独立存储任务、独立发布和独立处理故障；
- 本阶段不新增测试能力，不建设统一任务中心、统一报告中心或跨工具编排。

### 2.2 Figma 输入

Figma 概念稿包含三个主要画面：

| Figma 画面 | 核心表达 | 开发落点 |
|---|---|---|
| `01 首页工作台` | 平台定位、真实状态、两个 AI 主使命、四个专业工具入口 | `/` |
| `02 AI 测试能力域` | 两个独立 Agent、各自流程边界、从探索到回归的静态建议 | `/ai-testing` |
| `03 平台信息架构` | 平台控制面、四个能力域、明确不统一的内容 | 导航、路由、产品文案和本文架构约束 |

Figma 是视觉与信息层级基准，不要求逐像素复制画布中的演示数据。所有数量、状态和权限必须来自真实运行数据。

### 2.3 当前技术基线

平台当前技术栈保持不变：

| 层级 | 当前实现 |

| 前端 | React 19、TypeScript、Vite、React Router 7、Vitest、Testing Library |

| 部署入口 | 统一网关 `8080` |

### 2.5 当前主要差距

当前首页只完成“已授权工具列表”，存在以下差距：

1. 首页以工具为中心，没有首先回答“用户现在想完成什么测试目标”；
2. `AppShell` 主导航仍是“概览、工具、配置、权限、审计”，业务能力域不清晰；
3. 工具目录和健康状态只由 `HomePage` 持有，能力域页面无法复用；
4. 六项能力的使命、输入、输出和边界没有统一产品表达；
5. AI Agent 与普通工程工具在信息层级上没有清晰区分；
6. 平台状态、能力状态和权限状态没有形成统一展示模型；
7. `App.tsx` 已同时承载认证、首页、配置、Secret、凭证、用户、角色和审计，继续直接堆叠页面会降低可维护性；
8. 当前工具页面虽然能够独立运行，但平台上下文和返回入口仍需逐项确认。

- 不改变宿主机端口策略。

## 4. 设计原则与关键决策

### 4.1 设计原则

1. **使命优先**：先表达用户目标，再表达工具名称。
2. **真实能力**：只展示已经可用的六项能力和真实状态。
3. **独立自治**：平台不拥有工具任务，不修改工具任务阶段。
4. **权限优先**：工具目录以服务端过滤结果为真源。
5. **故障隔离**：单个工具异常不影响其他工具入口。
6. **最小改动**：优先前端确定性映射，不扩展数据库 Schema。
7. **可回滚**：第三阶段可只回滚平台前端镜像。
8. **桌面优先**：只为 1280px 以上桌面浏览器设计。

### 4.2 已锁定技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 能力域页面 | React Router 独立路由 | URL 可复制、刷新可恢复、导航状态清晰 |
| 产品文案来源 | 前端稳定 Tool ID 映射 | 不为六项固定能力引入 CMS 或迁移 |
| 工具权限来源 | `GET /api/v1/tools` | 后端已经按 `tool.view` 过滤 |
| 工具健康来源 | `GET /api/v1/tools/{tool_id}/health` | 保留现有协议和故障隔离 |
| 目录和状态共享 | React Context + 原生 Hook | 不新增状态库，避免页面重复请求 |
| 能力域映射 | 现有 `category` 确定性映射 | 现有数据已经足够 |
| 首页状态 | 真实工具健康、环境和受权管理提醒 | 不展示虚构任务指标 |
| 后端变更 | 原则上无业务 API、无数据库迁移 | 第三阶段主要是产品结构与前端体验 |
| 工具改造 | 只做平台上下文和公共状态校准 | 避免扩大工具回归范围 |
| 发布方式 | 重建平台网关前端镜像 | 不暂停工具任务，不切换配置来源 |

### 4.3 明确不采用的方案

- 不把六项能力做成三列同权重卡片墙；
- 不使用单页锚点代替能力域路由；
- 不在 Tool 表增加 `mission`、`input`、`output` 等字段；
- 不新增 `/workspace/summary` 聚合 API；
- 不让浏览器直接请求工具内部地址；
- 不根据前端权限自行补回服务端未返回的工具；
- 不在 API 失败时使用静态工具 fallback；
- 不为“平台感”统一工具任务状态；
- 不把管理页混入业务工具卡片。

## 5. 总体架构

### 5.1 逻辑架构

```text
浏览器
  │
  ├── React 平台工作台
  │     ├── AuthContext
  │     ├── EnvironmentContext（沿用现有行为）
  │     └── ToolCatalogContext
  │           ├── 已授权工具目录
  │           ├── 工具健康状态
  │           ├── 能力域分组
  │           └── 刷新与错误状态
  │
  ├── /api/v1/tools ----------------------┐
  ├── /api/v1/tools/{id}/health ----------┤
  ├── /api/v1/auth/* ---------------------┤
  └── 现有配置、凭证、审计 API ----------┤
                                           ▼
                                      Platform API
                                           │
                                      PostgreSQL

浏览器通过统一网关直接进入独立工具：
  /functional-test-agent/
  /api-test-agent/
  /api-autotest/
  /trackevents/
  /log-filter/
  /truthy-search/
```

### 5.2 平台与工具边界

平台负责：

- 身份、Session 和权限；
- 能力目录和导航；
- 工具健康探测；
- 环境、配置、Secret、Credential 和审计；
- 平台状态页面和统一错误页；
- 向工具提供平台身份上下文。

工具负责：

- 自己的输入表单；
- 自己的任务创建和任务阶段；
- 自己的执行、分析和生成逻辑；
- 自己的结果、报告和附件；
- 自己的任务数据库或文件存储；
- 自己的发布节奏和故障恢复。

### 5.3 第三阶段数据流

```text
登录成功
  ↓
加载当前用户 /auth/me
  ↓
加载已授权工具 /tools
  ↓
按稳定 Tool ID 合并产品文案
  ↓
按 category 生成可见能力域
  ↓
并行探测可见工具健康状态
  ↓
渲染首页、主导航和能力域页面
  ↓
用户点击入口
  ↓
Nginx 再次鉴权并代理到独立工具
```

任何页面都不得通过前端目录状态替代 Nginx 和 Platform API 的服务端权限校验。

## 6. 信息架构与路由设计

### 6.1 平台路由

新增路由：

| 路径 | 页面 | 访问条件 |
|---|---|---|
| `/` | AI 测试与质量工程工作台 | 已登录 |
| `/ai-testing` | AI 测试能力域 | 至少有一个 `ai-testing` 工具有 `tool.view` |
| `/automation` | 自动化能力域 | `api-autotest` 有 `tool.view` |
| `/quality-analysis` | 质量分析能力域 | 至少有一个 `analysis` 工具有 `tool.view` |
| `/domain-evaluation` | 专项评测能力域 | `truthy-search` 有 `tool.view` |

保留现有路由：

- `/login`；
- `/setup`；
- `/account`；
- `/account/password`；
- `/settings/config`；
- `/settings/secrets`；
- `/settings/credentials`；
- `/admin/users`；
- `/admin/roles`；
- `/audit`；
- `/403`；
- `*` 统一 404。

### 6.2 主导航

能力主导航按以下顺序展示：

```text
工作台 → AI 测试 → 自动化 → 质量分析 → 专项评测
```

规则：

1. “工作台”始终展示；
2. 某能力域没有任何已授权工具时隐藏该导航；
3. 不能依据 `AuthState.tool_permissions` 自行构造工具目录，必须以 `/tools` 返回为准；
4. 管理入口继续根据平台权限展示；
5. 为保持 Figma 的业务导航清晰度，平台管理位于页头右侧管理入口，不与五个业务导航争夺主层级；
6. 当前路由使用 `NavLink` 的 `aria-current="page"` 和底部蓝色指示线；
7. 不展示未实现的“报告中心”“用例管理”或“测试 Agent 市场”。

### 6.3 直接 URL 行为

- 已登录且能力域有可见工具：正常进入；
- 已登录但该能力域无可见工具：显示能力域无权限状态，不列出工具名称和内部信息；
- 未登录：跳转 `/login?next=<当前路径>`；
- Session 过期：现有 API 401 行为继续生效；
- 平台 API 异常：显示平台服务异常，不回退静态工具目录；
- 独立工具 URL：继续由 Nginx `auth_request` 强制校验。

## 7. 能力目录设计

### 7.1 前端产品元数据

新增一个只读 `capabilityCatalog`，以稳定 Tool ID 为键：

```ts
type CapabilityDomainId =
  | "ai-testing"
  | "automation"
  | "quality-analysis"
  | "domain-evaluation";

interface CapabilityDefinition {
  toolId: string;
  domainId: CapabilityDomainId;
  displayName: string;
  mission: string;
  scenario: string;
  inputSummary: string;
  outputSummary: string;
  boundary?: string;
  actionLabel: string;
  visualPriority: "primary" | "standard";
}
```

`capabilityCatalog` 只保存稳定产品文案，不保存：

- 工具健康状态；
- 权限；
- 运行数量；
- Token 或 Secret；
- 工具内部 URL；
- 任务或报告数据。

### 7.2 六项能力定义

| Tool ID | 展示名称 | 使命 | 输入 | 输出 | 行动 |
|---|---|---|---|---|---|
| `functional-test-agent` | 功能测试智能体 | 将需求转化为可 Review、可维护、可导出的测试设计 | 需求文档 | 测试点、测试用例、导出文件 | 生成测试用例 |
| `api-test-agent` | API 测试智能体 | 理解接口契约，设计并执行测试，发现问题并形成证据 | API 文档、环境、数据 | 契约、用例、结果、缺陷草稿 | 开始接口测试 |
| `api-autotest` | 接口自动化 | 将稳定接口沉淀为可重复执行的自动化回归 | 自动化用例、环境、执行配置 | 运行结果、自动化报告 | 执行自动化回归 |
| `trackevents` | 埋点分析 | 验证埋点事件、参数和采集结果是否符合预期 | TrackEvents 日志 | 事件统计、字段校验、结果报告 | 验证埋点数据 |
| `log-filter` | 日志分析 | 从复杂日志中筛选异常并定位问题 | 日志内容或文件 | 过滤结果、异常信息、导出文件 | 分析日志 |
| `truthy-search` | 检索评测 | 对检索结果进行字段对比、质量评估和报告输出 | 评测数据、查询、候选结果 | 字段对比、评测结论、报告 | 开始检索评测 |

### 7.3 运行时合并

前端将后端 `Tool` 与 `CapabilityDefinition` 合并为 `CapabilityViewModel`：

```ts
interface CapabilityViewModel extends CapabilityDefinition {
  tool: Tool;
  health: ToolHealthState;
}
```

合并规则：

1. 以后端 Tool 是否存在作为可见性真源；
2. 使用后端 `entry_url`，不得在产品文案映射中复制入口 URL；
3. 使用后端 `sort_order` 保持稳定顺序；
4. 使用前端定义的使命、输入、输出、边界和行动文案；
5. 未找到产品元数据的已授权工具不崩溃，降级为现有通用 ToolCard 表达并记录开发告警；
6. 前端不得把未返回的 Catalog 项补入页面；
7. `category` 与定义不一致时，以 Catalog 的已确认能力域展示，同时在开发环境输出非敏感告警，便于修复数据。

### 7.4 命名处理

数据库当前的 `trackevents.name` 和 `log-filter.name` 可以保持不变。平台工作台使用产品层展示名称“埋点分析”和“日志分析”，避免为了第三阶段文案修改历史迁移或数据库记录。

管理页、权限矩阵仍可以显示数据库原始工具名称，以免改变现有运维认知。

## 8. 前端状态架构

### 8.1 ToolCatalogContext

新增原生 React Context，统一提供：

```ts
interface ToolCatalogContextValue {
  tools: Tool[];
  capabilities: CapabilityViewModel[];
  groups: Record<CapabilityDomainId, CapabilityViewModel[]>;
  healthStates: Record<string, ToolHealthState>;
  loading: boolean;
  refreshing: boolean;
  error: string | null;
  refreshHealth: () => Promise<void>;
  reloadCatalog: () => Promise<void>;
}
```

### 8.2 Provider 生命周期

1. 未登录时不请求工具目录；
2. 登录完成后请求一次 `/tools`；
3. 目录成功后并行探测当前可见工具健康状态；
4. 路由切换不重复加载工具目录；
5. “重新检测状态”只刷新健康接口；
6. 环境切换不重新请求工具目录，因为平台 dev/prod 不改变当前部署的工具可见性；
7. 用户退出时清空工具目录和健康状态；
8. Session 失效由现有 API 401 行为处理；
9. Provider 卸载时忽略已经返回的过期请求结果；
10. 不在浏览器存储工具目录或健康状态。

### 8.3 请求并发与超时

- 继续使用现有 3 秒前端请求超时；
- 健康探测对可见工具使用 `Promise.all`；
- 单个健康请求失败转换为该工具 `unhealthy`，不使整个目录失败；
- 目录请求失败属于平台级错误，页面停止工具导航；
- 刷新期间保留上一次工具列表；
- 健康状态先标记 `checking`，完成后逐项更新或一次性提交；
- 同一时刻只允许一个用户触发的健康刷新。

### 8.4 状态层级

```text
平台级：认证、工具目录、Platform API
能力域级：是否存在已授权能力
工具级：checking / healthy / unhealthy
管理提醒级：Credential 或配置状态，仅授权用户可见
```

这四类状态不得混用。例如：工具异常不能显示成“平台不可用”，无权限不能显示成“暂无数据”。

## 11. 统一状态设计

### 11.1 工具健康状态

| 内部状态 | 展示文案 | 入口行为 |
|---|---|---|
| `checking` | 正在检测 | 保持入口可用 |
| `healthy` | 服务正常 | 正常进入 |
| `unhealthy` | 服务暂时不可用 | 入口保持可见，进入后使用现有不可用页 |

状态必须同时有文字和非纯颜色标识。

### 11.2 平台加载

- 页头、品牌、账户和管理入口先渲染；
- 首页主要内容使用与最终结构一致的骨架；
- 不使用阻塞全页的无限 Spinner；
- `aria-live="polite"` 报告目录加载完成；
- 骨架本身不进入 Tab 顺序。

### 11.3 平台错误

工具目录失败时显示：

```text
平台身份或数据服务暂时不可用，当前无法读取已授权能力。
```

同时提供：

- 重新加载目录；
- 进入账户页；
- 有权限时进入平台管理。

不显示：

- 静态 fallback 工具；
- 容器地址；
- SQL 或 Python 异常；
- Secret 或 Credential 内容。

### 11.4 能力域为空

区分两类：

1. 目录成功但该域无已授权工具：显示“当前账号没有此能力域的可见工具”；
2. 目录失败：显示平台错误，不显示无权限文案。

### 11.5 403 与会话过期

- 403 页面保留统一工作台返回入口；
- 401 继续跳登录，并保留安全 `next`；
- 登录后返回原能力域路径；
- 不泄露无权工具的任务或结果。

## 14. 权限与安全设计

### 14.1 前端可见性

- 业务导航和卡片由 `/tools` 结果驱动；
- 管理导航由 `AuthState.platform_permissions` 驱动；
- 前端隐藏只改善体验，不构成授权；
- 直接访问工具仍由 Nginx 和 Platform API 校验。

### 14.2 链接安全

- 工具入口只使用后端 `entry_url`；
- 入口必须是同源绝对路径；
- 不允许从前端产品目录注入外部 URL；
- 对未知或非 `/` 开头的入口拒绝渲染并显示配置异常；
- 登录 `next` 继续拒绝 `//` 开头路径。

### 14.3 敏感信息

首页和能力域不得展示：

- Token；
- Refresh Token；
- Session Token；
- Operator ID；
- Secret 值；
- 内部服务地址；
- Credential 失败原始响应。

凭证状态只展示状态、工具、环境、版本、过期时间和脱敏错误码。

### 14.4 失败关闭

- Platform API 不可用：停止能力导航；
- 数据库不可用：不使用静态 fallback；
- 权限计算失败：不显示工具；
- 单个工具不可用：只标记该工具；
- Credential Agent 不可用：不影响无凭证依赖的工具入口，但显示授权用户可见的提醒。

### 17.4 故障注入

| 场景 | 预期 |
|---|---|
| 停止单个工具 | 该工具显示不可用，其他入口正常 |
| 恢复单个工具 | 刷新后恢复正常 |
| 停止 Platform API | 已加载页面不能继续信任旧目录进行新导航；重新加载显示平台错误 |

## 21. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 只换视觉没有改变入口逻辑 | 仍像工具集合 | 用使命、输入、输出和边界重组首页 |
| Catalog 与数据库工具不一致 | 错误分组或缺少文案 | 稳定 ID 合并、未知工具降级、开发告警 |
| 为共享状态大改 App.tsx | 回归范围扩大 | 只提取 ToolCatalogContext 和新增页面组件 |
| 能力域路由泄露无权工具 | 权限信息泄露 | 以 `/tools` 为真源，空域只显示通用无权限文案 |
| 健康请求拖慢首屏 | 首屏延迟 | 目录先渲染，健康并行且不阻断入口 |
| 管理提醒请求失败 | 首页误报 | 权限门控、独立错误、不阻断工具导航 |
| API 测试与自动化被误解为联动 | 用户期待自动迁移 | 明确“使用建议，不传递任务数据” |
| 普通工具被强行 AI 化 | 产品定位失真 | 只有两个 Agent 使用 AI 标签 |
| 工具视觉改造扩大 | 六项目回归风险 | 已满足最低上下文的工具不改代码 |
| 新 SPA 路由被 Nginx 404 | 页面刷新失败 | 发布前逐路由冒烟和 `try_files` 检查 |
| 平台 API 失败后旧页面仍可点工具 | 可能使用过期权限 | 目录级错误停止新导航，不使用持久缓存 |
| 1280px 文案溢出 | 操作入口不可见 | 固定信息层级、限制摘要长度、双尺寸验收 |

## 24. 已锁定结论

1. 第三阶段是平台产品结构升级，不是工具能力扩建；
2. 首页是使命导航，不是统一任务中心；
3. 功能测试智能体与 API 测试智能体继续独立；
4. API 测试智能体与接口自动化只表达使用顺序；
5. 六个工具继续独立运行和独立存储；
6. 平台继续统一身份、权限、配置、Secret、凭证和审计；
7. 第三阶段不新增业务 API 和数据库迁移；
8. 产品文案使用稳定 Tool ID 前端映射；
9. `/tools` 是能力可见性的唯一目录真源；
10. 平台 API 或数据库异常时继续失败关闭；
11. Figma 的演示状态必须替换为真实数据；
12. 桌面 Web 是唯一设计和验收范围；
13. 完成标准是平台能帮助用户快速选择正确能力，而不只是首页更好看。
