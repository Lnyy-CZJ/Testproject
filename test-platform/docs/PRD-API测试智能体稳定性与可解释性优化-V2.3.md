# API 测试智能体稳定性与可解释性优化 PRD

> 文档版本：V2.3
> 文档状态：待评审
> 编制日期：2026-08-20
> 适用产品：API 测试智能体
> 优化范围：任务创建至基础用例生成阶段的稳定性、契约 Evidence 交互、Token 展示、阶段日志和调用成本分析
> 前置文档：`PRD-API测试智能体端到端闭环-V2.0.md`、`PRD-API测试智能体执行前阶段优化-V2.1.md`、`PRD-API测试智能体生成内核融合优化-V2.2.md`

## 1. 文档目的

V2.0～V2.2 已建立接口文档解析、契约 Review、Evidence、融合用例生成、静态门禁、阶段事件和模型用量记录，但本机真实任务暴露出以下问题：

1. 新任务创建成功后，契约版本尚未落盘，页面立即读取 `v0` 版本并显示请求失败；
2. 模型输出枚举值与 Schema 不一致时，一条候选用例会导致整个基础用例生成阶段失败；
3. Evidence 和质量门禁采用内部字段路径与技术术语，测试人员无法理解字段来源、问题类型和处理方式；
4. Token 数据已记录，但输出 Token 与总 Token 合并展示，含义不清；
5. 阶段事件、原始日志和平台审计分散，页面不会在运行期间持续刷新；
6. 缺少按 Attempt、阶段、模型和 Prompt 汇总的调用成本视图。

本 PRD 聚焦解决上述 P0～P2 问题，不重新设计 V2 状态机，不修改真实执行安全边界。

## 2. 问题证据与根因

### 2.1 新任务详情页初始化竞态

真实任务：`task_20260820_4ebe06bcd5dbd3cdd52b`。

真实调用顺序：

1. `POST /api-test-agent/api/v1/tasks` 返回 `202`，任务创建成功；
2. 页面跳转后立即调用 `GET /api-test-agent/api/v1/tasks/{task_id}/contracts`；
3. 契约生成尚未完成，任务记录中契约当前版本为 `0`；
4. 服务尝试读取 `versions/contracts/v0.json`；
5. 文件不存在，接口返回系统错误。

根因不是任务创建失败，而是读取接口没有区分“产物尚未生成”和“产物损坏”。

### 2.2 基础用例生成被单条模型输出阻断

真实模型输出包含：

```json
{
  "scenario_type": "positive"
}
```

`BaseTestCase.scenario_type` 只接受：

- `normal`；
- `negative`；
- `exploratory`。

当前 Prompt 没有明确列出枚举范围，生成适配层也没有归一化常见同义值。Pydantic 校验失败后，异常被映射为 `LLM_RESPONSE_INVALID`，整个阶段失败，已生成的确定性用例无法进入 Review。

同一日志中出现的 `SyntaxWarning: invalid escape sequence` 来自旧 Prompt 的 Windows 路径示例，不是阶段失败主因，但会干扰定位。

### 2.3 Evidence 表达不适合测试人员

真实待处理项：

```text
parameters[0].required
UNGROUNDED_FIELD
```

对应业务含义为：退出登录接口中的请求头 `X-CSRF-Token` 是否必填。

原文明确出现：

- “鉴权：会话 + CSRF”；
- Curl 示例携带 `X-CSRF-Token`。

但原文没有直接写“必填”，因此系统将 `required=true` 识别为 AI 推断，而非明确文档事实。这是“文档待确认”，不是真正的字段冲突。

当前页面存在以下问题：

- 使用英文内部字段路径；
- 将冲突、歧义和缺少依据合并展示；
- 不解释字段由文档、AI 还是人工产生；
- 不展示当前值、原文片段、推断依据和影响；
- 处理动作需要测试人员理解 Evidence 行号、Grounding 和人工覆盖等内部概念。

### 2.4 日志和 Token 数据存在但不可用

真实任务已经记录：

- 文档解析模型调用：输入 3274、输出 4705、总计 7979 Token，耗时 40134ms；
- 基础用例生成模型调用：输入 318、输出 786、总计 1104 Token，耗时 7338ms；
- 文档预检、模型调用、契约 Review、用例生成失败等阶段事件。

但页面存在以下问题：

- 输出 Token 与总 Token 合并为一个值；
- 阶段记录仅初次加载和人工刷新；
- 原始 Runner 日志正常路径几乎没有业务节点输出；
- 阶段事件、原始日志、平台请求日志和审计日志缺少统一关联字段。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 新任务创建后，所有尚未生成的阶段都以正常状态展示，不返回系统异常；
2. 单条 LLM 输出异常不得导致确定性产物和其他合法候选丢失；
3. 测试人员能够用业务语言理解每个待确认字段的来源、依据、影响和处理动作；
4. 输入、输出和总 Token 分开展示，并能追溯到实际模型调用；
5. 任务运行期间能够持续看到真实、脱敏的阶段进度；
6. 建立按 Attempt、阶段、模型和 Prompt 汇总的调用质量和成本分析基础。

### 3.2 非目标

- 不修改 `API_EXECUTION_ENABLED`；
- 不修改 Controller、Executor、受限容器、Egress 或目标凭证；
- 不发送真实目标 API 请求；
- 不恢复旧 CLI 直接执行；
- 不恢复旧 MySQL 默认写入；
- 不实现外部 Bug 提交或稳定资产发布；
- 不引入 WebSocket、消息队列或新的日志平台依赖；
- 不保存完整 Prompt、接口文档、Secret、请求或响应正文到日志。

## 4. 用户与使用场景

| 用户 | 核心诉求 | V2.3 提供的能力 |
| --- | --- | --- |
| 测试人员 | 看懂字段为何待确认并快速作出决定 | 业务化字段、来源标签、原文对照和向导式操作 |
| 测试开发 | 定位解析、生成和门禁失败原因 | 阶段记录、错误码、输入输出版本和调用详情 |
| 管理员 | 查看稳定性、模型消耗和异常趋势 | Attempt/阶段/模型/Prompt 汇总 |
| 只读人员 | 查看脱敏任务结果 | 只读 Evidence、事件和 Token 摘要 |

管理员、测试开发和测试人员沿用现有契约 Review 权限；只读角色不得修改字段或解决问题。

## 5. 优化后的用户流程

1. 用户创建 API 测试任务；
2. 页面进入任务详情，显示“正在分析接口文档”；
3. 文档预检、解析和质量门禁事件自动更新；
4. 契约版本生成后进入“接口信息确认”；
5. 测试人员处理“文档待确认、字段冲突、AI 建议”；
6. 契约确认后生成基础用例；
7. 模型单条异常被隔离，合法用例正常进入 Review；
8. 页面显示生成结果、拒绝条目、Token 和阶段记录；
9. 后续继续沿用 V2.2 的基础用例 Review、执行定义和受控执行门禁。

## 6. P0：契约未生成状态稳定化

### 6.1 稳定响应

`GET /api-test-agent/api/v1/tasks/{task_id}/contracts` 在没有契约版本时不得读取 `v0.json`，统一返回：

```json
{
  "stage_state": "generating",
  "version": 0,
  "sha256": "",
  "items": [],
  "task_status": "running"
}
```

`stage_state` 允许值：

| 状态 | 含义 |
| --- | --- |
| `not_generated` | 尚未开始生成 |
| `generating` | 当前 Attempt 正在生成 |
| `ready` | 当前契约版本可查看 |
| `failed` | 当前 Attempt 失败，上游产物仍可查看 |
| `stale` | 契约来自旧文档或旧范围 |

### 6.2 错误语义

- 尚未生成属于正常状态，返回 `200`；
- 指定不存在的正整数版本，返回 `404 CONTRACT_VERSION_NOT_FOUND`；
- 当前版本文件存在但 SHA 或 JSON 损坏，返回 `500 CONTRACT_VERSION_CORRUPTED`；
- 平台配置服务不可用才允许返回 `503 PLATFORM_CONFIG_UNAVAILABLE`；
- 前端不得把正常门禁或生成中状态显示为“请求失败”。

### 6.3 页面要求

- 显示当前节点、已耗时和“无需重复创建任务”；
- 契约未生成前隐藏字段编辑和确认操作；
- 页面轮询任务状态，不轮询不存在的具体版本文件；
- 契约生成完成后自动刷新当前工作区；
- 任务失败时显示稳定错误码和“从失败阶段重试”。

### 6.4 验收标准

- 新任务创建后 0～60 秒内反复刷新，不出现 500/503；
- `/contracts` 在契约尚未生成时始终返回 `200 + generating`；
- 契约落盘后无需用户刷新整页即可切换到 `ready`；
- 版本损坏与尚未生成能够被自动化测试区分。

## 7. P0：模型枚举归一化与输出契约

### 7.1 Prompt 输出约束

V2 基础用例 Prompt 必须明确说明：

```text
scenario_type 只能输出 normal、negative、exploratory。
normal：正常或正向场景。
negative：错误输入、缺失、越权或异常场景。
exploratory：文档无法支持确定预期，只记录观察目标。
```

Prompt 必须附带最小合法 JSON 示例，并继续禁止引入契约外业务域。

### 7.2 归一化规则

在进入 Pydantic Schema 前执行确定性归一化：

| 模型输出 | 归一化结果 |
| --- | --- |
| `positive`、`success`、`valid`、`happy_path` | `normal` |
| `abnormal`、`invalid`、`error`、`failure` | `negative` |
| `exploration`、`observe`、`unknown_expectation` | `exploratory` |

规则要求：

- 大小写不敏感；
- 去除首尾空白；
- 未知值不得静默归为正常场景；
- 未知值转换为 `exploratory` 时必须增加质量警告；
- 缺少观察目标时仍需拒绝该条用例。

### 7.3 Prompt 警告清理

- Prompt 中 Windows 路径使用 raw string 或正确转义；
- 启动和测试期间不得再出现 `invalid escape sequence`；
- 警告清理不得改变旧 CLI Prompt 的业务含义和导入路径。

### 7.4 验收标准

- 固定回放 `scenario_type=positive` 时成功归一化为 `normal`；
- `positive` 用例通过其他门禁后可进入 `confirmed_candidate`；
- 未知枚举值不会触发整个阶段异常；
- Prompt SHA 随 V2 Prompt 修改产生新值，旧 Prompt 快照保持兼容；
- Python 启动和测试日志不存在该转义警告。

## 8. P0：单条 LLM 输出隔离与部分成功

### 8.1 单条校验

模型返回数组后，系统逐条执行：

1. JSON 对象校验；
2. 枚举归一化；
3. `BaseTestCase` Schema 校验；
4. Evidence 和 Grounding 校验；
5. 完整性校验；
6. 去重。

任一条失败只拒绝当前条目，不得中断其他条目和确定性用例。

### 8.2 失败记录

拒绝条目保存脱敏摘要：

- Attempt ID；
- Contract ID；
- 模型调用 ID；
- 条目序号；
- Prompt ID 和 SHA；
- 错误码和字段路径；
- 拒绝阶段；
- 修复建议。

不得保存完整 Prompt、完整原始模型输出或 Secret。

### 8.3 阶段终态

| 结果 | 阶段状态 |
| --- | --- |
| 确定性和合法 LLM 用例全部保存 | `waiting_case_review` |
| 部分 LLM 条目被拒绝，但仍有合法用例 | `partial_success` 或带警告的 `waiting_case_review` |
| 模型全部不可用，但确定性用例完整 | `waiting_case_review`，标记 AI 补充失败 |
| 无任何合法用例且确定性生成失败 | `failed` |

LLM 补充失败不得删除契约、覆盖矩阵骨架或已经生成的确定性用例。

### 8.4 用户操作

- 页面显示“生成 N 条、拒绝 M 条”；
- 可查看每条拒绝原因和关联接口；
- 支持仅重试 AI 补充，不重复确定性阶段；
- 重试创建新 Attempt，不覆盖旧结果；
- 不允许用户直接确认未通过 Schema 或 Grounding 的条目。

### 8.5 验收标准

- 一个数组中包含 9 条合法和 1 条非法候选时，9 条正常保存；
- 单条 `scenario_type`、steps 或 expected_results 错误不导致全阶段失败；
- LLM 调用失败时确定性用例仍可 Review；
- 部分成功保留错误码、调用 ID和输入版本；
- 当前真实失败任务可以从 `base_case_generation` 重试，无需重新创建或重新解析文档。

## 9. P1：Evidence 产品化

### 9.1 产品术语

默认界面使用以下中文术语：

| 内部术语 | 测试人员界面 |
| --- | --- |
| Evidence | 文档依据 |
| Grounding | 依据校验 |
| `UNGROUNDED_FIELD` | 文档未明确说明 |
| `parameters[0].required` | 请求头 X-CSRF-Token 是否必填 |
| `human_override` | 人工确认 |
| `bind_evidence` | 关联原文 |

内部错误码和字段路径放入“技术详情”，默认折叠。

### 9.2 问题分类

待处理项分为三个互斥分组：

1. **字段冲突**：文档不同位置或确定性解析与模型结果不一致；
2. **文档待确认**：存在字段值，但原文没有明确说明；
3. **AI 建议**：不属于契约事实，只作为测试设计建议。

不得继续使用一个“冲突与未解决项”列表混合展示。

### 9.3 字段卡片

每个待确认字段必须展示：

- 业务化字段名称；
- 所属接口、method 和 path；
- 当前值；
- 来源标签：文档明确、OpenAPI、AI 推断、人工确认；
- 原文行号和原文片段；
- AI 推断理由；
- 影响：会影响哪些契约、覆盖项或用例；
- 推荐操作；
- 技术详情。

### 9.4 处理动作

针对“请求头 X-CSRF-Token 是否必填”提供：

- 确认必填；
- 确认非必填；
- 关联原文；
- 修改接口文档并重新分析；
- 删除 AI 推断；
- 转为测试建议。

人工确认必须填写原因，生成新契约版本并重新执行质量门禁。

### 9.5 原文联动

- 点击文档依据后打开原始文档并定位到对应行；
- JSON/YAML/OpenAPI 定位到 JSON Pointer；
- 绑定原文时显示所选片段预览；
- 当前字段允许绑定多个互补片段；
- 不得把无关的默认首行保存为 Evidence；
- 行号失效时标记旧 Evidence 为 stale，不静默重定位。

### 9.6 高级模式

默认模式面向测试人员；高级模式提供：

- 内部字段路径；
- Evidence 类型和置信度；
- Issue ID；
- 文档版本和 SHA；
- 契约版本和审计记录。

### 9.7 验收标准

- 测试人员无需理解 JSON Path 即可处理 `parameters[0].required`；
- 页面明确说明该字段来自 AI 推断，而参数本身来自 Curl 原文；
- “文档待确认”不显示为“字段冲突”；
- 每次处理均生成新版本和审计记录；
- blocker 未处理时仍不能确认契约；
- 键盘和屏幕阅读器能够识别分类、当前值、来源和操作。

## 10. P1：Token 展示拆分

### 10.1 摘要卡片

模型用量区域固定显示：

- 模型调用次数；
- 输入 Token；
- 输出 Token；
- 总 Token；
- Token 未报告调用数。

输入、输出和总 Token 必须使用三个独立卡片，不使用 `输出 / 总 Token` 合并格式。

### 10.2 调用明细

每次模型调用展示：

- 阶段和节点；
- Prompt ID、版本和短 SHA；
- 模型名称；
- 输入、输出、总 Token；
- 耗时；
- 重试次数；
- 成功、失败或拒绝状态。

供应商未返回 usage 时显示“未报告”，所有 Token 数值保持 0，不进行估算。

### 10.3 汇总口径

- 总 Token = 输入 Token + 输出 Token，仅对供应商已报告记录求和；
- Attempt 汇总不跨 Attempt 混算；
- 任务汇总明确包含的 Attempt 范围；
- 重试调用计入实际消耗；
- 被 Grounding 拒绝的模型输出仍计入模型消耗。

### 10.4 验收标准

- 3274、4705、7979 分别显示在三个卡片中；
- 页面明细和 `model-usage.json` 汇总一致；
- 未报告 usage 不影响其他调用汇总；
- Token 页面和下载内容不包含 Prompt 正文。

## 11. P1：统一结构化日志与阶段自动刷新

### 11.1 三层记录

V2.3 采用三层而非重复记录所有正文：

1. **阶段记录**：面向测试人员，描述正在做什么、结果和下一步；
2. **结构化应用日志**：面向测试开发和运维，定位请求、节点和异常；
3. **审计记录**：记录人员修改、确认和权限相关动作。

原始 Runner 日志作为二级技术入口，不替代阶段记录。

### 11.2 统一字段

结构化日志至少包含：

```text
timestamp
level
request_id
task_id
attempt_id
run_id
stage
node
event
status
duration_ms
error_code
model_call_id
input_versions
output_versions
```

不适用字段允许为空，不得使用空字符串伪造 ID。

### 11.3 必须打点的节点

- 任务创建、入队、取出和取消；
- 文档读取、格式识别、切片和预检；
- 模型调用开始、完成、失败和重试；
- 契约生成数量、Evidence 门禁和 blocker 数量；
- 契约 Review 和版本切换；
- 覆盖骨架、补齐轮次、用例去重和拒绝；
- 基础用例版本保存；
- 执行定义生成和静态校验；
- Run 创建、取消、超时、报告和回收；
- 本地 Bug 草稿生成、编辑和下载；
- 503、未处理异常和数据损坏。

### 11.4 页面自动刷新

- 任务为 `pending/running` 时每 2～3 秒读取增量阶段事件；
- 使用 cursor 只读取新事件；
- 页面隐藏时降低刷新频率；
- 进入 Review 或终态后执行最后一次刷新并停止；
- 用户可以手动刷新；
- 不引入虚假百分比；
- 不因日志接口失败中断主流程。

### 11.5 日志安全

禁止记录：

- 完整接口文档；
- 完整 Prompt 和模型原始输出；
- Authorization、Cookie、Session、CSRF、API Key；
- 完整请求与响应正文；
- 平台 Client Token、Controller Token、KEK 和数据库凭证；
- 未脱敏异常对象或宿主绝对路径。

所有阶段消息和技术日志在存储前脱敏。

### 11.6 验收标准

- 任务运行期间无需手动刷新即可看到新事件；
- 每个阶段都有 started/completed/failed 事件；
- 从页面错误可使用 request_id 关联服务日志；
- 当前 `scenario_type` 失败可定位到 Attempt、节点、模型调用和字段；
- 阶段事件缺失或损坏不影响任务主产物；
- Secret 负向测试覆盖事件、应用日志和下载。

## 12. P2：调用质量与成本分析

### 12.1 分析维度

支持按以下维度聚合：

- 时间范围；
- 项目和模块；
- Attempt；
- 阶段和节点；
- 模型；
- Prompt ID 和版本；
- 成功、失败、重试、拒绝；
- 生成内核。

### 12.2 指标

- 调用次数；
- 输入、输出和总 Token；
- 平均与最大耗时；
- 重试率；
- 输出 Schema 失败率；
- Grounding 拒绝率；
- 每个有效契约和有效用例的 Token；
- 部分成功率；
- 未报告 usage 比例。

### 12.3 成本

- P2 可配置模型单价版本；
- 成本只基于供应商已报告 Token 计算；
- 单价变更不得改写历史口径；
- 页面同时展示 Token 和估算成本，并标记币种、单价版本和估算状态；
- 未配置价格时只展示 Token，不显示 0 元成本。

### 12.4 数据保留

- P0/P1 继续使用 Attempt 下的不可变文件；
- P2 是否同步至 PostgreSQL 元数据表另行开发设计评审；
- 聚合数据不得包含接口文档、Prompt 正文或请求响应内容；
- 原始任务文件仍为生成产物权威来源，不因聚合失败丢失。

### 12.5 验收标准

- 管理员可查看任一 Attempt 的阶段和模型消耗；
- 汇总结果与原始 `model-usage.json` 一致；
- 重试 Token 被正确计入；
- 未报告用量不会被估算；
- 成本分析不可查看其他无权限项目的明细。

## 14. 数据与版本约定

### 14.1 阶段事件

继续保存：

```text
attempts/{attempt_id}/events.jsonl
```

单条损坏事件跳过并记录内部告警，不影响其他事件读取。

### 14.2 模型用量

继续保存：

```text
attempts/{attempt_id}/model-usage.json
```

每条记录必须绑定 call_id、Attempt、阶段、节点、Prompt SHA、模型、Token、耗时和状态。

### 14.3 生成拒绝记录

新增或扩展生成来源产物，保存逐条拒绝摘要，不保存原始敏感输出。拒绝记录必须绑定模型调用 ID，支持从页面定位到阶段事件。

### 14.4 兼容

- 历史任务缺少阶段事件和 Token 时只读显示“历史版本未记录”；
- 不回写历史文件；
- 新 Attempt 使用 V2.3 规则；
- 历史 Run、报告和 Bug 草稿不因 V2.3 回滚被删除。

## 15. 稳定错误码

| 错误码 | HTTP | 含义 | 用户动作 |
| --- | ---: | --- | --- |
| `CONTRACT_VERSION_NOT_FOUND` | 404 | 指定契约版本不存在 | 返回当前版本或重新分析 |
| `CONTRACT_VERSION_CORRUPTED` | 500 | 契约文件损坏或 SHA 不一致 | 从最近有效版本恢复或重试阶段 |
| `CASE_ENUM_NORMALIZED` | 非阻断 | 模型枚举已归一化 | Review 时查看来源 |
| `CASE_PROMPT_ITEM_INVALID` | 非阻断/422 | 单条模型候选格式错误 | 查看拒绝原因或重试 AI 补充 |
| `CASE_GENERATION_PARTIAL` | 非阻断 | 部分候选被拒绝 | Review 已生成用例 |
| `LLM_RESPONSE_INVALID` | 422 | 整体响应无法解析且无合法候选 | 重试模型阶段 |
| `MODEL_USAGE_UNAVAILABLE` | 200/提示 | 供应商未报告 Token | 查看调用结果，不估算 Token |
| `STAGE_EVENT_QUERY_INVALID` | 422 | 阶段记录查询参数不合法 | 修正筛选条件 |
| `PLATFORM_CONFIG_UNAVAILABLE` | 503 | 平台配置服务不可用 | 稍后重试 |

生成中、未生成、Review 门禁和部分成功不得映射为 503。

## 16. 非功能要求

### 16.1 可靠性

- 任一后续阶段失败不得删除上游版本；
- 文件写入继续使用临时文件、fsync 和原子替换；
- 单条模型输出失败不得扩大为阶段失败；
- 页面日志失败不得影响任务状态；
- 失败重试创建新 Attempt。

### 16.2 性能

- 阶段事件增量接口默认返回不超过 100 条，最大 500 条；
- 自动刷新只读取 cursor 后的新事件；
- 契约空状态响应不访问不存在文件；
- Token 汇总单个 Attempt 应在 500ms 内返回。

### 16.3 安全

- 所有新接口执行 RBAC、任务所有权和项目作用域检查；
- 所有写操作要求 CSRF、版本和修改理由；
- 日志、事件和用量下载前再次脱敏；
- Prompt 注入不能修改枚举白名单、契约、目标 Host 或执行权限。

### 16.4 可用性和无障碍

- 状态不能只依赖颜色；
- 自动刷新区域使用适度的 `aria-live`，避免逐条打断屏幕阅读器；
- 键盘可打开字段详情、选择处理动作并返回原焦点；
- 内部术语提供中文解释；
- reduced motion 下不使用持续动画。

- 不通过删除任务文件、历史 Run 或 Bug 草稿回滚；
- 不修改真实执行开关、目标登记和容器配置。

### 20.3 P2 指标

## 21. 已确认决策与风险

| 项目 | 决策 |
| --- | --- |
| 契约未生成如何返回 | 200 + 明确阶段状态，不返回 503 |
| 模型同义枚举如何处理 | 白名单确定性归一化，未知值不得静默变为 normal |
| 单条候选失败如何处理 | 单条隔离，保留确定性和其他合法产物 |
| Evidence 是否保留 | 保留底层追溯能力，默认界面改为测试人员语言 |
| 日志是否建设统一系统 | 使用标准结构化日志和现有 StageEvent，不引入大型依赖 |
| 是否实时展示日志 | 采用增量轮询，不引入 WebSocket 和虚假进度 |
| Token 是否估算 | 不估算；供应商未报告时明确标记 |
| P2 是否立即迁移数据库 | 不在本 PRD 中决定，另行开发设计评审 |
| 是否影响真实执行 | 不影响，不修改执行开关、容器、Egress 和凭证 |

主要风险：

1. 过度归一化可能掩盖模型质量问题，因此必须同时记录原值和归一化原因；
2. 自动刷新可能产生额外请求，因此必须使用 cursor、页面可见性和终态停止；
3. 业务字段名称映射可能不完整，因此必须保留高级技术详情；
4. P2 成本依赖准确单价和供应商 usage，因此估算必须带版本和可靠性标记。

## 22. 最终产品结论

V2.3 的目标不是降低契约质量要求，而是让系统在模型输出不稳定时仍能保住确定性产物，并让测试人员真正理解和处理质量门禁。

最终原则为：

> 生成中不是错误；单条模型错误不能拖垮整个阶段；文档依据必须可解释；日志和 Token 必须真实、分层且可追溯。
