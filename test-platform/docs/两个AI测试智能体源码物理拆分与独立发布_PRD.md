## 1. 执行文案

当前两个智能体虽然已经以两个服务运行，但源码、公共运行时、Docker 构建上下文、测试和部分开发依赖仍集中在 `AItestcase_Agents`。这会导致一个智能体的代码变更进入另一个智能体的镜像构建范围，公共模块修改需要同时承担两边回归风险，也无法真正做到独立版本、独立发布和独立回滚。

本项目将现有源码拆分为两个完全自包含的工程目录：

```text
/Users/admin/Testproject/functional-test-agent
/Users/admin/Testproject/api-test-agent
```

拆分后：

- 功能测试智能体只包含需求拆解、测试点、功能用例、在线 Review、AI Review 和自身任务运行时；
- API 测试智能体只包含 API 契约解析、用例生成、Review、执行、报告、缺陷草稿及其 Controller、Egress、Executor；
- 两个目录不允许通过相对路径、`PYTHONPATH`、符号链接、可编辑安装或源码挂载引用对方或旧目录；
- 每个项目拥有独立依赖锁、测试、镜像、版本号、变更记录、发布流程、Secret、任务数据和回滚入口；
- 测试开发平台只通过稳定 HTTP 契约和版本化镜像接入，不再作为两个项目的源码构建器；
- 旧 `AItestcase_Agents` 在迁移期冻结并保留回滚能力，确认两个独立项目稳定后再归档，不删除历史 `output/` 和任务数据。

本次选择“消除共享源码依赖、两个项目各自拥有完整实现”，不在首期创建第三个公共运行时仓库。该方案会保留少量经过裁剪的公共代码副本，但换取真正独立的开发、构建、发布和故障边界。

## 2. 背景与问题

### 2.1 当前实现

当前 `AItestcase_Agents` 同时包含：

| 区域 | 当前内容 |
|---|---|
| `agents/functional_test` | 功能测试工作流、Prompt 和模型 |
| `agents/api_test` | API 解析、生成、覆盖和可执行用例 |
| `services/common` | 两边共享的任务、配置、页面、Review、文件和安全能力 |
| `services/functional_agent` | 功能 Web、Runner、Adapter 和两级 Review AI |
| `services/api_agent` | API Web、Runner、Review、执行和缺陷草稿 |
| `services/execution_controller` | API 真实执行 Controller |
| `services/egress_proxy` | API 执行出口代理 |
| `executor` | API 单 Run 执行器 |

当前平台 Compose 中，功能镜像、API 镜像及 API 执行相关镜像均使用同一个 `../AItestcase_Agents` 构建上下文。两个服务虽然运行时隔离，但源码和构建边界没有完全隔离。

### 2.2 主要问题

1. 修改 `services/common` 会同时影响两个智能体，回归和发布边界不清晰；
2. 功能服务镜像构建上下文能够看到 API 源码，API 镜像也能够看到功能源码；
3. 两个智能体不能使用真正独立的 Git 历史、版本和发布节奏；
4. 回滚一个智能体时容易依赖同一源码基线中的公共模块版本；
5. API 真实执行具有更高安全等级，不应与功能生成源码处于同一工程边界；
6. 新增功能 Review 页面继续扩大 `services/common`，共享目录正在成为耦合点；
7. 平台生产部署仍包含本地源码路径和构建上下文，不利于不可变镜像发布。

### 2.3 拆分条件

原独立接入 PRD 约定满足多数条件后启动物理拆分。目前已满足：

- 两个服务具备独立 URL、端口、配置、Secret、数据目录和运行状态；
- 功能与 API 的产品能力、依赖和发布节奏已经明显不同；
- API 已增加 Controller、Egress Proxy 和 Executor 安全组件；
- 两边已有独立依赖锁和 Dockerfile；
- 公共代码的功能专属/API 专属边界已经可以识别；
- 用户已明确接受两个目录独立开发和操作。

因此，本 PRD 正式启动 POOL-017，并将 POOL-003 的独立生产发布作为目标结果。

## 3. 产品目标与成功标准

### 3.1 总体目标

把两个智能体从“同仓双服务”升级为“两个独立产品工程”，实现源码、依赖、构建、版本、发布、运行数据、安全权限和故障的完整隔离。

### 3.2 成功标准

1. 两个新目录均可在不读取旧仓库和兄弟目录源码的情况下完成安装、测试和镜像构建；
2. 功能智能体变更只触发功能项目测试和镜像发布，不重建 API 镜像；
3. API 智能体变更只触发 API 项目及执行组件测试和镜像发布，不重建功能镜像；
4. 两个项目使用独立版本号、依赖锁、镜像标签、发布记录和回滚版本；
5. 平台生产 Compose 只引用不可变镜像，不再使用 `context: ../AItestcase_Agents`；
6. 两个项目不共享源码目录、虚拟环境、`.env`、Secret、Client Token、任务目录或产物目录；
7. 停止、升级或回滚任一智能体不影响另一个智能体；
8. 拆分前后 HTTP API、Prompt 语义、任务状态、Review Schema、产物字段和黄金样例保持兼容；
9. API 执行安全边界不得因拆分而降低，生产执行仍遵循现有禁止决策；
10. 历史 `output/` 不迁移、不删除，现有任务数据可回退读取；
11. 两个项目分别通过完整自动化、镜像、安全和浏览器验收；
12. 旧目录经过至少两个稳定发布窗口后才进入只读归档。

### 3.3 量化指标

| 指标 | 目标 |
|---|---:|
| 跨项目源码 import | 0 |
| 兄弟目录源码挂载/符号链接 | 0 |
| 一个项目变更导致另一个项目镜像重建 | 0 |
| 拆分后黄金样例关键字段差异 | 0 |
| Secret/任务数据交叉挂载 | 0 |
| 独立回滚成功率 | 100% |
| 拆分引入的权限和数据隔离回归 | 0 |

## 4. 范围与非目标

### 4.1 本期范围

- 创建功能测试智能体独立工程目录；
- 创建 API 测试智能体独立工程目录；
- 分配和裁剪现有源码、Prompt、模板、静态资源和测试；
- 让两个项目各自拥有必要的任务运行时实现；
- 拆分依赖锁、Docker 构建上下文、镜像和版本；
- API 项目内保留 Web、Controller、Egress Proxy 和 Executor；
- 拆分本地开发命令、测试命令和启动/停止方式；
- 平台 Compose/Nginx/配置改为引用独立发布物；
- 迁移当前任务数据或提供旧任务只读兼容；
- 建立独立发布、灰度、回滚和故障隔离流程；
- 完成拆分前后功能、接口、产物和安全回归；
- 冻结并最终归档旧 `AItestcase_Agents`。

### 4.2 明确非目标

- 不重写两个智能体的 LangGraph、Prompt 或核心生成算法；
- 不同时重构任务状态机、Review 产品逻辑或 UI 视觉；

- 不创建第三个共享运行时仓库或内部公共包；
- 不开放 API 生产真实执行或扩大目标网络范围；
- 不迁移历史 `AItestcase_Agents/output/`；
- 不合并两个智能体的数据库、Secret、任务数据或发布流程；
- 不在本期建设统一任务中心、资产库或对象存储；
- 不要求两个项目使用相同依赖版本；
- 不删除旧仓库或历史任务数据。

## 5. 关键产品决策

### 5.1 两个自包含目录

目标目录固定为：

```text
/Users/admin/Testproject/functional-test-agent
/Users/admin/Testproject/api-test-agent
```

每个目录必须是完整构建上下文，可单独复制到干净环境执行测试和构建。

### 5.2 独立 Git 与版本

- 两个目录按独立 Git 仓库管理；远程仓库地址在实施前确认；
- 不使用 Git submodule 作为运行时依赖；
- 两个项目分别维护版本号和变更记录；
- 功能项目建议版本前缀 `functional-agent-vX.Y.Z`；
- API 项目建议版本前缀 `api-agent-vX.Y.Z`；
- 平台记录并展示各自 `APP_REVISION`，不再使用同一 Revision 代表两个服务。

### 5.3 不共享源码

首期采用原 PRD 允许的第二种方式：消除共享依赖，使两个工程分别拥有完整但独立的运行时实现。

禁止：

- `from ../AItestcase_Agents ...` 或跨项目 Python import；
- 设置 `PYTHONPATH` 指向旧目录或兄弟目录；
- 通过符号链接复用 `services/common`；
- 通过 Docker bind mount 把另一个项目源码挂入容器；
- 使用 editable install 引用本地兄弟项目；
- 平台生产构建使用父目录作为 Docker context。

允许：

- 在拆分基线一次性复制并裁剪必要公共代码；
- 拆分后由各项目独立维护自己的任务运行时；
- 使用相同的 HTTP/JSON 契约，但实现和发布互不依赖；
- 后续另行评审是否提取稳定的版本化公共 SDK。

### 5.4 API 作为一个独立发布包

API 项目包含多个镜像，但对外是一个版本化发布单元：

- `api-test-agent`；
- `api-execution-controller`；
- `api-egress-proxy`；
- `api-test-executor`。

四个镜像使用同一 API 项目 Release 版本和兼容矩阵。默认发布仍不启用 S2 Profile；真实执行开关和生产禁止规则保持不变。

### 5.5 平台只消费发布物

- dev 可使用独立项目构建的本地镜像；
- prod 只引用镜像仓库中的不可变 tag/digest；
- 平台不复制两个项目源码，也不承担它们的依赖安装；
- 平台只维护工具注册、权限、配置、Secret、网关路由和镜像版本引用；
- 平台升级不应强制两个智能体同步升级。

## 6. 目标目录边界

### 6.1 功能测试智能体

建议目标结构：

```text
functional-test-agent/
├── src/
│   ├── functional_agent/       # Web、Runner、Adapter
│   ├── functional_workflows/   # 需求、测试点、用例工作流
│   └── runtime/                # 功能项目自有任务/文件/权限实现
├── templates/
├── static/
├── prompts/
├── tests/
├── Dockerfile
├── requirements.lock
├── pyproject.toml
├── .dockerignore
└── README.md
```

功能项目必须拥有：

- 需求拆解、测试点生成、测试用例生成；
- 测试点 Review、测试用例 Review 和两类 AI Review；
- 功能任务 FIFO、任务存储、上传、产物、审计和平台 Client；
- 功能工作台模板和静态资源；
- 功能 CLI 兼容入口；
- 功能专属测试和镜像。

功能项目不得包含：

- API 契约/用例模型；
- MySQL API 用例持久化逻辑；
- API Controller、Docker SDK、Egress 和 Executor；
- API 执行目标或 Controller Token。

建议目标结构：

```text
api-test-agent/
├── src/
│   ├── api_agent/              # Web、Runner、Review、报告和缺陷草稿
│   ├── api_workflows/          # 契约、覆盖、基础/可执行用例
│   ├── runtime/                # API 项目自有任务/文件/权限实现

│   ├── egress_proxy/
│   └── executor/

├── static/

├── Dockerfile.executor
├── requirements-agent.lock
├── requirements-controller.lock
├── pyproject.toml
├── .dockerignore
└── README.md
```

API 项目必须拥有：

- API 文档解析、契约 Review、覆盖、用例 Review 和可执行用例；
- API 任务运行时、报告、缺陷草稿和可选数据库持久化；
- Controller、Egress Proxy、Executor 和安全策略；
- API 工作台模板和静态资源；
- API CLI 兼容入口；
- API 全部单元、契约、安全、容器和集成测试。

API 项目不得包含：

- 功能需求拆解和功能用例工作流；
- 测试点/功能用例 Review 页面和 Prompt；
- 功能智能体 LLM Secret、Client Token 或任务目录；
- 功能智能体镜像构建文件。

## 7. 功能需求

### FR-01 独立安装与测试

每个项目必须提供自己的安装、测试和静态检查命令。在一个只包含该项目源码的干净目录中，命令必须成功，不得读取父目录或兄弟目录。

### FR-02 独立构建

- 每个镜像的 Docker context 必须位于所属项目根目录；
- 功能镜像中不得出现 API 源码、Prompt 或执行组件；
- API 镜像中不得出现功能工作流、Review 页面或 Prompt；
- `.dockerignore` 必须排除 `.git`、Secret、`.env`、runtime、output、缓存和本地测试产物；
- 构建必须使用锁定依赖。

### FR-03 独立启动和停止

两个项目分别提供标准操作：

```text
test
build
up
down
smoke
```

具体使用 Makefile、脚本或 Compose 命令由详细设计决定，但命令语义必须一致。停止功能项目不得停止 API 项目及其执行组件；停止 API 项目不得影响功能任务。

### FR-04 独立发布

- 每个项目独立生成版本、镜像、SBOM、测试结果和发布说明；
- 一个项目发布失败不得阻塞另一个项目继续使用当前版本；
- 平台可分别升级两个工具镜像版本；
- API 四个镜像必须按同一 API Release 发布，禁止混用未经验证的版本组合；
- 发布物必须记录源码 Revision、构建时间和依赖锁摘要。

### FR-05 独立配置与 Secret

功能项目只读取功能配置和 Secret；API 项目只读取 API 配置和 Secret。两个项目必须使用不同：

- Platform Client Token；
- LLM API Key；
- 配置 Release；
- 任务数据根；
- Secret 文件目录；
- API Controller Token（仅 API）；
- API 数据库 Credential（仅 API 且开关开启时）；
- 执行目标登记（仅 API）。

### FR-06 独立任务与产物

目标数据目录：

```text
runtime/<environment>/functional-test-agent/
runtime/<environment>/api-test-agent/
```

两个服务不得挂载对方目录。任务 ID、日志、输入、Review、Run、报告和产物均在所属项目目录内完成 containment 校验。

### FR-07 平台契约兼容

拆分后继续兼容：

- `/functional-test-agent/` 和 `/api-test-agent/`；
- 现有 `/api/v1/tasks`、日志、产物、Review、Run 和缺陷草稿接口；
- 平台可信身份头、CSRF、RBAC、所有权和错误响应；
- Prompt/模型/Release/Revision 展示；
- Nginx 现有 auth_request 和路径前缀；
- 健康检查和 readiness 语义。

如确需改变接口，必须先增加版本并完成平台兼容期，不能在目录迁移中顺便修改。

### FR-08 Prompt、Schema 和产物兼容

- 不修改现有 Prompt 文本和默认模型行为；
- 保持测试点、功能用例、API 契约、基础用例和可执行用例 Schema；
- 保持 Review 草稿、确认版本和 artifact 类型；
- 保持 JSON/XLSX、报告和缺陷草稿关键字段；
- 使用黄金输入比较拆分前后结构和统计；
- 非确定性 LLM 文本允许差异，但 Schema、硬门禁和必要字段必须一致。

### FR-09 旧任务兼容

切换前暂停新任务并等待 `running` 任务完成。对其余任务采用以下策略：

- 终态任务：迁移任务目录并校验 SHA，或由旧服务提供只读历史入口；
- `waiting_review`/`waiting_case_review`：必须保留草稿、确认版本和继续操作能力；
- `pending`：切换前暂停接收，原则上清空队列；确需迁移时按原 FIFO 时间恢复；
- `running`：禁止迁移，必须等待结束或按现有规则取消；
- API Run：终态报告只读迁移，运行中 Run 必须结束并确认没有残留 Executor；
- 历史 `output/`：不迁移、不清理。

### FR-10 旧目录冻结与归档

- 新目录进入开发后，旧 `AItestcase_Agents` 只接受迁移阻断修复；
- 切换完成后禁止继续在旧目录开发新功能；
- 至少经过两个独立 Release 和约定回滚窗口后，旧目录标记只读归档；
- 归档前保存拆分基线 tag、目录映射、镜像 digest 和数据校验清单；
- 未经单独批准不得删除旧目录或历史数据。

## 8. 非功能与安全要求

### 8.1 隔离

- 两个项目构建时不能读取父目录；
- 容器只挂载自己的数据和 Secret；
- 功能容器不得访问 Docker Socket、API Controller 或执行网络；
- API Executor 不得获得平台、LLM、数据库或功能项目 Secret；
- dev/prod 继续严格隔离；
- 一个项目的异常、磁盘写满或队列满不得改变另一个项目状态。

### 8.2 性能

拆分不能导致核心任务执行时间较基线显著回退。建议门禁：

- 页面和短 API P95 不劣化超过 10%；
- 相同黄金输入的非 LLM 文件处理耗时不劣化超过 10%；
- 镜像体积应因裁剪无关源码和依赖而下降，至少不得上升超过 10%；
- 单槽 FIFO、上传限制和任务超时默认值保持不变。

### 8.3 可维护性

- 每个项目 README 能独立指导安装、测试、构建、配置、启动、发布和回滚；
- 每个项目只维护自己的依赖；
- 公共代码复制清单必须有来源基线和责任归属；
- 发现两边都需要的安全修复时，必须建立两个关联变更并分别回归；
- 不以重新创建大型 `common` 目录恢复隐式耦合。

### 8.4 供应链

- 两个项目分别生成 SBOM；
- 镜像使用不可变 digest 部署；
- Secret 不进入源码、镜像层、构建参数或日志；
- API Executor/Controller 的扫描和签名门禁继续独立于功能镜像；
- 平台记录实际运行镜像和 Revision。

## 9. 迁移方案

### 9.1 原则

采用“先复制裁剪、双线验证、逐个切换、最后冻结”的渐进迁移，不直接移动旧目录，也不在第一步删除任何文件。

### 9.2 阶段一：冻结基线

1. 记录当前 Git 状态并保护用户修改；
2. 选取功能和 API 黄金输入、Review 文件、产物和真实执行负向样例；
3. 记录测试结果、镜像 digest、依赖锁和任务目录 SHA；
4. 暂停对公共运行时的大范围重构；
5. 冻结对外 HTTP、Schema、Prompt 和 artifact 契约。

### 9.3 阶段二：拆分功能项目

1. 复制功能工作流、服务、模板、静态资源和测试；
2. 只复制功能实际使用的公共运行时；
3. 调整包名和 import，不保留旧路径兼容 hack；
4. 创建功能独立依赖锁和 Docker context；
5. 在干净目录执行单测、集成、镜像和黄金样例；
6. 平台 dev 临时切到新功能镜像，API 保持旧版本；
7. 验证功能升级/停止/回滚不影响 API。

### 9.4 阶段三：拆分 API 项目

1. 复制 API 工作流、服务、模板、静态资源和测试；
2. 将 Controller、Egress、Executor 全部纳入 API 项目；
3. 只复制 API 实际使用的公共运行时；
4. 创建 API Agent/Controller 独立依赖锁和四个 Docker context；
5. 验证默认执行关闭、prod 固定禁止和 S2 Profile 隔离；
6. 在本机已批准目标复跑正向执行和 SSRF 负向验证；
7. 平台 dev 切到新 API Release，功能保持新独立版本；
8. 验证 API 升级/停止/回滚不影响功能。

### 9.5 阶段四：平台改为镜像消费

1. prod Compose 删除两个项目的源码 build context；
2. 增加功能和 API 独立镜像版本配置；
3. dev 使用 override 文件选择本地 build 或远程镜像；
4. Nginx 路由、权限和健康检查保持不变；
5. 平台首页分别显示两个项目真实 Revision；
6. 验证平台升级不会重建两个智能体镜像。

### 9.6 阶段五：数据切换与旧目录归档

1. 暂停新任务并等待运行任务结束；
2. 对任务目录执行 dry-run、容量和 SHA 清单；
3. 按智能体分别复制到新数据根，禁止交叉复制；
4. 新服务只读验证历史任务后再开放写入；
5. 保留旧数据根只读回滚窗口；
6. 两个稳定 Release 后冻结旧源码目录；
7. 历史 `output/` 始终保留原地，不纳入新服务。

## 10. 独立开发与发布流程

### 10.1 功能智能体

```text
功能需求/缺陷
  → functional-test-agent 独立分支与测试
  → 构建 functional-test-agent 镜像
  → dev 配置 Release 验证
  → 功能流程和 Review 浏览器验收
  → 发布功能版本
  → 平台只更新功能镜像引用
```

### 10.2 API 智能体

```text
API 需求/缺陷
  → api-test-agent 独立分支与测试
  → 构建 Agent/Controller/Egress/Executor 同版本镜像
  → 默认执行关闭验证
  → dev 可信生成与 Review 验收
  → 获批环境执行专项验收
  → 发布 API 版本包
  → 平台只更新 API 镜像引用
```

### 10.3 独立操作要求

- 两边分别有维护人、版本、部署记录和回滚记录；
- 发布一个项目时不修改另一个项目源码、锁文件和镜像标签；
- 紧急回滚只回滚对应镜像和配置 Release；
- API 执行组件只能随 API Release 更新；
- 平台只负责路由、身份、权限、配置和版本选择。

## 11. 测试与验收

- [ ] 两个目录分别复制到临时干净目录后测试、构建成功；

- [ ] 功能镜像文件清单不包含 API 代码；
- [ ] API 镜像文件清单不包含功能代码；
- [ ] 平台 prod Compose 不含 `../AItestcase_Agents` build context；
- [ ] 两个项目没有共享可写目录和 Secret。

### 11.2 功能回归

- [ ] 需求拆解、测试点、测试点 Review、测试用例和用例 Review通过；

- [ ] 确认 JSON/XLSX 同源且字段兼容；
- [ ] CLI 和黄金输入通过；
- [ ] 原有功能自动化全部通过；
- [ ] 1280×800、1440×900 浏览器流程通过。

### 11.3 API 回归

- [ ] OpenAPI、Swagger、非结构化解析和质量门禁通过；
- [ ] 契约 Review、覆盖、用例 Review和可执行用例通过；
- [ ] 数据库写入关闭、开启和失败模式通过；
- [ ] 默认执行关闭和 prod 固定禁止通过；
- [ ] 本机获批目标真实执行、报告、取消、重试和缺陷草稿通过；
- [ ] SSRF、DNS、Host、path、重定向和未登记目标负向测试通过；
- [ ] 四个 API 镜像使用同一 Release 版本且兼容。

### 11.4 平台和发布

- [ ] 两个首页入口、权限和健康状态正常；
- [ ] 分别升级、停止和回滚两个项目，另一个持续可用；
- [ ] 普通用户、其他用户和管理员任务可见性不变；
- [ ] Prompt、模型、配置 Release 和项目 Revision 显示正确；
- [ ] Alembic、Nginx 和 Compose 检查通过；
- [ ] 两个项目分别生成测试报告、SBOM 和镜像 digest；
- [ ] 旧任务和 Review 草稿能够继续查看或操作；
- [ ] 历史 `output/` 校验摘要保持不变。

### 11.5 独立性验收场景

必须实际执行：

1. 只修改功能页面并发布功能新版本，确认 API 镜像 digest、容器和任务不变；
2. 只修改 API 解析逻辑并发布 API 新版本，确认功能镜像 digest、容器和任务不变；
3. 停止功能服务，API 解析和已批准本机执行仍正常；
4. 停止 API 服务及执行组件，功能生成和两级 Review 仍正常；
5. 功能回滚上一版本，API 继续保持当前版本；
6. API 回滚上一 Release 包，功能继续保持当前版本；
7. 删除本地旧源码访问权限后，两个新项目仍能完成测试和构建。

## 12. 发布与回滚

### 12.1 推荐发布顺序

1. 冻结并标记旧仓基线；
2. 发布功能独立项目 dev 版本；
3. 完成功能回归和独立性验收；
4. 发布 API 独立项目 dev 版本，默认执行关闭；
5. 完成 API 可信生成和 S2 本机专项验收；
6. 平台改为引用两个独立镜像版本；
7. 迁移或只读接入旧任务数据；
8. 分别灰度两个项目；
9. 完成回滚演练；
10. 经过两个稳定 Release 后冻结旧目录。

### 12.2 回滚原则

- 任一项目失败，只回滚该项目镜像和配置 Release；
- API 回滚必须同时回滚 Agent/Controller/Egress/Executor 兼容组合；
- 回滚不删除新旧任务卷；
- 数据迁移期间保留旧目录只读副本和 SHA 清单；
- 平台路由可临时切回旧服务镜像；
- 不通过 Git 破坏性命令恢复；
- 不执行数据库降级，除非已备份并确认旧代码无法兼容；
- 历史 `output/` 不参与回滚操作。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 公共代码复制后修复不同步 | 安全或行为漂移 | 记录复制基线；跨项目安全缺陷建立关联工单并分别回归 |
| import 路径调整引入隐性错误 | 启动或 Runner 失败 | 不保留路径 hack；干净目录测试、镜像启动和黄金样例验证 |
| 旧任务路径变化 | 历史任务不可读 | dry-run、SHA 复制、只读验证和旧数据回滚窗口 |
| API 多镜像版本不一致 | 执行失败或安全策略错配 | API 四镜像同一 Release 和兼容清单，禁止单独漂移 |
| 平台与智能体接口漂移 | 页面或权限失败 | 冻结 HTTP 契约，平台保留消费方契约测试 |
| 两个 Git 仓库管理成本增加 | 发布流程变复杂 | 统一最小命令和交付模板，但不重新共享源码 |
| 拆分期间继续在旧目录开发 | 双线冲突 | 旧目录冻结，只允许迁移阻断修复 |
| 一次切换两个服务 | 回滚定位困难 | 先功能、后 API，逐个灰度和回滚 |

## 14. 工作包与可执行计划

| 工作包 | 内容 | 完成标准 |
|---|---|---|
| W01 基线冻结 | Git/测试/镜像/产物/数据 SHA 和接口契约清单 | 可重复的拆分前基线完成 |
| W02 代码归属清单 | 将现有文件标记为功能、API、分别复制或废弃 | 无未归属运行代码 |
| W03 功能工程骨架 | 创建功能独立目录、包、锁和测试入口 | 干净目录可安装和测试 |
| W04 功能源码迁移 | 迁移工作流、运行时、Review、UI、CLI | 功能全回归和黄金样例通过 |
| W05 功能独立镜像 | 独立 Docker context、SBOM 和版本 | 镜像不含 API 代码 |
| W06 API 工程骨架 | 创建 API 独立目录、包、锁和测试入口 | 干净目录可安装和测试 |
| W07 API 源码迁移 | 迁移生成、Review、执行、报告、缺陷 | API 全回归和黄金样例通过 |
| W08 API 多镜像发布 | Agent/Controller/Egress/Executor 同版本构建 | 镜像不含功能代码且 S2 门禁通过 |
| W09 平台镜像接入 | Compose 改为独立镜像版本，dev override 可本地构建 | 平台不依赖旧源码 context |
| W10 数据和旧任务 | dry-run、复制/只读策略、SHA 校验 | 旧任务和草稿可访问，旧数据未删除 |
| W11 独立性 E2E | 分别升级、停止、故障、回滚 | 一个项目操作不影响另一个 |
| W12 灰度与归档 | 分批切换、观察、两次稳定发布后冻结旧目录 | 新目录成为唯一开发入口 |

实施顺序固定为 W01 → W05 → W08 → W12。功能和 API 不并行切流，避免同一时间存在两个未知变量。

## 15. 上线门禁

以下任一项未满足，不得完成正式切换：

- 两个项目无法在无旧仓源码环境独立构建；
- 存在跨项目源码 import、符号链接或共享可写目录；
- 黄金样例关键字段不兼容；
- 任一现有核心回归失败；
- 功能/API 镜像包含对方源码或 Secret；
- 平台 prod 仍依赖本地源码 build context；
- 独立升级、停止和回滚未实际演练；
- 旧任务或 Review 草稿无迁移/只读方案；
- API 默认执行关闭、prod 固定禁止或 S2 安全边界被削弱；
- 历史 `output/` 被修改、迁移或删除；
- 真实生产 Secret 被用于开发和验收。

## 16. 评审确认项

以下事项不阻塞本 PRD 形成，但必须在详细设计开始前确认：

1. 两个独立远程 Git 仓库的名称、地址和负责人；
2. 新目录最终命名是否采用 `functional-test-agent`、`api-test-agent`；
3. 镜像仓库地址和镜像命名规范；
4. prod 使用 Compose 还是现有企业部署平台消费镜像；
5. 现有非终态任务是迁移还是等待完成后只迁移终态；
6. 旧任务历史入口的保留时间；
7. 旧 `AItestcase_Agents` 冻结后的归档位置和只读权限；
8. 两个项目的 Release 审批人和紧急回滚责任人；
9. 复制公共运行时代码的基线 tag 和双项目安全修复流程；
10. 首个独立生产发布是否只完成可信生成/Review，继续关闭 API 真实执行。

推荐默认：第 10 项选择“是”，即源码拆分和生产部署不自动授权 API 生产真实执行。

## 17. 完成定义

当且仅当以下条件同时满足，本项目可标记完成：

1. 两个新目录成为各自唯一的功能开发入口；
2. 两个项目拥有独立 Git、依赖、测试、镜像、版本和发布流程；
3. 不存在跨项目或旧目录源码依赖；
4. 平台通过稳定接口和独立镜像接入两个项目；
5. 两个服务和 API 执行组件使用严格隔离的数据、Secret 和网络；
6. 拆分前后核心功能、Prompt 语义、Schema 和产物兼容；
7. 独立升级、故障和回滚验收通过；
8. 旧任务和 Review 数据有可验证的迁移或只读访问路径；
9. 历史 `output/` 和用户已有修改未被覆盖或删除；
10. 旧 `AItestcase_Agents` 已冻结并保留回滚窗口；
11. API 生产真实执行仍保持原安全决策，未因拆分被隐式启用；
12. W01～W12 全部完成并形成最终交付记录。

## 18. 结论

本项目不是简单地把文件复制到两个文件夹，而是把两个智能体升级为两个可以独立负责、独立开发、独立构建、独立发布、独立运行和独立回滚的产品工程。

推荐采用两个自包含项目、平台消费不可变镜像、旧仓渐进冻结的方案。该方案在接受少量公共运行时代码复制的前提下，最大程度满足“代码全部隔离”，同时避免引入第三个公共包和新的发布耦合。迁移过程以兼容和可回滚为第一原则，先拆功能、再拆 API、最后切平台与数据，不在同一阶段顺便重构核心工作流或扩大 API 执行权限。
