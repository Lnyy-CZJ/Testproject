# API 测试智能体生成内核融合优化 PRD

> 文档版本：V2.2
> 文档状态：待评审
> 适用产品：API 测试智能体
> 优化范围：契约确认后至受控执行前的基础用例、覆盖矩阵、可执行用例、过程日志与模型用量
> 前置文档：`PRD-API测试智能体端到端闭环-V2.0.md`、`PRD-API测试智能体执行前阶段优化-V2.1.md`

## 1. 文档目的

当前 V2 已建立契约 Evidence、人工 Review、版本化产物、静态安全校验和受控执行边界，但用例生成没有继续使用原 API 测试智能体的完整生成主流程，导致基础用例和可执行用例明显变简单，用户感受到“页面更完整，但智能体不像以前了”。

本 PRD 的目标不是回滚 V2，也不是继续维护两套互不相干的生成链路，而是：

1. 恢复旧版 API 测试智能体在基础用例设计、覆盖补齐、接口依赖、测试数据和可执行用例生成方面的核心能力；
2. 保留 V2 在确定性契约、Evidence、Review、版本、审计、安全校验和受控执行方面的能力；
3. 明确每个阶段实际使用的工作流、Prompt、模型、Token、输入版本、输出版本和日志；
4. 防止无接口依据的商品、订单、支付等幻觉场景进入覆盖矩阵和执行定义；
5. 让测试人员在执行前能够看懂、修改并确认“具体要测什么、怎么测、预期什么”。

## 2. 背景与问题证据

### 2.1 旧版 API 测试智能体定位

旧版以以下模块作为生成核心：

- `api_document_parser.py`：接口文档 LLM 解析；
- `base_case_generator.py`：生成包含场景、步骤、依赖和测试数据引用的基础用例；
- `base_case_check_coverage.py`：检查覆盖缺口；
- `supplement_case.py`：根据接口文档、已有用例和覆盖缺口补充用例；
- `api_case_generator.py`：根据基础用例、目标接口、依赖接口、测试数据和工具能力生成可执行用例；
- `api_basecase_workflow.py`、`api_case_generator_main_workflow.py`、`api_run_case_wrokflow.py`：组织 LangGraph 生成流程并输出节点日志。

旧版生成内容较丰富，但同时存在模型文本判定覆盖率、可选 MySQL 直写、旧 CLI 直接执行和静态安全校验不足等问题。

### 2.2 当前 V2 实际流程

当前平台任务入口为 `services.api_agent.runner`，主要流程为：

1. 文档预检；
2. OpenAPI/Swagger 确定性解析，或非结构化文档 LLM 解析；
3. 契约 Review；
4. 确定性规则生成基础用例；
5. 内联的最小 LLM Prompt 只补充 `contract_id、dimension、name、objective`；
6. 基础用例 Review；
7. 确定性地把已确认基础用例转换为仅包含 method/path 和默认状态码断言的执行定义；
8. 静态校验后进入执行预览；
9. Controller/Executor 受控执行。

当前平台没有调用旧版基础用例和可执行用例 LangGraph 主流程。

### 2.3 已确认的问题

在认证接口任务中，当前 V2 曾产生：

| 实际接口 | LLM 生成的业务场景 | 问题 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | 用户注册新账号 | 接口行为不一致 |
| `POST /api/v1/auth/logout` | 商品搜索与筛选 | 引入无原文依据的业务实体 |
| `GET /api/v1/auth/me` | 订单提交与支付 | 引入无原文依据的业务实体 |

上述 LLM 用例只有名称和目标，步骤、预期结果为空。其中“用户注册新账号”被确认后生成了 `POST /api/v1/auth/login`、`body=null`、期望状态码 200 的执行定义，并通过了当前静态校验。

这说明当前问题不是单纯的页面展示问题，而是：

- LLM 输入缺少目标接口契约和原文；
- 基础用例内容不完整；
- 覆盖矩阵只按 `contract_id + dimension` 关联，没有验证业务语义；
- 可执行用例转换丢失了旧版的参数、依赖和测试数据能力；
- 静态校验只能验证结构安全，不能验证用例语义是否成立；
- 页面没有展示生成过程和实际调用链，用户无法及时发现断层。

## 3. 新旧流程对比

| 对比维度 | 旧版实现 | 当前 V2 | 评价与目标选择 |
| --- | --- | --- | --- |
| 文档格式识别 | 主要依赖 LLM | OpenAPI/Swagger 确定性解析，非结构化走 LLM | 保留 V2 |
| 契约 Evidence | 无统一字段级门禁 | 有字段 Evidence、Grounding、冲突和未解决项 | 保留 V2 |
| 契约人工 Review | 较弱 | 有版本、审计和乐观锁 | 保留 V2 |
| 基础用例输入 | 目标接口文档、依赖接口 | 确定性契约；LLM 补齐只收到 ID 和维度 | 恢复旧版完整上下文并使用 V2 契约 |
| 基础用例内容 | 名称、步骤、依赖、数据引用 | 确定性用例较泛化；LLM 用例只有名称和目标 | 以旧版丰富度为基线，升级为 V2 Schema |
| 测试设计体系 | L1-L5、T1-T4、参数角色和边界设计 | 正常、必填、类型、枚举、边界、鉴权、错误响应 | 两者融合，确定性规则兜底，LLM 补充业务语义 |
| 覆盖判断 | LLM 文本包含“100%”即通过 | 结构化覆盖矩阵，最多补齐 3 轮 | 保留 V2，禁止恢复文本 100% 判定 |
| 业务场景 Grounding | Prompt 要求基于文档，但无强校验 | 当前补齐器未传文档，也无 Evidence 校验 | 增加用例级 Evidence 和质量门禁 |
| 用例 Review | 生成后直接进入后续流程较多 | 支持确认、禁用、高风险门禁和版本 | 保留 V2并补齐详情编辑 |
| 可执行用例生成 | 使用基础用例、目标/依赖接口、测试数据和工具说明 | 主要复制 method/path，默认 body 为空 | 恢复旧版生成内核，输出必须通过 V2 规范化 |
| 接口依赖 | 支持前置接口和变量传递 | Schema 有依赖能力，但当前生成较少使用 | 恢复并结构化 |
| 测试数据 | 支持 data_ref、baseline 和数据来源 | 当前执行定义基本未使用 | 恢复并记录数据血缘 |
| 脚本安全 | 主要做 `compile()` | 有变量、依赖、断言和 AST 白名单 | 保留 V2 |
| 数据持久化 | 可选写 MySQL | TaskStore 不可变版本文件 | 保留 V2，不恢复旧 MySQL 直写 |
| 真实执行 | 旧 CLI 可直接加载执行器 | Controller + 单 Run 受限容器 | 保留 V2，禁止旧 CLI 进入平台调用链 |
| 节点日志 | LangGraph `stream_writer` 有生成过程 | 成功阶段几乎没有日志 | 恢复节点事件思想，写入 V2 结构化阶段记录 |
| Prompt 追溯 | 文件明确但缺少任务级版本绑定 | 页面只有整个 Prompt 目录 Bundle SHA | 改为实际调用 Prompt SHA 和模块 |
| Token 统计 | API 旧版未形成页面闭环 | 当前 API V2 未采集 | 参考功能测试智能体实现并绑定 Attempt |

### 3.1 对比结论

不存在“旧版整体更好”或“当前 V2 整体更好”的单一结论：

- 旧版在测试设计和生成丰富度上更好；
- 当前 V2 在契约可信度、人工控制、版本追溯、安全隔离和失败恢复上更好；
- 当前最优方案是“旧生成内核 + V2 治理外壳”，而不是回滚或双轨长期并存。

## 4. 产品原则

1. **契约事实优先**：确定性解析结果和已确认人工决定优先于 LLM。
2. **旧能力不是旧入口**：复用旧 Prompt、规则和工作流节点能力，但平台不调用旧 CLI 直接执行入口。
3. **生成与放行分离**：LLM 可以提出用例，不能决定覆盖完成、确认状态或执行权限。
4. **无依据不补齐**：无法从接口契约、原文、分析范围或人工补充信息获得依据时，保留覆盖缺口，不允许编造业务场景。
5. **内容完整才可确认**：基础用例必须让测试人员明确知道测什么、怎么测、期望什么。
6. **执行定义必须可审计**：每个请求字段、变量、依赖和断言都能追溯到契约、基础用例、测试数据或人工决定。
7. **过程可观察**：用户能查看每阶段实际调用的工作流、Prompt、模型、Token、版本、耗时和结果。
8. **旧产物不覆盖**：融合内核生成新版本，历史 V2 产物保留并标记生命周期。

## 5. 目标流程

```text
上传/修订接口文档
→ 格式预检与确定性/LLM 契约解析
→ 契约 Evidence 与人工 Review
→ 生成上下文组装（当前契约、原文片段、依赖契约、测试数据）
→ 旧版基础用例生成能力输出 V2 基础用例候选
→ V2 确定性覆盖规则合并与去重
→ LLM 结构化覆盖检查和最多 3 轮补齐
→ 用例 Grounding、完整性和风险门禁
→ 覆盖矩阵与基础用例 Review
→ 旧版可执行用例生成能力输出执行候选
→ V2 Schema、变量、依赖、断言、AST 和风险校验
→ 执行预览与最终人工确认
→ Controller/受限容器执行
→ 报告和本地 Bug 草稿
```

沿用 V2.1 已确认权限：

| 操作 | 平台管理员 | 测试开发 | 测试人员 | 只读角色 |
| --- | --- | --- | --- | --- |
| 查看基础用例详情和生成依据 | 是 | 是 | 是 | 是，脱敏只读 |
| 编辑和确认普通基础用例 | 是 | 是 | 是 | 否 |
| 确认高风险基础用例 | 是 | 是 | 是 | 否 |
| 查看阶段记录和 Token | 是 | 是 | 是 | 是，隐藏内部异常堆栈 |

## 7. P0 需求：恢复可信的基础用例生成内核

### 7.1 生成上下文

需求编号：`KERNEL-01`

每个已确认契约独立生成上下文，至少包含：

- Contract ID、method、path、summary、module 和 tags；
- 参数、请求体、响应、鉴权、错误码和 SLA；
- 关联原文 Section、字段 Evidence 和人工决定；
- 已确认的前置依赖接口及调用顺序；
- 可用的测试环境变量和测试数据引用名称，不包含 Secret 明文；
- 已有用例和当前结构化覆盖缺口；
- 当前契约版本、文档版本和分析范围版本。

禁止只向模型提供 Contract ID、覆盖维度和规则名称。

### 7.2 基础用例候选生成

需求编号：`KERNEL-02`

复用旧 `base_case_generator` 的测试设计能力，并输出 V2 `BaseTestCase`。每条用例至少包含：

- `case_id`；
- `contract_id`；
- 名称；
- 测试目标；
- 覆盖维度和测试分类；
- 前置条件及依赖接口；
- 结构化测试步骤；
- 测试数据引用或参数变化说明；
- 预期结果或明确的探索式观察目标；
- 风险等级；
- 生成来源；
- Evidence 引用；
- 当前状态和版本来源。

LLM 返回名称或目标但缺少步骤、预期/观察目标、关联契约或 Evidence 时，不得进入 `confirmed_candidate`。

### 7.3 确定性规则与旧测试设计体系融合

需求编号：`KERNEL-03`

继续使用 V2 确定性规则生成：

- 正常请求；
- 必填缺失；
- 类型错误；
- 枚举和数值/长度边界；
- 鉴权缺失；
- 文档声明错误响应；
- 写接口的重复提交/幂等候选。

旧版 L1-L5、T1-T4 和参数角色规则用于补充：

- 参数组合；
- 状态流转；
- 权限角色；
- 跨接口依赖；
- 安全输入；
- 文档明确的业务规则；
- 探索式观察场景。

LLM 不得重复生成确定性规则已经完整覆盖的用例。

### 7.4 用例 Grounding 门禁

需求编号：`KERNEL-04`

每条 LLM 或 AI 补齐用例必须通过：

1. Contract ID 存在且为当前已确认版本；
2. method/path 与契约一致；
3. 用例涉及的参数、响应、错误码、状态和业务实体能够绑定 Evidence 或人工补充说明；
4. 不得出现目标文档和人工补充信息中不存在的商品、订单、支付等业务实体；
5. 每条步骤引用的依赖接口必须存在且已确认；
6. 预期结果不得静默编造文档没有声明的状态码或错误码；
7. 探索式用例必须标识 `exploratory`，只能记录实际响应，不能自动生成产品缺陷结论。

校验失败时：

- 用例保持 `draft` 或被拒绝；
- 覆盖项继续显示缺口；
- 页面显示拒绝原因和关联字段；
- 不因“有同一 contract_id 的用例”而把缺口标为已覆盖。

### 7.5 结构化覆盖矩阵

需求编号：`KERNEL-05`

保留 V2 结构化覆盖矩阵，禁止恢复“模型文本包含 100% 即通过”的逻辑。

- 确定性规则先生成覆盖骨架；
- LLM 只能返回结构化缺口建议和补齐用例；
- 补齐最多执行 3 轮；
- 新增有效用例数为 0 时提前结束；
- 缺口连续两轮不变时提前结束；
- 只有通过 Schema、Grounding 和完整性门禁的用例才能关联覆盖项；
- 未解决缺口进入 `partial_success` 或由人工填写理由接受；
- 保存每轮输入版本、缺口数量、候选数量、接受数量和拒绝数量。

## 8. P0 需求：基础用例详情与 Review

### 8.1 用例详情工作区

需求编号：`KERNEL-06`

覆盖矩阵与基础用例 Review 页面增加用例详情抽屉或三栏详情区域。点击用例名称后展示：

- 关联接口的 method、path 和名称；
- 测试目标和覆盖维度；
- 前置条件和依赖接口顺序；
- 每个测试步骤；
- 参数变化和测试数据来源；
- 预期状态码、响应字段、错误码或探索式观察目标；
- Evidence 原文定位；
- 确定性/LLM/人工来源；
- 风险、状态、版本和变更历史；
- Grounding、完整性和安全门禁结果。

用例名称必须是可聚焦的按钮或链接，支持键盘打开详情；不能只依赖点击整行或颜色区分状态。

### 8.2 编辑与确认

需求编号：`KERNEL-07`

- 支持编辑名称、目标、前置条件、步骤、数据引用和预期结果；
- 业务字段修改生成新版本，不覆盖生成稿；
- 编辑必须填写原因；
- 人工增加无文档依据的业务规则时，保存为 `human_override` 并记录人员、时间和理由；
- 普通候选支持批量确认；
- 高风险用例必须逐条确认；
- Grounding blocker、空步骤或空预期/观察目标不得确认；
- `stale` 用例只读，不得进入可执行用例生成。

## 9. P0 需求：恢复完整可执行用例生成

### 9.1 生成输入

需求编号：`KERNEL-08`

复用旧 `api_case_generator` 的生成能力。每条执行候选输入至少包含：

- 已确认基础用例完整内容；
- 当前目标接口契约；
- 已确认依赖接口契约；
- 测试数据引用和变量来源；
- 允许使用的受控工具和脚本能力；
- 目标环境占位符，不包含真实 Host 和 Secret；
- 当前静态安全策略版本。

### 9.2 执行候选内容

需求编号：`KERNEL-09`

执行候选至少包含：

- 相对 path 和 method；
- Header、Cookie、Query、Path 参数和 Body；
- 参数值来源及数据血缘；
- 前置接口及拓扑顺序；
- 响应变量提取；
- 结构化断言；
- 必要的 setup/teardown 脚本；
- 基础用例、契约和 Prompt 的来源版本。

对于契约声明存在必填请求体的接口，执行候选 `body=null` 必须被静态校验阻断。

### 9.3 V2 静态安全校验

需求编号：`KERNEL-10`

旧生成内核只负责产生执行候选，最终是否进入执行预览由 V2 决定。必须校验：

- Schema；
- method/path 与契约；
- 必填 Header、Query、Path 和 Body；
- 变量定义和引用；
- 数据来源；
- 依赖完整性、拓扑和循环；
- 断言操作符白名单；
- setup/teardown 语法和 AST；
- 文件、进程、网络和反射限制；
- 高风险人工确认；
- 基础用例 Grounding 状态；
- 当前契约和基础用例版本是否 stale。

平台继续禁止调用旧 `execute_test_cases()`。真实请求只能由已批准的 Controller/Executor 链路发送。

## 10. P1 需求：阶段记录与调用链可观察性

### 10.1 统一阶段记录

需求编号：`OBS-01`

阶段 1～4 均可访问同一个常驻“阶段记录”面板，不为每个页面复制独立日志窗口。

阶段记录按 Attempt、Run 和阶段筛选：

| 阶段 | 必须记录的产品事件 |
| --- | --- |
| 1 契约分析 | 格式识别、解析器、接口数量、Evidence 数量、质量门禁、重试和错误 |
| 2 覆盖与基础用例 | 确定性用例数量、LLM 调用、补齐轮次、候选/接受/拒绝数量、覆盖缺口和 Review |
| 3 执行定义与准备 | 执行候选数量、静态校验结果、禁用原因、目标登记和确认摘要 |
| 4 Run 与报告 | Run 生命周期、Controller 状态、取消、超时、结果数量、失败分类和报告生成 |

每条事件包含：

- 时间；
- Attempt ID 或 Run ID；
- 阶段和节点；
- 状态；
- 输入版本与 SHA；
- 输出版本与 SHA；
- 耗时；
- 模型和 Prompt；
- Token 摘要；
- 错误码和可执行的建议动作。

### 10.2 日志安全

需求编号：`OBS-02`

- 阶段记录不保存 Secret；
- 不默认保存完整原文、完整 Prompt 或请求/响应正文；
- 对 Header、Cookie、Query、Body、模型异常和执行日志脱敏；
- 测试人员查看产品事件；管理员可查看脱敏技术日志；
- 原始 Runner stdout/stderr 不能作为唯一阶段记录；
- 阶段成功也必须有开始、完成和产物事件，不能只在异常时写日志。

## 11. P1 需求：Prompt、模型和 Token 版本信息

### 11.1 实际调用来源

需求编号：`OBS-03`

版本信息不能只显示整个 prompts 目录的 Bundle SHA。每个模型调用保存：

- 阶段和节点；
- 实际 Prompt 模块或内联 Prompt 标识；
- Prompt SHA；
- 模型名称和配置 Release；
- 输入契约/文档/用例版本；
- 调用开始、结束和耗时；
- 是否重试；
- 输出 Schema 校验结果。

页面明确区分：

- “本阶段未调用模型”；
- “调用成功且供应商报告用量”；
- “调用成功但供应商未报告用量”；
- “调用失败”；
- “结果被 Grounding 门禁拒绝”。

### 11.2 Token 用量

需求编号：`OBS-04`

参考功能测试智能体的 Token 采集方式，统计：

- `input_tokens`；
- `output_tokens`；
- `total_tokens`；
- `calls`；
- `reported_calls`；
- 重试次数。

展示层级：

1. 当前模型调用；
2. 当前阶段；
3. 当前 Attempt；
4. 当前任务累计。

确定性阶段显示“不适用”；供应商未返回 usage 时显示“未报告”，不得显示为 0。

## 12. P1 需求：生成内核与版本兼容

### 12.1 内核标识

需求编号：`COMPAT-01`

每个基础用例和可执行用例版本保存生成内核标识：

- `legacy`：旧 CLI 历史产物；
- `v2_minimal`：当前 V2 极简生成产物；
- `v2_fused`：本 PRD 的融合生成产物；
- `human`：完全人工创建。

页面展示内核标识，避免用户误以为所有版本使用了同一套生成能力。

### 12.2 历史任务

需求编号：`COMPAT-02`

- 不修改或删除旧版、V2.0、V2.1 历史产物；
- `v2_minimal` 历史用例可查看和下载；
- 对缺少步骤、预期结果、Evidence 或请求体的历史用例重新执行门禁；
- 不满足门禁的历史可执行用例标记 `legacy_validation_required`，不得新建 Run；
- 用户可从已确认契约版本选择“使用融合内核重新生成”；
- 重新生成产生新 Attempt 和新版本，旧 Run、报告和草稿保持原终态。

## 13. P2 需求

以下内容放入 P2，不阻塞本次融合：

- Prompt 在线版本管理和灰度对比；
- 同一契约的新旧内核 A/B 结果对比；
- Token 成本预算和按项目配额；
- 用例质量离线评测集；
- 人工修改对 Prompt 优化的反馈闭环；
- PostgreSQL 元数据索引和对象存储迁移；
- 稳定资产发布到 Gateway 自动化工具。

## 14. 接口与存储约定

### 14.1 建议新增只读接口

```http
GET /api-test-agent/api/v1/tasks/{task_id}/stage-events
GET /api-test-agent/api/v1/tasks/{task_id}/model-usage
GET /api-test-agent/api/v1/tasks/{task_id}/generation-provenance
```

支持按 `attempt_id`、`run_id`、`stage` 和游标查询。继续执行任务所有权、RBAC 和脱敏。

### 14.2 现有接口扩展

`GET /tasks/{task_id}/cases` 中的基础用例需要返回完整 Review 字段，但不能返回 Secret 或真实环境凭证。

用例确认接口在现有 `base_version` 之外增加质量门禁结果；存在 blocker 时返回稳定错误码，不得只返回通用 409/503。

### 14.3 文件存储

继续使用任务目录的不可变版本、原子写入和 SHA 校验。建议增加：

```text
attempts/{attempt_id}/events.jsonl
attempts/{attempt_id}/model-usage.json
attempts/{attempt_id}/generation-provenance.json
```

不恢复旧工作流对 MySQL 用例表的直接写入。本期不增加数据库迁移。

## 16. 非目标与产品边界

本 PRD 不改变既有边界：

- 不支持 Postman Collection 导入；
- 不支持 gRPC、WebSocket、GraphQL；
- 不实现压测、并发、吞吐量、P95/P99；
- 不实现外部 Bug 系统提交；
- 不实现稳定资产发布；
- 不允许平台 Web 或生成 Runner 直接请求目标 API；
- 不允许旧 CLI 执行器进入平台生产调用链；
- 不绕过 `API_EXECUTION_ENABLED`、目标登记、人工确认和受限容器门禁。

## 17. 验收标准

### 17.1 生成质量

- 登录、退出登录、当前用户信息黄金文档不得生成商品、订单、购物车或支付场景；
- 固定回放的无依据 LLM 输出必须 100% 被 Grounding 门禁拒绝；
- LLM 用例缺少步骤、预期/观察目标或 Evidence 时不得进入确认候选；
- 通过确认的基础用例完整展示目标、步骤、数据、预期、Evidence 和来源；
- 确定性用例和 LLM 用例去重，不因名称变化重复覆盖同一测试点；
- 覆盖补齐最多 3 轮，不使用模型文本中的“100%”作为结束条件。

### 17.2 可执行用例

- 已确认基础用例能够生成 Header、Query、Path、Body、依赖、变量和断言；
- 有必填请求体但 `body=null` 的执行候选必须被阻断；
- 业务语义与契约不一致的基础用例不得生成 `ready/enabled` 执行定义；
- 变量无来源、依赖缺失/循环、断言不支持、AST 不安全和高风险未确认均不得进入执行预览；
- 平台代码不得调用旧 `execute_test_cases()`。

### 17.3 可观察性

- 阶段 1～4 均能打开统一阶段记录；
- 成功和失败阶段都有开始、完成、输入版本、输出版本和耗时；
- 页面能明确显示当前阶段实际使用的工作流/模块和 Prompt SHA；
- Token 能按阶段、Attempt 和任务累计展示；
- 供应商未报告用量时显示“未报告”；
- 阶段记录和下载内容全部脱敏。

### 17.4 兼容与安全

- 历史任务不删除、不覆盖；
- 不满足新门禁的 `v2_minimal` 历史用例不能创建新 Run；
- 融合内核可通过配置回退到“停止新生成、历史只读”，不回退契约和 Run 数据；
- 不增加真实 Host、Credential、Docker Socket 或外部系统写入能力。

## 18. 发布策略与回滚

1. 先上线历史版本识别和执行阻断门禁；
2. 再上线融合基础用例生成，仅对新 Attempt 开启；
3. 通过认证接口黄金集后上线融合可执行用例生成；
4. 最后上线阶段记录和 Token 页面；
5. 灰度期间保留当前 V2 生成器作为只读对比，不允许两套结果自动混合；
6. 出现问题时停止创建 `v2_fused` Attempt，保留已生成版本，不切换到旧 CLI 直接执行。

## 19. 风险与建议决策

| 风险或待确认项 | 建议决策 |
| --- | --- |
| 是否直接恢复完整旧 LangGraph 图 | 不直接恢复整图；复用生成节点和 Prompt，通过适配层接入 V2 状态机 |
| 是否恢复旧 MySQL 用例持久化 | 不恢复，继续使用不可变版本文件 |
| 是否恢复旧 CLI 真实执行 | 不恢复，继续使用 Controller/受限容器 |
| 是否保留旧 L1-L5、T1-T4 体系 | 保留为测试设计标签和补充规则，不作为模型自报覆盖率依据 |
| 是否允许无文档依据的探索用例 | 允许，但必须标识 exploratory、人工确认，不能自动生成产品 Bug |
| 是否自动确认 LLM 业务场景 | 不自动确认；先通过 Grounding 和完整性门禁，再由人员确认 |
| 历史 `v2_minimal` 可执行用例如何处理 | 重新执行新门禁；不合格版本禁止新 Run |
| 阶段日志是否做四套窗口 | 不做；使用跨阶段统一记录面板 |

## 20. 成功指标

上线后持续观察：

- LLM 用例 Grounding 拒绝率及原因分布；
- 测试人员禁用或大幅修改 LLM 用例的比例；
- 基础用例完整率；
- 可执行用例首次静态校验通过率；
- 每个接口平均有效基础用例数；
- 覆盖补齐平均轮次；
- 从契约确认到执行准备的平均耗时；
- 每阶段模型调用数和 Token；
- 因生成错误导致的执行失败比例；
- 阶段记录页面的查看率和问题定位时长。

## 21. 最终产品结论

API 测试智能体原有 prompts 和 workflows 是测试设计与用例生成的核心资产，不应被页面化改造旁路。V2 的价值是为这些能力增加可信契约、人工门禁、版本追溯、静态安全校验和受控执行，而不是用极简规则替代原生成内核。

本 PRD 确定的目标产品形态为：

> 旧版负责“像测试工程师一样设计和生成”，V2 负责“确保生成有依据、可 Review、可追溯且只能受控执行”。
