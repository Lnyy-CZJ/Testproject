# 测试开发平台第二阶段接口文档

> 版本：V3.1
> 更新日期：2026-08-30
> 基础地址：`http://127.0.0.1:8080`
> 用途：接口测试、联调、安全验证和故障定位

## 1. 通用约定

平台 API 前缀为 `/api/v1`。除 `health/live`、`health/ready`、`setup`、`auth/login`、`auth/registration-status` 和 `auth/register` 外，公共接口要求有效统一会话。

浏览器登录后获得：

- `tp_session`：HttpOnly 服务端 Session Cookie；
- `tp_csrf`：CSRF Cookie；
- 写请求同时发送 `X-CSRF-Token: <tp_csrf>`。

工具内部接口不接受用户 Cookie，固定使用每工具独立的：

```http
Authorization: Bearer <tool-client-token>
```

Client Token 绑定 `tool_id`、`environment_id` 和能力。工具 A 不能读取工具 B 或其他环境的数据。

所有平台错误使用：

```json
{
  "code": "STABLE_ERROR_CODE",
  "message": "中文错误信息",
  "request_id": "req_xxx"
}
```

主要错误码：`AUTH_REQUIRED`、`PERMISSION_DENIED`、`CSRF_INVALID`、`REGISTRATION_UNAVAILABLE`、`REGISTRATION_RATE_LIMITED`、`REGISTRATION_PAYLOAD_TOO_LARGE`、`VERSION_CONFLICT`、`SECRET_UNAVAILABLE`、`CREDENTIAL_REFRESH_FAILED`、`CONFIG_VALIDATION_FAILED`、`TOOL_CLIENT_UNAUTHORIZED`、`TOOL_CLIENT_FORBIDDEN`。

## 2. 健康与统一登录

### 2.1 健康

```http
GET /api/v1/health/live
GET /api/v1/health/ready
```

`live` 只检查进程；`ready` 检查 PostgreSQL，数据库不可用返回 503。

```json
{
  "service": "platform-api",
  "status": "ok",
  "version": "1.00.000"
}
```

`ready` 的 `status` 为 `ready`，并返回相同的 `version`。版本格式固定为 `主版本.两位平台版本.三位发布序号`。

### 2.2 一次性初始化

```http
POST /api/v1/setup
Content-Type: application/json

{
  "bootstrap_token": "一次性引导 Token",
  "username": "admin",
  "display_name": "平台管理员",
  "password": "6–18 个 Unicode 字符"
}
```

仅在数据库没有用户时有效。成功后直接创建统一会话；已有用户后返回 404，响应不泄露 Bootstrap Token。

### 2.3 注册状态与自助注册

```http
GET /api/v1/auth/registration-status

200 OK
Cache-Control: no-store
{"mode":"open"}
```

`mode` 只可能为 `open`、`disabled` 或 `invite`。当前版本只有 `open` 允许提交；其他模式失败关闭。

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "username": "new-tester",
  "display_name": "新测试人员",
  "password": "6–18 个 Unicode 字符"
}
```

成功返回 `201` 与当前用户响应，并立即写入 Session/CSRF Cookie。新用户固定为 active tester，不创建项目关系、额外授权或其他业务数据。请求不得包含角色、项目、状态等额外字段；请求体上限为 64 KiB。重复用户名返回安全的 `409 REGISTRATION_UNAVAILABLE`，来源限流返回 `429 REGISTRATION_RATE_LIMITED`，模式关闭、邀请制、全局熔断或计数服务不可用返回 `503 REGISTRATION_UNAVAILABLE`。

### 2.4 登录、退出与当前用户

```http
POST /api/v1/auth/login
{"username":"admin","password":"..."}

POST /api/v1/auth/logout
X-CSRF-Token: <tp_csrf>

GET /api/v1/auth/me
```

`auth/me` 响应包含当前用户、角色、平台权限、按工具聚合的权限和 Session 过期时间。登录在 15 分钟内连续失败 5 次后锁定 15 分钟。登录密码字段继续接受 1–256 位，以兼容历史长密码。

### 2.5 密码与会话

```http
POST /api/v1/auth/change-password
{"current_password":"1–256 位存量密码","new_password":"6–18 个 Unicode 字符"}

GET /api/v1/auth/sessions
DELETE /api/v1/auth/sessions/{session_id}
```

注册、初始化、改密、管理员创建与重置的新密码统一为 6–18 个 Unicode 字符，密码不裁剪。修改密码会撤销同一用户的其他会话。管理员重置密码后，用户必须先完成修改密码流程。

新签发 Session 的空闲和绝对期限均为 168 小时，Cookie `Max-Age=604800`；恰好在创建后第 7 天失效。发布前已存在的 Session 保留数据库中的原到期时间。注销、停用、改密、管理员撤销和权限版本变化仍可提前使会话失效。

## 3. 工具目录与网关鉴权

```http
GET /api/v1/tools
GET /api/v1/tools/{tool_id}/health
```

目录只返回当前用户具备 `tool.view` 的启用工具，内部 `health_url` 永不返回。四个工具 ID：

```text
trackevents
log-filter
truthy-search
api-autotest
```

Nginx 对 `/trackevents/`、`/log-filter/`、`/truthy-search/`、`/api-autotest/` 强制执行内部授权。页面与静态资源要求 `tool.view`，任务写操作要求 `tool.execute`，历史结果、日志、Raw、报告和下载要求 `tool.result.view`。

匿名 HTML 请求重定向到 `/login?next=...`；匿名 API 请求返回 401；无权限返回 403；平台身份服务异常返回 503。客户端伪造的 `X-Platform-*` Header 会被 Nginx 清除。

## 4. 用户和角色管理

需要对应平台权限和 CSRF：

```http
GET  /api/v1/admin/users
POST /api/v1/admin/users
GET  /api/v1/admin/users/{user_id}
PATCH /api/v1/admin/users/{user_id}
POST /api/v1/admin/users/{user_id}/reset-password
DELETE /api/v1/admin/users/{user_id}/sessions

GET  /api/v1/admin/roles
POST /api/v1/admin/roles
GET  /api/v1/admin/roles/{role_id}
PATCH /api/v1/admin/roles/{role_id}
DELETE /api/v1/admin/roles/{role_id}
GET  /api/v1/admin/permissions
```

角色授权项格式：

```json
{
  "permission_code": "tool.execute",
  "resource_type": "tool",
  "resource_id": "truthy-search"
}
```

`resource_id="*"` 表示全部工具。平台权限的资源范围必须为 `*`；权限类型与资源类型不匹配返回 422。用户多角色权限取并集，没有显式 Deny。

## 5. 普通配置 Release

```http
GET  /api/v1/config/definitions
GET  /api/v1/config/releases?environment_id=dev&owner_type=tool&owner_id=truthy-search
POST /api/v1/config/releases
PUT  /api/v1/config/releases/{release_id}/items
POST /api/v1/config/releases/{release_id}/validate
POST /api/v1/config/releases/{release_id}/publish
POST /api/v1/config/releases/{release_id}/rollback
POST /api/v1/config/releases/{release_id}/promote?target_environment=prod
```

创建草稿：

```json
{
  "environment_id": "dev",
  "owner_type": "tool",
  "owner_id": "truthy-search"
}
```

更新草稿使用乐观锁：

```json
{
  "revision": 1,
  "items": [
    {"definition_id":"truthy-search.SEARCH_API_URL","value":"https://example.test"}
  ]
}
```

revision 过期返回 `409 VERSION_CONFLICT`。发布冻结本次 Secret Version 引用；回滚创建新 Release，不修改历史。提升只复制普通配置并创建 prod 草稿，Secret 不跨环境复制。运行任务保存 Release ID。

## 6. Secret 与 Credential

```http
GET /api/v1/secrets?environment_id=dev&owner_type=tool&owner_id=truthy-search
PUT /api/v1/secrets/{secret_id}

GET  /api/v1/credentials?environment_id=dev
POST /api/v1/credentials
```

写入 Secret：

```json
{
  "environment_id": "dev",
  "owner_type": "tool",
  "owner_id": "truthy-search",
  "definition_id": "truthy-search.AUTH_TOKEN",
  "value": "仅在本次请求出现的明文",
  "expires_at": "2026-08-11T00:00:00Z"
}
```

响应只包含 ID、作用域、状态、版本和过期时间，永不返回明文、密文、Nonce 或 Wrapped DEK。Secret 使用 AES-256-GCM 信封加密并绑定 Secret/环境/版本 AAD。

创建 Credential：

```json
{
  "tool_id": "truthy-search",
  "environment_id": "dev",
  "provider_type": "gateway_session"
}
```

Provider 为 `gateway_session` 或 `admin_login`。Credential Agent 每分钟扫描，提前 60 分钟刷新；并发刷新使用数据库租约和行锁。只读请求在刷新后最多重放一次，非幂等写请求不自动重放。

## 7. 审计

```http
GET /api/v1/audit/events?page=1&page_size=50
GET /api/v1/audit/events/{event_id}
POST /api/v1/audit/exports?start_at=<ISO-8601>&end_at=<ISO-8601>
```

导出必须指定时间范围，最多 100,000 行。API 没有更新或删除审计接口；PostgreSQL 触发器拒绝普通应用角色更新或删除。所有响应和 CSV 再次执行脱敏。

审计用于回答“谁、何时、对哪个资源、执行了什么、结果如何”，覆盖登录、权限变更、配置发布/回滚、Secret 替换、凭证刷新和工具任务生命周期，便于故障复盘、安全追踪和责任边界确认。

## 8. LLM 统一配置

需要登录；Profile 管理要求 `platform.llm.manage`，Profile Secret 要求 `platform.llm.secret.manage`。Binding 普通参数与独立 Secret 分别复用对应工具的 `tool.config.manage`、`tool.secret.manage`。

```http
GET    /api/v1/llm/profiles?environment_id=dev
POST   /api/v1/llm/profiles
PATCH  /api/v1/llm/profiles/{profile_id}?environment_id=dev
POST   /api/v1/llm/profiles/{profile_id}/archive?environment_id=dev
POST   /api/v1/llm/profiles/{profile_id}/restore?environment_id=dev
GET    /api/v1/llm/bindings?environment_id=dev
GET    /api/v1/llm/bindings/{binding_id}?environment_id=dev
GET    /api/v1/llm/effective-config?environment_id=dev&binding_id=...
POST   /api/v1/llm/test-connection
```

参数版本继续复用 `/config/releases`，API Key 继续复用 `/secrets`。安全摘要只返回 `api_key_configured` 和版本，不返回明文。连接测试使用固定最小 Prompt，不返回模型文本，不重试、不跟随重定向；prod 只允许 HTTPS。可能返回：`LLM_PROFILE_NOT_FOUND`、`LLM_BINDING_NOT_FOUND`、`LLM_CONFIG_NOT_READY`、`LLM_SECRET_UNAVAILABLE`、`LLM_CONNECTION_FAILED`、`LLM_CONNECTION_TIMEOUT`、`LLM_RESPONSE_INVALID`、`LLM_TARGET_NOT_ALLOWED`。

## 9. 工具内部接口

Nginx 使用用户 Cookie 调用 `authorize`；其余接口只能由绑定工具的 Client Token 调用。Nginx 不向浏览器公开 `/api/v1/internal/*`：

```http
GET  /api/v1/internal/authorize
GET  /api/v1/internal/tools/{tool_id}/runtime-config?include_secrets=true&llm_capability=default
POST /api/v1/internal/tools/{tool_id}/config-ack
POST /api/v1/internal/tools/{tool_id}/audit-events
POST /api/v1/internal/tools/{tool_id}/credential-status
PUT  /api/v1/internal/tools/{tool_id}/credentials/{credential_id}/session
```

`authorize` 接收 Nginx 传入的原始 URI、方法和工具 ID，只返回授权状态及经过百分号编码的可信身份 Header。

`runtime-config` 响应设置 `Cache-Control: no-store`：

```json
{
  "tool_id": "truthy-search",
  "environment": "dev",
  "release_id": "rel_xxx",
  "release_version": 3,
  "normal": {"SEARCH_API_URL":"https://example.test"},
  "secrets": {"AUTH_TOKEN":"仅工具进程可见"},
  "credential_metadata": {"credential_version":4,"expires_at":"..."}
}
```

当工具传入已登记的 `llm_capability` 时，响应额外包含 `llm`。`include_secrets=false` 只返回 `api_key_configured`；`true` 仅对绑定工具 Client 返回本次固定 Secret Version 的 `api_key`。`snapshot_id` 由环境、工具、能力、Profile/Binding Release、Secret Version 和普通参数生成，不包含 API Key 明文。

Session 写回必须携带 `expected_version`，旧任务覆盖新会话时返回 `409 VERSION_CONFLICT`。内部审计事件携带全局唯一 `event_id`，重复上报保持幂等。

## 10. 工具公开路由

| 工具 | 页面 | 健康 | 主要写操作 |
|---|---|---|---|
| TrackEvents | `/trackevents/` | `/trackevents/health` | `POST /trackevents/api/analyze` |
| Log Filter | `/log-filter/` | `/log-filter/health` | `POST /log-filter/`、`POST /log-filter/export` |
| Truthy Search | `/truthy-search/` | `/truthy-search/health` | Run、导入、处理、重试等既有表单/API |
| API AutoTest | `/api-autotest/` | `/api-autotest/health` | 任务创建、取消、重试和报告接口 |

平台模式下所有工具写操作同时要求统一会话、对应工具权限和 CSRF。工具独立模式继续按各项目原有 `.env` 和路由运行。

## 11. 调试顺序

1. `GET /health/live`；
2. `GET /health/ready`；
3. 登录并保存 Cookie；
4. `GET /auth/me` 核对权限；
5. `GET /tools` 核对目录过滤；
6. 调试写请求时同时发送 Cookie 与 `X-CSRF-Token`；
7. 401 检查 Session，403 检查权限/CSRF，503 检查平台 API、PostgreSQL、KEK 和 Credential Agent；
8. 使用响应中的 `request_id` 在平台日志和审计中关联排障。
