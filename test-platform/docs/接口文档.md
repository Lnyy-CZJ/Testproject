# 测试开发平台 MVP 接口文档

> 文档版本：V1.2
> 更新日期：2026-07-31
> 适用模块：测试开发平台、`TrackEvents_tess`、`log_filter_tool`、`Truthy_Search`
> 使用目的：接口测试、联调、故障定位和自动化冒烟

---

## 1. 接口概览

### 1.1 基础地址

本地默认地址：

```text
http://127.0.0.1:8080
```

如果 `.env` 中修改了 `PLATFORM_PORT`，请将文档中的 `8080` 替换为实际端口。

建议在调试终端中定义：

```bash
export PLATFORM_BASE_URL=http://127.0.0.1:8080
```

### 1.2 鉴权

MVP 暂未实现登录和接口鉴权，建议仅部署在受控内网。后续增加统一登录后，本文档需同步补充 Token、Cookie 或会话规则。

### 1.3 请求限制

| 项目 | 当前约束 |
|---|---|
| 最大请求体 | 25 MB |
| Nginx 上游连接超时 | 3 秒 |
| 平台 API 上游响应超时 | 10 秒 |
| 工具上游响应超时 | 60 秒 |
| 字符编码 | UTF-8 |
| JSON Content-Type | `application/json` |
| 表单 Content-Type | `application/x-www-form-urlencoded` 或浏览器默认表单格式 |

请求体超过 25 MB 时，统一入口返回 `413 Request Entity Too Large`。

### 1.4 路由清单

| 模块 | 方法 | 路径 | 响应类型 | 用途 |
|---|---|---|---|---|
| 平台 | GET | `/` | HTML | 平台首页和工具导航 |
| 平台 | GET | `/assets/*` | JavaScript/CSS | Vite 生产静态资源 |
| 平台 API | GET | `/api/v1/health/live` | JSON | 进程存活检查 |
| 平台 API | GET | `/api/v1/health/ready` | JSON | 数据库就绪检查 |
| 平台 API | GET | `/api/v1/tools` | JSON | 已启用工具目录 |
| 平台 API | GET | `/api/v1/tools/{tool_id}/health` | JSON | 平台侧工具健康探测 |
| 埋点工具 | GET | `/trackevents/` | HTML | 埋点测试页面 |
| 埋点工具 | GET | `/trackevents/health` | JSON | 服务健康检查 |
| 埋点工具 | GET | `/trackevents/favicon.svg` | SVG | 页面图标 |
| 埋点工具 | POST | `/trackevents/api/analyze` | JSON | 分析埋点日志 |
| 日志工具 | GET | `/log-filter/` | HTML | 日志筛选页面 |
| 日志工具 | POST | `/log-filter/` | HTML | 提交日志并显示筛选结果 |
| 日志工具 | GET | `/log-filter/health` | JSON | 服务健康检查 |
| 日志工具 | GET | `/log-filter/sample` | Text | 获取示例日志 |
| 日志工具 | POST | `/log-filter/export` | JSON | 将页面日志导出到服务端 |
| 检索工具 | GET | `/truthy-search/` | HTML | 检索评测页面 |
| 检索工具 | GET | `/truthy-search/health` | JSON | Flask 与 SQLite 健康检查 |

平台首页先读取工具目录，再调用各工具的平台健康接口。API 不可用时，前端使用内置只读目录回退。

## 2. 通用响应与状态码

| 状态码 | 含义 | 常见场景 |
|---:|---|---|
| 200 | 请求成功 | 页面、健康检查、分析、筛选或导出成功 |
| 308 | 永久重定向 | 三个工具的不带尾斜杠入口跳转到标准入口 |
| 400 | 请求参数或内容错误 | JSON 格式错误、字段类型错误、导出内容为空 |
| 404 | 路由不存在 | URL 错误，或平台模式下误用工具根路径 |
| 413 | 请求体过大 | 日志内容超过 25 MB |
| 500 | 工具内部错误 | 日志导出目录不可写等服务端异常 |
| 502 | 上游服务不可用 | 工具未启动、异常退出或代理暂时无法连接 |
| 503 | 平台暂未就绪 | PostgreSQL 不可用 |
| 504 | 上游连接或处理超时 | 工具不可达或处理时间超过代理限制 |

工具不可用时，页面请求返回统一的“工具暂时不可用”HTML。测试脚本应以 HTTP 状态码为准，不要只检查响应正文。

## 3. 平台接口

### 3.1 获取平台首页

```http
GET /
```

#### 请求示例

```bash
curl -i "$PLATFORM_BASE_URL/"
```

#### 成功响应

```text
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: no-cache
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
Referrer-Policy: same-origin
```

页面由 React 渲染，正常情况下工具数据来自 `/api/v1/tools`。API 异常时页面显示“平台服务暂时不可用，当前显示基础工具入口”，并保留：

```text
/trackevents/
/log-filter/
/truthy-search/
```

### 3.2 平台存活与就绪

```bash
curl -i "$PLATFORM_BASE_URL/api/v1/health/live"
curl -i "$PLATFORM_BASE_URL/api/v1/health/ready"
```

存活成功：

```json
{"service":"platform-api","status":"ok"}
```

数据库可用时就绪接口返回 200：

```json
{"service":"platform-api","status":"ready"}
```

数据库不可用时返回 503 和统一错误结构。

### 3.3 工具目录

```bash
curl -i "$PLATFORM_BASE_URL/api/v1/tools"
```

只返回启用工具，按 `sort_order`、`name` 排序；内部 `health_url` 不对外返回。

```json
{
  "items": [
    {
      "id": "trackevents",
      "name": "埋点测试",
      "description": "解析 TrackEvents 日志并校验事件字段",
      "entry_url": "/trackevents/",
      "short_code": "EVENT",
      "icon_key": "event",
      "category": "analysis",
      "features": ["事件统计", "字段校验", "结果报告"],
      "sort_order": 10
    }
  ]
}
```

### 3.4 工具健康状态

```bash
curl -i "$PLATFORM_BASE_URL/api/v1/tools/trackevents/health"
```

上游正常或异常都返回 200，`status` 分别为 `healthy` 或 `unhealthy`：

```json
{
  "tool_id": "trackevents",
  "status": "healthy",
  "checked_at": "2026-07-31T04:33:49.050419Z"
}
```

未知或禁用工具返回 404。平台 API 错误统一为：

```json
{
  "code": "NOT_FOUND",
  "message": "工具不存在",
  "request_id": "req_xxx"
}
```

响应头同时包含 `X-Request-ID`。

### 3.5 无末尾斜杠跳转

```bash
curl -I "$PLATFORM_BASE_URL/trackevents"
curl -I "$PLATFORM_BASE_URL/log-filter"
curl -I "$PLATFORM_BASE_URL/truthy-search"
```

预期：

```text
HTTP/1.1 308 Permanent Redirect
Location: /trackevents/
```

或：

```text
HTTP/1.1 308 Permanent Redirect
Location: /log-filter/
```

`Location` 使用相对地址，可以保留当前访问域名和端口。

### 3.6 Truthy_Search 平台健康代理

```bash
curl -i "$PLATFORM_BASE_URL/api/v1/tools/truthy-search/health"
```

响应继续使用平台统一格式，正常时 `status=healthy`。上游 Flask 或 SQLite 不可用时仍返回 HTTP 200，且 `status=unhealthy`。

## 4. 埋点测试接口

### 4.1 健康检查

```http
GET /trackevents/health
Accept: application/json
```

#### 请求示例

```bash
curl -sS "$PLATFORM_BASE_URL/trackevents/health"
```

#### 成功响应

```json
{
  "service": "trackevents",
  "status": "ok"
}
```

#### 响应说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `service` | string | 固定为 `trackevents` |
| `status` | string | 正常时固定为 `ok` |

该接口只验证 Web 服务可访问，不读取默认日志、不执行分析，也不验证外部业务系统。

### 4.2 埋点日志分析

```http
POST /trackevents/api/analyze
Content-Type: application/json
```

#### 4.2.1 请求体

```json
{
  "log_text": "待分析的完整日志文本",
  "expected_counts": {
    "app_start": 2,
    "paywall_show": 1
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `log_text` | string | 否 | 待分析日志；为空字符串或未传时读取容器中的 `default.log` |
| `expected_counts` | object | 否 | 事件名到预期触发次数的映射；默认 `{}` |
| `expected_counts.<事件名>` | integer/string integer | 否 | 可转换为整数的预期次数 |

约束：

- `expected_counts` 必须是 JSON 对象；
- 每个预期次数必须可以转换为整数；
- `log_text` 优先于默认日志；
- 业务校验失败通常仍返回 HTTP 200，具体通过或失败状态在响应 JSON 中表达；
- 请求解析失败或参数类型错误返回 HTTP 400。

#### 4.2.2 使用默认日志

```bash
curl -sS -X POST \
  "$PLATFORM_BASE_URL/trackevents/api/analyze" \
  -H 'Content-Type: application/json' \
  --data '{"log_text":"","expected_counts":{}}'
```

#### 4.2.3 分析本地日志文件

以下命令使用 `jq` 生成合法 JSON，避免日志中的引号和换行破坏请求体：

```bash
jq -Rs '{log_text: ., expected_counts: {app_start: 2}}' ./default.log \
  | curl -sS -X POST \
      "$PLATFORM_BASE_URL/trackevents/api/analyze" \
      -H 'Content-Type: application/json' \
      --data-binary @-
```

不使用 `jq` 时，可以通过 Python 构造请求：

```bash
python3 -c 'import json,sys; print(json.dumps({"log_text":sys.stdin.read(),"expected_counts":{}}))' \
  < ./default.log \
  | curl -sS -X POST \
      "$PLATFORM_BASE_URL/trackevents/api/analyze" \
      -H 'Content-Type: application/json' \
      --data-binary @-
```

#### 4.2.4 成功响应结构

```json
{
  "summary": {
    "request_count": 2,
    "response_count": 0,
    "event_count": 2,
    "passed_event_count": 0,
    "failed_event_count": 2,
    "failed_response_count": 2,
    "failed_count_check_count": 0
  },
  "event_counts": {
    "app_start": 2
  },
  "event_stats": [
    {
      "module": "app",
      "event_name": "app_start",
      "count": 2
    }
  ],
  "count_checks": [
    {
      "event_name": "app_start",
      "expected": 2,
      "actual": 2,
      "status": "pass"
    }
  ],
  "events": [],
  "response_checks": [],
  "common_param_summary": [],
  "common_param_events": [],
  "markdown_report": "# 埋点测试报告\n..."
}
```

上例中的计数仅用于说明结构，实际内容由提交日志决定。

#### 4.2.5 顶层响应字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `summary` | object | 分析结果总览 |
| `event_counts` | object | 每个事件名对应的实际次数 |
| `event_stats` | array | 按模块和事件聚合的统计 |
| `count_checks` | array | 预期次数与实际次数的比较结果 |
| `events` | array | 逐事件字段校验详情 |
| `response_checks` | array | 请求与响应匹配及服务端接收结果检查 |
| `common_param_summary` | array | 每个公共参数的汇总检查 |
| `common_param_events` | array | 每个事件的公共参数实际值与缺失项 |
| `markdown_report` | string | 可保存或展示的 Markdown 报告 |

#### 4.2.6 `summary` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `request_count` | integer | 识别到的 TrackEvents 请求数 |
| `response_count` | integer | 识别到的对应响应数 |
| `event_count` | integer | 解析出的事件总数 |
| `passed_event_count` | integer | 业务字段校验通过的事件数 |
| `failed_event_count` | integer | 业务字段校验失败的事件数 |
| `failed_response_count` | integer | 响应检查失败数 |
| `failed_count_check_count` | integer | 预期次数检查失败数 |

#### 4.2.7 `events` 元素

```json
{
  "request_index": 1,
  "event_index": 1,
  "event_id": "94f65e82-e0b7-4d80-b726-d76827e01152",
  "event_name": "app_start",
  "event_time_ms": 1784023979001,
  "properties": {
    "logtime": 1784023979001,
    "log_id": "94f65e82-e0b7-4d80-b726-d76827e01152"
  },
  "module": "app",
  "required_params": ["is_first", "search_count"],
  "business_params": {
    "is_first": null,
    "search_count": null
  },
  "extra_params": {},
  "status": "fail",
  "errors": [
    "缺少业务子参: is_first",
    "缺少业务子参: search_count"
  ],
  "warnings": []
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `request_index` | integer | 事件所属请求序号 |
| `event_index` | integer | 事件在请求中的序号 |
| `event_id` | string/null | 事件唯一标识 |
| `event_name` | string | 事件名/action |
| `event_time_ms` | integer/null | 事件时间戳，单位毫秒 |
| `properties` | object | 原始事件属性 |
| `module` | string | 根据规则识别的功能模块 |
| `required_params` | array | 当前事件要求的业务参数 |
| `business_params` | object | 业务参数实际值 |
| `extra_params` | object | 疑似多传的业务参数及其值 |
| `status` | string | `pass` 或 `fail` |
| `errors` | array | 阻断通过的错误信息 |
| `warnings` | array | 非阻断警告信息 |

#### 4.2.8 `response_checks` 元素

```json
{
  "request_index": 1,
  "request_event_count": 1,
  "accepted_count": null,
  "success": null,
  "status": "fail",
  "errors": ["存在请求但没有对应响应"]
}
```

#### 4.2.9 `common_param_summary` 元素

```json
{
  "key": "logtime",
  "required": true,
  "allow_empty": false,
  "event_count": 2,
  "present_count": 2,
  "missing_count": 0,
  "empty_count": 0,
  "status": "pass"
}
```

#### 4.2.10 `common_param_events` 元素

```json
{
  "request_index": 1,
  "event_index": 1,
  "module": "app",
  "event_name": "app_start",
  "event_id": "94f65e82-e0b7-4d80-b726-d76827e01152",
  "values": {
    "logtime": 1784023979001,
    "action": "app_start"
  },
  "missing_required": ["net", "pkg"],
  "empty_not_allowed": [],
  "status": "fail"
}
```

#### 4.2.11 参数错误响应

请求：

```bash
curl -i -X POST \
  "$PLATFORM_BASE_URL/trackevents/api/analyze" \
  -H 'Content-Type: application/json' \
  --data '{"log_text":"test","expected_counts":[]}'
```

响应：

```json
{
  "error": "expected_counts 必须是 JSON 对象"
}
```

HTTP 状态：`400 Bad Request`。

无效 JSON、无法转换为整数的预期次数、默认日志不存在或分析过程异常，也使用以下结构：

```json
{
  "error": "具体错误信息"
}
```

## 5. 日志分析接口

### 5.1 健康检查

```http
GET /log-filter/health
Accept: application/json
```

#### 请求示例

```bash
curl -sS "$PLATFORM_BASE_URL/log-filter/health"
```

#### 成功响应

```json
{
  "service": "log-filter",
  "status": "ok"
}
```

该接口不读取示例日志、不执行日志分析、不检查导出目录。

### 5.2 获取日志分析页面

```http
GET /log-filter/
```

#### 请求示例

```bash
curl -i "$PLATFORM_BASE_URL/log-filter/"
```

成功时返回 `200 OK` 和 HTML 页面。

### 5.3 提交日志筛选

```http
POST /log-filter/
Content-Type: application/x-www-form-urlencoded
```

该接口是 HTML 表单接口，成功响应为渲染后的 HTML，不是 JSON。

#### 5.3.1 表单字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `log_text` | string | 是 | 需要分析的完整日志 |
| `method` | string/list | 否 | 要筛选的方法名；可重复提交多个值 |

特殊值：

```text
__ALL__
```

表示显示全部识别到的接口日志。未传 `method` 时，也按全部处理。

#### 5.3.2 筛选全部接口

```bash
curl -sS -X POST \
  "$PLATFORM_BASE_URL/log-filter/" \
  --data-urlencode 'log_text@./sample.log' \
  --data-urlencode 'method=__ALL__' \
  -o result.html
```

#### 5.3.3 筛选单个接口

```bash
curl -sS -X POST \
  "$PLATFORM_BASE_URL/log-filter/" \
  --data-urlencode 'log_text@./sample.log' \
  --data-urlencode 'method=GetMe' \
  -o result.html
```

#### 5.3.4 筛选多个接口

```bash
curl -sS -X POST \
  "$PLATFORM_BASE_URL/log-filter/" \
  --data-urlencode 'log_text@./sample.log' \
  --data-urlencode 'method=GetMe' \
  --data-urlencode 'method=TrackEvents' \
  -o result.html
```

#### 5.3.5 业务提示

HTTP 200 不一定表示识别到了有效日志。以下业务情况会在 HTML 页面中显示提示：

- 日志为空：`请先粘贴日志内容`；
- 未识别到 method：`未识别到 method，请检查日志格式`；
- 所选接口没有匹配日志：`没有匹配到相关日志`。

自动化测试如需判断业务结果，应解析页面中的提示、接口名称和统计内容，而不能只断言 HTTP 200。

### 5.4 获取示例日志

```http
GET /log-filter/sample
```

#### 请求示例

```bash
curl -sS "$PLATFORM_BASE_URL/log-filter/sample" -o sample.log
```

#### 成功响应

- HTTP 状态：`200 OK`；
- 当前 Content-Type：`text/html; charset=utf-8`；
- 响应正文：`log_default.log` 的完整文本；
- 示例文件不存在时返回空字符串，当前仍为 HTTP 200。

### 5.5 导出日志

```http
POST /log-filter/export
Content-Type: application/json
```

该接口将内容保存到服务端目录，不会直接向客户端返回日志文件。

#### 5.5.1 请求体

```json
{
  "export_type": "filtered_result",
  "content": "需要保存的日志文本"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `export_type` | string | 是 | `log_content` 或 `filtered_result` |
| `content` | string | 是 | 待保存内容，不能是空字符串或纯空白 |

导出类型与文件名前缀：

| `export_type` | 文件名前缀 |
|---|---|
| `log_content` | `log_content_` |
| `filtered_result` | `filtered_result_` |

文件名使用 Asia/Shanghai 时区的时间戳；同一秒内重名时自动增加序号，不覆盖已有文件。

#### 5.5.2 请求示例

```bash
curl -sS -X POST \
  "$PLATFORM_BASE_URL/log-filter/export" \
  -H 'Content-Type: application/json' \
  --data '{
    "export_type": "filtered_result",
    "content": "[HTTP] <-- 200 method=GetMe"
  }'
```

#### 5.5.3 成功响应

```json
{
  "message": "导出成功",
  "filename": "filtered_result_20260721_153000.log",
  "path": "/tmp/log-exports/filtered_result_20260721_153000.log"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `message` | string | 操作结果 |
| `filename` | string | 服务端生成的文件名 |
| `path` | string | 服务端显示路径 |

平台 Compose 默认将导出目录设为容器内 `/tmp/log-exports`。该目录不提供 HTTP 下载接口，容器重建后文件会清除。

#### 5.5.4 不支持的类型

请求：

```json
{
  "export_type": "invalid",
  "content": "test"
}
```

响应状态：`400 Bad Request`。

```json
{
  "message": "不支持的导出类型"
}
```

#### 5.5.5 空内容

请求：

```json
{
  "export_type": "log_content",
  "content": ""
}
```

响应状态：`400 Bad Request`。

```json
{
  "message": "当前内容为空，无法导出"
}
```

#### 5.5.6 文件系统错误

导出目录无法创建或写入时返回 `500 Internal Server Error`：

```json
{
  "message": "导出失败：具体文件系统错误"
}
```

客户端不能通过请求参数指定服务端保存目录。

### 9.5 常见问题

#### 无法连接 `127.0.0.1:8080`

依次检查：

1. Docker Desktop 是否已启动；
2. `docker compose ps -a` 是否有五个常驻服务和退出码为 0 的迁移服务；
3. `.env` 中是否修改了 `PLATFORM_PORT`；
4. 8080 端口是否被其他进程占用；
5. `platform-gateway` 日志是否存在配置错误。

如果出现以下信息：

```text
failed to connect to the docker API
```

说明 Docker daemon 没有运行，应先启动 Docker Desktop，再执行 Compose 命令。

#### 首页正常，但工具返回 502 或 504

说明 Nginx 正常，但对应工具服务不可用。检查：

```bash
docker compose ps
docker compose logs --tail=100 trackevents-web
docker compose logs --tail=100 log-filter-tool
docker compose logs --tail=100 truthy-search
```

#### 请求返回 404

检查是否遗漏平台前缀：

```text
错误：/api/analyze
正确：/trackevents/api/analyze

错误：/export
正确：/log-filter/export
```

#### 表单返回 200，但没有筛选结果

日志筛选接口使用 HTML 表达业务结果。检查返回页面是否包含：

- `未识别到 method`；
- `没有匹配到相关日志`；
- `请先粘贴日志内容`。

#### 导出成功但宿主机找不到文件

平台默认导出到日志工具容器的 `/tmp/log-exports`。调试时可以查看：

```bash
docker compose exec log-filter-tool ls -la /tmp/log-exports
```

该目录为临时目录，当前没有下载接口，容器重建后文件会清除。

## 10. 独立运行时的路径差异

平台 Compose 为工具配置了基础路径：

测试平台聚合功能时，应始终通过统一入口访问，不要直接依赖工具内部容器端口。

## 11. 当前接口限制

- 没有登录、鉴权、权限和限流；
- 没有统一任务 ID、任务查询和取消接口；
- 没有批量聚合所有工具状态的单一接口；
- 日志筛选主接口返回 HTML，不是 JSON；
- 日志导出只保存到服务端，没有下载接口；
- 导出文件默认不持久化；
- 埋点分析为同步接口，大日志处理受 60 秒代理超时限制；
- 健康检查只表示 Web 服务可用，不代表全部业务能力正常。
- Truthy_Search 使用单机 SQLite，平台模式与独立模式必须互斥运行。

这些限制属于 MVP 范围，后续建设统一任务记录、结果汇总和权限体系时，应对接口进行版本化设计，避免直接破坏本文档中的现有路径。
