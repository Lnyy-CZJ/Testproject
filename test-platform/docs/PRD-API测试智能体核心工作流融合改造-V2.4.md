### 1.1 文档优先级

V2.4 不是 V2.2/V2.3 的小范围补丁，而是 API 测试智能体三个执行前阶段的新产品基线。

当历史 PRD、现有实现与 V2.4 冲突时，按以下顺序处理：

1. 真实执行安全、数据脱敏、历史产物不丢失等不可降低的安全与数据边界；
2. 用户在 V2.4 已确认的核心工作流、阶段门禁和角色权限；
3. V2.4 阶段一至四的产品流程、产物 Schema、状态机和页面要求；
4. V2.2/V2.3 中不冲突的稳定性、可解释性和可观察性能力；
5. 当前代码仅作为迁移起点，不作为限制 V2.4 产品设计的理由。

V2.4 允许为了忠实表达旧核心流程而调整现有 Schema、API、状态机、模块边界和页面交互。历史任务通过兼容读取层保留，不要求新流程继续受历史字段结构限制。

## 2. 文档目的

本次改造解决“页面具备 V2 Review 和安全门禁，但实际生成体验与旧 API 测试智能体核心流程割裂”的问题。

V2.4 不回退版本、Evidence、人工 Review、审计和执行安全边界，但允许重新设计 V2.2/V2.3 中不符合真实测试工作方式的门禁、权限和数据结构。旧 API 测试智能体中已经验证有效的解析、测试设计、步骤编排、依赖识别和完整请求生成能力，将保留 LangGraph/Workflow 的内部节点编排，剥离副作用后正式成为平台主调用链。

本 PRD 重点回答并固化以下产品问题：

1. 如何避免接口解析丢失请求体和鉴权信息；
2. 如何真正复用旧 L1～L5、T1～T4 测试设计能力生成基础用例；
3. 如何真正复用旧 `api_case_generator` 能力生成完整可执行用例；
4. 如何让测试人员在阶段二完成 Review 后，明确、受控地进入阶段三；
5. 如何证明每个阶段实际运行了哪个工作流、Prompt、模型和输入版本；
6. 如何在复用旧核心能力的同时，禁止旧 MySQL 写入、旧 CLI 直接执行和任何安全门禁绕过。
7. 如何在一个 Run 中可靠执行登录、取数、写入、校验、退出等多接口参数依赖链。

## 3. 背景与已确认问题

### 3.1 当前产品体验问题

- 非结构化接口文档经过模型解析后，适配为 V2 Contract 时可能丢失 `requestBody`、Cookie、鉴权和会话要求。
- “明确无需鉴权”与“没有解析出鉴权信息”都表现为空数组，测试人员无法区分。
- 基础用例虽然标记为 `v2_fused`，但当前主要由新的纯函数生成，未完整运行旧核心工作流中的测试设计节点。
- 可执行用例生成虽使用了旧 Prompt 的部分能力，但没有完整接入旧请求编排工作流，容易出现 `body=null`、断言不完整或大量候选被禁用。
- 页面缺少完整的可执行用例详情，无法直观看到 Header、Query、Cookie、Body、变量、依赖和断言。
- “生成来源为 v2_fused”只能说明配置标识，不能证明旧核心流程的哪些节点真实执行过。
- 当前平台真实 Executor 虽能发送 HTTP 请求，但只是按输入数组逐条执行，没有消费 `precondition_case_ids`、变量来源和依赖拓扑。
- 当前 Executor 没有 Run 级变量仓库、共享 Cookie Jar、响应提取、依赖失败传播和分支执行能力。

### 3.2 根因判断

当前实现属于“能力借用”，而不是“工作流接入”：

- 新 Runner 掌握主要生成流程；
- 旧 Prompt 和部分纯函数被复用；
- 旧工作流反向委托新函数；
- 旧工作流中的上下文编排、节点边界、修复循环和完整生成语义没有成为平台主调用链。

因此，本次改造不是恢复旧入口，而是恢复旧核心能力，并将其纳入 V2 控制平面。

### 3.3 当前真实执行能力结论

当前代码和本机开发部署已经具备真实执行基础设施：API Agent、独立 Execution Controller、固定 Executor 镜像、单 Run 容器、Egress Proxy 和目标登记均已存在。本机开发环境已经开启执行并登记一个测试目标。

但现有 Executor 只适合彼此独立的单接口用例：它可以发送 method、path、query、header 和 JSON body，请求结果也能保存为 CaseResult；它不能完整执行“登录返回 Token/Cookie → 提取变量 → 注入后续请求 → 根据依赖结果继续或阻断”的链路。

旧 `BaseTestCase`/`TestExecutor` 具有前置接口、变量替换、响应提取、Cookie Session 和 setup/teardown 等能力，但混有 MySQL 回写、DB 权限、宽松脚本执行和不完整的依赖图语义。因此阶段四必须复用旧执行语义，而不是直接恢复旧执行入口。

## 4. 产品原则与锁定决策

### 4.1 控制平面与主生成引擎分离

| 职责 | 平台 V2 控制平面 | 改造后的旧核心工作流生成引擎 |
| --- | --- | --- |
| 任务与 Attempt | 负责 | 不负责 |
| 版本、SHA、审计 | 负责 | 只返回来源元数据 |
| 人工 Review 和权限 | 负责 | 不负责 |
| Evidence、Grounding、完整性与安全门禁 | 定义规则并最终裁决 | 在节点中执行并返回结果 |
| 文档解析候选 | 调度、Review 和保存 | 通过阶段一 LangGraph 负责生成 |
| 测试设计候选 | 调度、Review 和保存 | 通过 `ApiBaseCaseGeneratorWorkFlow` 负责生成、检查和补齐 |
| 执行定义候选 | 调度、Review 和保存 | 通过 `ApiRunCaseGeneratorWorkFlow` 负责完整请求编排和修复 |
| ExecutionPlan | 固化版本、确认 SHA、目标和策略 | 确定性计划编译器生成依赖 DAG，不调用模型 |
| 真实接口执行 | Controller、容器、Egress、权限和审计 | 容器内确定性 DAG Executor 执行，旧 LangGraph 不发送请求 |
| MySQL 或外部存储写入 | 禁止 | 禁止 |
| 真实接口执行 | 只能走受控 Controller/Executor | 禁止 |

### 4.2 “旧工作流是主引擎，但不是独立平台入口”

V2.4 正式保留并接入旧 LangGraph/Workflow 的内部节点编排。平台 Runner 不得再绕过工作流，直接把 `generate_fused_cases()` 或 `build_executable_cases()` 当作主生成器；这些 V2 函数应调整为工作流节点可调用的确定性规则、规范化或最终校验能力。

本期保留：

- LangGraph 的状态、节点、条件边和有限修复循环；
- `ApiBaseCaseGeneratorWorkFlow` 的生成、覆盖检查、补充和输出语义；
- `ApiRunCaseGeneratorWorkFlow` 的工具/数据加载、用例生成、静态检查和输出语义；
- 旧 Prompt 的测试设计和完整请求生成能力；
- 每个节点独立的事件、模型调用和 Token 记录。

本期明确不恢复：

- 旧智能体作为独立 Web/CLI 平台入口；
- 跨越人工 Review 边界的一次性总图自动运行；
- 旧 MySQL 保存节点；
- 旧 CLI 的 `execute_test_cases()`；
- 旧工作流自行改变任务状态；
- 旧工作流自行读写任意任务目录；
- 旧工作流直接发送真实请求。

旧核心流程必须被改造成：输入明确、输出结构化、除模型调用外无外部副作用、可记录节点事件、可由 V2 控制平面校验和保存的主生成工作流。

### 4.3 LangGraph 分段方式

人工 Review 是产品门禁，不应被一个无暂停点的总图跨越。因此保留三个可独立运行、可独立重试的 LangGraph：

1. `ContractAnalysisWorkflow`：阶段一契约分析；
2. `ApiBaseCaseGeneratorWorkFlow`：阶段二基础用例生成；
3. `ApiRunCaseGeneratorWorkFlow`：阶段三执行定义生成。

三个图由平台 Runner 顺序调度，但不会自动串行到底。每个图完成后先将结构化候选交给 V2 控制平面保存和 Review；只有人工门禁通过，Runner 才能启动下一个图。

旧 `api_case_generator_main_workflow` 可保留为 CLI 兼容外壳，但平台不得使用它跨越阶段一至三的人工门禁。

阶段四不使用 LLM 或 LangGraph 临时决定请求顺序。阶段三输出的已确认执行定义必须先由确定性 `ExecutionPlanCompiler` 编译为有向无环图，再交给受限容器中的 `DependencyAwareExecutor` 执行。这样既保留旧核心的前置接口和变量传递能力，又避免模型在执行时改变目标、参数依赖或安全策略。

### 4.4 Schema 重设计权限

V2.4 不强制将旧工作流输出压缩进现有不完整 Schema。允许新增更完整的产物 Schema，并建议使用独立 `artifact_schema_version=3`：

- `ApiContractV3`：显式表达请求体、鉴权结论、会话、依赖和字段 Evidence；
- `BaseTestCaseV3`：表达完整测试设计、步骤、数据、依赖、预期、风险和生成节点；
- `ExecutableCaseV3`：表达结构化请求、变量、依赖、数据引用、断言、观察目标和受控脚本；
- `WorkflowAttempt`：表达图版本、节点状态、重试、输入输出版本和模型用量。

Task Schema 是否继续显示 V2 不影响产物 Schema 独立升级。历史 V1/V2 产物通过 Adapter 只读展示；需要创建新 Run 时，必须重新生成或转换为通过 V2.4 门禁的 current 产物。

### 4.5 硬边界与可重设计项

为了避免再次因历史方案限制核心流程，V2.4 只锁定以下硬边界：

- 确定性契约事实优先，模型不能静默覆盖；
- 人工 Review 不能被工作流自动跨越；
- 生成过程不得调用真实目标 API；
- 真实执行不能绕过 Controller/Executor 和最终确认；
- 不向旧 MySQL 或外部系统写入；
- 历史版本、Run、报告和 Bug 草稿不删除、不覆盖；
- 文档、Prompt、日志、产物和页面展示必须脱敏。

除上述硬边界外，以下内容允许在开发设计阶段根据核心工作流重新设计，不受 V2.2/V2.3 既有实现约束：

- LangGraph 的节点拆分、条件边、状态对象和修复循环；
- Contract、BaseCase、ExecutableCase 的字段和嵌套结构；
- 阶段状态和 Attempt 类型；
- Review 页面布局、操作名称和批量确认方式；
- API 路径、请求体和返回信封；
- 角色到执行前能力的映射；
- 原有 Prompt 的拆分、参数化和版本升级；
- 为隔离副作用而新增的 Adapter、Port 或输出模型。
- ExecutionPlan 的节点、依赖边、失败传播和变量作用域模型。

开发设计不得为了保持当前代码改动更小，而牺牲请求体、鉴权、测试步骤、依赖或完整执行定义。

### 4.3 人工门禁

- 阶段一契约未确认，不得进入阶段二。
- 阶段二基础用例未 Review，不得进入阶段三。
- 阶段三只生成可执行用例，不自动发起真实执行。
- 可执行用例生成完成后，仍需进入“执行准备”并完成目标、风险、权限和确认 SHA 校验，才允许创建 Run。

## 5. 产品目标与非目标

### 5.1 产品目标

- 请求体、Header、Query、Cookie、鉴权、响应和依赖信息能够从原文进入规范化 Contract。
- 登录、退出登录、当前用户等接口只能生成与其契约和文档上下文有关的场景。
- 基础用例包含前置条件、步骤、参数变化、测试数据、依赖、预期结果、来源和风险。
- 可执行用例包含完整请求、变量提取、依赖、断言或探索观察目标。
- 多接口依赖链可以在同一 Run 容器中按拓扑顺序执行，并正确传递变量、Cookie 和 CSRF Token。
- 测试人员可以逐条确认或一键确认基础用例，并通过明确按钮进入阶段三。
- 页面能够证明实际执行的工作流节点、Prompt、模型、Token 和版本。
- 单条模型坏数据不导致整个接口或整个阶段失败。

### 5.2 非目标

- 不降低真实执行 Controller、容器、Egress、目标登记和 Credential 注入的安全要求。
- 不取消现有 Controller、单 Run 容器、Egress 和目标登记架构；阶段四允许升级容器内 Executor 的执行能力及其输入输出 Schema。
- 不绕过 `API_EXECUTION_ENABLED`。
- 不实现 Postman、gRPC、WebSocket、GraphQL。
- 不恢复旧 MySQL 写入。
- 不实现外部 Bug 提交或稳定资产发布。
- 不允许模型生成 Host、Credential、网络模式或任意环境变量。
- 不将“生成执行定义”与“执行真实接口”合并为同一个操作。

## 6. 角色与权限

本节为 V2.4 的独立权限基线。若 V2.2/V2.3 或当前迁移中的角色授权与本节冲突，以本节为准，不得因历史权限设计限制测试人员完成执行前流程。

| 操作 | 管理员 | 测试开发 | 测试人员 | 只读角色 |
| --- | --- | --- | --- | --- |
| 查看阶段一至四产物 | 是 | 是 | 是 | 是，按任务可见范围 |
| 修改并确认契约 | 是 | 是 | 是 | 否 |
| 编辑、确认基础用例 | 是 | 是 | 是 | 否 |
| 一键确认可确认用例 | 是 | 是 | 是 | 否 |
| 确认高风险基础用例 | 是 | 是 | 是 | 否 |
| 生成执行定义 | 是 | 是 | 是 | 否 |
| Review 可执行用例 | 是 | 是 | 是 | 否 |
| 查看依赖图和执行预览 | 是 | 是 | 是 | 是，按任务可见范围 |
| 创建真实 Run | 继续服从现有 execute 权限及安全门禁 | 继续服从现有 execute 权限及安全门禁 | 继续服从现有 execute 权限及安全门禁 | 否 |

高风险用例允许批量确认，但确认对话框必须单独列出高风险数量和用例，且每条高风险用例生成独立审计记录。任何质量 blocker 不得被批量操作绕过。

权限按能力而不是页面名称判断：`contract.review`、`case.review`、`executable.generate`、`executable.review` 和 `run.execute` 相互独立。拥有前三项不等于拥有真实执行权限；因此测试人员可以完整完成阶段一至三，但创建 Run 仍必须单独满足 `run.execute` 和现有安全门禁。

## 7. 目标端到端流程

```text
上传或修订接口文档
→ 阶段一：核心契约解析工作流
→ V2 Contract Adapter
→ 完整性与依据门禁
→ 测试人员 Review 并确认契约
→ 阶段二：核心基础用例工作流
→ 确定性覆盖合并与最多 3 轮补齐
→ Grounding、完整性和风险门禁
→ 测试人员逐条检查或一键确认
→ 点击“确认并生成执行定义”
→ 阶段三：核心可执行用例工作流
→ 请求规范化与静态安全校验
→ 保存并展示可执行用例
→ 测试人员 Review
→ 阶段四：编译 ExecutionPlan 依赖图
→ 展示执行准备、依赖链和失败策略
→ 最终人工确认
→ 一个 Run 创建一个受限容器
→ 按依赖图执行并生成逐步骤报告
```

其中，“确认并生成执行定义”表示进入阶段三自动生成可执行用例，不表示立即执行真实 API。

## 8. P0：阶段一——核心契约解析工作流改造

### 8.1 输入范围

阶段一对每个文档版本和分析范围创建独立 Attempt，输入必须包含：

- 脱敏后的文档切片及 Section ID；
- 文档版本、SHA 和格式；
- 当前分析范围；
- OpenAPI/Swagger 确定性解析结果（如有）；
- 支持类型和大小限制；
- Prompt ID、版本和 SHA。

结构化 OpenAPI/Swagger 的确定性事实继续优先。旧 AI 解析能力仅用于非结构化文档，或对确定性解析无法覆盖的业务说明形成建议，不得覆盖确定性事实。

### 8.2 核心解析主工作流

```text
文档预检与格式路由
→ 确定性解析或文档切片
→ 旧 AI 接口解析能力
→ 逐接口结构化候选
→ V2 Contract Adapter
→ 请求体与鉴权完整性检查
→ 字段 Evidence 绑定
→ 质量门禁
→ 输出候选契约
```

阶段一允许新建 `ContractAnalysisWorkflow`，把现有确定性解析器、旧 `AIAPIDocumentParser` 和 V2 Adapter 纳入同一个可观测 LangGraph。每个节点必须返回结构化结果和节点状态，不得直接写数据库、任务目录或任务状态；候选契约由 Runner 接收后统一保存。

### 8.3 V2 Contract Adapter

Adapter 至少映射并保留：

- method、path、接口名称和说明；
- Path、Query、Header、Cookie 参数；
- 请求体媒体类型、Schema、字段、必填性、约束和示例；
- 响应状态码、媒体类型、Schema、字段和示例；
- 鉴权结论、鉴权方案、Token/Cookie/CSRF 要求；
- 前置接口、会话或数据依赖；
- 字段来源、原文位置和推断类型。

### 8.4 鉴权结论模型

不得继续用空 `security` 同时表达“无需鉴权”和“未解析”。契约必须新增明确结论：

| 结论 | 含义 | 是否可确认 |
| --- | --- | --- |
| `none` | 文档明确说明无需鉴权或无需会话 | 有直接 Evidence 时可确认 |
| `required` | 文档明确要求鉴权、会话、Cookie、CSRF 或 Bearer | 方案和 Evidence 完整时可确认 |
| `optional` | 文档明确说明鉴权可选 | 有直接 Evidence 时可确认 |
| `unresolved` | 文档未说明或解析结果不足 | 不可直接确认，必须人工处理 |

`required` 还必须保存方案类型、凭证位置、关联字段和 Evidence。平台只保存契约要求，不在本阶段保存真实凭证值。

### 8.5 请求体完整性

请求体字段至少包括：

- 字段名称和嵌套路径；
- 类型；
- 是否必填；
- 枚举、长度、范围、格式等约束；
- 示例或测试值提示；
- 媒体类型；
- 原文 Evidence。

若原文存在“请求体、Body、JSON、Form、字段表或 Curl `-d`”等信号，但标准化结果中 `request_body` 为空，必须产生 `CONTRACT_REQUEST_BODY_MISSING` blocker。

### 8.6 鉴权完整性

若原文存在“鉴权、登录态、会话、Cookie、CSRF、Bearer、Authorization、Token”等信号，但没有明确鉴权结论，必须产生 `CONTRACT_AUTH_CONCLUSION_MISSING` blocker。

若文档明确写明“无需会话”或“无需鉴权”，必须保存 `auth_conclusion=none` 及对应 Evidence，不得只保存空列表。

### 8.7 Evidence 与人工 Review

每个关键字段必须展示：

- 业务字段名称；
- 当前解析值；
- 来源类型：确定性解析、文档事实、AI 推断或人工决定；
- 原文 Section、行号/字符范围或 JSON Pointer；
- 原文片段；
- 该字段对后续用例的影响。

测试人员可修改契约、重新关联原文、删除 AI 推断、转为测试建议或进行人工确认。人工确认必须填写理由并生成新版本。

### 8.8 阶段一完成条件

- 至少一个契约为 `confirmed`；
- 请求体和鉴权 blocker 已解决；
- 关键字段具备 Evidence 或明确的人工决定；
- 当前契约版本和 SHA 已固定；
- 阶段事件与生成来源已保存。

## 9. P0：阶段二——核心基础用例工作流改造

### 9.1 单接口最小上下文

每个契约独立构造 Generation Context，只包含：

- 当前已确认契约；
- 与当前接口直接相关的文档片段；
- 字段 Evidence；
- 已确认依赖契约的摘要；
- 当前分析范围；
- 已接受的测试建议；
- 已有覆盖矩阵和相关历史用例摘要。

不得将其他无关接口、整个任务文档或示例业务域无差别发送给模型，以避免登录接口生成商品、订单或支付场景。

### 9.2 核心基础用例主工作流

```text
加载并校验 Generation Context
→ “生成基础测试用例”节点：运行旧 L1～L5 / T1～T4 测试设计
→ 合并 V2 确定性覆盖骨架并去重
→ “检查用例覆盖率”节点：计算结构化覆盖缺口
→ 条件边：输出或进入补齐
→ “补充生成测试用例”节点：最多 3 轮定向补齐
→ Grounding、完整性和风险校验节点
→ “输出基础测试用例”节点：返回结构化候选
→ V2 控制平面保存 confirmed_candidate
→ 人工 Review
```

`ApiBaseCaseGeneratorWorkFlow` 是阶段二主生成路径。当前 V2 分支中由它反向委托 `generate_fused_cases()` 的实现必须调整：旧工作流节点负责测试设计和补齐；`fused_kernel`、覆盖规则和 Grounding 作为图内确定性节点或工具使用，不得替代整张图。

### 9.3 必须保留的旧核心能力

- 完整测试设计 Prompt；
- L1～L5 和 T1～T4 的测试设计规则；
- 前置条件和测试步骤；
- 参数角色和参数变化；
- 测试数据和 `data_ref`；
- 接口依赖和数据依赖；
- 业务场景补充；
- 预期接口结果和业务结果；
- 工作流节点日志和模型修复记录。

### 9.4 V2 必须替换的旧行为

- 覆盖率由结构化矩阵计算，不读取模型文本中的“100%”；
- 补齐最多 3 轮；新增数为 0 或缺口连续两轮不变时提前结束；
- 不写 MySQL；
- 不自动确认任何模型用例；
- 不自动进入阶段三；
- 单条候选失败只拒绝该条，不导致整个阶段失败；
- 确定性用例和 LLM 用例都先进入 `confirmed_candidate`；
- 探索性用例必须人工确认，且不自动形成产品 Bug。

### 9.5 基础用例最小内容

每条基础用例必须包含：

- 用例名称、目标和场景类型；
- 关联 Contract 和覆盖维度；
- 前置条件；
- 明确的执行步骤；
- 参数变化和测试数据；
- 接口/数据依赖；
- 预期状态码、响应字段和业务结果，或探索观察目标；
- Evidence 和 Grounding 结果；
- 风险等级；
- 生成来源、工作流版本和 Prompt SHA；
- 质量报告和阻断原因。

缺少步骤、预期/观察目标、关联契约或依据的候选不得进入可确认状态。

### 9.6 Review 交互

测试人员可以：

- 查看完整用例详情；
- 编辑步骤、参数变化、依赖和预期；
- 新增或禁用用例；
- 逐条确认；
- 一键确认全部可确认用例；
- 接受有理由的非阻断覆盖缺口；
- 重试失败的 AI 补充。

“一键确认全部”只处理 `confirmed_candidate` 且通过质量门禁的用例。被 blocker 阻断、`stale`、无依据或结构不完整的用例必须跳过并在结果中列明原因。

### 9.7 “确认并生成执行定义”语义

用户确认的流程如下：

```text
基础用例生成完成
→ 测试人员逐条检查或一键确认
→ 点击“确认并生成执行定义”
→ 系统创建阶段三 Attempt
→ 自动生成可执行用例
```

产品行为固定为：

1. 按钮只在至少一条 current、confirmed 基础用例存在时可用；
2. 所有未处理 blocker 必须先解决；
3. 点击后展示确认摘要：用例版本、确认数量、禁用数量、高风险数量、接受缺口和输入 SHA；
4. 用户确认后，服务端校验 `base_version`、确认 SHA 和幂等键；
5. 校验成功后创建新的 `executable_case_generation` Attempt；
6. 页面切换到阶段三生成中状态并自动刷新；
7. 阶段三生成完成后展示可执行用例详情；
8. 此操作不创建 ExecutionRun，也不发送真实 API 请求。

如果阶段三生成失败，阶段二已经确认的基础用例保持有效，用户可从阶段三重试，无需重新解析文档或重新确认基础用例。

## 10. P0：阶段三——核心可执行用例工作流改造

### 10.1 输入

阶段三仅接收：

- current 且 confirmed 的基础用例版本；
- 对应目标契约和依赖契约；
- 受控测试数据定义；
- 已确认的变量来源；
- Prompt、工作流和安全策略版本。

不得接收浏览器传入的任意 Host、Credential、命令、宿主路径或环境变量。

### 10.2 核心可执行用例主工作流

```text
加载已确认基础用例及契约
→ “加载工具函数和文件列表”节点：只加载白名单工具和受控资源清单
→ “生成接口用例”节点：运行旧 api_case_generator 完整请求生成
→ “加载测试数据”节点：解析受控 data_ref 和 Baseline 数据
→ 逐条模型输出修复和请求规范化
→ “静态语法校验”节点：扩展为 V2 完整性与安全校验
→ “输出执行定义”节点：返回 ExecutableCaseV3 候选
→ V2 控制平面保存执行定义
→ 页面 Review
```

`ApiRunCaseGeneratorWorkFlow` 是阶段三主生成路径。当前 V2 分支中由它反向委托 `build_executable_cases()` 的实现必须调整：旧工作流负责 Header、Query、Cookie、Body、依赖、变量、数据和脚本的完整编排；`build_executable_cases()` 可拆分为规范化和静态校验工具，但不得继续成为主生成器。

旧“保存用例”节点不得连接 MySQL。该节点应重命名或替换为“输出执行定义”，只返回结构化结果，由 Runner 负责原子保存。

### 10.3 必须保留的旧核心能力

- Header、Query、Cookie 和 Body 完整生成；
- 前置接口和依赖顺序；
- 响应变量提取与后续引用；
- `data_ref` 与 Baseline 数据；
- setup/teardown 受控脚本；
- 断言和业务观察目标；
- 单条输出修复和有限重试；
- 每个工作流节点的日志。

### 10.4 执行定义完整性门禁

以下任一条件必须禁用当前执行定义，并返回明确错误：

- 契约声明必填请求体，但 Body 为空；
- 必填 Header、Query、Cookie 或 Path 参数缺失；
- 变量没有来源；
- 依赖缺失或循环；
- 成功状态码或断言没有契约依据；
- 用默认 200 代替未知预期；
- 探索用例缺少观察目标；
- setup/teardown AST 不安全；
- 高风险用例未确认；
- 基础用例或契约版本为 `stale`；
- 候选包含 Host、Credential、任意文件、进程或网络控制能力。

### 10.5 逐条隔离

模型输出必须逐条完成：对象校验、枚举归一化、Schema 校验、完整性校验、静态安全校验和去重。

一条执行定义失败不得丢弃其他合法定义。页面显示“生成 N 条、可用 X 条、禁用 Y 条”，并为每条禁用项展示错误码、字段路径和修复建议。

### 10.6 可执行用例详情页面

每条用例必须可查看：

- 来源基础用例和契约；
- method 与相对 path；
- Header、Query、Cookie、Path 参数；
- Body 媒体类型和结构化内容；
- 前置接口和依赖拓扑；
- 变量定义、提取和引用；
- 测试数据和 `data_ref`；
- 断言或探索观察目标；
- setup/teardown；
- 静态校验结果；
- 工作流、Prompt、模型和输入版本；
- 生成与拒绝记录。

Host 只在执行准备阶段由已登记 `target_id` 解析；执行定义详情不得包含模型生成的 Host 或真实凭证。

### 10.7 阶段三完成条件

- 至少一条 current、ready 的可执行用例；
- 每条 ready 用例通过完整性和静态安全校验；
- 失败候选已隔离并可查看；
- 执行定义版本和 SHA 已固定；
- 页面进入“等待执行准备”，而不是自动创建 Run。

## 11. P0：阶段四——依赖编排与受控执行

### 11.1 阶段目标

阶段四负责把阶段三已经确认的可执行用例编译成可审查、可复现的依赖执行计划，并在最终人工确认后，通过现有 Controller、单 Run 受限容器和 Egress Proxy 执行真实 API。

阶段四必须同时满足：

- 支持单接口和多接口依赖链；
- 复用旧核心执行器的前置接口、变量、Cookie 和响应提取能力；
- 不直接恢复旧 `TestExecutor`；
- 执行顺序由确定性依赖图决定，不由模型临时决定；
- 一个 ExecutionRun 对应一个独立短生命周期容器；
- 一个 Run 内的相关接口共享受控运行上下文；
- 每个请求步骤具有独立结果、日志和失败分类。

### 11.2 ExecutionPlan

创建 Run 前，`ExecutionPlanCompiler` 必须将所选 current、ready 的 `ExecutableCaseV3` 编译为不可变 `ExecutionPlan`。计划至少包含：

- `plan_id`、版本和 SHA；
- 来源执行定义版本和 SHA；
- `target_id` 和环境，不包含任意 Host；
- 节点列表、依赖边和稳定拓扑顺序；
- 每个节点的 method、相对 path 和结构化请求；
- 变量生产、提取、消费和默认值规则；
- Cookie、会话和 CSRF 传递要求；
- 断言或探索观察目标；
- 节点失败策略、超时和重试策略；
- setup/teardown 的受控能力声明；
- 资源策略、出口策略和 Credential Profile 引用；
- 确认摘要和确认 SHA。

ExecutionPlan 是真实执行的唯一业务输入。Executor 不得再次读取基础用例、Prompt、接口文档或模型输出，也不得在运行时调用模型补齐参数。

### 11.3 依赖图编译

依赖边来源包括：

1. `precondition_case_ids` 显式前置关系；
2. 变量生产者与消费者关系；
3. Cookie、会话或 CSRF Token 的建立与消费关系；
4. 契约声明的数据依赖；
5. 测试人员在 Review 中确认的顺序关系。

编译器必须：

- 验证所有依赖节点存在且为 current、ready；
- 验证每个变量只有明确来源，或具有经过确认的受控输入；
- 检测循环依赖；
- 检测变量名称冲突和覆盖；
- 检测写操作前置条件是否完整；
- 生成稳定、可重复的拓扑顺序；
- 将依赖图和每条边的来源展示给测试人员；
- 在输入版本、目标或策略变化后使旧确认 SHA 失效。

存在循环、缺失依赖、变量无来源或目标未登记时，不得创建 Run。

### 11.4 RunContext

一个 Run 容器中维护独立的内存态 `RunContext`：

- 运行变量仓库；
- HTTP Cookie Jar；
- 会话状态；
- 当前目标的解析结果；
- 短生命周期 Credential 引用；
- 每个节点的输出和提取结果；
- 分支状态和阻断原因。

RunContext 仅在当前容器生命周期内有效，不跨 Run 共享。Secret 和原始 Cookie 不得写入 ExecutionPlan、普通日志或报告；需要留存时只能保存脱敏摘要和 Secret 引用 ID。

### 11.5 变量提取与替换

阶段四必须支持从以下位置提取变量：

- JSON 响应体：JSON Pointer 或受控 JMESPath；
- 响应 Header；
- `Set-Cookie`/Cookie Jar；
- 状态码；
- 受控正则提取，仅适用于文本响应并设置长度与复杂度限制。

变量可以注入：

- Path 参数；
- Query 参数；
- Header；
- Cookie；
- JSON/Form Body；
- 后续断言的期望值。

替换必须保留原生类型。变量缺失时不得静默替换为空字符串，必须将当前节点标记为 `blocked` 或 `error`，并记录 `VARIABLE_VALUE_MISSING`。

### 11.6 Cookie、会话与鉴权

同一 Run 的依赖链默认使用同一个受控 HTTP Session/Cookie Jar，以支持：

```text
登录
→ 保存 Session Cookie
→ 从响应或页面信息提取 CSRF Token
→ 调用需要登录态的接口
→ 退出登录
→ 验证会话失效
```

鉴权值来源只能是：

- 当前 Run 前置步骤的已确认提取结果；
- 登记环境的短生命周期 Credential Profile；
- 测试人员在最终确认前选择的受控测试数据引用。

不得接受模型生成或页面明文提交的真实 Credential。Credential 只注入所需节点和字段，不向无关步骤暴露。

### 11.7 调度与失败传播

默认执行策略为确定性拓扑顺序和单容器内串行执行。本期不以并发或吞吐量为目标。

节点终态包括：

- `passed`
- `failed`
- `error`
- `blocked`
- `skipped`
- `cancelled`
- `timed_out`

采用已确认的失败策略：

- 节点失败或错误后，依赖它的所有后继节点标记为 `blocked`；
- 与失败节点无依赖关系的独立分支继续执行；
- 取消和 Run 级超时终止所有尚未开始的节点；
- teardown 节点按已确认的清理策略执行，并单独记录结果；
- 原始失败节点、被阻断节点和独立分支必须在报告中分开展示。

### 11.8 重试规则

- GET、HEAD 等只读请求可在明确配置后进行有限网络重试；
- 写操作默认不自动重试；
- 写操作只有在契约明确幂等或提供幂等键并经测试人员确认后才允许重试；
- 节点重试不得改变 ExecutionPlan；
- Run 级重试创建新的 ExecutionRun，不覆盖原 Run；
- 失败节点重试必须重新计算其后继节点状态，不能复用可能已失效的下游结果。

### 11.9 受控脚本

阶段四 P0 优先使用结构化变量提取和请求模板，不依赖脚本完成常规接口依赖。

如执行定义包含 setup/teardown：

- 必须已经通过 AST 白名单校验；
- 只能访问受控 RunContext API；
- 禁止文件、进程、反射、任意导入和直接网络访问；
- 必须具有独立 CPU 时间和执行超时；
- 脚本失败只按对应节点规则传播；
- 旧 `_safe_exec` 和旧 DB/global_function 对象不得原样注入新 Executor。

### 11.10 Executor 改造要求

现有容器 Executor 从“用例数组循环器”升级为 `DependencyAwareExecutor`，但继续遵循现有运行时边界：

- 非 root；
- 只读根文件系统；
- 无 Docker Socket；
- 只挂载当前 Run 的只读输入；
- 结果只通过标准输出文件返回；
- 仅能经 Egress Proxy 访问已登记目标；
- 无模型凭证、平台 Token、KEK 和数据库能力；
- 不访问其他任务或 Run 目录。

旧 `BaseTestCase` 中可复用的 Session、变量替换和响应提取逻辑应通过无副作用组件重写或适配进入新 Executor；MySQL 回写、DBClient 和旧直接执行入口不得进入容器镜像。

### 11.11 执行预览与最终确认

创建 Run 前页面必须展示：

- 真实登记目标摘要和环境；
- ExecutionPlan 版本和 SHA；
- 接口节点数量和依赖边数量；
- 拓扑顺序和分支；
- 写操作、高风险和 teardown 数量；
- 变量来源、Cookie/鉴权传递摘要；
- 超时、重试和失败传播策略；
- Credential Profile 的名称和作用范围，不展示 Secret；
- 预计将被执行和可能被阻断的节点；
- 最终确认摘要和确认 SHA。

只有权限、任务所有权、目标登记、计划完整性、安全策略和人工确认全部通过，才允许创建 Run。

### 11.12 逐步骤结果与报告

每个节点结果至少包含：

- 节点和执行用例 ID；
- 前置节点和实际启动原因；
- 开始、结束和耗时；
- 脱敏请求摘要；
- 脱敏响应摘要；
- 提取变量名称及脱敏状态；
- Cookie/会话状态变化摘要；
- 断言或观察结果；
- 失败分类和错误码；
- 重试次数；
- 被其阻断的后继节点。

报告必须同时提供依赖图视图和时间顺序视图，以区分根因失败、连带阻断和独立分支结果。

### 11.13 阶段四完成条件

- ExecutionPlan 已由 current、ready 执行定义编译并通过静态校验；
- 依赖图无循环、缺失节点和无来源变量；
- 最终确认 SHA 与实际计划一致；
- Run 在独立受限容器中完成、取消或超时；
- 每个节点均具有明确终态；
- 依赖失败传播符合“阻断后继、继续独立分支”；
- 原 Run、节点结果和报告不会被重试覆盖；
- 请求、响应、变量、Cookie、日志和报告均已脱敏。

## 13. P1：状态机、版本与失败恢复

### 13.1 阶段状态

每个阶段统一使用：

- `not_generated`
- `generating`
- `ready`
- `partial_ready`
- `failed`
- `stale`

### 13.2 状态迁移

```text
契约 ready + confirmed
→ 基础用例 generating
→ 基础用例 ready/partial_ready
→ 人工 confirmed
→ 执行定义 generating
→ 执行定义 ready/partial_ready
→ ExecutionPlan compiling
→ ExecutionPlan ready
→ 等待最终执行确认
→ Run created/running
→ Run succeeded/failed/cancelled/timed_out
```

### 13.3 版本失效

- 契约新版本确认后，旧覆盖矩阵、基础用例和执行定义标记为 `stale`。
- 基础用例新版本确认后，旧执行定义标记为 `stale`。
- 执行定义、目标或执行策略变化后，旧 ExecutionPlan 标记为 `stale`，旧确认 SHA 失效。
- `stale` 产物只读可查看，不得用于创建新 Run。
- 历史 Run、报告和 Bug 草稿保持原终态，不删除、不覆盖。

### 13.4 失败恢复

- 每次重试创建新 Attempt；
- 复用明确的已确认上游版本和 SHA；
- 不重复执行已成功且输入未变化的阶段；
- 阶段三失败不改变阶段二确认状态；
- ExecutionPlan 编译失败不改变阶段三 ready 状态；
- Run 失败、取消或超时不改变已确认计划和上游版本；
- 单接口失败时保留其他接口的成功产物；
- 旧 Attempt、事件和 Token 记录不可覆盖。

## 18. 非功能要求

### 18.1 可靠性

- 单条输出失败不得中断整个数组；
- 下游失败不得删除上游成功产物；
- 重试不得覆盖历史 Attempt；
- 相同确认 SHA 和幂等键不得重复创建阶段三 Attempt；
- 页面刷新后必须恢复当前真实阶段。

### 18.2 安全

- 工作流无 TaskStore、数据库、容器运行时和宿主执行权限；
- 工作流不得获得模型凭证之外的目标系统 Credential；
- 生成阶段不得发送真实目标 API 请求；
- 所有输入摘要、日志和产物存储前脱敏；
- Prompt 注入不得改变 Contract 事实、Host、执行权限或目标范围。

### 18.3 可用性

- 阶段二必须展示完整基础用例，不只显示标题；
- 阶段三必须展示完整执行定义，不只显示状态；
- 生成中每 2～3 秒增量刷新状态和事件；
- 页面隐藏时降频，终态最后刷新一次后停止；
- 空态、阻断、部分成功和失败必须给出下一步；
- 状态不能只依赖颜色表达。

### 18.4 性能

- 单接口上下文按需构造，不无差别发送整个文档；
- 补齐最多 3 轮；
- 节点日志使用 cursor 增量读取；
- 页面不重复加载完整原文和完整历史事件。

## 19. 测试与验收要求

### 19.1 阶段一

- 登录接口请求体字段、约束和 Evidence 完整进入 Contract。
- “无需会话”保存为 `auth_conclusion=none`，不是未知空值。
- 退出登录的会话 Cookie 与 CSRF Header 被识别并关联 Evidence。
- 原文有 Body 但结果为空时被 blocker 阻断。
- 原文有鉴权信号但无结论时被 blocker 阻断。
- OpenAPI/Swagger 确定性事实不会被模型覆盖。

### 19.2 阶段二

- 登录接口不得生成商品、订单或支付场景。
- 基础用例包含步骤、参数变化、依赖、测试数据和预期。
- 覆盖补齐最多 3 轮并可提前停止。
- 9 条合法、1 条非法时保存 9 条并拒绝 1 条。
- 一键确认只确认通过门禁的候选，blocker 不可绕过。
- 管理员、测试开发、测试人员都能确认高风险基础用例，并逐条产生审计。

### 19.3 阶段二到阶段三

- 未确认基础用例时按钮禁用并显示原因。
- 点击“确认并生成执行定义”后创建阶段三 Attempt。
- 重复点击相同幂等键不会创建多个 Attempt。
- 页面刷新后保持阶段三 generating/ready，不回到阶段一。
- 阶段三失败后基础用例仍保持 confirmed。
- 该操作不会创建 Run，也不会发送真实 API 请求。

### 19.4 阶段三

- 登录请求包含契约要求的 Body。
- 退出登录请求包含 Cookie 与 CSRF Header 占位及来源。
- 依赖接口能够提取并引用变量。
- 不得默认伪造 200；未知预期转为探索观察或禁用。
- 循环依赖、无来源变量和不安全 AST 被阻断。
- 单条坏输出不影响其他合法执行定义。
- 页面可以查看 Header、Query、Cookie、Body、依赖、变量和断言。

### 19.5 阶段四

- ExecutionPlan 能根据显式依赖、变量来源和 Cookie/会话关系生成稳定 DAG。
- 循环依赖、缺失节点、变量无来源和未登记目标会阻止创建 Run。
- 登录 → 提取 Token/Cookie → 调用鉴权接口 → 退出登录链路可在一个容器中完成。
- 参数可以从响应 JSON、Header 和 Cookie 提取并以原生类型注入后续请求。
- 根节点失败后，其后继节点为 blocked，独立分支继续执行。
- 写接口默认不自动重试，只有显式幂等并人工确认后才允许重试。
- Run 重试产生新 Run，原 Run、步骤结果和报告不被覆盖。
- Executor 不能访问模型凭证、数据库、Docker Socket、其他任务目录或未登记目标。
- 报告能够区分根因失败、依赖阻断和独立分支结果。

### 19.6 可观察性与兼容

- 页面可证明阶段一至三实际运行的工作流节点，以及阶段四的计划编译和执行节点。
- Prompt、模型、输入/输出/总 Token 分开显示。
- 生成来源和模型调用明细默认收起。
- 历史任务无来源记录时显示“历史版本未记录”，不回写历史文件。
- 平台调用链静态确认不导入或调用旧 `execute_test_cases()`。
- 三个核心生成工作流均没有 MySQL 写入。

## 21. 发布、灰度与回滚

### 21.1 发布顺序

1. Schema 和读取兼容层；
2. 阶段一 Adapter 与完整性门禁；
3. 阶段二核心 LangGraph 工作流和 Review 过渡；
4. 阶段三核心 LangGraph 工作流、静态校验和详情页；
5. ExecutionPlan 编译器、依赖图预览和 Fake Executor 验证；
6. 容器内 DependencyAwareExecutor 和逐步骤报告；
7. 工作流事件和统计；
8. 本机登录/退出登录多接口链路试点验收；
9. 生产继续关闭真实执行，生成和执行能力分别灰度。

### 21.2 灰度

- 新 Attempt 快照工作流内核版本，同一 Attempt 不得混用；
- 历史 `legacy`、`v2_minimal`、旧 `v2_fused` 只读兼容；
- 历史用例创建新 Run 前仍需通过当前完整性门禁；
- 本机开发环境先启用新核心融合内核，生产环境初始关闭。
- 阶段四先使用 Mock API Server 验证依赖链，再对已登记的本机无生产数据目标进行真实试点。

### 21.3 回滚

- 停止创建 V2.4 Attempt，并将新入口切回上一生成内核；
- 已生成 V2.4 产物保持只读，不删除；
- 当前指针只允许依据来源 SHA 切回上一有效版本；
- 不回写历史任务，不删除历史 Run、报告或 Bug 草稿；
- 回滚不改变真实执行开关和安全配置。

## 22. 已确认决策与风险

| 项目 | 决策 |
| --- | --- |
| 阶段一至三 | 采用“V2 控制平面 + 改造后的旧核心工作流生成引擎” |
| 阶段四 | 正式纳入 V2.4，采用确定性 ExecutionPlan DAG 和受限容器执行 |
| 阶段二结束行为 | 不自动进入阶段三，必须经过测试人员 Review |
| 阶段过渡 | Review 后点击“确认并生成执行定义”，系统自动执行阶段三生成 |
| 真实执行 | 阶段三不执行 API，真实执行继续使用独立最终确认 |
| 多接口依赖 | 同一 Run 容器共享受控变量和 Cookie；失败阻断后继但继续独立分支 |
| 旧执行器 | 复用前置接口、变量、Session 和提取语义，不恢复旧 TestExecutor 入口 |
| 高风险确认 | 管理员、测试开发、测试人员均可确认；批量操作逐条审计 |
| 旧工作流 | 复用生成能力，不恢复旧入口、MySQL 或直接执行 |
| 失败隔离 | 单条失败隔离，上游成功产物和人工确认不丢失 |
| 历史版本 | 只读兼容，不回写；创建新 Run 前重新通过门禁 |

主要风险：

- 旧 Prompt 输出与 V2 Schema 仍可能存在字段差异，需要 Adapter 和逐条归一化覆盖黄金集；
- 鉴权表达从空列表升级为显式结论后，需要读取兼容层区分历史未知值；
- 基础用例与执行定义的组合数量可能增加，需要按接口限制上下文和补齐轮次；
- 旧工作流若仍隐藏副作用，必须通过依赖扫描和测试确认全部隔离后才能接入平台主链路。

## 24. 最终产品结论

V2.4 将恢复用户原 API 测试智能体的核心价值，但不恢复旧系统的副作用和安全缺陷：

- 阶段一真正恢复完整契约解析，并由 V2 Evidence 和人工 Review 兜底；
- 阶段二真正恢复完整测试设计，在人工确认后才允许进入下一阶段；
- 阶段三真正恢复完整请求和依赖编排，并由 V2 静态校验控制质量与安全；
- 阶段四把已确认执行定义编译成确定性依赖图，在单 Run 受限容器中完成真实多接口执行；
- 生成流程、人工门禁、计划编译和真实执行继续明确分层。

用户确认的阶段二到阶段三流程是正确且正式采用的产品流程：

```text
基础用例生成完成
→ 测试人员检查或一键确认
→ 点击“确认并生成执行定义”
→ 系统自动进入阶段三生成可执行用例
→ 测试人员查看可执行用例
→ 阶段四编译并展示 ExecutionPlan 依赖图
→ 另行完成执行准备和最终确认
→ 在单 Run 受限容器中按依赖图发起真实 API 执行
```
