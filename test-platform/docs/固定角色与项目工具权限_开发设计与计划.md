# 固定角色、项目范围与额外工具授权 Implementation Plan

> 计划版本：V1.1（对应 PRD V1.1）
> 更新日期：2026-08-24
> 状态：待 PRD V1.1 技术评审后执行

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按 PRD V1.1 将 test-platform 改造为“三种固定单角色 + 公共/项目工具范围 + 有期限额外授权”，并确保测试人员只能查看和操作自己的任务、结果与报告。

**Architecture:** User.platform_role、Project、ProjectMembership、Tool 范围及 UserToolGrant 决定“能否使用工具”；BusinessResourceSnapshot 固化任务所有者和创建时项目范围，独立决定“能否读取或控制某条业务资源”；RuntimeContext 收敛为只允许完成既有任务的 Execution Lease。平台授权、资源授权和控制面授权分别由显式权限注册表与统一服务判定，旧 RBAC 在切换后只读保留。

**Tech Stack:** Python 3、FastAPI 0.141.1、SQLAlchemy 2.0.51、Alembic 1.18.5、PostgreSQL 17、SQLite 迁移测试、React 19、React Router 7、TypeScript 7、Vite 8、Vitest 4、Testing Library。

**Spec:** [PRD-固定角色与项目工具权限-V1.0.md](./PRD-固定角色与项目工具权限-V1.0.md)

## Global Constraints

- 每个用户恰好一个角色：platform_admin、admin 或 tester。
- 每个工具恰好为 public 或 project；project 工具必须且只能属于一个项目。
- 公共工具对所有 active 用户开放，不能按用户拒绝。
- 额外授权只允许单个项目工具，必须设置 expires_at（默认 7 天、最长 90 天），不增加他人数据、配置、Secret、成员或项目管理能力。
- 用户、项目或工具非 active/enabled 时必须失败关闭。
- 工具访问只允许进入工具并创建本人任务，不得映射为 task.view.all、result.view.all 或 task.cancel.any。
- 测试人员只能读取和操作本人业务资源；管理员仅可管理当前负责项目快照下的资源；平台管理员可全局运维。
- 公共工具任务默认仅创建者本人和平台管理员可见。
- 不可见对象与不存在对象统一返回 404；可见对象缺少具体动作权限时才返回 403。
- 普通管理员只管理自己负责项目的测试成员和项目工具。
- 用户私有 Credential、个人 LLM API Key 不因项目管理关系暴露。
- 迁移未明确分类的工具进入“存量工具项目”，不得默认公开。
- 旧 readonly/auditor 用户不得自动加入项目，旧 test_developer 不得自动升级为 admin。
- 未知/无角色用户及无法确定 owner/project snapshot 的历史资源必须在回填前阻断迁移。
- 权限迁移固定采用 expand → compatibility → backfill → cutover → contract；新模型接受写入后不得恢复陈旧旧 RBAC。
- 成功高风险审计与业务变更同事务；失败尝试通过独立可靠安全事件通道持久化。
- 所有 Pydantic 写模型使用 ConfigDict(extra="forbid")；所有权限代码显式分类，未登记权限默认拒绝。
- 不新增第三方依赖，不替换现有 FastAPI、SQLAlchemy、React Router 或 CSS 架构。
- 所有新增和修改代码使用与仓库一致的清晰中文注释，重点解释业务规则、边界、异常和失败关闭原因。
- 前端仅验收 1280px 及以上桌面浏览器；保持 Apple Developer 风格的克制层级，不增加营销化卡片墙、渐变或无意义动效。
- 执行前必须使用独立 worktree；当前工作区已有大量用户未提交修改，不得暂存、覆盖或提交这些修改。

## 1. 设计判断

目标用户是平台管理员、项目管理员和测试人员；主要任务是识别“我能用什么、我能管理什么、权限来自哪里”，信息密度中高，属于桌面产品工作台而非营销页面。

界面优先顺序固定为：

1. 当前角色、项目或工具状态；
2. 当前用户可执行的下一步操作；
3. 成员、工具、授权来源和审计细节。

不把每项数据包装成独立阴影卡片。项目和用户管理以清晰表格、分组标题、状态标签、影响摘要和确认弹窗为主。

新模型下的权威数据只有：

- User.status；
- User.platform_role；
- Project.status；
- ProjectMembership；
- Tool.is_enabled；

### 3.3 兼容策略

- MeResponse 新增 role，同时保留 roles=[role]；
- UserAdminResponse 新增 role，同时在一个发布窗口保留 role_ids=[role]；
- GET /admin/roles 返回固定三角色和只读矩阵；
- POST/PATCH /admin/roles 返回 409 FIXED_ROLE_MODEL；
- 旧权限代码继续用于网关路径映射，但由有效工具访问统一生成；
- 旧业务权限代码只作为显式动作注册表的兼容名称，不按 tool_id/前缀自动扩权；
- 兼容期网关同时生成旧 Header 与签名 ResourceAccessContext；工具完成迁移后只信任签名上下文；
- 旧 RBAC 表不在本期物理删除。

运行开关固定为：

- AUTHORIZATION_MODEL=legacy|shadow|project；
- RESOURCE_AUTHORIZATION_MODE=off|shadow|enforce；
- ACCESS_MANAGEMENT_WRITES_ENABLED=true|false。

0019 后先运行 legacy + off：旧模型放行，但兼容后端对可确定的用户/工具变化双写 nullable 新字段。shadow 模式同时计算新工具访问和资源访问，只记录非敏感差异，绝不以旧允许兜底新拒绝。最终写冻结和增量回填通过后原子切换 project + enforce，再开启新项目/grant 管理写入。数据库记录 cutover_at/cutover_generation；一旦 generation 存在新模型写入，回滚脚本禁止 legacy 模式和 destructive downgrade。


active grant 条件固定为 status='active' AND revoked_at IS NULL AND expires_at > now，并叠加用户 active、工具 enabled、项目 active。授权服务遇到已过期但 status 仍为 active 的记录必须按无效处理；定时任务和下一次管理写入负责把状态收敛为 expired。创建接口未提交 expires_at 时写 now + 7 days；提交值不得晚于 now + 90 days。续期在同一事务中先把旧行标记 expired，再创建新的 active 历史行并写 tool.grant.renew 审计，不允许无期限记录。

### 4.5.1 公共工具安全策略与用量

V1.1 首期仅允许无需真实外部目标的 `log-filter` 成为公共工具。其他四个第一方 Agent 在统一公共沙箱和出口代理落地前由范围 API 拒绝设为 public；前端根据 `public_eligible=false` 不展示公共选项。该限制是安全能力门禁，不改变公共资源 owner-only 的数据规则。

ToolPublicSafetyPolicy 以 tool_id 为主键，至少保存 per_user_requests_per_minute、per_user_tasks_per_day、per_user_daily_cost_units、target_allowlist、real_execution_mode（disabled/allowlist_only）和 revision。PublicToolUsageBucket 以 tool_id + user_id + bucket_type + window_started_at 唯一，原子累计 request_count、task_count、reserved_cost_units、actual_cost_units。

REQUEST_AUTHORIZATION_REGISTRY 为 create/execute 路由登记 estimated_cost_units。网关在 public 用户请求进入前原子消费分钟请求额度；create 路由再消费日任务额度并预留成本。Tool Client 通过内部 usage-report 上报实际 cost units 并核销预留。缺少策略、额度不足、目标不在 allowlist 或真实执行门禁关闭均失败关闭；项目工具仍保留已有运行门禁，但不强制使用公共用户配额。

### 4.6 BusinessResourceSnapshot

平台当前不保存各工具任务实体，因此新增不可变授权索引，只保存授权元数据，不复制任务输入、结果正文、日志或 Secret：

```python
            "(access_scope_snapshot = 'project' AND project_id_snapshot IS NOT NULL)",
            name="ck_business_resource_project",
```

### 4.7 RuntimeContext 作为 Execution Lease

保留 runtime_contexts 表名，并复用现有 status/expires_at 作为 lease status/expiry；只新增 business_resource_snapshot_id、emergency_revoked_at/reason 和 selector_hash。创建 RuntimeContext 时同时原子创建 BusinessResourceSnapshot；task/tool/environment 创建后不可变。首次 materialize 以 compare-and-set 写入 selector_hash，后续只接受完全相同的配置 Release、Credential/LLM 版本选择器，从而在实际派发时锁定允许引用。

session_id 改为 nullable 且 FK ondelete=SET NULL，防止 Session 清理级联删除仍需完成或审计的租约；创建时仍记录 dispatch_session_id。用户不物理删除，BusinessResourceSnapshot 与租约均保留稳定 user_id 引用。

交互请求继续校验用户 current permission_version、Project.authorization_epoch 和 Tool.authorization_epoch；后台物化使用 validate_execution_lease，只校验 Tool Client、固定作用域、RuntimeContext.status/expires_at、selector hash 与显式紧急撤销，不因普通 Session 撤销或 permission_version 变化自动失败。租约只能完成原任务，不能创建新资源、浏览其他资源或改变 tool/environment/credential selector。

用户禁用、项目停用和工具停用默认只阻止新交互与新任务，不批量撤销租约。平台管理员执行显式 emergency_revoke_leases=true 时才按 task_id 精确撤销，并记录原因、影响任务和审计；V1 不提供无确认的全局隐式取消。

### 5.3 单工具判定顺序

resolve_tool_access 必须按以下顺序：

1. User.status 不是 active：拒绝 user_inactive；
2. Tool.is_enabled 为假：拒绝 tool_disabled；
3. public 工具：
   - platform_admin 返回 platform_admin + can_manage=true；
   - 其他 active 用户返回 public + can_manage=false；
4. project 工具项目缺失：拒绝 project_missing；
5. 项目 inactive：拒绝 project_inactive；
6. platform_admin：允许，source=platform_admin，can_manage=true；
7. admin + manager：允许，source=project_manager，can_manage=true；
8. tester + member：允许，source=project_member，can_manage=false；
9. admin/tester + status=active、未撤销且未过期的额外授权：允许，source=extra_grant，can_manage=false；
10. 关系类型与用户角色冲突：拒绝 relation_invalid；
11. 其他情况：拒绝 out_of_scope。

平台管理员也不能绕过 tool disabled 或 project inactive 做业务执行，但仍可通过独立管理 API 查看和恢复资源。

### 5.4 批量目录算法

list_accessible_tool_decisions 不允许 N+1：

1. 一次读取所有 enabled 工具及其项目状态；
2. 非平台管理员一次读取其 membership；
3. 非平台管理员一次读取其 active extra grant；
4. 在内存中按同一判定顺序生成结论；
5. 仅返回 allowed 项。

工具目录规模远小于任务和结果规模，该方案保持 SQL 简单、可测试，并把查询数固定为 1 或 3。

### 5.5 权限代码映射

现有函数名继续保留：

```python
def has_platform_permission(database: Session, user_id: str, code: str) -> bool:
    user = database.get(User, user_id)
    if user is None or user.status != "active":
        return False
    try:
        role = PlatformRole(user.platform_role)
    except ValueError:
        # 非法存量数据必须失败关闭，不能回退旧 RoleGrant 放行。
        return False
    return code in FIXED_PLATFORM_PERMISSIONS[role]


def tool_permissions(database: Session, user_id: str, tool_id: str) -> set[str]:
    user = database.get(User, user_id)
    tool = database.get(Tool, tool_id)
    if user is None or tool is None:
        return set()
    decision = resolve_tool_access(database, user, tool)
    if not decision.allowed:
        return set()
    # 这里只表达工具入口和“可创建本人资源”，不能表达对既有资源的所有权。
    permissions = {"tool.view", "tool.execute"}
    if decision.can_manage:
        permissions.update(TOOL_MANAGEMENT_PERMISSIONS)
    return permissions


def has_tool_permission(
    database: Session,
    user_id: str,
    code: str,
    tool_id: str,
) -> bool:
    definition = permission_definition(code)
    if definition is None:
        return False
    if definition.permission_class in {
        PermissionClass.BUSINESS_OWN,
        PermissionClass.BUSINESS_PROJECT_MANAGE,
        PermissionClass.BUSINESS_GLOBAL,
    } and definition.action != "create":
        # 既有资源动作必须改走 resolve_resource_access，禁止工具访问权代替对象授权。
        return False
    return code in tool_permissions(database, user_id, tool_id)
```

configuration.py 现有 _can_manage_config / _can_manage_secret 继续走 CONTROL_PLANE 分支；任务/结果接口不得调用 has_tool_permission 作为最终放行条件。

### 5.6 业务资源判定顺序

resolve_resource_access 固定顺序：

1. 用户不存在或 inactive：拒绝；
2. 快照缺失/冲突：失败关闭并告警；
3. platform_admin：允许 global；
4. public 快照：仅 created_by_user_id == user.id 允许 own；
5. project 快照且项目当前 inactive：普通用户拒绝；
6. admin 当前仍是 project_id_snapshot manager：允许 project；
7. 资源创建者当前仍是该项目 manager/member：允许 own；
8. 资源创建者仍持有 tool_id + project_id_snapshot 匹配的有效 grant：允许 own；
9. 其他情况按不可见处理，返回与不存在对象一致的 404。

read 与 review/cancel/retry/export 分别登记 action；允许 read 不自动允许其他动作。新建与重试分开：retry 既要允许操作旧快照，又要重新通过当前 resolve_tool_access 和运行安全策略。

### 5.7 权限版本与缓存失效

下列写操作必须调用 bump_authorization_epochs：

| 变更 | 递增对象 |
|---|---|
| 用户状态、角色 | 当前用户 |
| membership 新增/删除 | 对应用户 + Project.authorization_epoch |
| extra grant 新增/撤销/到期/续期 | 对应用户 + Tool.authorization_epoch |
| project 状态 | Project.authorization_epoch/revision |
| tool enabled | Tool.authorization_epoch/revision |
| tool public ↔ project | Tool.authorization_epoch/revision；不批量更新全部用户 |
| tool 项目 A → B | Tool.authorization_epoch/revision + A/B Project.authorization_epoch |

用户自身变化批量更新 User.permission_version；项目/工具变化只更新对应 epoch：

```python
database.execute(
    update(User)
    .where(User.id.in_(sorted(user_ids)))
    .values(permission_version=User.permission_version + 1)
)
```

交互授权缓存键至少包含 user.permission_version、project.authorization_epoch、tool.authorization_epoch。Execution Lease 不读取这些版本决定是否继续，只接受显式 emergency revoke 和到期控制。

```python
            raise ValueError("公共工具不能关联项目")
        if self.access_scope == "project" and self.project_id is None:
            raise ValueError("项目工具必须指定项目")
        return self


class UserToolGrantCreateRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    user_id: str
    tool_id: str
    reason: str = Field(min_length=1, max_length=500)
    expires_at: datetime | None = None


class UserToolGrantRevokeRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    reason: str = Field(min_length=1, max_length=500)


class UserToolGrantRenewRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    reason: str = Field(min_length=1, max_length=500)
    expires_at: datetime
```

工具范围更新在一个事务中：

1. 锁定 Tool；
2. 校验目标 Project；
3. 校验 expected_revision / impact_token 并从权威任务源重算影响；
4. 撤销该工具 active extra grant；
5. 更新 Tool；
6. 递增 Tool/Project authorization_epoch 和 revision；
7. 写审计；
8. commit。

设为 public 前调用 PublicToolSafetyPolicy.validate：必须存在每用户请求/任务配额、日成本上限、目标地址白名单和真实执行门禁声明；缺失任一项返回 409 PUBLIC_TOOL_POLICY_INCOMPLETE。

### 6.7 网关与配置中心

backend/app/api/internal.py 保留现有身份 Header，并新增由平台签名、网关覆盖的 X-Platform-Resource-Context：

- X-Platform-User-ID；
- X-Platform-Username；
- X-Platform-Display-Name；
- X-Platform-Permissions；
- X-Platform-User-Context；
- X-Platform-Resource-Context。

required_tool_permission 替换为显式 REQUEST_AUTHORIZATION_REGISTRY。每个已知路由逐项登记 tool_id、HTTP method、path template、action、root resource extractor；不得再按 URL fragment 或工具 ID 前缀推断。未登记的业务写路由返回 403 UNCLASSIFIED_TOOL_ACTION 并告警。

签名 ResourceAccessContext 固定包含：uid、tool_id、environment_id、action、data_scope（own/project/global）、managed_project_ids、resource_type/resource_id（列表/create 时为空）、project_id_for_new_resource、user/project/tool 版本、iat/exp/nonce。对象路由先查 BusinessResourceSnapshot 并调用 resolve_resource_access；不可见对象返回 404。列表路由签发 query scope，工具必须在存储查询阶段过滤，不能先返回再由前端隐藏。

授权顺序按请求类型分开：工具首页和创建新任务要求当前 ToolAccessDecision.allowed；任务/结果/报告列表按 ResourceQueryScope 返回当前仍有权查看的历史资源，不以当前工具入口为前置；历史对象 read/download 只要求 ResourceAccessDecision，不因工具后来改项目或用户失去当前工具入口而拒绝；review/cancel 等控制动作要求对象动作允许；retry/new execute 同时要求资源动作、当前工具访问和运行安全门禁。internal authorize 不得在解析资源列表或历史对象前用 `tool disabled/out_of_scope` 提前短路。

Nginx 删除浏览器自报的全部 X-Platform-* 后，仅注入 auth_request 响应 Header。ResourceAccessContext TTL 不超过 300 秒，作为不透明 token 交给工具；工具不得自行解码或信任 claims，而是使用自身 Tool Client 凭证调用平台 resource-access/check，平台校验签名、tool/environment/audience、method/action 和 TTL 后返回安全 scope。工具可按 token_hash 缓存不超过 60 秒，撤权仍受平台 token 版本校验。

configuration.py 保持现有 _can_manage_config / _can_manage_secret 调用方式；新增回归测试证明公共工具 admin、extra_grant 用户和 tester 均不能管理 Secret。

### 6.8 资源注册与执行租约 API

| 方法 | 路径 | 调用方 | 说明 |
|---|---|---|---|
| POST | /internal/tools/{tool_id}/runtime-contexts | Tool Client | 校验 create ResourceAccessContext，原子创建资源快照和 Execution Lease |
| POST | /internal/tools/{tool_id}/resource-access/check | Tool Client | 校验不透明 ResourceAccessContext，返回 query/object scope；派生资源携带 root_resource_id |
| POST | /internal/tools/{tool_id}/execution-leases/{id}/revoke | 平台安全策略 | 显式紧急撤销租约 |
| GET | {tool.runtime_status_url} | 平台 → 工具 | 工具从自身权威任务存储返回 running count/status，不使用 RuntimeContext 数量代替 |

RuntimeContextCreateRequest 必须包含 resource_type/resource_id；服务端从已验证的 create ResourceAccessContext 取 owner、scope、project、source，拒绝客户端自报。重复 tool/environment/type/id 只能在 owner 和快照完全一致时幂等返回；冲突返回 409 RESOURCE_SNAPSHOT_CONFLICT。

runtime_status_url 仅允许 Docker/内网 allowlist 地址。平台以独立 internal-status HMAC 对 method/path/timestamp/nonce 签名；工具拒绝超过 30 秒、重复 nonce 或签名错误的请求。响应固定为 `{"status":"known","running_task_count":N,"observed_at":"..."}` 或 `{"status":"unknown"}`，超时、非法响应和部分工具失败统一聚合为 unknown。

execution_mode=synchronous 的工具由平台权威返回 running_task_count=0，且不得创建后台 Execution Lease；background 工具必须配置 runtime_status_url，缺失即 unknown。TrackEvents 与当前 Log Filter 同步分析路径标记 synchronous；Functional/API Agent、Truthy Search/ApiAutoTest 标记 background。

### 7.2 事务要求

- API 写路由只调用服务并在成功后 database.commit()；
- 服务函数发生任何异常时由请求生命周期回滚；
- 自动撤销额外授权和 Tool 更新必须同事务；
- 审计与业务变更同事务；
- 高风险成功审计写入失败时抛错并回滚业务变更；
- denied/failed 审计使用独立 Session 写入 security event；不可复用将要回滚的业务 Session；
- 重复关系、重复 grant 依赖唯一索引并转换为稳定 409；
- 不捕获并暴露 SQLAlchemy 原始错误。

并发写固定锁序：全局角色保护行 → project id 升序 → tool id 升序 → user id 升序 → membership/grant。取得锁后重新读取角色、状态、revision、impact 和有效授权；最后平台管理员、角色/成员、grant/tool scope、project deactivate/关系变化均按此顺序串行化。SQLite 测试用应用级互斥模拟，PostgreSQL 使用 SELECT ... FOR UPDATE；竞争失败统一 409。

## 9. 错误、安全与性能设计

### 9.1 稳定错误码

| code | HTTP | 使用场景 |
|---|---:|---|
| AUTH_REQUIRED | 401 | Session 失效 |
| ACCOUNT_DISABLED | 401 | 用户停用 |
| PERMISSION_DENIED | 403 | 普通越权 |
| NOT_FOUND | 404 | 对象不存在或不在调用者可见范围 |
| PROJECT_INACTIVE | 409 | 对停用项目写入或业务访问 |
| TOOL_INACTIVE | 409 | 对停用工具发起业务写入 |
| MEMBERSHIP_CONFLICT | 409 | 重复或角色不匹配 |
| GRANT_CONFLICT | 409 | 重复、冗余或非法额外授权 |
| LAST_PLATFORM_ADMIN | 409 | 影响最后一个 active 平台管理员 |
| FIXED_ROLE_MODEL | 409 | 创建或修改角色定义 |
| ACCESS_SCOPE_INVALID | 422 | public/project 与 project_id 冲突 |
| STALE_IMPACT | 409 | revision/impact_token 已过期 |
| PUBLIC_TOOL_POLICY_INCOMPLETE | 409 | 公共开放安全策略缺失 |
| RESOURCE_SNAPSHOT_CONFLICT | 409 | 同一业务资源 ID 的 owner/scope 冲突 |

列表隐藏无权对象；直接构造不可见的项目、用户、任务、结果、报告或导出 ID 返回与真实不存在一致的 404。只有对象本身可见但缺少具体动作时返回 403。响应体使用相同 code/message 形状，测试排除明显时序和计数枚举信号。

### 9.2 安全边界

- 所有管理写操作依赖 require_csrf；
- register 不依赖 CSRF，但使用现有登录限流等价的注册频率保护；
- 注册增加 IP + normalized username + device signal 组合限流、全局熔断和 open/invite/disabled 模式；
- public 工具必须配置每用户请求/任务配额、日成本预算、目标白名单和真实执行门禁；网关及工具任务创建端双重执行；
- 项目管理员查找成员只支持精确 username；
- 用户私有配置沿用 owner_user_id 校验；
- 网关继续覆盖浏览器自报的 X-Platform-*；
- 旧 RoleGrant 永不作为新访问 fallback；
- 授权查询异常和不一致全部拒绝。
- Pydantic 写模型统一 extra="forbid"，审计 reason 统一 redact；
- 任务列表、总数、搜索、分页、详情、Review、取消、重试、日志、artifact、报告与导出均在数据访问层执行相同 scope filter；
- 未登记权限或路由默认拒绝，不允许 code.startswith(tool_id) 推断。

## 14. 发布门禁

满足以下条件才可全量：

- 预检无 unknown/no-role、非法关系或无法确定 owner/project 的历史资源；
- 0019 expand 在旧应用下兼容，0020 contract 在合规回填后通过；
- dry-run/资源 manifest 报告无 conflict；
- platform_admin 数量至少 1；
- 所有用户单角色；
- 所有工具范围合法；
- readonly/auditor-only 未默认加入项目；
- 后端全量测试通过；
- functional-test-agent、api-test-agent、Truthy_Search、api-autotest、log_filter_tool 全量测试通过；
- 前端测试和构建通过；
- 52 个 AC 均有自动或浏览器证据；
- /tools P95 增量不超过 100ms；
- Secret 哨兵测试通过；
- dev 灰度无“新模型比旧模型更宽”的未解释差异；
- prod 备份、cutover 前/后不同回滚手册和负责人已确认。

## 15. 明确不实施的内容

- 不创建第四种只读角色；
- 不支持多角色；
- 不支持 deny grant；
- 不支持工具多项目归属；
- 不支持无期限 extra grant、自动审批或多级审批；
- 不支持单条任务人工 ACL、共享名单或逐条授权；
- 不删除旧 RBAC 表；
- 不引入 Redis 权限缓存；
- 不重写配置中心或个人凭证模型；
- 不新增前端组件库、状态库或 CSS 框架；
- 不做移动端布局；
- 不自动取消项目停用前已进入后台的任务。
