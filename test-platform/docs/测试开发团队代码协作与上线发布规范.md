# 测试开发团队代码协作与上线发布规范

> 文档版本：V1.1
> 编写日期：2026-08-31
> 适用项目：`Testproject` 及其平台、工具和智能体组件
> 适用对象：测试开发工程师、组件负责人和轮值发布协调人
> 文档状态：团队试行；Codeup、Flow 和工具接入自动化完成验收后转为正式规范

---

## 1. 规范目的

`Testproject` 采用单仓库多组件模式。不同测试开发工程师可以独立维护自己的工具目录，同时共享平台、网关、数据库迁移、版本清单和发布基础设施。

本规范用于统一以下工作：

- 日常代码开发和分支管理；
- 目录所有权、工具自助接入和公共变更同行复核；
- 合并请求、测试门禁和版本升级；
- Dev 集成验证和 Prod 上线；
- 单组件独立发布、回滚和生产并发控制；
- Codeup、Flow、ACR 和生产服务器之间的职责边界。

本规范的目标不是限制各组件独立开发，而是确保任何一次合并和上线都可验证、可追溯、可回滚，并且不会意外影响其他组件。

---

## 2. 当前阶段说明

云效包含两个与本项目相关的主要能力：

- **Codeup**：Git 代码仓库和合并请求管理，作用类似 GitHub；
- **Flow**：自动测试、构建镜像和部署，作用类似 GitHub Actions。

在 Codeup 和 Flow 正式验收前，当前 GitHub、GitHub Actions 和 GHCR 仍是生产发布事实源。迁移完成后，Codeup、Flow 和 ACR 将成为新的事实源。

迁移期间必须遵守：

1. 只能指定一个代码仓库作为主写入源；
2. 禁止 GitHub 和 Codeup 长期双向写入；
3. 禁止同一个 Release Tag 在两个系统分别构建不同镜像；
4. 未经过影子流水线验证和正式切换公告，不得直接从云效发布 Prod；
5. 无论使用 GitHub 还是 Codeup，本文中的分支、自动门禁、版本和发布规则保持一致。

---

## 3. 核心原则

团队所有成员必须遵守以下原则：

1. **一个仓库、组件独立**：保留 `Testproject` 单仓库，每个一级工具目录作为独立组件管理。
2. **目录有负责人**：组件负责人对该目录的需求、代码、测试、版本、发布和故障负责。
3. **自动化优先、人工复核例外**：组件内部改动和符合接入契约的清单变更，在自动门禁通过后可由组件负责人自行合并；公共框架或高风险变更才需要相关同事复核。
4. **Dev 用于集成，Main 用于生产**：个人分支不能直接发布 Prod，`dev` 也不能直接作为 Prod 发布源。
5. **生产只认 Release**：Prod 只能发布 `main` 上经过验证的 `release-YYYY.MM.DD.N` 标签。
6. **构建一次，到处运行**：生产镜像由流水线构建并推送镜像仓库，服务器只拉取不可变镜像，不现场编译。
7. **组件可以独立发布**：组件内部改动只升级和重启对应组件，不能重启无关服务。
8. **公共变更整体发布**：平台、网关、数据库或跨组件协议变更必须走平台完整发布，并由相关组件共同验证。
9. **同一时间只允许一条 Prod 部署**：生产发布必须有并发锁，避免两次发布互相覆盖。
10. **所有变更可追溯和回滚**：发布必须记录组件版本、Git SHA、镜像 digest、数据库版本和验收结果。

## 5. 公共文件与高风险范围

即使每个人只开发自己的目录，以下文件仍可能被多人共同修改：

- `test-platform/docker-compose.yml` 和生产 Compose 文件；
- `test-platform/versions.json`；
- Nginx 路由和工具入口；
- 平台前后端公共接口；
- Alembic 数据库迁移；
- 工具权限、配置范围、Tool Client 和 Bootstrap 配置；
- Codeup/Flow 流水线文件；
- 根目录构建、发布和运维脚本；
- 公共依赖、基础镜像和环境配置示例。

直接修改上述公共内容时必须：

1. 在合并请求中明确标记“公共变更”；
2. 说明受影响的组件和兼容性；
3. 同步最新 `dev` 后重新测试；
4. 至少由一名熟悉受影响范围且不是提交者的同事复核；
5. 提供完整发布和回滚说明；
6. 数据库、登录、权限和 Secret 变更不得按普通工具改动处理。

如果工具只修改自己的 `platform-tool.yaml`，且平台接入生成器和全部自动门禁均已通过，则该变更按普通组件改动处理，不视为手工修改公共文件。

## 6. 工具接入 test-platform 规范

工具接入采用“目录独立负责、清单声明、平台自动生成、自动门禁”的自助模式。目标是让开发者主要修改自己的工具目录，不需要多人反复手工修改 Nginx、Compose、平台菜单和发布矩阵。

### 6.1 接入边界

每个工具必须在独立一级目录中维护以下内容：

- 工具前后端源码和测试；
- Dockerfile、依赖声明和本地启动说明；
- 独立组件版本；
- 配置、Secret、Credential 和数据目录声明；
- 平台接入清单 `platform-tool.yaml`；
- 健康检查、版本信息和最小 Smoke Test。

工具不得直接读取或修改其他工具的源码、数据库、数据卷、Secret、任务、日志和产物。确实需要跨工具协作时，必须通过明确的公共 API 或平台公共能力完成。

### 6.2 平台接入清单

每个接入平台的工具在自己的目录根部维护：

```text
<tool-directory>/platform-tool.yaml
```

清单至少描述以下信息：

```yaml
schema_version: 1

tool:
  id: dating-tool
  name: Dating Tool
  owner: team-a

component:
  id: dating-tool
  version: 1.0.0

runtime:
  service: dating-tool
  container_port: 5001
  health_path: /health
  version_path: /version

platform:
  base_path: /tools/dating-tool
  menu_title: Dating Tool
  enabled_by_default: true

config:
  scopes:
    - dating-tool
  secrets: []
  credentials: []

storage:
  data_directory: dating-tool-data
  backup_required: true

smoke_test:
  path: /tools/dating-tool/
  expected_status: 200
```

示例只说明字段语义；最终字段、枚举值和必填项以仓库中的机器校验 Schema 为准。Schema 变化属于公共接入契约变化，需要同行复核并保持向后兼容，或明确给出迁移方案。

### 6.3 标识、路由和服务发现

- `tool.id`、`component.id`、Docker 服务名、平台路由和宿主机端口必须全局唯一；
- 平台入口统一使用 `/tools/<tool-id>/`，没有末尾斜杠时由网关统一跳转；
- 容器之间必须使用 Docker 服务名通信，不能使用 `127.0.0.1` 访问其他容器；
- 工具必须支持清单声明的 `base_path`，不能假设自己始终部署在网站根路径；
- 只有平台网关对外映射正式访问端口，工具端口默认仅在 Docker 网络内可见；
- 工具容器重建后，平台必须通过稳定服务名自动访问新容器，不依赖固定容器 IP。

### 6.4 健康和版本契约

每个工具必须提供清单声明的健康检查和版本信息接口。新工具默认使用：

```text
GET /health
GET /version
```

已有工具可以保留兼容路径，但必须在清单中准确声明。版本信息至少返回：

```json
{
  "service": "dating-tool",
  "status": "ok",
  "version": "1.0.0",
  "revision": "Git SHA",
  "runtime_environment": "dev"
}
```

健康检查不得依赖长耗时业务任务。版本信息不得包含环境变量明文、Secret、Credential、用户数据或其他敏感信息。

### 6.5 配置、权限和数据隔离

- 普通配置通过 Config Center 管理，代码中不得硬编码 Dev/Prod 地址和账号；
- Secret、Credential 和 Tool Client 权限必须在清单中声明，遵循最小权限；
- Dev 和 Prod 使用独立的 Secret 密文、Client Token、登录 Session 和业务数据；
- 每个工具使用独立数据卷或数据目录，不得复用其他工具的数据目录；
- 工具自己的数据迁移只作用于自己的存储；修改平台公共数据库表时按公共高风险变更处理；
- Dev 和 Prod 只要求数据库结构及迁移目标按发布基线一致，不要求具体业务数据一致；
- 未经单独的数据迁移计划、备份和校验，不得把本机业务数据复制或覆盖到 Prod。

### 6.6 平台配置生成

接入生成器启用后，应根据 `platform-tool.yaml` 生成或校验以下公共结果：

- Docker Compose 服务和共享网络接入；
- Nginx 工具路由；
- 平台菜单与工具目录；
- 版本清单和镜像变量映射；
- CI 构建矩阵、发布范围和 Smoke Test 列表。

生成结果不得由开发者绕过清单长期手工维护。生成器尚未上线的过渡期内，如果必须手工修改这些公共文件，仍按第 5 节执行同行复核和完整回归。

### 6.7 自动接入门禁

工具合并到 `dev` 前，流水线至少检查：

- 清单满足 Schema，必填字段完整；
- 工具 ID、组件 ID、服务名、路由和端口不存在冲突；
- 组件版本按 SemVer 规则递增；
- Docker 镜像能够构建，且版本、Git SHA 和源码哈希可追溯；
- 健康检查和版本接口返回符合契约；
- 平台网关能够访问工具入口；
- 未修改其他工具目录，未声明的 Secret、数据卷和宿主机端口不存在；
- 停止或重建该工具时，平台和其他工具仍可用；
- 单组件升级和回滚不会重启无关容器；
- 工具的单元测试、集成测试和最小 Smoke Test 通过。

全部自动门禁通过后，组件负责人可以自行合并普通工具改动。自动门禁失败时必须修复原因，不能通过手工改平台公共配置绕过检查。

### 6.8 需要同行复核的例外

以下变更不能按普通自助接入处理，需要至少一名熟悉相关范围且不是提交者的同事复核：

- 修改接入清单 Schema、生成器或公共接入协议；
- 修改平台网关、统一登录、权限或身份透传边界；
- 修改平台公共数据库表或引入不兼容迁移；
- 修改 Secret、Credential、KEK、Tool Client 或生产权限模型；
- 修改公共发布、回滚、备份或配置中心机制；
- 一次改动影响两个及以上组件，或要求多个组件原子发布。

## 7. 分支模型

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 生产可发布主线 | 禁止直接开发和直接 Push |
| `dev` | 日常集成和 Dev 部署 | 通过合并请求进入，禁止作为 Prod 发布源 |
| `feature/<组件>/<主题>` | 新功能 | 从最新 `dev` 创建 |
| `fix/<组件>/<主题>` | 普通缺陷修复 | 从最新 `dev` 创建 |
| `hotfix/<组件>/<主题>` | 线上紧急修复 | 从当前 `main` 或生产 Tag 创建 |
| `docs/<主题>` | 文档 | 从 `dev` 创建 |
| `chore/<主题>` | CI、构建和维护 | 从 `dev` 创建 |

示例：

```text
feature/dating-tool/batch-analysis
feature/api-autotest/dating-case-expansion
fix/functional-test-agent/task-retry
hotfix/log-filter/export-timeout
docs/codeup-release-guide
```

禁止使用含义不明的分支名，例如 `test`、`new`、`temp`、`aaa`。

项目不设置 `release` 分支。正式发布以 `main` 上已经通过门禁的提交为准，创建不可变的 `release-YYYY.MM.DD.N` Tag；Tag 创建后不得移动或复用。`dev → main` 发布合并保留 merge commit，避免生产主线与集成分支再次分叉。

## 8. 日常开发流程

### 8.1 开始开发

```bash
git fetch origin
git switch dev
git pull --ff-only origin dev
git status --short
git switch -c feature/<组件>/<简短主题>
```

开始前必须确认：

- 工作区没有不属于自己的未提交改动；
- 当前需求属于哪个组件；
- 是否涉及公共文件、数据库或跨组件协议；
- 组件负责人已经明确；如果属于公共或高风险变更，同时明确一名同行复核人。

禁止使用 `git reset --hard`、强制覆盖或删除其他人的未提交文件来清理工作区。

### 8.2 开发过程中

- 优先只修改自己负责的组件目录；
- 同步修改相关测试、注释和文档；
- 业务代码变化必须判断是否需要升级组件 SemVer；
- 不得在代码中硬编码 Dev 或 Prod 地址、账号、密码和 Token；
- 不得将本地任务、报告、日志、截图或数据库误提交；
- 涉及共享文件时，应尽早通知受影响组件负责人，避免最后合并时才发现冲突。

### 8.3 提交规范

提交信息使用以下前缀：

```text
feat: 新增向后兼容功能
fix: 修复缺陷
test: 增加或调整测试
docs: 修改文档
refactor: 不改变业务行为的重构
chore: CI、构建、版本或运维维护
```

一次提交只表达一个能够独立解释、测试和回滚的目的。

## 9. 合并请求规范

标准流程：

```text
功能分支
→ 合并请求到 dev
→ 自动测试和接入契约门禁
→ 普通组件改动由负责人自行合并
→ 公共或高风险变更由相关同事复核
→ Dev 集成验证
→ dev 合并请求到 main
→ 创建正式 Release Tag
```

每个合并请求必须说明：

- 改动目的；
- 修改目录和影响组件；
- 是否修改公共文件；
- 是否修改 API、数据结构或数据库迁移；
- 组件版本是否升级；
- 执行过的测试命令和结果；
- Dev 验证方式；
- Prod 发布范围；
- 回滚方法。

人工复核触发规则：

| 改动类型 | 合并要求 |
|---|---|
| 单组件内部改动 | 自动门禁通过后，组件负责人可以自行合并 |
| 符合 Schema 的 `platform-tool.yaml` | 接入契约门禁通过后可以自行合并 |
| 跨组件行为或协议变更 | 通知受影响组件负责人，并由至少一名相关同事复核 |
| 平台公共框架、Nginx 模板、Compose 生成器或流水线 | 由至少一名熟悉该范围的同事复核 |
| 数据库、登录、权限、Secret | 由至少一名相关同事复核，并执行专项验证 |
| 生产发布 | 不设固定审批人；在约定窗口由轮值发布协调人启动 |

合并前必须同步最新 `dev`。个人独占分支可执行：

```bash
git fetch origin
git rebase origin/dev
```

多人共享的功能分支不得随意改写历史，应使用合并方式同步，并由分支负责人统一处理冲突。

## 10. 冲突管理

### 10.1 代码冲突

不同人员修改不同一级目录时，Git 冲突通常较少。直接冲突主要发生在同一个文件或相邻行。

冲突由功能分支提交者负责解决。解决后必须重新运行测试，不能只保证文本能够合并。

### 10.2 集成冲突

即使 Git 没有报冲突，也可能出现以下问题：

- 两个组件使用了相同端口或路由；
- 一个组件修改公共 API，另一个组件仍使用旧协议；
- 两个数据库迁移使用相同 revision 或顺序错误；
- 版本清单已经更新，但对应容器没有重建；
- 两条 Prod 流水线同时更新镜像清单；
- 单组件发布误重启其他服务。

因此，“Git 自动合并成功”不等于“可以安全上线”。CI、Dev 验证和发布门禁必须继续执行。

## 11. 版本管理

项目采用“产品版本 + 独立组件版本 + 数据库版本 + Release 发布号”模型。

- 产品版本：整套测试平台版本，例如 `1.3.0`；
- 组件版本：每个可独立发布服务的 SemVer，例如 `1.2.0`；
- 数据库版本：Alembic revision，例如 `20260828_0023`；
- 配置版本：Config Center 的 `vN` 和 `rel_xxx`；
- 生产发布号：`release-YYYY.MM.DD.N`；
- 精确运行身份：Git SHA、镜像 digest 和源码内容哈希。

组件版本升级规则：

- Bug 修复：递增 PATCH，例如 `1.2.0 → 1.2.1`；
- 向后兼容的新功能：递增 MINOR，例如 `1.2.1 → 1.3.0`；
- 不兼容升级：递增 MAJOR，例如 `1.9.0 → 2.0.0`。

只修改一个组件时，只升级该组件版本。数据库结构变化必须同时更新 Alembic revision，并升级平台后端版本。

---

## 12. 自动测试与 Dev 验证

流水线应根据变更目录执行对应测试：

```text
dating_tool/**
→ Dating Tool 测试与镜像构建

Truthy_ApiAutoTest2/**
→ API Autotest 测试与镜像构建

functional-test-agent/**
→ 功能测试智能体测试与镜像构建

test-platform/** 或公共文件
→ 平台前端、后端、Compose、版本和相关组件完整验证
```

合并到 `dev` 后必须确认：

- 组件单元测试和集成测试通过；
- Dev 实际运行版本与源码清单一致；
- 健康接口、页面入口和关键业务流程正常；
- 修改的组件已经重建，而不是继续运行旧容器；
- 公共接口和数据库变更完成跨组件回归；
- 测试结果已经记录在合并请求或流水线中。

测试失败时不得通过重复运行掩盖问题。必须确认失败属于代码问题、环境问题还是外部服务问题，并记录结论。

---

## 13. Prod 发布模型

团队采用约定发布窗口。各组件负责人在截止时间前完成 `dev` 合并和验证，轮值发布协调人负责汇总本次发布范围、确认没有并行部署，并在约定时间启动流水线。发布协调人是轮值执行角色，不是固定管理者或审批人。

生产标准流程：

```text
dev 验证通过
→ 合并请求进入 main
→ 创建 release-YYYY.MM.DD.N
→ Flow 从该 Tag 检出代码
→ 运行测试和版本门禁
→ 构建 linux/amd64 镜像
→ 推送 ACR 并锁定 digest
→ 生成 Release BOM
→ 生成待发布清单并通知团队
→ 轮值发布协调人在约定窗口启动部署
→ 生产服务器拉取镜像
→ 数据库迁移、启动和健康检查
→ 保存发布记录
```

生产服务器禁止：

- 直接从 `dev` 发布；
- 直接 `git pull` 驱动正式上线；
- 执行 `docker compose build` 现场构建；
- 使用 `latest` 或其他可变镜像标签；
- 手工修改容器后不写发布记录；
- 在没有备份和回滚目标时执行数据库迁移。

### 13.1 单组件发布

仅修改组件内部代码时：

- 只构建该组件镜像；
- 只更新该组件镜像 digest；
- 只启动该组件，使用等价于 `docker compose up -d --no-deps <service>` 的发布方式；
- 验证其他组件容器没有重启；
- 保存新的 Deployment Record；
- 失败时恢复该组件前一 digest。

组件负责人可以把自己的组件加入发布清单。流水线和自动门禁通过后，由当次轮值发布协调人统一启动部署，不需要另一名固定审批人确认。

### 13.2 平台完整发布

以下情况必须走完整发布：

- 平台网关、后端或公共前端变化；
- Nginx、Compose、网络或端口变化；
- 数据库迁移；
- 登录、权限、Secret、Credential 或 Config Center 变化；
- 跨组件 API 或数据协议变化；
- 多个组件需要保持原子一致性。

### 13.3 生产并发锁

所有 Prod 流水线必须共享同一个生产环境锁：

- 同一时间只允许一条部署执行；
- 后续发布必须排队，不能并行覆盖镜像清单和 `current.json`；
- 只运行测试和构建的流水线可以并行；
- 紧急发布需要先确认当前部署状态，不能直接抢占。

---

## 14. 云效权限建议

| 资源 | 团队成员 | 组件负责人 | 轮值发布协调人/流水线管理员 |
|---|---|---|---|
| Codeup 功能分支 | 创建、Push | 创建、Push | 创建、Push |
| `dev` | 通过合并请求进入 | 自动门禁通过后可合并本组件改动 | 同团队成员 |
| `main` | 禁止直接 Push | 通过发布合并请求进入 | 在发布窗口合并已验证内容 |
| CI 流水线 | 查看、运行 | 查看、运行 | 查看、运行；配置管理员负责编辑 |
| 组件发布流水线 | 可按团队约定启动 | 可将负责组件加入发布清单 | 在当次窗口协调启动 |
| 平台完整发布 | 查看、参与验证 | 可发起 | 在当次窗口协调启动 |
| ACR 服务连接 | 不直接管理 | 流水线受控使用 | 流水线受控使用；管理员维护连接 |
| Prod 主机组 | 不直接操作 | 流水线受控使用 | 流水线受控使用；管理员维护主机组 |
| 生产 Secret | 不直接查看 | 不直接查看 | 不因轮值身份获得明文权限，由受控系统管理 |

“所有人可以发布”是指团队成员都可以按规范进入发布轮值或启动被授权的流水线，不代表任何人都可以修改流水线、绕过自动门禁、读取生产 Secret 或直接操作生产服务器。流水线管理员只负责维护云效配置、服务连接和密钥，不承担每次业务发布审批职责。

---

## 15. 数据库、配置与 Secret

### 15.1 数据库

- Dev 和 Prod 的业务数据彼此独立，不要求内容一致；
- Dev 和 Prod 的表、字段、约束、索引和 Alembic revision 应保持兼容并按发布目标一致；
- 禁止为了“版本一致”将本地业务数据直接覆盖 Prod；
- 每个迁移必须有唯一 revision，并验证从上一生产版本升级；
- 生产迁移只向前执行，不自动 downgrade；
- 迁移前必须备份，失败时按发布预案恢复服务或数据库。

### 15.2 配置与 Secret

- 普通配置通过 Config Center 发布和回滚；
- Secret、密码、Token、KEK 和真实 `.env` 不得提交 Codeup；
- Dev 和 Prod 的 Secret 密文、Client Token 和登录 Session 不得复用；
- 流水线日志不得打印 Secret 明文；
- 生产配置通过 Config Center 或受控流水线管理，变更必须可追溯和可回滚，不依赖固定人员保存明文。

---

## 16. 回滚规则

单组件回滚：

```text
确认故障组件
→ 找到前一 Deployment Record
→ 恢复该组件旧 digest
→ 只重启该组件
→ 健康检查和业务回归
→ 记录回滚原因与结果
```

平台完整回滚：

- 恢复前一发布清单的镜像组合；
- 数据库默认不自动 downgrade；
- 配置回滚通过新的 Config Release 激活旧值；
- 如果新版本包含不兼容数据库变化，按发布前备份和专项预案处理；
- 回滚后仍需生成新的 Deployment Record，不能删除失败记录。

---

## 17. 紧急修复流程

线上紧急问题使用：

```text
当前生产 main/Release Tag
→ hotfix/<组件>/<主题>
→ 最小修复和回归测试
→ 合并请求进入 main
→ 新 Release Tag
→ 自动门禁通过后由当次发布协调人启动
→ 将修复同步回 dev
```

禁止直接在服务器修改源码或容器后结束处理。确因止损进行了临时操作，也必须立即补齐 Git 提交、Release、发布记录和 Dev 同步。

---

## 18. 禁止事项

- 禁止直接 Push `main`；
- 禁止个人分支直接发布 Prod；
- 禁止使用可变 `latest` 镜像上线；
- 禁止生产服务器现场构建正式镜像；
- 禁止两个 Prod 发布任务并行执行；
- 禁止发布自己的代码同时顺手重启其他组件；
- 禁止组件直接修改其他组件的数据；
- 禁止本地业务数据未经单独迁移计划、备份和校验覆盖 Prod；
- 禁止提交 Secret、真实 `.env`、任务产物、日志、备份和隐私截图；
- 禁止未升级组件版本就发布行为变化；
- 禁止数据库迁移与版本清单不一致；
- 禁止跳过失败测试或删除失败发布记录。

## 21. 两个典型示例

### 示例 A：A 修改 `dating_tool`

```text
feature/dating-tool/new-rule
→ 修改 dating_tool/**

→ 升级 dating_tool 组件版本

不需要重启 `Truthy_ApiAutoTest2`、两个智能体或平台服务。

→ 合并请求进入 dev
→ Dev 验证
→ 合并 main 并创建 Release
→ 只构建、发布和重启 api-autotest
```

如果同时修改平台路由、权限、数据库或公共配置，则升级为平台完整发布，不能继续按单组件发布处理。

## 23. 最终约定

团队日常协作统一遵循：

```text
目录独立负责
→ 按 platform-tool.yaml 自助接入
→ 功能分支开发
→ 合并请求进入 dev
→ 自动测试、接入门禁和 Dev 验证
→ 合并请求进入 main
→ Release Tag
→ 流水线构建不可变镜像
→ 约定时间由轮值发布协调人启动
→ 单组件或平台完整发布
→ 健康检查、发布记录和可回滚
```

目录独立可以降低 Git 文本冲突，接入清单和自动门禁负责阻止路由、端口、版本及运行契约冲突。公共或高风险变更仍需同行复核；普通组件变更不设置固定平台维护者或生产审批人。
