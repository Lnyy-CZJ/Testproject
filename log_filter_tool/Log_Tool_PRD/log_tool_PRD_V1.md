# Log 过滤工具 PRD

## 一、背景

当前调试日志内容较长，HTTP 请求和响应混在一起，人工查找某个接口方法的日志效率较低。需要一个简单工具，用户把日志粘贴到 Web 页面后，工具自动识别日志中的 `method`，并支持按方法名过滤出相关日志内容。

本工具以根目录下的 `log_default.log` 作为样例日志和规则参考。

## 二、目标

1. 提供一个简单 Web 界面，用户可以直接粘贴日志内容。
2. 自动从日志中提取所有出现过的 `method`，生成下拉列表。
3. 用户选择某个 `method` 后，返回该方法对应的日志内容（包含请求和响应日志块）。
4. 实现方式保持简单，优先使用 Python，不做复杂架构。

## 三、非目标

1. 不做用户登录、权限管理。
2. 不做数据库存储，日志只在当前页面或当前请求中处理。
3. 不做复杂查询语法，例如多条件组合、正则搜索、高亮规则编辑器。
4. 不做日志文件上传功能，第一版只支持文本框粘贴日志。
5. 不做前后端分离项目，避免引入复杂构建流程。

## 四、用户场景

### 场景 1：查看某个接口的请求和响应

用户从控制台复制一段日志，粘贴到页面文本框中。页面自动识别出 `GetTaskCandidateDetail`、`TrackEvents` 等方法名。用户选择 `GetTaskCandidateDetail` 后，页面展示该方法相关的 HTTP 请求、请求体、响应和响应体日志块。

### 场景 2：快速查看当前日志包含哪些接口

用户粘贴日志后，不需要手动阅读整段日志，直接通过下拉列表看到当前日志中包含的方法名。

## 五、输入说明

用户输入为一整段纯文本日志，格式参考 `log_default.log`。

样例中的 method 可能出现在以下位置：

```text
[HTTP] --> POST ... service=xxx method=GetTaskCandidateDetail
[HTTP] <-- 200 POST ... service=xxx method=TrackEvents
"method_name": "TrackEvents"
```

第一版主要识别以下两类写法：

1. `method=方法名`
2. `"method_name": "方法名"`

方法名由英文字母、数字、下划线组成，例如：

```text
GetMe
GetSubscriptionStatus
GetSubscriptionList
GetTaskCandidateDetail
TrackEvents
```

## 六、过滤规则

### 6.1 日志块划分

`log_default.log` 中的日志通常使用以下边界表示一个完整日志块：

```text
┌────────────────
│ 日志内容
└────────────────
```

第一版按日志块过滤，而不是只过滤单行。

原因：HTTP 请求和响应的 method 通常只出现在日志块的第一行或 JSON 中。如果只返回包含 method 的单行，会丢失 request body、response body 等关键信息。

### 6.2 method 提取

工具从用户粘贴的完整日志中提取 method：

1. 扫描所有 `method=xxx`。
2. 扫描所有 `"method_name": "xxx"`。
3. 去重后按字母顺序展示在下拉列表中。
4. 如果没有识别到 method，则提示“未识别到 method”。

### 6.3 method 过滤

用户选择一个 method 后，工具返回该 method 对应的日志块。

匹配规则：

1. 如果某个日志块包含 `method=选择的方法名`，则返回该日志块。
2. 如果某个日志块包含 `"method_name": "选择的方法名"`，则返回该日志块。
3. 如果匹配到的是 `[HTTP] --> ... method=xxx` 请求头日志块，并且它后面紧跟 `[HTTP] request:` 日志块，则同时返回后面的 request 日志块。
4. 如果匹配到的是 `[HTTP] <-- ... method=xxx` 响应头日志块，并且它后面紧跟 `[HTTP] response:` 日志块，则同时返回后面的 response 日志块。
5. 输出结果保持原始日志文本，不改写日志内容。

这样可以避免只显示 HTTP header，漏掉请求体或响应体。

### 6.4 全部显示

下拉列表提供“全部”选项：

1. 默认选择“全部”。
2. 选择“全部”时展示原始日志内容。
3. 用户切换到具体 method 后，只展示过滤结果。

## 七、页面需求

页面保持简单，包含以下区域：

1. 日志输入框：大文本框，支持粘贴完整日志。
2. 解析按钮：点击后提取 method 并刷新下拉列表。
3. method 下拉列表：展示“全部”和自动提取到的 method。
4. 过滤结果区域：展示过滤后的日志文本。
5. 统计信息：展示识别到的 method 数量、当前匹配到的日志块数量。

页面不要求复杂样式，能清晰使用即可。

## 八、交互流程

1. 用户打开页面。
2. 用户把日志粘贴到输入框。
3. 用户点击“解析日志”。
4. 系统提取 method，并更新下拉列表。
5. 用户选择一个 method。
6. 系统展示对应过滤结果和匹配数量。

## 九、异常处理

1. 输入为空：提示“请先粘贴日志内容”。
2. 没有识别到 method：提示“未识别到 method，请检查日志格式”。
3. 某个 method 没有匹配结果：提示“没有匹配到相关日志”。
4. 日志格式不完整：尽量按已有文本处理，不因为缺少 `┌` 或 `└` 报错。

## 十、推荐技术方案

### 10.1 推荐方案：Python + Flask 单体应用

采用 Python + Flask 实现一个简单 Web 工具。

推荐原因：

1. 代码量少，适合当前需求。
2. Flask 可以直接渲染一个 HTML 页面，不需要前后端分离。
3. 过滤逻辑可以集中在一个 Python 文件中，便于理解和修改。
4. 本地运行简单，适合调试场景。

### 10.2 不推荐方案

1. 纯命令行脚本：实现更简单，但不满足 Web 界面和下拉选择需求。
2. 前后端分离：对当前工具过重，会增加依赖、构建和部署成本。
3. 数据库存储：第一版不需要保存历史日志，暂不引入。

## 十一、建议文件结构

```text
log_filter_tool/
├── app.py
├── templates/
│   └── index.html
├── requirements.txt
├── log_default.log
└── log_tool_PRD.md
```

说明：

1. `app.py`：Flask 入口，包含 method 提取和过滤逻辑。
2. `templates/index.html`：页面模板。
3. `requirements.txt`：记录 Flask 依赖。
4. `log_default.log`：样例日志。
5. `log_tool_PRD.md`：当前需求文档。

## 十二、核心逻辑说明

### 12.1 提取 method

使用 Python 正则表达式提取：

```text
method=([A-Za-z0-9_]+)
"method_name"\s*:\s*"([A-Za-z0-9_]+)"
```

提取后合并、去重、排序。

### 12.2 拆分日志块

优先按 `┌` 到 `└` 的范围拆分日志块。

如果日志中没有这些边界，则退化为按行处理，保证工具仍然可用。

### 12.3 过滤日志块

遍历所有日志块，只保留包含目标 method 的日志块。

为了简单处理请求体和响应体，第一版增加一个相邻块规则：

1. 当前块命中 `[HTTP] --> ... method=xxx` 时，如果下一个块包含 `[HTTP] request:`，也一起返回。
2. 当前块命中 `[HTTP] <-- ... method=xxx` 时，如果下一个块包含 `[HTTP] response:`，也一起返回。

最终按原始顺序去重后，用换行拼接展示。

## 十三、验收标准

1. 用户可以在浏览器中打开工具页面。
2. 用户可以粘贴 `log_default.log` 的内容并点击解析。
3. 下拉列表能自动出现 `GetTaskCandidateDetail`、`TrackEvents` 等 method。
4. 选择 `GetTaskCandidateDetail` 后，只展示相关日志块。
5. 选择 `TrackEvents` 后，只展示相关日志块。
6. 选择“全部”后展示原始日志。
7. 空输入时有明确提示。
8. 未识别到 method 时有明确提示。
9. 不需要数据库，不需要登录，不需要复杂部署。

## 十四、第一版优先级

### P0 必须实现

1. Web 页面。
2. 日志粘贴输入。
3. method 自动提取。
4. method 下拉过滤。
5. 结果展示。

### P1 可以后续再做

2. 加载 `log_default.log` 作为默认示例。

4. 显示每个 method 的匹配数量。

3. 保存历史记录。
