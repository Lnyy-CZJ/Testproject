# Log 工具 V1.5 接口分析 PRD

## 一、产品定位

面向测试工程师的本地接口日志分析工具。在现有日志过滤能力的基础上，增加接口请求、响应和状态统计，帮助用户快速判断接口整体情况。

## 二、背景与目标

当前 V1 支持粘贴日志、提取 method 和按 method 过滤日志，但用户仍需人工判断接口调用次数、成功率和失败情况。

V1.5 需要把日志块解析成简单的结构化数据，并提供基础接口统计。用户粘贴日志后，工具应能够：

1. 识别接口 method、请求日志和响应日志。
2. 提取 `request_id`、`trace_id` 和 HTTP 状态码。
3. 统计每个接口的请求、响应、成功、失败和未响应情况。
4. 支持查看接口对应的原始日志。

## 三、用户场景

### 3.1 查看接口总体情况

用户选择 `TrackEvents` 后，查看请求次数、响应次数、成功次数、失败次数和成功率。

### 3.2 查看状态码分布

例如：

```text
200：10次
400：1次
500：1次
```

### 3.3 查看失败日志

用户点击失败数量后，查看对应原始日志，继续排查问题。

## 四、功能需求

### 4.1 日志输入

- 支持粘贴文本日志。
- 支持加载默认示例日志。
- 支持较大的日志内容。
- 输入为空时给出明确提示。
- 只在当前请求内存中处理，不使用数据库。

### 4.2 method 提取

支持：

```text
method=TrackEvents
"method_name": "TrackEvents"
```

必须精确匹配。例如选择 `GetTask` 时，不能匹配 `GetTaskCandidateDetail`。

### 4.3 日志块解析

优先按照以下边界拆分：

```text
┌────────────────
│ 日志内容
└────────────────
```

没有标准边界时，退化为按非空行处理，不能因为格式不完整导致程序报错。

### 4.4 日志类型识别

识别：`request_header`、`request_body`、`response_header`、`response_body`、`other`。

识别关键词包括：

```text
[HTTP] -->
[HTTP] request:
[HTTP] <--
[HTTP] response:
```

### 4.5 字段提取

每个日志块尽量提取：

| 字段 | 说明 |
|---|---|
| `method` | 接口名称 |
| `request_id` | 请求唯一标识 |
| `trace_id` | 链路唯一标识 |
| `status_code` | HTTP 状态码 |
| `timestamp` | 日志时间 |
| `raw_text` | 原始日志内容 |

兼容以下写法：

```text
request_id: abc123
"request_id": "abc123"
trace_id: trace456
"trace_id": "trace456"
```

### 4.6 接口统计

针对每个 method 统计：

- 请求次数。
- 响应次数。
- 成功次数。
- 失败次数。
- 未响应次数。
- 成功率。
- HTTP 状态码分布。

默认规则：状态码 200 到 299 为成功，状态码大于等于 400 为失败，没有响应状态码为未响应或未完成。

### 4.7 原始日志查看

选择接口后，可以查看统计数据和原始日志。展示结果时继续清理控制台前缀，例如：

```text
17:17:58.193950+0800 Runner flutter:
```

## 五、建议数据结构

```python
{
    "method": "TrackEvents",
    "request_id": "abc123",
    "trace_id": "trace456",
    "kind": "response",
    "status_code": 200,
    "timestamp": "17:17:58",
    "raw_text": "原始日志"
}
```

只在内存中处理，不引入数据库。

## 六、页面设计

页面包含日志输入区、解析按钮、接口选择下拉框、接口统计概览、状态码统计表和原始日志结果区。

接口统计表字段：

| 接口 | 请求次数 | 响应次数 | 成功 | 失败 | 未响应 | 成功率 |
|---|---:|---:|---:|---:|---:|---:|

## 七、异常处理

- 没有 method：提示未识别到接口。
- 没有状态码：保留日志，但不计入成功或失败。
- JSON 不完整：保留原始文本，跳过结构化解析。
- 请求没有响应：统计为未响应。
- 日志边界不完整：尽量处理已有内容。

## 八、验收标准

1. 可以提取全部 method，且精确匹配。
2. 可以识别请求和响应日志。
3. 可以提取 `request_id`、`trace_id` 和 HTTP 状态码。
4. 可以统计请求、响应、成功、失败和未响应数量。
5. 可以展示接口成功率和状态码分布。
6. 可以查看接口原始日志。
7. 大日志提交不会出现 `Request Entity Too Large`。
8. 异常日志格式不会导致页面崩溃。

## 九、非目标

- 数据库存储。
- 实时日志监听。
- 复杂查询语法。
- 用户登录和权限管理。
- 分布式部署。
- 复杂图表系统。
