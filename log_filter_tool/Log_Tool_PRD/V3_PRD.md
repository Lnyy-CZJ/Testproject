# Log 工具 V3 失败分析 PRD

## 一、产品定位

在 V2 单次请求链路的基础上，自动识别失败调用、进行失败分类、提取错误信息，并提供简单的排查建议。

## 二、背景与目标

V2 可以查看单次请求的完整链路，但测试人员仍需要人工判断这是 HTTP 失败、业务失败、超时、异常，还是请求没有响应。

V3 需要提供规则驱动的失败分析能力：

1. 自动识别失败调用。
2. 对失败进行分类。
3. 提取错误码和错误信息。
4. 展示失败请求的完整上下文。
5. 给出初步排查建议。
6. 支持按失败类型筛选。

分析结果用于辅助判断，不承诺自动给出唯一根因。

## 三、失败分类规则

### 3.1 HTTP 失败

规则：HTTP 状态码大于等于 400。

- 400 到 499：请求、参数、认证或权限问题。
- 500 到 599：服务端或网关问题。

### 3.2 业务失败

HTTP 状态码为 2xx，但响应内容表示业务失败，例如：

```json
{
  "code": 10001,
  "message": "参数非法"
}
```

初期识别以下规则：

- `success: false`。
- `status: false`。
- `error` 字段有值。
- `message` 包含失败关键词。
- 业务 `code` 不属于默认成功值。

### 3.3 超时

日志中出现以下关键词时标记为超时：

```text
timeout
timed out
connect timeout
read timeout
request timeout
```

有请求、没有响应且耗时超过阈值时，也可以标记为“疑似超时”。默认阈值为 10 秒。

### 3.4 异常

出现以下关键词时标记为异常：

```text
Exception
Error
StackTrace
Traceback
Fatal
Unhandled
crash
```

尽量提取异常类型、错误信息、第一行堆栈、关联 method、`request_id` 和 `trace_id`。

### 3.5 无响应

有请求日志，但在关联范围内没有找到响应，标记为“无响应”。页面需要提示这可能是超时、应用异常、日志缺失或关联失败，不能直接断言具体原因。

### 3.6 数据不完整

以下情况标记为数据不完整：

- 有响应但没有请求。
- 有状态码但没有响应体。
- 有 `request_id` 但没有 method。
- 日志块缺少结束边界。
- JSON 解析失败。

## 四、失败优先级

一条调用符合多个规则时，主失败类型优先级为：

```text
异常 > 超时 > HTTP 失败 > 业务失败 > 无响应 > 数据不完整
```

同时可以保留多个失败标签。

## 五、失败详情

每条失败记录至少展示：

- 接口名称。
- 失败类型。
- 请求时间。
- `request_id`。
- `trace_id`。
- HTTP 状态码。
- 业务错误码。
- 错误信息。
- 请求参数。
- 响应内容。
- 关联日志。
- 初步排查建议。

示例：

```text
接口：TrackEvents
失败类型：HTTP 失败
状态码：500
request_id：abc123
trace_id：trace456
错误信息：Internal Server Error
初步判断：服务端返回 500，需要检查服务端异常日志
```

## 六、失败摘要

选择接口后，页面顶部显示总调用、成功、失败、无响应和失败率。

失败类型统计示例：

```text
HTTP 失败：2
业务失败：1
超时：1
异常：1
```

## 七、失败筛选

支持筛选：全部、HTTP 失败、业务失败、超时、异常、无响应、数据不完整。

支持按 method、`request_id`、`trace_id`、错误信息和 HTTP 状态码搜索。

## 八、初步排查建议

| 失败类型 | 建议 |
|---|---|
| 4xx | 检查请求参数、认证信息和接口权限 |
| 5xx | 检查服务端异常日志和 trace_id |
| 业务失败 | 检查业务错误码和响应 message |
| 超时 | 检查网络、服务响应时间和下游依赖 |
| 无响应 | 检查日志完整性、客户端异常和超时配置 |
| 异常 | 查看异常类型和第一处堆栈信息 |
| 关联失败 | 检查 request_id、trace_id 是否被正确打印 |

这些建议仅用于辅助排查，不替代人工判断。

## 九、页面设计

增加“失败分析”视图：失败总览、失败类型统计、失败记录列表、失败详情和原始日志。

失败记录列表字段：

| 时间 | 接口 | 失败类型 | 状态码 | 错误信息 | Request ID |
|---|---|---|---:|---|---|

失败详情提供复制 `request_id`、复制 `trace_id`、复制失败摘要、查看完整链路和查看原始日志。

## 十、敏感信息处理

页面展示时对 Token、Cookie、密码、Authorization、手机号等字段进行基础脱敏：

```text
Authorization: Bearer ******
password: ******
token: ******
```

日志只在当前请求中处理，不进行持久化。

## 十一、验收标准

1. 可以自动识别 HTTP 失败。
2. 可以自动识别常见业务失败。
3. 可以识别超时关键词。
4. 可以识别常见异常堆栈。
5. 可以识别请求无响应。
6. 可以统计不同失败类型的数量。
7. 可以按失败类型筛选。
8. 可以展示失败记录的完整链路。
9. 可以提取错误码和错误信息。
10. 可以根据失败类型给出初步排查建议。
11. 页面展示敏感字段时能够脱敏。
12. 解析异常日志时页面不会崩溃。
13. 用户仍然可以查看原始日志。

## 十二、非目标

- 自动修复问题。
- 自动调用接口重试。
- 自动生成缺陷单。
- AI 自动判断唯一根因。
- 实时监控告警。
- 多人协作。
- 日志长期存储。
- 完整的分布式链路追踪平台。
