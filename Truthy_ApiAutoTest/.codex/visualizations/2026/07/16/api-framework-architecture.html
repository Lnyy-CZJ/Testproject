当前定位 已可执行的业务型框架
主要缺口 接口、数据和步骤尚未配置化
目标形态 配置驱动 + 复杂流程插件

已经具备

  • 统一 Gateway HTTP 入口与安全策略
  • 双层断言、异步等待、脱敏和报告
  • Identity、Subscription、Search 等业务封装
  • Pytest、Jenkins、飞书的统一执行链

现在不够通用的地方

  • 接口定义散落在各个 Service 方法中
  • 大部分请求数据和期望值写在测试代码里
  • 没有真正落地 data/cases 用例数据目录
  • 新增普通接口仍要写 Service 方法和测试函数

流程 02：当前问题与改造方向

你的判断成立：当前版本更像“针对现有业务用例实现的自动化工程”，还不是“只配接口和数据就能扩展”的通用框架。

接口管理 现在：Service 类中硬编码 service_name、method_name 和参数
目标：apis/*.yaml 统一注册，按接口名称查找和执行
接口数据 现在：参数主要写在测试函数、fixture 或 mock 响应中
目标：data/payloads 管理请求模板，支持变量引用
用例数据 现在：Loader 已存在，但多数 contract 用例仍是 Python 内联
目标：data/cases 作为数据唯一入口，Python 只保留行为
工具代码 现在：按 assertions/client/reporting/security 等目录分散
目标：统一聚合到 core，内部仍按职责分包，避免扁平 utils
用例管理 现在：新增接口通常要新增 Service 方法和 test_*.py
目标：普通接口只新增 API YAML + Case YAML；复杂流程才写 Python 插件

流程 03：目标通用架构

采用“双轨制”：80% 普通接口由配置驱动，上传、轮询、条件分支等复杂场景由流程插件扩展。

配置驱动：普通接口 插件扩展：复杂流程 安全门禁：执行层统一控制

流程 04：推荐目录与职责

接口、数据、工具和用例各有唯一入口；Jenkinsfile 仍保留在根目录，这是 Jenkins 的标准约定。

目标目录

Truthy_ApiAutoTest/
├── apis/                    # 接口管理
│   ├── identity.yaml
│   ├── subscription.yaml
│   ├── search.yaml
│   └── media.yaml
├── data/                    # 所有可变测试数据
│   ├── environments/

│   ├── cases/               # 单接口用例数据
│   ├── flows/               # 多接口步骤数据
│   ├── schemas/             # 数据结构校验
│   └── public_samples/      # 脱敏公开样例
├── core/                    # 框架工具代码
│   ├── http/                # Gateway/REST/COS
│   ├── config/              # 配置加载
│   ├── logging/             # 日志与脱敏
│   ├── assertions/          # 通用断言
│   ├── reporting/           # Allure/JUnit
│   ├── notification/        # 飞书
│   └── execution/           # Registry/Executor/Context
├── flows/                   # 复杂 Python 流程插件
├── tests/
│   ├── test_api_cases.py    # 通用单接口驱动
│   ├── test_flow_cases.py   # 通用流程驱动
│   ├── contract/
│   └── unit/
├── runtest.py               # 唯一执行入口
└── Jenkinsfile              # CI 标准入口

每层只负责一件事

  • apis：这个接口怎么请求、需要什么鉴权
  • data：本次用什么输入、期望什么结果
  • core：怎么安全发送、记录、断言和报告
  • flows：多个接口如何传值、轮询和分支
  • tests：选择哪些数据集并交给执行器
  • runtest.py：决定环境、范围和安全级别
  • Jenkinsfile：决定什么时候运行以及是否阻断

流程 05：以后新增接口和用例怎么做

普通接口不再要求新增 Service 类；只有框架不能表达的特殊协议或流程才补 Python。

flowchart TB A["新增 apis/业务域.yaml
声明名称、transport、path/service、method、auth"] --> B["新增 data/payloads/请求模板.yaml"] B --> C["新增 data/cases/业务域/TC-xxx.yaml
输入、期望、marker"] C --> D{"是否为普通单接口?"} D -->|是| E["test_api_cases.py 自动收集"] D -->|否| F{"能否用 YAML 步骤表达?"} F -->|是| G["data/flows/*.yaml
call / extract / assert / wait"] F -->|否| H["flows/*.py
编写上传、轮询或条件插件"] G --> I["test_flow_cases.py 自动收集"] H --> I E --> J["runtest.py --suite contract/smoke/regression"] I --> J J --> K["Allure / JUnit / Jenkins / 飞书"]

普通新增

  1. 注册接口 YAML
  2. 准备请求模板
  3. 增加 Case YAML
  4. 运行统一测试入口

需要写 Python 的情况

  • COS 二进制上传
  • 异步任务轮询与非法状态倒退
  • 复杂条件分支和跨域一致性校验
  • 外部夹具、数据库只读核验等适配器
