# Bug Agent Web DESIGN.md

> Last updated: 2026-04-13
> Scope: `/web` 全站设计系统与页面实现约束
> Status: Active

---

## 1. Purpose

这份文档定义 Bug Agent Web 端的统一设计语言，约束登录注册、平台级页面、项目级页面、缺陷创建、缺陷列表、缺陷详情、问题池、质量情报和配置类页面的视觉与交互实现。

目标不是把系统做成“传统后台”，也不是把系统做成“AI 营销站”，而是把它做成：

> 面向处理者的缺陷协作工作台

界面必须同时表达三件事：

1. 问题在流动
2. AI 在参与
3. 用户能快速行动

---

## 2. Core Direction

### 2.1 Product Character

全站采用 `结构化实验型` 设计方向：

- 保留浅色主界面
- 保留当前紫青品牌色
- 保留项目级工作区心智
- 全站都体现创新性，但不牺牲效率型页面的扫描能力

创新感不通过夸张造型堆叠，而通过统一空间语言建立：

`浅色底面` + `紫青能量层` + `模块化场景卡片` + `明确操作轨道` + `可收敛的数据区`

### 2.2 Reference, Not Imitation

视觉母体参考：

- 整体气质参考 `Cohere` 式企业 AI 产品感
- 列表与详情结构参考 `Linear` 式秩序、阅读效率和信息分层

禁止直接复制任何外部产品的视觉细节。Bug Agent 的目标是建立自己的工作台语言。

### 2.3 Inheritance Rules

必须继承当前系统中已经成立的资产：

- 浅色背景与冷白工作区
- 紫青渐变品牌识别
- 左侧导航 + 顶部状态栏的工作区骨架
- 项目上下文明确的页面组织
- AI 相关模块在主链路中的存在感

必须抛弃当前系统中不成立的部分：

- 默认后台式大白卡堆叠
- 一页中叙事、操作、数据混在一个层级
- 列表与详情缺乏主次
- AI 模块像装饰，不像工作流参与者

## 3. Global Principles

### 3.1 Three-Layer Page Model

每个页面必须拆成三层：

1. `Narrative Layer`
   - 页面标题
   - 当前状态
   - 角色说明
   - 当前任务
2. `Action Layer`
   - 搜索
   - 筛选
   - 视图切换
   - 主按钮
   - 批量动作
3. `Data Layer`
   - 列表
   - 卡片
   - 详情
   - 表单
   - 时间线
   - 图表

禁止把这三层混在单一容器里。

### 3.2 Information Density

允许高信息密度，但必须满足：

- 远看有分区
- 近看有重点
- 扫描路径明确
- 主动作不丢失

列表页和配置页优先保证效率。工作台、创建页、详情页允许更强的版面表达。

### 3.3 AI Expression

AI 模块必须被理解为“协作角色”，而不是彩色广告位。

AI 模块必须始终优先展示：

1. 摘要
2. 建议
3. 依据
4. 风险
5. 下一步动作

原始日志、完整分析、JSON、长文本一律折叠到深层。

### 3.4 Motion

动效原则：

- 低频
- 低噪
- 可解释
- 有明确反馈价值

允许：

- 页面入场
- 模块展开
- 筛选切换
- 状态变更反馈
- AI 处理中状态推进

禁止：

- 全站持续发光
- 大量漂浮 hover
- 无意义的呼吸动画
- 粒子特效
- 页面级花哨转场

## 4. Page Families

### 4.1 Auth Pages

适用页面：

- 登录
- 注册
- 找回密码

结构：

- `Brand Story Panel`
- `Auth Form Panel`

规则：

- 左侧品牌叙事区允许更强视觉表达
- 右侧表单区必须克制、安静、易填写
- 品牌区负责建立“AI 缺陷协作产品”的世界观
- 表单区不承载复杂说明，不加入无关炫技元素

### 4.2 Platform Console Pages

适用页面：

- 项目列表
- 用户管理
- 审计日志
- AI 目录
- 平台凭证
- 平台配置

结构：

- 全局侧栏
- 顶部状态栏
- 标题区
- 操作轨道
- 主数据区

规则：

- 项目列表可以拥有更强品牌感
- 用户管理、审计、平台配置更偏控制台气质
- 即便是配置与管理页，也要保留统一的页面骨架和品牌边界

### 4.3 Project Workspace Pages

适用页面：

- 项目工作台
- 问题池
- 信号接入
- 路由治理
- 回归预防
- 质量情报
- 迭代管理
- 成员管理
- 仓库管理
- AI 配置
- 通知管理

结构：

- 项目上下文区
- 当前页面任务区
- 业务内容区

规则：

- 用户必须始终知道自己处于哪个项目上下文
- 页面说明要明确“本页职责”
- 项目工作区不是普通二级后台，而是面向当前项目的处理空间

### 4.4 Workspace Dashboards

适用页面：

- 全局工作台
- 项目工作台

结构：

- 高优先摘要区
- 快速行动区
- 动态信息区

规则：

- 工作台不是统计卡片堆叠页
- 第一屏必须优先展示“当前最重要的事”
- 快速行动必须靠前
- 动态区要支撑从发现问题到进入流程

### 4.5 Data List Pages

适用页面：

- 缺陷列表
- 问题池
- 迭代列表
- 成员列表
- 仓库列表
- 配置型清单页面

结构：

- 标题区
- 操作轨道
- 数据舞台
- 选择态/空态/批量反馈层

规则：

- 列表页必须优先保证搜索、筛选、扫描与批量操作效率
- 可以拥有创新性，但不能让表格失去工具属性
- 行内信息要有稳定语法：主信息、状态、辅助元信息

### 4.6 Detail Workbench Pages

适用页面：

- 缺陷详情
- 后续可扩展到问题簇详情、修复任务详情

结构：

- 顶部摘要带
- 主阅读区
- 决策侧轨

规则：

- 详情页是工作台，不是字段页
- 摘要、动作、上下文、深层技术信息必须分层
- AI 结论是主阅读区的一级内容，不是附件
- 原始数据默认折叠

### 4.7 Guided Creation Pages

适用页面：

- Chat-first 新建缺陷
- 高级模式创建缺陷

结构：

- 入口说明
- 输入区
- AI 整理区
- 确认区

规则：

- `Chat-first` 是主路径
- 高级模式是专家入口
- 用户感知应是“表达问题 -> AI 帮我整理 -> 我确认落库”
- 不能退回成大表单堆字段

### 4.8 Configuration Pages

适用页面：

- 平台设置
- AI 配置
- 仓库配置
- 通知配置
- 接入配置

结构：

- 分组说明
- 配置模块卡
- 状态反馈区

规则：

- 配置页允许产品感，但要比工作台、详情页更克制
- 以分组和反馈清晰为先，不以视觉冲击为先

## 5. Component System

### 5.1 Buttons

按钮分四级：

- `Primary`
- `Secondary`
- `Tertiary`
- `Danger`

规则：

- `Primary` 只给当前页面最重要动作
- 同一屏不应出现超过 1 到 2 个品牌型主按钮
- 渐变主按钮只能用于高价值动作
- 二级和三级按钮必须明显退后

### 5.2 Cards

卡片分三类：

- `Base Card`
- `Scene Card`
- `Utility Card`

用途：

- `Base Card`: 普通信息承载
- `Scene Card`: AI 摘要、重点状态、关键工作区
- `Utility Card`: 筛选、配置、小信息块

规则：

- 不允许全页所有卡片都做成场景卡
- 普通卡片保证秩序
- 场景卡负责品牌辨识度
- 工具卡负责效率与密度

### 5.3 Tables And List Rows

规则：

- 表头轻背景
- 行 hover 必须明确
- 第一信息列最强
- 状态、优先级、负责人、时间形成稳定视觉语法
- 复杂记录允许采用“卡片化行”，但仍需支持扫描和批量处理

### 5.4 Search And Filters

筛选区是 `Action Rail`，不是简单表单横排。

必须支持：

- 搜索入口
- 高频筛选
- 低频筛选折叠
- 当前筛选回显
- 主动作或批量动作

规则：

- 当前筛选状态必须可见
- 高频项优先
- 操作区要像工具条，不像问卷

### 5.5 Tags And Badges

标签分三类：

- `Status Tag`
- `Priority Tag`
- `Meta Tag`

规则：

- 状态标签服务流程识别
- 优先级标签服务风险判断
- 辅助标签退后
- 禁止所有标签都高饱和、高权重

### 5.6 Navigation

规则：

- 平台级导航和项目级导航共用一套语言
- 项目级导航必须更强上下文感
- 当前页高亮必须稳定且一眼可见
- 导航不是普通菜单，而是工作轨道

### 5.7 Page Headers

页面标题区必须能回答两个问题：

1. 我在看什么？
2. 我现在能做什么？

可包含：

- 标题
- 状态
- 一句话职责说明
- 主动作
- 当前上下文提示

### 5.8 AI Modules

AI 模块固定采用以下结构：

- `AI Header`
- `AI Summary`
- `AI Evidence`
- `AI Action`
- `AI Deep Detail`

规则：

- AI 模块可以有更强紫青高光与轻渐变
- 只能用于关键 AI 场景
- 必须可读、可折叠、可操作
- 不能只是一块彩色 Markdown 容器

### 5.9 Detail Side Rail

详情页侧轨负责：

- 负责人
- 优先级
- 流程状态
- 关联对象
- 关键时间
- 建议动作

规则：

- 侧轨服务决策
- 侧轨不重复正文
- 正文负责理解问题，侧轨负责推动处理

### 5.10 Inputs

规则：

- 默认克制
- Focus 时体现品牌感
- 校验反馈清晰但不过度高亮
- 聊天输入框与普通表单输入同属一套输入系统

### 5.11 Empty, Loading, Error States

空态分三类：

- 首次引导型空态
- 筛选结果为空
- 异常中断型空态

加载分五类：

- Page Loading
- Module Loading
- Table Loading
- AI Processing
- Background Sync

规则：

- 空态必须带下一步动作
- AI Processing 必须表现为“任务推进”
- 普通加载保持低干扰

## 6. Design Tokens

### 6.1 Color Tokens

```css
--bg-page
--bg-surface
--bg-elevated
--brand-purple
--brand-cyan
--brand-gradient
--text-primary
--text-secondary
--text-tertiary
--border-default
--border-strong
--status-success
--status-warning
--status-error
--status-info
--status-neutral
```

规则：

- 品牌色服务身份与关键动作
- 功能色服务状态判断
- 两者不得混用

### 6.2 Typography

建议：

- 正文：`PingFang SC`, `Microsoft YaHei`, `sans-serif`
- UI 英数与标题：`Geist`, `PingFang SC`, `sans-serif`
- 代码与技术信息：`Geist Mono`, `SFMono-Regular`, `monospace`

规则：

- 中文正文优先可读性
- 创新感来自层级与版面，而不是怪异字体

### 6.3 Radius

统一三档：

- `12px`
- `16px`
- `24px`

规则：

- 小控件使用 12
- 常规卡片使用 16
- 场景卡与重点模块使用 24
- 禁止全站圆角失控

### 6.4 Shadow

统一三档：

- `shadow-sm`
- `shadow-md`
- `shadow-lg`

规则：

- 阴影只做层级提示
- 禁止重阴影堆“高级感”

### 6.5 Spacing

统一节奏：

`4 / 8 / 12 / 16 / 24 / 32 / 48`

规则：

- 控件级紧凑
- 模块级呼吸更大
- 页面级分区必须明显大于组件级间距

### 6.6 Motion Timing

建议时长：

- `120ms` hover / focus
- `180ms` 轻切换
- `240ms` 抽屉 / 折叠
- `320ms` 页面或重点模块入场

## 7. Hard Constraints

禁止：

1. 大面积高饱和渐变做页面底
2. 全站所有主卡都做成发光 AI 卡
3. 为了视觉感牺牲表格扫描效率
4. 把摘要、日志、原始 JSON 放在同一层级
5. 同一屏出现多个相互竞争的主按钮
6. 让所有标签都高权重高饱和
7. 用品牌色替代功能状态色
8. 为了“独特”破坏常见交互习惯
9. 用默认组件样式直接拼整站而不做统一收敛
10. 在配置页引入与任务无关的强视觉噪音

---

## 8. Implementation Priorities

UI 重构建议按以下顺序推进：

1. 认证页与品牌入口
2. 全局工作台与项目工作台
3. Chat-first 新建缺陷
4. 缺陷列表
5. 缺陷详情
6. 问题池 / 质量情报 / 路由治理
7. 配置类页面收口

---

## 9. Working Rules For Future Changes

在实现任何新页面或重构既有页面前，先判断它属于哪一类页面家族，再决定：

1. 页面骨架
2. 组件权重
3. 品牌能量层出现位置
4. AI 是否为一级内容
5. 该页是效率优先还是表达优先

如果一个实现同时违背以下任意两项，则默认视为不符合本设计系统：

- 页面主次不清
- 主动作不明确
- AI 区块不可读
- 列表扫描效率下降
- 品牌色使用失控
- 层级只靠颜色堆叠
