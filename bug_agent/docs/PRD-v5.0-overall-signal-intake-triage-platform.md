# BugAgent v5.0 总体 PRD

> Version: v5.0  
> Date: 2026-04-12  
> Status: Draft  
> Owner: Product + Engineering

---

## 1. 背景

BugAgent 在 v1.0 ~ v4.0 阶段已完成以下核心能力：

1. 项目、迭代、缺陷、仓库、评论、附件、通知等基础缺陷域。
2. AI 配置、AI 目录、AGENT 分析、多 AGENT 协作、自动修复等智能处置能力。
3. 平台凭证、项目通知、个人中心、SMTP、用户安全等平台治理能力。
4. 云效接入、AI 配置数据库化、浏览器与后端联调、性能优化和上线前验收闭环。

当前系统已经具备“正式缺陷进入平台后被分析、协作和修复”的处理能力，但仍存在一个结构性缺口：

1. 线上问题、外部反馈、崩溃异常、群消息上报仍主要依赖人工二次录入。
2. 缺少“正式缺陷之前”的问题池和分诊层，弱信号、重复问题和高频问题无法先聚类再处理。
3. 缺少面向 App 业务的外部信号接入能力，尤其是 Bugly 与日志平台的上下文接入。
4. AI 当前主要服务于“已建缺陷”，尚未真正覆盖“生产问题信号 -> 分诊 -> 缺陷 -> 修复”的完整链路。
5. 当前平台治理已经较完整，继续优先堆平台设置类功能的边际收益较低。

v5.0 的目标是在不推翻现有缺陷主域的前提下，新增“问题信号接入 + 智能分诊 + 路由闭环 + 质量沉淀”能力，使 BugAgent 从“有 AI 的缺陷工具”升级为“面向 App 团队的质量闭环平台”。

---

## 2. 产品定位

### 2.1 产品定位

BugAgent v5.0 的定位为：

**面向 App 团队的缺陷信号接入、智能分诊、AI 处置与质量闭环平台。**

### 2.2 面向对象

1. 内部研发团队自用，优先解决真实生产问题接入、分诊与处置效率。
2. 未来面向外部客户交付，要求平台架构具备连接器通用化、接入多元化和双向同步预留能力。

### 2.3 产品主链路

v5.0 的新主链路为：

`外部信号 -> 统一接入 -> 问题池 -> 智能分诊 -> 转正式缺陷 -> AI 分析/协作/修复 -> 质量沉淀`

---

## 3. 产品目标与非目标

### 3.1 Goals

1. 建立统一的问题信号接入内核，支持多渠道连接器接入。
2. 首期交付 Bugly、钉钉、飞书、通用 Webhook 四类接入能力。
3. 新增问题池与问题簇模型，支持正式缺陷前的聚类、分诊和转化。
4. 新增智能分诊建议：项目归属、责任人、严重级别、优先级、疑似重复。
5. 复用现有缺陷、AI 分析、协作、自动修复能力，形成从外部信号到修复的完整闭环。
6. 为阿里云日志平台接入、版本/发布关联、回归预防与质量看板预留统一扩展模型。
7. 在首期坚持单向接入，确保内核稳定；同时在数据模型中预留未来双向回写能力。

### 3.2 Non-Goals

1. 不在 v5.0 首期自研 App 崩溃采集 SDK。
2. 不在 v5.0 首期做外部系统的强双向同步。
3. 不在首期做大而全的客服工单系统。
4. 不在首期做复杂自定义规则编排器。
5. 不在首期一次性接入所有渠道，按连接器分阶段落地。
6. 不把问题池伪装成缺陷列表的一种筛选模式。

---

## 4. 设计原则

1. **问题池与缺陷域分层**：外部信号先进入问题池，分诊后才进入正式缺陷域。
2. **连接器通用化**：Bugly、钉钉、飞书、日志平台等都只是连接器，归一化逻辑必须在平台内核中统一处理。
3. **单向接入优先**：v5.0 首期以稳定接入、分诊和转化为优先，双向回写只做模型预留和后续规划。
4. **弱自动化、强建议**：首期智能分诊以建议和人工确认并存，不做不可控的全自动处理。
5. **复用现有处置主域**：正式缺陷、AI 分析、协作、修复、通知能力继续复用现有系统。
6. **外部数据可追溯**：原始 payload、幂等键、接入记录、分诊记录必须完整留存。

## 5. Personas

1. **平台管理员**：维护连接器、全局接入模板、平台级路由模板、查看全局质量视图。
2. **项目管理员**：维护问题池、模块路由、项目级分诊策略和缺陷转化配置。
3. **分诊人员**：处理问题池，执行聚类、忽略、合并、转缺陷等动作。
4. **研发/测试成员**：接收路由结果、进入正式缺陷处理、查看问题来源上下文。
5. **管理者**：关注版本质量、高频问题、重复问题和处理时效。

## 6. 核心概念

### 6.1 连接器

负责从外部系统将问题信号拉入或接收入平台。

### 6.2 问题信号（Issue Signal）

外部系统进入平台后的标准化单条问题记录，是归一化后的最小接入单元。

### 6.3 问题簇（Issue Cluster）

多个相似信号聚合后的问题对象，是问题池和分诊中心的主要处理对象。

### 6.4 问题池

外部问题进入平台后的前置处理区，用于分诊、聚类、去重、忽略和转缺陷。

### 6.5 正式缺陷

延续现有 `Defect` 模型，是进入研发正式处理流程后的对象。

## 7. 整体架构

### 7.1 五层结构

1. **Connector Layer**
   - Bugly
   - 钉钉
   - 飞书
   - 阿里云日志平台
   - 通用 Webhook
   - 后续邮件、企业微信、更多第三方平台

2. **Ingestion Core**
   - 标准化信号模型
   - 幂等控制
   - 去重与聚类基础
   - 原始 payload 留存
   - 接入任务与失败重试

3. **Triage Engine**
   - 项目归属建议
   - 模块归属建议
   - 责任人建议
   - 严重级别和优先级建议
   - 疑似重复识别

4. **Execution Core**
   - 问题池转缺陷
   - AI 分析
   - 多 AGENT 协作
   - 自动修复
   - 通知与审计

5. **Quality Intelligence**
   - 问题趋势
   - 版本影响
   - 模块热度
   - 回归预防
   - 质量看板

### 7.2 与现有系统的关系

1. `Project / Iteration / Defect` 继续作为正式研发协作主域。
2. `AI Config / Collaboration / FixTask` 继续作为处置层核心能力。
3. `Notification / Credential / Platform Settings` 继续作为平台治理底座。
4. `Issue Signal / Issue Cluster / Triage` 作为 v5 新增前置域，为现有缺陷和 AI 域提供入口和上下文。

## 8. 功能结构

## 8.1 Phase 5A 首期必须交付

### FR-1 统一接入内核

1. 支持连接器配置与实例化管理。
2. 支持拉取型、推送型、手动导入型三类连接方式。
3. 支持标准化问题信号落库。
4. 支持原始 payload 留存。
5. 支持幂等去重、失败重试、死信记录。
6. 支持接入任务查看与手动重试。

验收标准：
1. 通用 Webhook 可将数据稳定写入问题信号表。
2. 同一外部事件重复发送不会生成重复信号。
3. 管理员可看到最近同步记录和失败原因。

### FR-2 首批连接器

首期必须支持：
1. Bugly
2. 钉钉
3. 飞书
4. 通用 Webhook

#### Bugly 接入要求
1. 支持拉取崩溃/异常问题。
2. 归一化字段至少包含：
   - 标题
   - 堆栈摘要
   - App 版本
   - 设备/系统信息
   - 首次发生时间
   - 最近发生时间
   - 次数
   - 影响用户数
   - 原始问题链接
3. 支持周期同步和手动同步。
4. 支持同源问题幂等更新。

#### 钉钉 / 飞书接入要求
1. 支持机器人/Webhook 接入。
2. 支持将结构化消息转成问题信号。
3. 支持保留原始消息链接或消息标识。
4. 首期不要求审批流或复杂 IM 回写。

#### 通用 Webhook 要求
1. 定义标准接入协议。
2. 支持签名校验。
3. 支持来源实例标识和幂等键。
4. 作为未来多渠道扩展的基础协议。

### FR-3 问题池

1. 新增问题池列表页和详情页。
2. 新增问题簇视图。
3. 支持按以下维度筛选：
   - 来源类型
   - 状态
   - 项目
   - 严重级别
   - 优先级
   - 责任人
   - 最近发生时间
4. 支持展示：
   - 来源摘要
   - 技术上下文
   - 影响次数
   - 影响用户数
   - 版本信息
   - 设备信息
   - 原始信号列表
   - 推荐路由结果
5. 支持状态：
   - `new`
   - `triaging`
   - `clustered`
   - `converted`
   - `ignored`
   - `closed`

### FR-4 智能分诊中心

首期支持以下建议能力：
1. 疑似重复建议。
2. 项目归属建议。
3. 责任人建议。
4. 严重级别建议。
5. 优先级建议。

首期支持以下分诊动作：
1. 忽略。
2. 标记重复。
3. 合并到已有问题簇。
4. 调整项目归属。
5. 调整责任人。
6. 转正式缺陷。
7. 指派分诊人。

设计约束：
1. 所有建议必须允许人工确认或覆盖。
2. 首期不做不可逆的全自动分诊。

### FR-5 转缺陷联动

1. 问题池支持一键转正式缺陷。
2. 转缺陷时自动带入：
   - 标题
   - 描述
   - 堆栈/日志摘要
   - 版本和设备信息
   - 来源渠道
   - 原始信号链接
   - 聚类统计信息
3. 转缺陷后在问题簇与缺陷之间建立双向关联。
4. 支持可选动作：
   - 自动指派
   - 自动进入待分析
   - 自动触发 AI 分析
   - 自动通知责任人

验收标准：
1. 问题池中的一条问题簇可成功转正式缺陷。
2. 缺陷详情页可回溯到来源问题簇和原始信号。
3. 现有 AI 分析主链路能在转缺陷后继续工作。

## 9. 核心业务流程

### 9.1 Bugly 信号流程

1. 平台管理员配置 Bugly 连接器。
2. 系统手动或定时拉取 Bugly 问题。
3. 数据归一化后写入 `IssueSignal`。
4. 系统按幂等键去重，按 fingerprint 聚类。
5. 问题进入问题池并等待分诊。
6. 分诊人确认项目、模块、责任人、优先级等。
7. 问题簇可被忽略、合并、标记重复或转缺陷。
8. 转缺陷后，进入现有 AI 分析/协作/修复主链路。

### 9.2 钉钉/飞书上报流程

1. 用户通过机器人或 Webhook 上报问题。
2. 平台解析结构化消息为标准 signal。
3. 问题进入问题池。
4. 可由 AI 做摘要和归类建议。
5. 分诊人决定是否转缺陷。

### 9.3 阿里云日志流程

1. 平台配置日志查询任务。
2. 按规则周期拉取日志片段。
3. 日志结果可单独形成 signal，也可补充已有问题簇上下文。
4. 日志上下文参与分诊和后续分析。

### 9.4 问题池 -> 正式缺陷流转规则

首期转缺陷条件满足任一即可：
1. 分诊人手动确认转缺陷。
2. 高严重级别且高频。
3. 命中关键模块且影响用户数超过阈值。
4. 历史上同类问题已多次进入正式缺陷流程。

## 11. 权限与治理

### 11.1 权限原则

1. 连接器配置权限仅向管理员开放。
2. 分诊权限开放给项目管理员和指定分诊角色。
3. 转缺陷与 AI 处置仍尽量复用现有项目权限。
4. 所有关键动作必须具备审计。

### 11.2 角色能力

#### 平台管理员
1. 管理连接器实例。
2. 查看全局接入任务与失败记录。
3. 管理全局路由模板。
4. 查看平台级质量看板。

#### 项目管理员
1. 管理本项目问题池。
2. 管理模块和路由规则。
3. 执行分诊。
4. 转正式缺陷。
5. 管理问题簇负责人。

#### 分诊人员
1. 查看问题池。
2. 忽略、合并、标记重复、调整归属、转缺陷。
3. 不能管理连接器实例。

#### 普通成员
1. 查看与自己有关的问题簇。
2. 接收责任归属结果。
3. 进入正式缺陷处理链路。

### 11.3 连接器治理

1. 连接器配置必须加密存储。
2. 连接器必须具备启停、健康状态、最近同步状态。
3. 失败记录必须可读且可重试。
4. Webhook 接入必须支持签名校验。
5. 外部数据原始 payload 允许脱敏处理。

### 11.4 审计范围

以下动作必须审计：
1. 新建、修改、删除连接器。
2. 手动触发同步。
3. 分诊动作。
4. 转缺陷动作。
5. 忽略或关闭问题簇。
6. 路由规则修改。
7. 后续双向回写动作。

---

## 12. 非功能要求

### 12.1 性能目标

1. 问题池列表：`P95 < 500ms`
2. 问题簇详情：`P95 < 800ms`
3. 转缺陷操作：`P95 < 1s`
4. 连接器同步任务：异步执行，页面展示任务状态，不阻塞 UI

### 12.2 数据规模基线

1. 单项目 10 万级 `issue_signals`
2. 单项目 1 万级 `issue_clusters`
3. 单连接器每日万级事件导入
4. 问题池列表需支持分页、筛选和聚类视图

### 12.3 可用性与容错

1. 外部连接器失败不能拖垮主业务系统。
2. 同步失败不能影响现有缺陷域能力。
3. 数据解析失败允许进入失败队列或死信记录。
4. 对外部限流、超时、鉴权失败需标准化错误语义。

### 12.4 安全要求

1. 外部密钥统一加密存储。
2. 回显时脱敏。
3. Webhook 签名校验。
4. 字段级隐私脱敏预留。
5. 操作遵循最小权限控制。

---

## 13. 风险与约束

### 13.1 风险

1. **连接器先多后乱**
   - 约束：首期只交付 Bugly、钉钉、飞书、Webhook。
2. **问题池与缺陷域混掉**
   - 约束：模型、状态、UI、API 必须分层。
3. **自动分诊准确率不够**
   - 约束：首期以建议为主，不做强自动化。
4. **外部数据质量差异大**
   - 约束：保留原始 payload，记录标准化失败原因。

### 13.2 外部依赖

1. Bugly 真实 API 权限与租户数据。
2. 钉钉/飞书机器人或应用权限。
3. 阿里云日志平台访问权限。
4. App 版本、构建号、渠道口径统一。

## 14. 后续规划

### 14.1 双向回写规划

虽然 v5.0 首期只做单向接入，但后续版本需支持：

1. 外部问题状态回写。
2. 评论回写。
3. 处理链接回写。
4. IM 卡片状态更新。
5. 渠道消息线程同步。

### 14.2 渠道多元化规划

后续可扩展渠道包括：
1. 企业微信
2. 邮件
3. 客服工单系统
4. 更多日志和告警系统
5. 第三方质量平台

扩展原则：
1. 基于统一连接器模型扩展。
2. 不改变问题池和缺陷域边界。
3. 优先保证标准化模型不膨胀。

---

## 15. 成功标准

v5.0 成功的标志是：

1. Bugly 等外部问题能稳定进入平台问题池。
2. 重复问题能聚类，不再大量重复建缺陷。
3. 分诊人员能在问题池中快速判断归属与处置方式。
4. 问题池能一键转为正式缺陷，并进入 AI 分析/协作/修复主链路。
5. 平台从“缺陷处理工具”升级为“线上问题接入与质量闭环平台”。
