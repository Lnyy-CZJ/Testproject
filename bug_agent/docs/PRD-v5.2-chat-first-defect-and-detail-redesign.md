# BugAgent v5.2 PRD

> Version: v5.2
> Date: 2026-04-13
> Status: Draft
> Owner: Product + Engineering

---

## 1. Background

当前版本已完成缺陷流转、问题池、信号接入、路由治理、回归预防和质量情报主干能力，但在真实使用中，缺陷域暴露出三个直接影响效率的问题：

1. 创建缺陷仍依赖复杂表单，字段多且描述质量不统一。
2. 手工创建缺陷绕开问题池，导致问题治理、趋势统计和回归预防样本不完整。
3. 缺陷详情页阅读体验差，Markdown 未正确渲染，系统和 AI 内容以纯文本堆叠，处理效率低。

`v5.2` 的目标是围绕这三个问题，完成一次面向高频主链路的重构：

1. 用对话式交互替代繁琐表单。
2. 让手动缺陷进入问题池统一治理体系。
3. 重构缺陷详情页为可阅读、可处理的工作台。

---

## 2. Goals And Non-Goals

### 2.1 Goals

1. 新建缺陷默认通过对话方式发起。
2. AI 自动生成结构化缺陷草稿并辅助统一字段质量。
3. 手工创建缺陷自动生成 `manual signal / issue cluster`，进入问题池。
4. 问题池、回归预防、质量情报覆盖手动来源。
5. 缺陷详情页按 Markdown 和结构化摘要重构，显著降低阅读成本。
6. 系统评论、AI 分析、自动修复结果不再以大段纯文本直接铺开。

### 2.2 Non-Goals

1. 不做“AI 对话结束后自动直接创建缺陷”。
2. 不删除高级模式表单入口。
3. 不做手动缺陷强自动聚类合并。
4. 不用问题池替代正式缺陷入口。
5. 不在本期引入复杂富文本编辑器体系。
6. 不在本期做跨项目相似手工缺陷的强治理。

---

## 3. Personas

1. 测试人员：希望快速用自然语言描述问题，不想被表单字段打断。
2. 研发人员：希望缺陷标题、描述、严重级别和类型更一致，方便理解与接手。
3. 项目管理员 / 分诊人员：希望手工问题也进入问题池和质量视图，避免治理盲区。
4. 缺陷处理者：希望详情页能快速看懂 AI 结论、修复进展和下一步动作。

---

## 4. Product Decisions

### 4.1 Chat-First Is Default

1. 缺陷列表页主入口为 `对话创建缺陷`。
2. 现有表单保留为 `高级模式`。
3. chat-first 是默认路径，高级模式是次级入口。

### 4.2 AI Generates Draft, User Confirms Creation

1. AI 只负责生成结构化草稿。
2. 用户必须在确认页完成最终确认。
3. 确认前不允许真正落库。

### 4.3 Manual Defects Join The Issue Pool Automatically

1. 手动创建缺陷后自动生成 `manual` 来源 signal。
2. 自动创建或关联 issue cluster。
3. 缺陷与 cluster 双向关联。
4. 手动来源区分为：
   - `manual_chat`
   - `manual_form`

### 4.4 Defect Detail Must Render Markdown Correctly

1. 缺陷描述、系统评论、AI 分析摘要、修复结果摘要统一按 GFM Markdown 渲染。
2. 原始 JSON 默认折叠。
3. 评论区改为时间线视图。

---

## 5. User Stories

1. 作为测试人员，我希望输入一句自然语言就能开始创建缺陷，而不是先填很多字段。
2. 作为测试人员，我希望 AI 自动帮我整理标题和描述，并建议严重级别、类型和标签。
3. 作为研发人员，我希望看到统一风格的缺陷描述，而不是每个人写法都不同。
4. 作为分诊人员，我希望手工创建的缺陷也进入问题池，便于统一统计和相似问题识别。
5. 作为缺陷处理者，我希望详情页优先展示摘要、AI 结论和修复进展，而不是被长文本和 JSON 淹没。

---

## 6. Functional Requirements

### FR-1 对话式创建缺陷

1. 缺陷列表页主按钮改为 `对话创建缺陷`。
2. 对话输入支持：
   - 文本输入
   - 附件 / 截图
   - 线上 / 测试环境提示
   - 可选模块 / 迭代上下文
3. AI 根据用户输入生成结构化草稿。
4. 草稿必须至少包含：
   - 标题
   - Markdown 描述
   - 严重级别
   - 优先级
   - 缺陷类型
   - 标签
   - 建议迭代
   - 缺失信息提醒
   - 路由建议
   - 置信度
5. 用户进入确认页后，可：
   - 一键确认创建
   - 修改字段后确认
   - 切换到高级模式
   - 取消

验收标准：
1. 新用户可在 1 分钟内完成基本缺陷创建。
2. AI 草稿具有统一格式，不是自由散文回复。
3. 用户确认前不会真正创建缺陷。

### FR-2 AI 失败降级创建

1. 当 AI 草稿生成失败时，系统必须自动降级到最小草稿。
2. 最小草稿默认字段：
   - `type = other`
   - `severity = normal`
   - `priority = P2`
3. 界面必须提示：
   - `AI 整理失败，请手动确认字段。`

验收标准：
1. AI 不可用时，创建入口仍可用。
2. 用户不会因为 AI 失败完全无法提单。

### FR-3 高级模式保留

1. 高级模式作为次级入口保留。
2. 高级模式与 chat-first 共用同一套最终创建接口。
3. 高级模式创建的缺陷也必须进入问题池统一模型。

验收标准：
1. 复杂场景仍可手动精细填单。
2. 不会因为来源不同而绕开统一治理。

### FR-4 手动缺陷自动进入问题池

1. 对话创建成功后，自动生成 `manual_chat` signal。
2. 高级模式创建成功后，自动生成 `manual_form` signal。
3. 系统自动创建或关联 issue cluster。
4. defect 与 cluster 建立双向关联。
5. 首期默认新建 `manual cluster`，不强自动合并。
6. 可展示“疑似相似问题”建议，但不强执行。

验收标准：
1. 所有手动创建缺陷都能在问题池中找到对应来源记录。
2. 问题池可跳转到正式缺陷详情。
3. 不会重复生成多个 signal。

### FR-5 手动来源纳入下游能力

1. 质量情报页统计手工来源占比。
2. 回归预防支持来源为手工创建的问题项。
3. 问题池来源筛选支持：
   - `manual_chat`
   - `manual_form`
4. 相似问题识别覆盖手工来源样本。

验收标准：
1. 手工缺陷不再是问题治理盲区。
2. 来源分析能够反映人工与外部接入的真实占比。

### FR-6 缺陷详情页布局重构

1. 页面采用：
   - 顶部摘要区
   - 中部双栏
   - 底部原始数据折叠区
2. 顶部摘要区展示：
   - 标题
   - 状态流转
   - 一句话摘要
   - 标签
   - 负责人 / 迭代 / 严重级别 / 优先级
   - 主操作按钮
3. 左栏展示：
   - 问题描述
   - AI 分析摘要
   - 评论与系统动态时间线
4. 右栏展示：
   - 属性卡
   - 修复任务卡
   - 多 AGENT 协作卡
   - 操作面板
5. 底部折叠区展示：
   - 原始分析 JSON
   - 原始修复结果 JSON
   - 调试信息

验收标准：
1. 处理者能快速读懂缺陷核心信息。
2. 长文本与原始机器数据不会直接淹没正文。

### FR-7 Markdown 渲染与时间线

1. 以下内容统一按 GFM Markdown 渲染：
   - 缺陷描述
   - AI 分析摘要正文
   - 修复任务摘要
   - 系统评论
   - 人工评论
2. 评论区改为时间线，区分：
   - 用户评论
   - 系统事件
   - AI 分析事件
   - 自动修复事件
3. 长系统消息默认折叠，并支持展开全文。

验收标准：
1. Markdown 内容正确渲染。
2. 代码块、列表、标题、表格和换行表现正常。
3. 时间线能帮助用户理解处理过程。

### FR-8 修复任务卡简化

1. 默认只突出最近关键任务。
2. 每条任务显示：
   - 状态
   - 分支
   - 模型
   - 耗时
   - Token
   - 成本
3. 风险摘要和验证建议默认折叠。

验收标准：
1. 右侧信息密度明显下降。
2. 修复进展更易读。

---

## 7. Interaction Requirements

1. chat-first 页面应明显弱化字段噪音，突出“先描述问题”。
2. 确认页应是可编辑的结构化卡片，不是只读预览。
3. 高级模式必须可随时切换，但不抢占主路径。
4. 缺陷详情页正文宽度、行高、卡片间距和分组留白必须明显优于当前版本。
5. 系统内容和人工内容需要明显区分样式。

---

## 8. Data Model Draft

### 8.1 New Draft Object

建议新增临时草稿模型或草稿响应结构，至少包含：

1. `title`
2. `description_markdown`
3. `severity`
4. `priority`
5. `type`
6. `tags`
7. `suggested_iteration_id`
8. `missing_information`
9. `routing_suggestion`
10. `confidence`
11. `source_mode` (`chat` / `form`)

### 8.2 Manual Signal

在现有 signal 模型内扩展来源：

1. `manual_chat`
2. `manual_form`

并要求：

1. `defect_id` 与 `signal_id` 建立唯一关联
2. cluster 默认状态使用 `converted` 或等效“已关联缺陷”状态

---

## 9. API Design (Draft)

### 9.1 Draft Generation

1. `POST /api/v1/projects/:id/defects/draft-from-chat`
2. `POST /api/v1/projects/:id/defects/draft-from-form`（可选复用）

### 9.2 Confirm Creation

1. `POST /api/v1/projects/:id/defects/confirm-create`
   - 输入：用户确认后的草稿
   - 输出：正式缺陷 + signal / cluster 关联信息

### 9.3 Detail Rendering Support

1. `GET /api/v1/defects/:id`
   - 补充结构化摘要字段
2. `GET /api/v1/defects/:id/timeline`
   - 评论与系统事件时间线化（可合并到已有接口）
3. `GET /api/v1/defects/:id/raw-data`
   - 原始调试信息（可选）

---

## 10. Success Metrics

1. 缺陷创建平均输入成本下降。
2. 缺陷描述结构化完整度提高。
3. 手工缺陷进入问题池覆盖率达到 100%。
4. 问题池来源统计中手工来源可见。
5. 缺陷详情页的关键内容阅读效率提升。

---

## 11. Risks

1. AI 草稿质量不稳定
   - 用确认页和最小草稿降级兜底。
2. 手动缺陷自动入问题池可能引入重复 signal
   - 通过唯一约束控制。
3. 详情页重构可能影响现有交互
   - 需要补浏览器回归和内容渲染测试。
4. 现有历史评论/报告内容格式不统一
   - 需要在渲染前做归一化处理。

---

## 12. PRD Conclusion

`v5.2` 的重点不是继续扩平台，而是收紧最核心的两条体验链路：

1. 把“创建缺陷”从表单负担变成对话式输入。
2. 把“看缺陷”从大段日志堆积页改成真正可读的处理工作台。
3. 用 manual signal 把手工问题重新纳入问题池统一治理。
