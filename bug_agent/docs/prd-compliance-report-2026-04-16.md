## 五、差异原因分析

| 差异项 | 根因 | 分类 |
|--------|------|------|
| 智能推荐分配对象 | 需要建立"用户→技能→历史处理"映射模型，当前无历史数据积累，无法训练推荐模型 | 技术实现限制 |
| Webhook签名校验 | 通用Webhook连接器已实现数据接收，但未增加HMAC签名验证中间件。属于安全加固而非功能缺失 | 优先级调整 |
| 自动推荐AGENT | 需要建立"缺陷类型→AGENT能力"映射规则，当前项目仓库绑定的AgentTypes已提供手动选择 | 优先级调整 |
| OAuth/SSO | 需要对接外部身份提供商（GitHub/GitLab/企业IdP），涉及回调URL配置和租户管理，属于基础设施扩展 | 技术实现限制 |
| P95监控与压测 | 需要引入APM工具（如Prometheus/Grafana）和压测框架，属于运维基础设施 | 优先级调整 |

## 六、改进措施

| # | 优先级 | 措施 | 预期效果 |
|---|--------|------|---------|
| 1 | P1 | 在AssignDefect handler中增加基于历史处理记录的推荐逻辑：统计每个用户处理过的缺陷类型和数量，按匹配度排序推荐前3名 | 分配效率提升 |

| 3 | P2 | 在分析触发时根据defect.Type自动推断AgentTypes：functional→backend, ui→frontend, performance→backend, security→backend, compatibility→client | AGENT选择自动化 |
| 4 | P2 | 引入OAuth2.0授权码流程：支持GitHub/GitLab作为外部IdP，用户可使用第三方账号登录 | 登录体验提升 |
| 5 | P2 | 引入Prometheus metrics中间件记录API P95延迟，补充压测脚本验证10万级信号规模 | 性能可观测 |
