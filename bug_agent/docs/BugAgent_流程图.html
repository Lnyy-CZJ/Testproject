流程 01：缺陷状态流转图

stateDiagram-v2 [*] --> 新建: 测试创建缺陷 新建 --> 待分配: 提交缺陷 待分配 --> 待分析: 分配给用户 待分析 --> 分析中: 系统自动触发 待分析 --> 驳回: 用户拒绝处理 分析中 --> 待修复: 分析完成 待修复 --> 修复中: 发起自动修复 待修复 --> 暂停: 用户暂停 修复中 --> 待验证: 修复完成 待验证 --> 待修复: 验证失败\n继续修复 待验证 --> 已修复: 验证通过 已修复 --> 已完成: 代码合并 暂停 --> 待修复: 恢复处理 驳回 --> [*] 已完成 --> [*] note right of 新建: 状态: 新建 note right of 待分配: 状态: 待分配 note right of 待分析: 状态: 待分析 note right of 分析中: 状态: 分析中 note right of 待修复: 状态: 待修复 note right of 修复中: 状态: 修复中 note right of 待验证: 状态: 待验证 note right of 已修复: 状态: 已修复 note right of 已完成: 状态: 已完成

📋 状态说明

  • 新建：缺陷刚创建，尚未提交
  • 待分配：缺陷已提交，等待分配处理人
  • 待分析：已分配，等待AGENT分析
  • 分析中：AGENT正在执行分析
  • 待修复：分析完成，等待修复决策
  • 修复中：正在执行自动修复
  • 待验证：修复完成，等待测试验证
  • 已修复：验证通过，等待代码合并
  • 已完成：代码已合并，流程结束

流程 02：缺陷创建与分配流程

flowchart TD A[测试人员登录系统] --> B[选择目标迭代] B --> C[点击新建缺陷] C --> D[填写缺陷信息] D --> E{信息完整?} E -->|否| D E -->|是| F[提交缺陷] F --> G[系统生成缺陷编号] G --> H[状态: 待分配] H --> I[系统智能推荐分配对象] I --> J[测试选择被分配用户] J --> K[确认分配] K --> L[状态: 待分析] L --> M[发送通知给被分配用户] M --> N[激活用户AGENT身份] N --> O[自动触发AGENT分析] style A fill:#e1f5fe style O fill:#c8e6c9 style H fill:#fff9c4 style L fill:#fff9c4

📋 流程要点

  • 缺陷创建时自动关联当前迭代绑定的代码仓库
  • 系统基于历史数据和技能匹配智能推荐分配对象
  • 分配后自动激活被分配用户的AGENT身份
  • 缺陷编号格式：BUG-{项目缩写}-{年月}-{序号}

流程 03：AGENT自动分析流程

flowchart TD A[缺陷被分配] --> B[获取用户AGENT身份] B --> C{判断AGENT类型} C -->|UI问题| D[激活UI_AGENT] C -->|功能缺陷| E{判断系统模块} C -->|性能问题| F[前端/后端协作] E -->|前端模块| G[激活前端AGENT] E -->|后端模块| H[激活后端AGENT] D --> I[读取缺陷上下文] G --> I H --> I F --> I I --> J[获取关联代码仓库] J --> K[搜索相关代码文件] K --> L[执行静态代码扫描] L --> M[分析日志文件] M --> N[代码逻辑推演] N --> O[生成分析报告] O --> P[以用户身份发布评论] P --> Q[状态: 待修复] style A fill:#e1f5fe style Q fill:#c8e6c9 style O fill:#fff9c4

📋 分析内容

  • 根本原因：定位问题根源
  • 影响范围：评估问题影响面
  • 修复建议：提供具体修复步骤
  • 代码示例：给出修复代码片段
  • 风险等级：评估修复风险

流程 04：协作讨论流程

flowchart TD A[AGENT发布分析报告] --> B{测试评估方案} B -->|满意| C[确认方案] B -->|需调整| D[回复AGENT调整] B -->|不满意| E[拒绝方案] D --> F[AGENT重新分析] F --> A E --> G[AGENT生成替代方案] G --> A C --> H{是否需要协作?} H -->|是| I[@其他成员] H -->|否| J[发起自动修复] I --> K[激活成员AGENT] K --> L[多AGENT协作讨论] L --> M[生成综合建议] M --> N{达成共识?} N -->|否| L N -->|是| J style A fill:#e1f5fe style J fill:#c8e6c9 style L fill:#fff9c4

📋 协作场景

  • 方案调整：测试对分析结果不满意，请求补充分析
  • 方案替代：方案不可行，AGENT重新生成方案
  • 跨端协作：@前端+后端AGENT，对齐接口方案
  • 需求确认：@产品AGENT，确认需求理解是否正确

流程 05：自动修复执行流程

flowchart TD A[测试发起自动修复] --> B[选择目标修复分支] B --> C[确认发起] C --> D[创建修复任务记录] D --> E[状态: 修复中] E --> F[任务初始化] F --> G[获取缺陷上下文] G --> H[获取分析报告] H --> I[生成修复计划] I --> J[克隆代码仓库] J --> K[切换到目标分支] K --> L[创建修复分支] L --> M[定位目标文件] M --> N[执行代码修改] N --> O{需要构建验证?} O -->|是| P[执行本地构建] O -->|否| Q[提交代码变更] P --> Q Q --> R[推送到远程仓库] R --> S[创建Pull Request] S --> T[记录PR信息] T --> U[更新任务状态: 完成] U --> V[在评论区发布修复报告] V --> W[通知测试人员] W --> X[状态: 待验证] style A fill:#e1f5fe style X fill:#c8e6c9 style D fill:#fff9c4 style S fill:#fff9c4

📋 修复任务信息

  • 任务编号：FT-{年月}-{序号}
  • 修复分支：fix/{缺陷编号}-{任务序号}
  • 目标分支：迭代绑定的测试分支
  • PR链接：代码审查入口
  • 变更文件：列出所有修改的文件

流程 06：验证与合并流程

flowchart TD A[收到修复完成通知] --> B[拉取测试分支] B --> C[执行测试验证] C --> D{验证结果} D -->|失败| E[描述问题] E --> F[继续与AGENT对话] F --> G{需要新修复?} G -->|是| H[发起新修复任务] H --> I[创建新修复分支] I --> J[执行新修复] J --> A G -->|否| F D -->|通过| K[流转状态: 已修复] K --> L[发送通知给被分配用户] L --> M[被分配用户审核代码] M --> N{审核结果} N -->|需要修改| O[反馈问题] O --> F N -->|通过| P[选择目标合并分支] P --> Q[执行合并操作] Q --> R[关闭关联PR] R --> S[流转状态: 已完成] S --> T[发送完成通知] T --> U[更新迭代统计] style A fill:#e1f5fe style S fill:#c8e6c9 style K fill:#fff9c4

📋 多轮修复支持

  • 第一次修复：fix/BUG-xxx-001
  • 第二次修复：fix/BUG-xxx-002（基于第一次）
  • 第三次修复：fix/BUG-xxx-003（如需要）
  • 每次修复都创建独立的修复分支和PR
  • 验证通过后可选择合并到dev/release/main分支

📋 核心实体说明

  • 组织：最上层管理单元，包含多个项目
  • 项目：具体软件开发项目
  • 迭代：时间盒管理单元，可绑定多个仓库
  • 缺陷：核心业务实体，记录问题
  • 修复任务：AGENT执行的自动修复实例
  • AGENT身份：内置AI角色，与用户多对多绑定

📋 主流程阶段

  • 缺陷创建：测试创建并提交缺陷（蓝色阶段）
  • 缺陷分配：分配给具体开发人员（绿色阶段）
  • AGENT分析：自动分析问题成因（橙色阶段）
  • 协作讨论：多AGENT协作确定方案（粉色阶段）
  • 自动修复：AGENT自动修改代码（紫色阶段）
  • 验证合并：测试验证并合并代码（青色阶段）
