# Web Design System Design

> Date: 2026-04-13
> Status: Draft
> Scope: Bug Agent Web 端整体设计系统与视觉重构约束

---

## 1. Context

当前 Web 端已经具备完整的业务主链路，包括：

- 平台级管理
- 项目级工作区
- 缺陷流转
- Chat-first 缺陷创建
- 问题池
- 路由治理
- 回归预防
- 质量情报
- AI 分析与自动修复

但在 UI 层面仍然存在四类系统性问题：

1. **产品气质不稳定**
   - 登录页、项目页、列表页、详情页各自成立，但缺少统一设计母体。
   - 目前界面更像“带渐变的标准后台”，还没有形成足够独特的产品识别。

2. **页面家族边界不清**
   - 工作台页、列表页、详情页、配置页之间的骨架差异不明确。
   - 很多页面都采用“标题 + 白卡片 + 数据内容”的单一结构，导致体验趋同。

3. **AI 能力表达尚未系统化**
   - AI 区块已经开始进入主链路，但缺少统一的布局、视觉、折叠层级和动作规范。
   - 一些页面里 AI 内容仍然更像“附加信息”，没有成为明确工作流角色。

4. **创新性与效率尚未达成统一**
   - 用户希望产品有明显创新感，而不是传统后台。
   - 但如果不加约束地强化表现力，会直接伤害缺陷列表、问题池、配置页等高密度页面的使用效率。

因此，需要一份项目级 `DESIGN.md` 作为 Web 端的统一设计系统文档，明确全站的设计方向、页面模式、组件规则和落地约束。

---

## 2. Goals

这次设计系统落地要解决四件事：

1. 统一 Bug Agent 全站视觉语言
2. 建立“创新型缺陷协作产品”而不是“传统后台”的产品气质
3. 保留高密度业务页面的效率与可读性
4. 给后续页面重构提供明确设计边界，避免再次各页各做各的

---

## 3. Fixed Constraints

用户已确认以下约束：

1. 设计系统约束范围覆盖整个 Web 端
2. 文档形式采用：
   - 项目级 `DESIGN.md`
   - 过程留档 spec
3. 保留当前紫青品牌色体系
4. 全站保持浅色主界面
5. 不强制以 `Ant Design` 为默认设计母体
6. 鼓励更灵活、贴合需求的组件实现
7. 整体气质偏创新型产品，而不是传统企业后台
8. 创新表达要覆盖全站，但必须受统一结构约束

---

## 4. Evaluated Design Directions

在参考 `awesome-design-md` 仓库后，最终没有采用“纯粹复制某个 demo”的思路，而是评估了三种方向：

### 4.1 Cohere 视觉 + Linear 结构

优点：

- 最贴近当前产品基因
- 适合企业 AI 平台气质
- 易于统一全站

不足：

- 相比用户预期，创新性仍偏保守

### 4.2 Linear 结构 + Cohere 点缀

优点：

- 非常稳
- 列表和详情效率高

不足：

- 更像优秀后台，而不是有独特辨识度的新产品

### 4.3 创新实验型产品界面

优点：

- 品牌辨识度最高
- 更适合承接 AI 工作台、Chat-first、阅读优先详情等体验

不足：

- 如果没有统一约束，容易牺牲效率型页面

结论：

最终采用：

> `结构化实验型`

即：

- 全站走创新型产品方向
- 但用统一骨架和组件分层来控制风险
- 让工作台、创建页、详情页拥有更强表达力
- 让列表页和配置页保持工具效率

## 5. Core Decision

### 5.1 设计母体

结论：**采用“结构化实验型”作为 Bug Agent Web 端的设计母体。**

解释：

1. 这符合用户对“有创新性的产品”的预期。
2. 它允许全站都具备明显产品感，而不是只在局部页面表现。
3. 它比“激进沉浸型”更适合承接高密度业务页面。

### 5.2 参考来源

结论：**视觉气质参考 Cohere，结构秩序参考 Linear，但不做直接复刻。**

解释：

1. `Cohere` 更适合作为企业 AI 平台视觉母体。
2. `Linear` 更适合作为列表、详情和工作流结构参考。
3. Bug Agent 需要在两者之间建立自己的“缺陷协作工作台”语言。

### 5.3 品牌色

结论：**保留当前紫青品牌色，但从“到处使用”改为“分层使用”。**

解释：

1. 当前品牌色已经形成初步记忆点。
2. 问题不在于颜色本身，而在于缺少统一场景定义。
3. 品牌色应服务身份与关键节点，而不是替代所有状态和层级。

### 5.4 基底色

结论：**坚持浅色主界面，不采用全站暗色未来感路线。**

解释：

1. 业务页面信息密度高，浅色更适合长时间使用。
2. 当前产品的企业协作属性也更适合浅色控制台。
3. AI 感应通过局部能量层和模块语法体现，而不是通过整站暗黑化体现。

### 5.5 组件策略

结论：**不把 `Ant Design` 设为设计母体，而是允许按业务需求实现更灵活的组件。**

解释：

1. 用户明确不希望被默认组件库气质绑死。
2. Bug Agent 需要更强的产品辨识度。
3. 组件可以复用现有能力，但视觉与结构必须受项目级设计系统统一约束。

## 6. Global Design Principles

### 6.1 页面必须分层

全站统一使用三层页面模型：

- `Narrative Layer`
- `Action Layer`
- `Data Layer`

理由：

1. 当前很多页面的问题并不是颜色和留白，而是信息层级失真。
2. 只有先把叙事、动作、数据拆开，后续的创新表达才不会干扰效率。

### 6.2 创新感来自结构，而不是装饰

设计创新的来源应是：

- 更明确的舞台式布局
- 更稳定的页面家族
- 更成熟的 AI 模块语法
- 更有辨识度的品牌能量层

而不是：

- 大面积渐变
- 过重阴影
- 无意义动效
- 花哨卡片堆叠

### 6.3 AI 是一级角色

AI 内容在 Bug Agent 中不是注释，也不是推荐小组件，而是流程参与者。

因此：

1. AI 摘要必须优先于原始长文本
2. AI 建议必须能直接连接后续动作
3. AI 深层信息必须折叠，不得干扰主阅读流

### 6.4 效率型页面优先可扫描

对于列表页、配置页、清单页：

1. 一次性扫描效率优先
2. 操作路径优先
3. 批量处理优先

创新性只能建立在效率不下降的前提上。

## 7. Page Family Decisions

### 7.1 认证页定义为品牌叙事页

认证页不是简单表单，而是品牌世界观入口。

因此：

- 保留双区结构
- 强表达集中在品牌区
- 操作区保持安静、清晰

### 7.2 工作台定义为行动优先页

工作台页必须回答：

- 当前最重要的风险是什么
- 当前可以直接做什么
- 最近发生了什么

不再允许退化成统计卡片堆叠页。

### 7.3 列表页定义为高效率数据舞台

列表页不是默认表格容器，而是：

> 标题 + 操作轨道 + 数据舞台 + 状态反馈

其核心职责是缩短用户“找、筛、判断、批量处理”的路径。

### 7.4 详情页定义为阅读优先工作台

缺陷详情页必须明确分成：

- 顶部摘要带
- 主阅读区
- 决策侧轨

理由：

1. 当前详情页承载 AI、流程、评论、修复和技术原始信息
2. 如果不分层，用户无法快速回答“问题是什么、AI 怎么看、我下一步做什么”

### 7.5 配置页定义为受控实验区

配置页不是主品牌展示面，因此：

- 允许保留产品气质
- 但必须比工作台和详情页更收敛
- 重点放在分组、说明和反馈清晰度

## 8. Component Decisions

### 8.1 按钮必须分级

不再允许多个主按钮同时争夺视觉重心。

### 8.2 卡片必须分层

不再允许所有卡片使用同一套视觉强度。

### 8.3 状态标签必须统一语法

不再允许状态、优先级、辅助信息全部使用同等强度标签。

### 8.4 AI 模块必须标准化

AI 模块固定采用：

- Header
- Summary
- Evidence
- Action
- Deep Detail

这是后续所有 AI 场景的统一母版。

### 8.5 空态与加载态必须区分业务含义

尤其要区分：

- 普通加载
- AI 处理中
- 背景同步
- 首次引导空态
- 筛选无结果

---

## 9. Token Strategy

### 9.1 色彩

采用：

- 浅色中性基底
- 紫青品牌层
- 独立功能状态色

其中品牌色只负责：

- 关键操作
- 品牌入口
- 当前态
- AI 场景强调
- 重点摘要

### 9.2 形态

采用有限的圆角、阴影、间距阶梯，防止组件各自漂移。

### 9.3 动效

只保留低频、高价值动效，避免全站持续噪音。

---

## 10. Non-Goals

这次设计系统不做以下方向：

1. 全站暗色化
2. 完全抛弃当前品牌色
3. 纯粹复刻任一外部产品
4. 把所有页面做成营销感 AI 界面
5. 用设计系统替代具体业务交互设计

## 12. Rollout Recommendation

建议后续按以下顺序把设计系统落到页面：

1. 认证页与品牌入口
2. 平台/项目工作台
3. Chat-first 创建缺陷
4. 缺陷列表
5. 缺陷详情
6. 问题池 / 质量情报 / 路由治理
7. 配置类页面统一收口

理由：

1. 先建立产品气质
2. 再打通主链路体验
3. 最后统一效率型页面的一致性
