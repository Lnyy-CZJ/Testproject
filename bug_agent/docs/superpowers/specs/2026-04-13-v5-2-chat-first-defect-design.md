# V5.2 Chat-First Defect Creation And Detail Redesign Design

> Date: 2026-04-13
> Status: Draft
> Scope: v5.2

---

## 1. Context

当前版本已经具备完整的缺陷流转、问题池、AI 分析和自动修复链路，但在真实使用过程中暴露出三个高频体验问题：

1. **缺陷创建成本过高**
   - 当前创建缺陷仍然以表单为主。
   - 字段较多，严重级别、类型、标签、描述质量高度依赖个人习惯。
   - 同一个问题由不同人创建时，标题和描述风格差异很大，后续问题池聚类、回归预防和质量统计都会受影响。

2. **手动创建缺陷绕开问题池**
   - 外部接入问题已经进入 `IssueSignal / IssueCluster` 体系。
   - 手工创建缺陷仍然直接进入缺陷域，没有同步进入问题池。
   - 这导致来源统计、相似问题识别、回归预防和质量情报只覆盖部分样本。

3. **缺陷详情页已退化成“长文本与日志堆叠页”**
   - 页面结构层级不清，摘要、分析、修复、评论和原始 JSON 混在一起。
   - Markdown 内容没有按 GFM 正确渲染，系统和 AI 内容以大段纯文本展示。
   - 结果是阅读成本高，处理者无法快速回答“现在出了什么问题、AI 结论是什么、下一步该做什么”。

因此，`v5.2` 的核心目标不是再扩平台边界，而是把“问题录入”和“问题阅读”两段主链路体验做顺。

---

## 2. Product Direction

`v5.2` 聚焦三件事：

1. **对话式创建缺陷**
   - 用自然语言代替繁琐表单。
   - 由 AI 把原始表达整理成统一质量的结构化缺陷草稿。
   - 正式落库前保留人工确认，避免 AI 直接污染缺陷库。

2. **手动缺陷统一进入问题池**
   - 手工创建的缺陷同步生成 `manual` 来源信号，并归入问题池。
   - 让问题池、回归预防、质量情报、相似问题识别继续使用统一模型。

3. **缺陷详情页重构**
   - 把当前“文本密集、渲染错误、结构混乱”的详情页改成可阅读、可操作、可追踪的工作台。
   - 结构化摘要优先显示，原始 JSON 与调试信息默认折叠。

---

## 3. Core Decisions

### 3.1 缺陷创建默认改为 Chat-First

结论：**新建缺陷默认入口改为对话创建；原表单降级为“高级模式”。**

原因：

1. 这是直接解决“创建太繁琐”的唯一有效方式。
2. 只在现有表单上增加 AI 助手，无法从根上降低录入成本。
3. Chat-first 可以把描述、标签、类型、严重级别的质量统一到同一条 AI 草稿链路上。

### 3.2 AI 只生成草稿，不直接创建缺陷

结论：**AI 负责生成结构化草稿，用户确认后才真正创建缺陷。**

原因：

1. AI 误判不可避免，直接落库会污染缺陷和问题池。
2. 用户确认页可以同时承接“修改”和“补充缺失信息”。
3. 该机制也为后续 `manual signal` 建模提供稳定输入。

### 3.3 手动缺陷进入问题池，但不改变“先建缺陷”的用户心智

结论：**用户仍然是在“创建缺陷”，系统在落库后自动补齐 `manual signal / issue cluster`。**

原因：

1. 当前用户操作目标是“我要建缺陷”，不是“我要先上报一个问题”。
2. 直接把手动入口改成问题池入口，会对现有心智造成不必要冲击。
3. 通过自动生成 `manual signal`，可以在不改变主流程的前提下让问题池继续统一建模。

### 3.4 缺陷详情页必须按内容类型重构，而不是只调样式

结论：**这次改造是布局 + 内容分层 + Markdown 渲染三件事一起做。**

原因：

1. 当前问题不只是留白少，而是正文、系统日志、原始 JSON 和 AI 摘要混在同一级。
2. 只调 CSS 不会解决“读不懂、看不到重点、Markdown 没渲染”的问题。
3. 必须把“摘要层、处理层、原始数据层”彻底分开。

## 4. Chat-First Defect Creation Flow

### 4.1 Entry

项目内“新建缺陷”默认进入：

- `对话创建缺陷`

次级入口保留：

- `高级模式`

建议入口位置：

1. 缺陷列表页主按钮
2. 问题池页的“补录缺陷”入口
3. 后续可在工作台添加快捷入口，但不属于本期必须项

### 4.2 Conversation Step

用户输入一段自然语言即可开始，例如：

- “云效仓库导入弹窗里搜索应该本地过滤，现在每次都打远端接口。”
- “iOS 18 下登录页键盘弹起后按钮被遮挡，影响提交。”
- “支付成功后偶现重复回调，订单状态错乱。”

本期支持的补充信息：

1. 附件 / 截图
2. 是否来自线上
3. 建议关联的模块或仓库
4. 建议迭代

### 4.3 AI Draft Generation

AI 必须输出结构化缺陷草稿，而不是纯自然语言回复。

草稿至少包含：

1. `title`
2. `description_markdown`
3. `severity`
4. `priority`
5. `type`
6. `tags`
7. `suggested_iteration_id`
8. `missing_information`
9. `routing_suggestion`
10. `confidence`

目标：

1. 标题更统一
2. 描述更专业且可读
3. 严重级别、类型、标签更一致
4. 给出建议归属信息，但不强制落库

### 4.4 Confirmation Step

AI 生成草稿后，进入确认页。

确认页分三块：

1. `AI 整理后的缺陷内容`
   - 标题
   - 描述
   - 严重级别
   - 优先级
   - 缺陷类型
   - 标签
2. `系统建议`
   - 建议迭代
   - 建议模块
   - 建议负责人
   - 建议依据 / 置信度
3. `用户操作`
   - 一键确认创建
   - 修改后确认
   - 切换到高级模式
   - 取消

要求：

1. 用户必须在确认页完成最终确认。
2. 不允许 AI 在确认前直接创建缺陷。
3. 确认页字段应可编辑，而不是只读卡片。

### 4.5 Fallback Strategy

当 AI 草稿生成失败时，不允许阻塞提单。

降级规则：

1. 用用户原始输入生成最小草稿。
2. 默认字段：
   - `type = other`
   - `severity = normal`
   - `priority = P2`
3. 明确提示：
   - `AI 整理失败，请手动确认字段。`

### 4.6 Advanced Mode

高级模式保留，但定位改变：

1. 只服务复杂场景和精细控制字段场景。
2. 不再作为默认入口。
3. 与 chat-first 共享同一套创建接口和落库逻辑。

## 5. Manual Defects Enter The Issue Pool

### 5.1 Unified Model

手动创建缺陷时，系统自动执行：

1. 创建正式缺陷
2. 创建 `manual` 来源的 `IssueSignal`
3. 创建或关联一个 `IssueCluster`
4. 建立 `defect <-> cluster` 双向关联

建议来源细分：

1. `manual_chat`
2. `manual_form`

### 5.2 Persistence Order

建议固定为：

1. 用户确认缺陷草稿
2. 创建正式缺陷
3. 创建 `issue_signal`
4. 创建或关联 `issue_cluster`
5. 建立 `linked_defect_id`
6. 写入分诊/审计记录

原因：

1. 用户当前明确目标仍是“建缺陷”。
2. 先建缺陷更符合现有缺陷域流程。
3. 问题池模型作为后补统一治理层更自然。

### 5.3 Cluster Strategy

首期采用保守策略：

1. 默认为手动缺陷新建一个 `manual cluster`
2. 系统可以提示“疑似相似问题”
3. 首期不强自动合并到已有 cluster

原因：

1. 手工描述主观性更高
2. 一开始就强自动聚类误伤概率高

### 5.4 Status Strategy

由于手动缺陷创建时已经存在正式缺陷，manual cluster 不应停留在“待转缺陷”。

首期建议：

1. 使用现有 `converted` 状态
2. 在 UI 上展示为：
   - `已关联缺陷`
   - `手动创建`

### 5.5 Downstream Effects

引入 `manual signal` 后，以下能力均应覆盖手动缺陷：

1. 问题池来源统计
2. 相似问题识别
3. 回归预防来源统计
4. 质量情报来源占比
5. 手工问题与外部信号的统一趋势分析

### 5.6 Risk Controls

1. 以 `defect_id -> signal_id` 唯一关系避免重复生成 signal
2. 首期不做强自动聚类，只做建议
3. 缺陷删除/归档时需要同步考虑 signal / cluster 关系，作为实现计划项明确处理

## 6. Defect Detail Page Redesign

### 6.1 Redesign Goal

缺陷详情页应从“文本与日志堆叠页”变成：

> 面向处理者的缺陷工作台

页面必须优先回答：

1. 这是什么问题
2. 当前处于哪个状态
3. AI 的主要判断是什么
4. 修复进展如何
5. 下一步该做什么

### 6.2 New Layout

建议采用：

`顶部摘要 + 中部双栏 + 底部折叠原始数据`

#### 顶部摘要区

展示：

1. 标题
2. 状态流转
3. 一句话摘要
4. 关键标签
5. 负责人 / 迭代 / 严重级别 / 优先级
6. 主操作按钮

#### 中部左栏

作为主阅读区，依次放：

1. `问题描述`
2. `AI 分析摘要`
3. `评论与系统动态时间线`

#### 中部右栏

作为处理辅助区，放：

1. 属性卡
2. 修复任务卡
3. 多 AGENT 协作卡
4. 操作面板

#### 底部折叠区

统一承接原始调试信息：

1. 原始分析 JSON
2. 原始修复结果 JSON
3. 系统原始事件
4. 其他调试数据

### 6.3 Markdown Rendering Rules

以下内容统一按 **GFM Markdown** 渲染：

1. 缺陷描述
2. AI 分析摘要正文
3. 修复任务说明
4. 系统评论正文
5. 人工评论正文（本期推荐一起支持）

至少支持：

1. 标题
2. 段落
3. 列表
4. 引用
5. 粗体 / 斜体
6. 行内代码
7. 代码块
8. 表格
9. 链接
10. 正确换行

### 6.4 Raw Data Handling

当前最影响阅读的问题之一，是将结构化对象直接以纯文本或 JSON 铺到正文。

`v5.2` 的要求：

1. 正文只展示整理后的可读摘要
2. 原始 JSON 默认折叠
3. 代码块使用专门代码展示组件
4. 允许“查看原始数据”而不是强迫用户先看到原始数据

### 6.5 Timeline Design

评论区改为时间线视图，并区分内容类型：

1. 用户评论
2. 系统事件
3. AI 分析事件
4. 自动修复事件

要求：

1. 长系统消息默认折叠
2. 优先显示摘要
3. 支持展开全文
4. 系统和 AI 消息按 Markdown 渲染

### 6.6 Fix Task Card Simplification

右侧修复任务卡只展示最关键任务信息：

1. 状态
2. 分支
3. 模型
4. 耗时
5. Token
6. 成本

风险摘要与验证建议默认折叠，按需展开。

## 7. Delivery Order

建议按以下顺序实施：

1. `P1` 对话式创建缺陷
2. `P2` 手动缺陷进入问题池
3. `P3` 缺陷详情页重构

原因：

1. 先改变创建入口，直接解决高频痛点。
2. 再统一手动缺陷和问题池模型，避免继续产生双轨数据。
3. 最后重构详情页，确保新创建的数据能在新页面结构中被正确消费。

建议 Sprint 拆分：

1. `Sprint 5.2-1`
   - chat-first 创建
   - AI 草稿生成
   - 确认页
   - 高级模式降级入口
2. `Sprint 5.2-2`
   - `manual signal / cluster`
   - 问题池打通
   - 质量情报来源打通
3. `Sprint 5.2-3`
   - 缺陷详情布局重构
   - Markdown 渲染
   - 时间线与原始数据折叠

---

## 8. Testing Focus

`v5.2` 必须覆盖以下验证：

1. 对话输入 -> AI 草稿 -> 确认页 -> 正式创建缺陷
2. AI 失败 -> 最小草稿降级 -> 用户确认创建
3. 高级模式创建 -> 自动生成 `manual_form` signal
4. chat-first 创建 -> 自动生成 `manual_chat` signal
5. 问题池可见手动来源问题项，并能跳转正式缺陷
6. 质量情报可统计手动来源
7. 缺陷详情 Markdown 渲染正确
8. 原始 JSON 默认折叠
9. 长系统/AI 消息默认折叠但可展开
10. 关键操作按钮和状态流转回归无破坏

---

## 9. Out Of Scope

本期明确不做：

1. AI 自动创建缺陷而不经确认
2. 手动缺陷自动强聚类合并
3. 用问题池完全替代“创建缺陷”入口
4. 评论编辑器的复杂富文本体系
5. 跨项目手动缺陷聚类治理

---

## 10. Design Conclusion

`v5.2` 的核心不是再加一个 AI 功能点，而是把两个最基础的交互重做正确：

1. 用对话把缺陷创建变简单，并把描述质量标准化
2. 用统一问题池模型把手工问题与外部问题放回同一治理体系
3. 用真正可读的缺陷详情页，把 AI、修复和评论从噪音里解放出来

这三件事做完后，`v5.x` 主链路会从“功能多但偏重”明显迈向“录入顺、阅读顺、治理顺”。
