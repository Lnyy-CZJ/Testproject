---

## 1. 背景与现状

截至 `v5.2`，BugAgent 已完成项目级缺陷治理主链路：

1. Chat-first 缺陷创建与详情重构已上线。
2. 问题池、路由治理、回归预防、质量情报均可运行。
3. 平台治理（用户/凭证/通知/AI 目录）具备可用基础。

但当前进入“从可用到可持续”的阶段，主要瓶颈从“功能缺失”转为“稳定性、一致性、安全性、智能化深度”：

1. 统一设计系统已落地，但跨页面仍有样式与交互回归（尤其筛选/搜索栏）。
2. 分配与协作存在“可操作但不够智能”的效率上限（推荐分配、AGENT 推荐不足）。
3. 外部接入能力可用，但安全与企业级能力（Webhook 签名、SSO）仍需补齐。
4. 缺少系统级可观测与规模压测闭环，难以支撑更大接入规模。

`v5.3` 的核心目标是：**补齐生产级短板，提升平台稳定性和智能效率，建立可持续演进底座。**

---

## 2. v5.3 目标与非目标

### 2.1 目标（Goals）

1. 消除核心页面 UI 组件不一致和回归问题，建立“统一组件、统一行为”基线。
2. 落地“智能推荐分配 + AGENT 自动推荐”第一版，提升分诊和指派效率。
3. 补齐 Webhook 签名校验，提升接入安全基线。
4. 建立基础可观测能力（关键接口延迟/错误率）与压测基线。
5. 输出可执行迭代计划，确保每个迭代可验收、可度量。

### 2.2 非目标（Non-Goals）

1. 不在 v5.3 重做问题池/路由治理整体架构。
2. 不在 v5.3 引入复杂规则引擎 2.0（仅做现有规则增强）。
3. 不在 v5.3 一次性覆盖所有外部连接器渠道扩展。
4. 不在 v5.3 实现完整企业 IAM 套件（仅做 SSO 第一版）。

## 3. 核心问题定义（按优先级）

### P0（必须做）

1. **搜索/筛选栏样式与行为回归反复出现**
   - 影响：页面一致性下降，用户信任受损，回归成本高。
2. **Webhook 接入缺少签名校验**
   - 影响：安全风险，生产环境不可放大接入。

### P1（应该做）

1. **缺陷分配缺少数据驱动推荐**
   - 影响：人工判断成本高，响应速度不稳定。
2. **AGENT 推荐仍依赖手选**
   - 影响：协作效率和命中率受限。

### P2（可以并行推进）

1. **缺少性能可观测和规模压测基线**
   - 影响：难以预测扩容风险。
2. **OAuth/SSO 未接入**
   - 影响：企业落地门槛较高。

## 4. 功能需求（FR）

### FR-1 统一筛选/搜索组件治理（P0）

1. 所有列表页搜索输入统一使用 `PageFilterBar` + 标准输入模式。
2. 禁止页面内私有 `Input.Search` 样式分叉（统一为可控样式方案）。
3. 建立 UI 回归检查清单（至少覆盖：缺陷管理、问题池、回归预防、用户管理、审计日志、项目列表）。
4. 增加页面级快照基准（关键筛选栏区域）。

验收标准：
1. 核心页面搜索/筛选栏视觉结构一致，无空白按钮、双边框、错位。
2. 新增页面必须复用公共组件，不允许新造同类筛选栏。

### FR-2 Webhook 签名校验（P0）

1. 连接器支持配置签名密钥（Secret）。
2. 服务端校验 `X-Hub-Signature-256`（HMAC-SHA256）。
3. 签名失败请求拒绝并记录审计事件。
4. 提供调试模式（仅测试环境允许关闭强校验）。

验收标准：
1. 正常签名请求通过，非法签名请求 401/403。
2. 审计日志可追溯签名失败来源与原因。

### FR-3 智能推荐分配（P1）

1. 基于历史处理记录建立“用户处理能力画像”。
2. 指派时返回 Top-N 推荐对象与推荐理由（类型匹配、历史命中、负载）。
3. UI 提供一键采用推荐。
4. 记录推荐是否采纳，为后续优化提供反馈数据。

验收标准：
1. 可用推荐列表稳定返回。
2. 分配平均耗时下降（目标 20%+）。

### FR-4 AGENT 自动推荐（P1）

1. 根据缺陷类型/模块/历史成功率给出 AGENT 推荐组合。
2. 支持手动覆盖，并记录偏好。
3. 在分析触发前展示推荐理由与置信度。

验收标准：
1. 至少覆盖主流类型（功能/UI/性能/安全/兼容性）。
2. 推荐命中率可统计且持续提升。

### FR-5 可观测与压测基线（P2）

1. 增加 API 级延迟、错误率、吞吐指标采集。
2. 给出关键链路 SLO（登录、项目切换、缺陷列表、问题池查询、缺陷创建）。
3. 提供标准压测脚本与报告模板。

验收标准：
1. 可输出 P50/P95/P99。
2. 形成每次发布前可复用的性能检查流程。

### FR-6 OAuth/SSO 第一版（P2）

1. 支持至少 1 个外部身份源（建议 GitLab/GitHub 二选一起步）。
2. 保留现有用户名密码登录作为回退路径。
3. 首版支持账号绑定与基础权限映射。

验收标准：
1. 企业用户可通过外部账号登录并进入既有权限体系。

## 5. 迭代计划（最需要优先做的事情）

> 节奏建议：每迭代 2 周，总计 4 个迭代（8 周）。  
> 优先顺序：稳定性与安全 > 智能效率 > 可观测与企业接入。

### Iteration 5.3.1（P0）- 统一体验与回归收敛

目标：先止血，消除反复出现的 UI 回归。

必须完成：
1. 搜索/筛选栏组件统一改造（全核心列表页）。
2. 组件使用白名单与禁用清单（禁止私有重复实现）。
3. 关键页面视觉回归快照基线。
4. “发布前 UI 巡检”脚本化。

交付物：
1. 统一后的筛选/搜索栏组件使用矩阵。
2. 回归检查报告（含前后对比截图）。

### Iteration 5.3.2（P0/P1）- 接入安全与分配提效

目标：补齐 Webhook 安全底线，并完成推荐分配首版。

必须完成：
1. Webhook 签名校验（含审计）。
2. 推荐分配算法 v1（规则+统计混合）。
3. 指派 UI 增加推荐与一键采纳。
4. 推荐采纳行为埋点。

交付物：
1. 签名校验联调用例集。
2. 推荐分配效果周报（采纳率/耗时变化）。

### Iteration 5.3.3（P1）- AGENT 智能协作增强

目标：减少手动选择，提升分析链路自动化。

必须完成：
1. AGENT 自动推荐策略 v1。
2. 推荐理由与置信度展示。
3. 人工覆盖与反馈记录机制。
4. 与缺陷类型、模块、路由规则联动。

交付物：
1. AGENT 推荐命中率仪表。
2. 典型案例回放（命中/误判样例）。

### Iteration 5.3.4（P2）- 可观测与企业化基线

目标：为下一阶段规模扩展和企业接入准备底座。

必须完成：
1. API 关键链路性能指标接入。
2. 标准压测脚本与压测报告。
3. OAuth/SSO 第一版打通。
4. 发布门禁加入性能与稳定性检查项。

交付物：
1. 版本级性能基线报告。
2. 企业登录接入文档（管理员视角）。

## 6. 里程碑与成功指标

### 里程碑

1. M1（第 2 周）：UI 回归类问题收敛，核心页面样式统一。
2. M2（第 4 周）：Webhook 签名校验上线，推荐分配可用。
3. M3（第 6 周）：AGENT 推荐上线并可度量。
4. M4（第 8 周）：性能基线与 SSO 首版完成。

### 成功指标（建议）

1. UI 样式回归问题数：较 v5.2 阶段下降 80%。
2. 缺陷分配平均耗时：下降 20%+。
3. 推荐采纳率：首版目标 35%+。
4. Webhook 非法请求拦截率：100%（签名失败场景）。
5. 关键 API P95：建立基线并持续可见。

## 7. 风险与对策

1. **风险：历史数据不足影响推荐效果**
   - 对策：先规则+统计混合，不做纯模型依赖；保留人工覆盖。
2. **风险：样式统一改造影响现网页面**
   - 对策：分页面灰度 + 快照回归 + 高频页面优先。
3. **风险：SSO 接入拉长周期**
   - 对策：先单 IdP MVP，接口预留多源扩展。
4. **风险：可观测体系接入成本高**
   - 对策：先覆盖关键链路与核心指标，避免全量铺开。

---

## 8. v5.3 最终优先级结论（给管理层）

如果资源不足，按以下顺序确保收益最大化：

1. **必须先做**：`FR-1 统一搜索/筛选` + `FR-2 Webhook 签名校验`
2. **第二优先**：`FR-3 推荐分配` + `FR-4 AGENT 推荐`
3. **第三优先**：`FR-5 可观测压测` + `FR-6 SSO`

这条顺序能够保证：先把线上体验和安全底盘打稳，再拉升智能化效率，最后扩展企业化能力。
