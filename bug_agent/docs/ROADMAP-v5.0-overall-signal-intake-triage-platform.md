# BugAgent v5.0 路线图

> Version: v5.0  
> Date: 2026-04-12  
> Status: Planning

---

## 1. 路线图总原则

1. 先做统一接入内核，再做连接器。
2. 先做问题池和分诊中心，再做版本、日志、质量看板。
3. 首期坚持单向接入，双向回写只做模型和协议预留。
4. 复用现有缺陷、AI 分析、协作、修复主链路，避免重复造轮子。

---

## 2. 版本结构

v5.0 建议拆为 3 个阶段、6 个迭代：

1. `Phase 5A`：统一接入内核 + 首批高价值连接器 + 问题池 + 分诊闭环
2. `Phase 5B`：责任路由增强 + 日志上下文 + 版本/发布关联 + 修复闭环增强
3. `Phase 5C`：回归预防 + 质量情报中心 + 渠道扩展 + 双向回写准备

---

## 3. Phase 5A

目标：让外部问题信号能够稳定进入平台，并完成问题池分诊和转缺陷闭环。

### Sprint 5A-1 统一接入内核

交付范围：
1. 连接器实例管理
2. 通用 Webhook 接入
3. 问题信号标准模型
4. 幂等去重
5. 接入任务中心
6. 失败重试与死信记录

里程碑：
1. 外部系统可通过标准协议把问题写入平台。
2. 同一事件重复发送不会重复建信号。
3. 管理员可查看同步状态和错误记录。

### Sprint 5A-2 Bugly 接入

交付范围：
1. Bugly 连接器配置页
2. Bugly 定时/手动同步
3. Bugly 数据标准化映射
4. Bugly 原始 payload 保存
5. Bugly 问题详情展示

里程碑：
1. 真实 Bugly 问题可进入问题池。
2. 版本、设备、堆栈、次数等关键字段完整可用。
3. 同源问题能幂等更新而不是重复建单。

### Sprint 5A-3 问题池与分诊中心

交付范围：
1. 问题池列表和详情
2. 问题簇模型
3. 重复识别与基础聚类
4. 分诊动作：忽略、标记重复、合并、指派、转缺陷
5. 分诊审计记录

里程碑：
1. 问题池形成独立工作区。
2. 分诊人员可完成问题簇处理闭环。
3. 形成“待分诊 -> 已转缺陷/已忽略”的稳定状态流。

### Sprint 5A-4 钉钉/飞书接入与转缺陷联动

交付范围：
1. 钉钉机器人/Webhook 接入
2. 飞书机器人/Webhook 接入
3. IM 消息结构化解析
4. 问题簇一键转缺陷
5. 转缺陷带来源上下文
6. 可选自动触发 AI 分析

里程碑：
1. IM 上报消息可进入问题池。
2. 问题池可稳定转正式缺陷。
3. 缺陷详情页可追溯到外部来源。

---

## 4. Phase 5B

目标：提升分诊准确性，并让问题与版本、模块、日志和修复链路形成更强关联。

### Sprint 5B-1 责任路由与模块建模

交付范围：
1. 项目模块模型
2. 模块负责人维护
3. 最小路由规则
4. 项目/模块/负责人建议
5. 分诊建议准确率优化

里程碑：
1. 分诊时能给出可信的归属建议。
2. 人工修正成本明显下降。

### Sprint 5B-2 阿里云日志平台接入与发布关联

交付范围：
1. 阿里云日志连接器
2. 查询规则与同步任务
3. 日志上下文关联问题簇
4. App 版本与构建号模型
5. 发布后问题趋势
6. 修复闭环进展展示

里程碑：
1. Bugly 问题可补全日志上下文。
2. 问题可按 App 版本聚合。
3. 支持基本的版本影响分析。

---

## 5. Phase 5C

目标：从处理问题进一步走向预防问题和组织级质量运营。

### Sprint 5C-1 回归预防

交付范围：
1. 问题簇转测试点
2. 问题簇转回归清单
3. 相似问题预警
4. 高频问题模式沉淀

### Sprint 5C-2 质量情报中心

交付范围：
1. 版本质量评分
2. 模块质量热度
3. 重复问题率
4. 响应/修复时效
5. AI 处置采纳率
6. 修复后再发率

说明：
1. `Phase 5C` 可以作为 v5.0 后半段或 v5.1 承接。
2. 不建议作为首期上线的阻塞条件。

---

## 6. 优先级排序

按产品价值和实施顺序排序如下：

1. 统一接入内核
2. Bugly 接入
3. 问题池
4. 分诊中心
5. 转缺陷联动
6. 钉钉/飞书接入
7. 模块与责任路由
8. 阿里云日志增强
9. 版本/发布关联
10. 回归预防与质量情报

---

## 7. 资源与依赖

### 7.1 外部依赖

1. Bugly API 权限和真实测试数据
2. 钉钉/飞书机器人权限
3. 阿里云日志平台访问权限
4. App 版本/渠道/构建号字段统一口径

### 7.2 内部依赖

1. 项目与模块命名规范
2. 模块负责人规则
3. 分诊角色范围确认
4. 问题池与缺陷域边界执行到位

---

## 8. 风险控制

### 风险 1：连接器先多后乱

策略：
1. 首期只落 4 个连接器。
2. 所有接入必须先走统一内核。

### 风险 2：问题池与缺陷域职责混乱

策略：
1. 问题池单独建模。
2. 单独 API、单独 UI、单独状态机。

### 风险 3：智能分诊准确率不足

策略：
1. 首期只做建议，不做强自动执行。
2. 保留人工确认和覆盖能力。

### 风险 4：外部数据质量差异大

策略：
1. 原始 payload 完整留存。
2. 标准化失败记录和重试。
3. 字段级容错与脱敏。

---

## 9. 后续规划预留

### 9.1 双向回写

后续阶段可扩展：
1. 状态回写
2. 评论回写
3. 外部卡片更新
4. 线程消息回写

### 9.2 渠道多元化

后续建议扩展：
1. 企业微信
2. 邮件
3. 客服工单系统
4. 更多日志/告警系统
5. 其他质量平台或自研系统

原则：
1. 扩展连接器，不重构问题池内核。
2. 维持单一标准化信号模型。

---

## 10. 路线图结论

v5.0 的成败关键不是“接了多少平台”，而是：

1. 外部问题是否能稳定进入平台。
2. 重复问题是否能被聚类而不是继续冲击缺陷域。
3. 分诊是否足够高效。
4. 转缺陷后是否能无缝进入现有 AI 处置闭环。

如果以上 4 点做成，BugAgent 就会从“智能缺陷工具”升级成“面向 App 场景的质量闭环平台”。
