# Gateway 接口自动化 V1.2 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.2 |
| 日期 | 2026-07-17 |
| 技术栈 | Python + pytest + requests + PyYAML |
| 核心目标 | 请求/响应日志持久化；标准多接口 Flow YAML 编排 |
| 文档状态 | 待 Review |

## 2. 背景

当前框架已经完成 Gateway 单接口自动化的基础能力，并在此基础上增加了会话管理、运行时变量和一条媒体搜索流程。下一阶段需要将调试日志保存到磁盘，同时把现有固定流程升级为可以通过 YAML 持续扩展的标准多接口流程。

V1.2 不重新设计现有单接口体系，继续复用 `data/cases/*.yaml`、`GatewayApi`、`RuntimeContext` 和通用断言器。

## 3. 当前版本能力盘点

### 3.1 已有能力

- 通过 `data/cases/*.yaml` 管理单接口请求、标签、断言和响应字段提取。
- 固定调用 `POST /gateway/invoke`，自动构造 `comm + requests[req_0]`。
- 支持 HTTP、Gateway 顶层、业务子响应和 `data_fields` 分层断言。
- 支持 `{{变量名}}` 在字典、列表和字符串中的递归替换。
- 支持以业务响应 `data` 为根的 `$.field[index]` 路径提取。
- 支持运行时内存上下文，不把 token 和业务动态值写回 YAML。
- 支持匿名会话自动创建、临期刷新和刷新失败后重新创建。
- 支持使用预签名 URL 和响应请求头进行 COS 二进制 PUT。
- 支持终端输出脱敏后的请求和响应。
- 支持 `--env`、`--module`、`--tag` 及 pytest 参数透传。

### 3.2 当前不足

- 日志只输出到终端，测试结束后无法按执行批次追溯。
- 当前流程只读取固定的 `anonymous_session_media_search.yaml`。
- 流程解析和步骤执行写在 `test_gateway_flow.py` 中，新增流程可能需要修改 Python。
- Flow YAML 与场景测试数据尚未独立管理，也没有一一对应校验。
- 当前流程只支持顺序调用和固定 COS 上传，不支持通用等待、轮询终止条件和步骤级断言覆盖。
- 缺少流程加载前的配置校验、重复步骤检查和清晰的步骤失败定位。

## 4. V1.2 目标

### 4.1 日志系统

1. 每次 pytest 执行生成独立日志文件并保存到根目录 `logs/`。
2. Gateway POST 和 COS PUT 的请求、响应、耗时、失败信息全部写入日志。
3. 日志同时输出到终端和文件，保持当前本地调试体验。
4. token、Authorization、refresh token 和预签名 URL 查询参数必须脱敏。
5. 二进制文件不写入日志，只记录文件名、Content-Type 和字节数。

### 4.2 标准多接口 Flow

1. 使用 Flow YAML 声明接口调用顺序、变量提取、断言和等待。
2. 每个 Flow YAML 必须存在一个同名场景数据 YAML，二者共同组成一条独立测试用例。
3. Flow 复用 `data/cases` 中的接口定义，不复制公共接口请求和默认断言。
4. 前序步骤提取的响应数据可通过 `{{变量名}}` 在后续接口请求、断言或等待条件中引用。
5. 新增普通流程只增加 Flow YAML 和同名场景数据 YAML，不修改 Python 执行器。
6. pytest 自动发现全部有效 Flow，并支持按名称、标签和环境运行。

## 5. 范围

### 5.1 V1.2 包含

- 终端与文件双输出日志。
- 每次执行生成唯一日志文件。
- 请求/响应脱敏和步骤上下文信息。
- Flow 与场景数据一一对应。
- 通用接口调用步骤。
- 请求参数覆盖和运行时变量引用。
- 响应字段提取。
- 默认断言复用与步骤断言扩展。
- 固定时间等待。
- 基于字段相等条件的轮询等待。
- 已有 COS PUT 步骤继续可用。
- Flow 配置预检查和明确错误信息。
- `runtest.py` 支持指定 Flow 运行。

### 5.2 V1.2 不包含

- Allure、Jenkins、飞书等第三方集成。
- 多进程共享运行时上下文。
- 并发步骤、条件分支、循环语法和任意 Python 表达式。
- 数据库、消息队列或非 HTTP 协议校验。
- 性能测试、压力测试和失败步骤断点续跑。
- 自动删除历史日志；V1.2 由使用者自行清理 `logs/`。
- 完整 JSON Schema 校验。

## 6. 目录规划

```text
.
├── config/
│   └── settings.yaml                     # 增加 logging 与 flow 默认配置
├── data/
│   ├── cases/                            # 现有单接口定义，继续复用
│   ├── flows/
│   │   └── AnonymousSessionMediaSearch.yaml
│   └── scenarios/
│       └── AnonymousSessionMediaSearch.yaml
├── logs/                                 # 每次运行生成日志文件
├── test_cases/
│   └── test_gateway_flow.py              # 通用 Flow 参数化入口
└── utils/custom/
    ├── logger.py                          # 终端与文件日志初始化
    ├── flow_loader.py                     # Flow/场景配对、加载与校验
    └── flow_runner.py                     # 通用步骤执行器
```

配对规则：

```text
data/flows/AnonymousSessionMediaSearch.yaml
data/scenarios/AnonymousSessionMediaSearch.yaml
                    ↑ 文件名必须完全一致
```

一个配对文件组对应 pytest 中的一条流程测试用例。缺少任意一侧、文件名不一致或同名重复时，在发送第一个请求前直接报错。

## 7. 日志系统需求

### 7.1 日志目录与文件名

根目录固定使用 `logs/`。每次 pytest 进程创建一个日志文件：

```text
logs/20260717_153012_test_12345.log
```

文件名组成：`日期时间_环境_进程号.log`。同一次执行中的单接口和 Flow 共用一个文件，保证调用顺序可完整追溯。

### 7.2 日志配置

```yaml
# config/settings.yaml
logging:
  level: INFO
  directory: logs
  console: true
  file: true
```

V1.2 只支持 `DEBUG`、`INFO`、`WARNING`、`ERROR` 四种级别，默认 `INFO`。

### 7.3 必须记录的信息

每个 HTTP 步骤至少记录：

- 测试用例名称、Flow 名称、场景名称、步骤 ID 和步骤序号。
- 请求时间、HTTP 方法、脱敏 URL、请求头和请求体。
- 响应时间、耗时毫秒数、HTTP 状态和脱敏响应体。
- 断言结果和提取出的变量名称；敏感变量只记录变量名，不记录值。
- 网络异常、配置异常、断言异常和等待超时信息。

### 7.4 脱敏规则

以下键忽略大小写并统一显示为 `***`：

- `auth_token`
- `access_token`
- `refresh_token`
- `authorization`
- `token`

预签名 URL 只记录 scheme、host 和 path，所有 query 参数替换为 `***`。二进制内容只记录 `content_length`。

### 7.5 日志验收

1. 执行任意单接口后，`logs/` 中新增一个 UTF-8 日志文件。
2. 日志包含完整的一组请求和响应记录。
3. 流程中每个步骤都能通过 Flow 名称和 step ID 定位。
4. 测试失败时日志文件仍正常关闭并保留失败上下文。
5. 日志文件中搜索真实 token、refresh token 或签名参数，结果必须为空。

## 8. Flow 与场景数据模型

### 8.1 职责边界

| 文件 | 职责 | 不保存 |
| --- | --- | --- |
| `data/cases/*.yaml` | 单接口路由、默认参数、默认断言、可复用提取规则 | 流程顺序 |
| `data/flows/*.yaml` | 步骤顺序、调用动作、提取、等待和步骤关系 | 具体场景输入值 |
| `data/scenarios/*.yaml` | 测试输入、步骤参数覆盖、场景期望值 | Python 执行逻辑 |

### 8.2 Flow YAML 示例

```yaml
name: 搜索流程
tags: [flow, media, search]
scenario: AnonymousSessionMediaSearch.yaml
steps:

  - id: create_task
    name: 创建搜索任务
    call: CreateIntentTask.yaml
    extract:
      task_id: $.task_id

  - id: poll_task
    name: 等待任务完成
    call: GetTask.yaml
    until:
      path: $.status
      equals: SUCCEEDED
      interval_seconds: 2
      timeout_seconds: 120

  - id: list_candidates
    name: 查询候选列表
    call: ListTaskCandidates.yaml
    extract:
      candidate_id: $.items[0].candidate_id

  - id: candidate_detail
    name: 查询候选详情
    call: GetTaskCandidateDetail.yaml
```

### 8.3 场景数据 YAML 示例

```yaml
name: 姓名搜索成功场景
step_data:
  create_task:
    params:
      match_strategy: UNION
      clues:
        - type: FULL_NAME
          full_name_query:
            full_name: JOJO CCQQ MOCK
    assert:
      data_equals:
        status: QUEUED
  poll_task:
    assert:
      data_equals:
        status: SUCCEEDED
```

场景数据中的 `params` 递归覆盖接口 case 的默认 `request.params`；`assert` 在默认接口断言基础上增加或覆盖场景断言。接口 case 文件本身保持可独立运行。

## 9. Flow 执行规则

### 9.1 加载与发现

1. pytest 扫描 `data/flows/*.yaml`。
2. 按 `scenario` 字段加载对应的 `data/scenarios` 文件。
3. 校验 Flow、场景、步骤和引用的 case 文件。
4. 一个合法配对生成一条 pytest 参数化用例。
5. Flow 中标记的 tags 注册为 pytest marker。

### 9.2 步骤类型

V1.2 支持以下最小步骤：

| 类型 | 配置 | 行为 |
| --- | --- | --- |
| 接口调用 | `call` | 加载 case、合并场景参数、解析变量、请求、断言、提取 |
| 固定等待 | `wait.seconds` | 等待指定秒数后进入下一步 |
| 条件轮询 | `call + until` | 重复调用同一 case，直到字段等于目标值或超时 |
| COS 上传 | `action: prepared_media_upload` | 复用现有预签名 PUT 能力 |

一个步骤只能声明一种主动作。步骤 ID 在同一 Flow 内必须唯一。

### 9.3 参数合并优先级

接口调用步骤的最终参数按以下顺序合并，后者覆盖前者：

1. `data/cases` 中的默认 `request.params`。
2. 同名场景文件中 `step_data.<step_id>.params`。
3. RuntimeContext 中通过 `{{变量名}}` 解析得到的动态值。

V1.2 不允许 Flow YAML 直接保存大段业务测试数据，避免编排与数据重新耦合。

### 9.4 断言规则

执行顺序：

1. 执行 case 的 HTTP、Gateway、业务子响应和 `data_fields` 默认断言。
2. 合并场景中该步骤的断言。
3. 支持最小场景断言：
   - `data_fields`：字段存在；
   - `data_equals`：指定路径值等于期望值。
4. 断言全部通过后才执行字段提取。
5. 任一断言失败立即终止当前 Flow，后续步骤不再执行。

路径均以目标业务响应的 `data` 为根，例如 `$.progress.stage`。

### 9.5 响应提取与变量引用

- Flow 步骤 `extract` 覆盖或扩展 case 自身的提取规则。
- 提取值写入当前 Flow 独立的 RuntimeContext。
- 不同 Flow 之间不共享业务变量，避免执行顺序造成污染。
- 完整占位符保留原始类型，混合字符串转换为文本。
- 缺少变量、路径不存在或数组越界时立即失败，并在错误中包含 Flow、step ID、变量名和路径。

### 9.6 固定等待

```yaml
- id: wait_one_second
  wait:
    seconds: 1
```

- `seconds` 必须为大于或等于 0 的数字。
- 单次固定等待最大 300 秒，超过时在配置校验阶段失败。

### 9.7 条件轮询

```yaml
until:
  path: $.status
  equals: SUCCEEDED
  interval_seconds: 2
  timeout_seconds: 120
```

规则：

- 每次请求先完成 HTTP 与 Gateway 基础断言，再判断 `until` 条件。
- 条件满足后执行该步骤的最终场景断言和提取。
- 超时后失败，错误包含最后一次响应值、累计次数和总耗时。
- `interval_seconds` 必须大于 0，`timeout_seconds` 必须大于等于间隔时间。
- V1.2 只支持相等判断，不支持脚本表达式。

## 10. 配置校验与失败策略

发送请求前必须校验：

- Flow 和场景文件根节点为对象。
- Flow 名称、场景引用和 steps 非空。
- 步骤 ID 唯一。
- `call` 引用的 case 文件存在。
- 场景 `step_data` 中的 step ID 在 Flow 中存在。
- `extract`、`data_equals` 和 `until.path` 路径格式合法。
- 等待和轮询数值在允许范围内。
- 步骤动作没有冲突。

运行时失败策略：

- 普通调用、断言、提取或等待失败后立即终止当前 Flow。
- 一个 Flow 失败不影响 pytest 继续执行其他 Flow，除非用户传入 `-x`。
- 日志记录失败步骤；异常消息不得包含敏感变量值。

## 11. 执行入口

保留现有命令：

```bash
python3 runtest.py --env test
python3 runtest.py --env test --module gateway_flow
python3 runtest.py --env test --tag flow
```

V1.2 新增按 Flow 文件名筛选：

```bash
python3 runtest.py --env test --flow AnonymousSessionMediaSearch
```

`--flow` 只影响 Flow 参数化用例，不影响单接口用例。指定的 Flow 不存在时，执行入口应返回非零退出码并显示可用 Flow 名称。

## 12. 验收标准

### 12.1 日志系统

1. 任意测试执行后在 `logs/` 生成唯一日志文件。
2. 文件日志与终端日志均包含请求、响应、HTTP 状态和耗时。
3. Flow 日志包含 Flow 名称、场景名称、step ID 和序号。
4. Gateway POST、COS PUT、网络异常和断言失败均有日志。
5. 自动化测试确认 token、refresh token 和签名 URL 参数没有泄露。

### 12.2 Flow 编排

1. 新增一对同名 Flow/场景 YAML 后，无需修改 Python 即可被 pytest 收集。
2. 一个 Flow 至少可串行执行三个接口。
3. 前序接口提取的字符串、数字、字典和列表可以用于后续请求。
4. 场景参数可以覆盖 case 默认参数，且不会修改原始 YAML 对象。
5. 默认接口断言和场景步骤断言均生效。
6. 固定等待按配置执行。
7. 条件轮询在成功条件满足时结束，在超时时提供明确失败信息。
8. 缺少配对场景、引用不存在 case、重复 step ID 和缺失变量均在请求前或对应步骤明确失败。
9. 两条 Flow 连续执行时，业务运行时变量互不污染。
10. 现有单接口、自动会话、变量替换、响应提取和 COS PUT 能力回归通过。

## 13. 测试策略

- 日志文件创建、命名、UTF-8 内容和双输出测试。
- 请求、响应、异常、签名 URL 和二进制日志脱敏测试。
- Flow/场景一一对应与非法配置测试。
- case 参数与场景参数递归合并测试。
- 多步骤提取、引用和上下文隔离测试。
- 固定等待使用可注入时钟，单元测试不真实等待。
- 轮询成功、超时、间隔非法和最后响应值测试。
- 步骤断言覆盖、提取顺序和失败即停止测试。
- 运行现有全部单元测试，确认无回归。
