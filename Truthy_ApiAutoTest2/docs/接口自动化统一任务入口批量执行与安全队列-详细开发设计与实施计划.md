# 接口自动化统一任务入口、批量执行与安全队列详细开发设计与实施计划

## 1. 背景与目标

当前 Web 端把“执行任务”固定指向单接口页面，Flow 需要从概览进入；精确选择 Case/Flow 后仍允许输入 `tag`，该值会再次转换成 `pytest -m`，可能把已经选中的资产过滤成 0 条。执行器同时采用单槽模型，繁忙时第二个任务直接返回 `SLOT_BUSY`。

本次改造统一任务入口，增加多个 Case 或多个 Flow 的批量回归，并把独立任务改为可恢复的 FIFO 队列。批次坚持“一个 Task、一个 Runtime Context、一个 pytest 进程、多个逻辑结果项”，避免多个子进程冻结同一 Credential 旧版本后发生 Session CAS 冲突。

## 2. 不可变设计原则

- YAML 继续是 API、Case、Flow、Scenario 和 fixture 的唯一真源。
- 平台继续是 Scope、Release、Secret、Credential、RBAC 与运行快照的唯一真源。
- dev 平台只执行 test Gateway；prod 平台只映射 prod，本期不向 prod 发业务请求。
- 批次只允许 Cases 或 Flows，同一批次不混合两类资产。
- 批次使用 YAML 默认业务参数，不接受 `runtime_overrides`。
- 图片仍保存在任务输入目录，Analysis/Reply 不调用 `DeleteTaskData`。
- 业务日志不脱敏，不增加任务级日志目录。

## 3. 核心数据流

```text
Web 提交 -> 平台创建 Runtime Context -> Task V3(pending)
        -> FIFO 调度 -> dispatch-materialize
        -> 一个 pytest 进程 -> 聚合 JUnit
        -> Task detail 中映射 batch.items
```

任务提交时平台固化 Release、系统 Secret 和资源权限。真正调度时，平台在同一事务中重新校验 Session、用户、权限、Scope，并只把原 selector 中的 Credential ID 刷新到当前健康版本；Release、系统 Secret、LLM 选择和 Credential ID 集合均不得漂移。

## 4. Task V3

普通任务与批次任务共用 Task JSON：

```json
{
  "schema_version": 3,
  "status": "pending",
  "queue": {
    "sequence": 12,
    "queued_at": "2026-08-30T10:00:00+08:00",
    "dispatched_at": null
  },
  "batch": {
    "type": "cases",
    "selection_mode": "selected",
    "item_count": 2,
    "items": []
  }
}
```

`pending` 对外显示“排队中”；`queue_position` 由服务端根据非终态任务实时计算，不写回历史记录。批次逻辑项保存 `asset_id`、`asset_revision`、稳定 pytest ID、风险标签、状态、耗时和错误摘要。旧 V2 记录继续按普通任务读取。

## 5. 批次资产与执行

- `selection_mode=selected` 要求每个条目携带当前 `asset_revision`。
- `selection_mode=all_safe` 由服务端从当前 Catalog 解析并固化条目。
- 自动安全项排除 `explicit`、`destructive`、`interactive`、不可用资产及缺少必填文件的 Flow。
- 手动选择风险资产必须提交对应确认；图片 Flow 的文件契约不兼容时拒绝整个批次。
- TaskManager 对每个条目构建完整不可变执行资产，写入任务级 `execution-asset.json`（0600）。pytest 检测到批次文档后只从该文档参数化，禁止回退当前 YAML。
- 同一个 pytest 进程不启用 fail-fast；JUnit 中每个 testcase 映射回一个逻辑条目。缺少选中条目的结果时父任务以 `BATCH_RESULT_INCOMPLETE` 失败。

## 6. 队列与并行

- 默认最多 20 个 pending 任务，超限返回 429 `QUEUE_FULL`。
- 默认 `API_AUTOTEST_MAX_CONCURRENCY=1`。
- 调度顺序为同一隔离键 FIFO、全局最早可执行任务优先。
- 隔离键由 Runtime Scope 与 selector 中的 Credential IDs 组成；有交集的 Credential 永不并行。
- 服务重启后，`running` 任务标记 `SERVICE_RESTARTED`；带完整 queue/runtime context 的 `pending` 任务恢复执行。
- Runtime Context 过期时不续期，任务 fail-closed 并提示重新提交。

## 7. Web 与 API

统一入口为 `/tasks/new?mode=single|flow|batch`，旧 `/tasks/new/single` 与 `/tasks/new/flow` 重定向。精确 Case/Flow 不再接受 `tag`。批量页提供资产类型、选择模式、搜索、真实标签 AND 筛选、全选筛选结果、风险确认、图片上传、预检和提交。

`POST /api/tasks` 的批次增量字段包括 `batch_type`、`selection_mode`、`items`、`tag_filters`、`risk_acknowledgements`。Catalog 增加批次资格与风险标签；任务列表增加队列位置；Retry 支持 `all` 与 `failed`。

## 8. 日志与报告

日志继续位于：

```text
logs/<project>/<target_env>/<YYYY-MM-DD>/
```

新文件名为 `<timestamp>_<env>_<task_id>_<pid>.log`。历史日志继续通过 PID 与时间窗回退关联。批次使用一份聚合 JUnit；Allure HTML 不作为 P0 完成条件。报告发布锁放到任务报告根目录，使不同任务可并行发布、同一任务保持互斥。

## 9. 实施与验收顺序

1. 平台 dispatch-materialize 与身份强校验。
2. 批次领域模型、不可变执行资产与 JUnit 映射。
3. FIFO 队列、取消、Retry、恢复与 Retention。
4. 统一任务入口、批量回归 UI、任务列表与详情。
5. Credential 隔离并行、日志 task ID、报告锁。
6. 后端与工具全量测试、项目校验、本机发布和已登录 Web 验收。

## 10. 模块落点与职责

| 模块 | 主要职责 | 关键约束 |
| --- | --- | --- |
| `web/task_manager.py` | 批次解析、Task V3、FIFO 调度、隔离锁、Retry、取消、恢复和 JUnit 子项映射 | 浏览器只提交逻辑 ID；任务开始后不再读取可变 YAML |
| `web/task_store.py` | 任务 JSON、附件、执行清单和 Retention | 执行清单权限为 `0600`；非终态任务不得清理 |
| `web/catalog.py` | 输出批次资格、真实标签、风险标签和文件输入契约 | 不向浏览器暴露资产物理路径 |
| `web/app.py` | `/tasks/new`、Catalog/Preflight/Task API、平台 Context 与 dispatch 物化 | 拒绝单条任务 tag 过滤和批次 runtime override |
| `test_cases/*` | 从不可变执行清单参数化一个或多个 Case/Flow | 清单非法时失败关闭，不回退当前 YAML |
| `web/templates/*`、`web/static/*` | 三模式统一入口、批量选择、队列和子项详情 | 原生 JavaScript；真实链接；可键盘操作 |
| `utils/custom/logger.py` | 在既有日期目录中生成带 task ID 的日志名 | 不脱敏；不增加任务级日志目录 |
| `scripts/publish_allure_report.sh` | 报告发布互斥 | 不同任务可并行，同一任务互斥 |
| `test-platform/backend/app/api/internal.py` | dispatch 时重验身份并刷新原 Credential 版本 | Release、系统 Secret、Credential ID 集合不可漂移 |

## 11. 状态机与竞态处理

```text
submit -> pending -> running -> succeeded / failed / cancelled
                    └-------> failed(timeout)
pending --cancel--> cancelled
```

- 调度器在锁内预占任务并写入 `queue.dispatched_at`，在锁外执行平台物化和 `Popen`，避免长网络请求阻塞提交与取消。
- `Popen` 前后都检查任务状态；若取消发生在启动窗口，立即终止刚创建的进程，且不得把 `cancelled` 覆盖回 `running`。
- 服务启动时将遗留 `running` 标记为基础设施失败；对已进入 dispatch 但仍为 `pending` 的任务，先删除受控 snapshot/execution asset，再按原序列重新调度。
- dispatch 接口允许同一 Context、同一 Credential ID 集合和同一固定系统快照的幂等重试；任何 Scope、Release、系统 Secret、LLM 或 Credential 集合漂移仍失败关闭。
- Credential 隔离键有交集时，即使并发配置大于 1 也保持 FIFO 串行；无交集任务才进入可用 worker。

## 12. API 校验与稳定错误

提交阶段依次执行：请求字段白名单、运行类型、资产存在性和版本、批次类型、数量上限、标签 AND 筛选、风险确认、文件契约、平台 Runtime Context 规划、队列容量。主要错误码如下：

| 错误码 | HTTP | 含义 |
| --- | --- | --- |
| `TAG_FILTER_NOT_ALLOWED` | 400 | 精确单 Case/Flow 不允许再次用 marker 过滤 |
| `BATCH_SELECTION_REQUIRED` | 400 | 批次未解析到条目 |
| `BATCH_SELECTION_INVALID` | 400/409 | 逻辑 ID 或资产版本非法 |
| `BATCH_MIXED_TYPE` | 400 | Case 与 Flow 混选 |
| `BATCH_TOO_LARGE` | 400 | 条目超过 200 |
| `BATCH_UNSAFE_CONFIRMATION_REQUIRED` | 400 | 显式或破坏性资产未确认 |
| `BATCH_INPUT_CONTRACT_CONFLICT` | 400 | 多 Flow 的文件执行约束不兼容 |
| `QUEUE_FULL` | 429 | pending 数达到上限 |
| `RUNTIME_DISPATCH_CREDENTIAL_UNAVAILABLE` | 409 | 排队期间原 Credential 不再健康或版本缺失 |
| `BATCH_RESULT_INCOMPLETE` | 终态失败 | JUnit 缺少某个已固化逻辑条目 |

Preflight 不创建任务，以 HTTP 200 返回 `ready=false`、字段级错误、解析条目数、排除原因、Profile 并集、文件契约和队列摘要；Task 提交返回真实 4xx/409/429。

## 13. 测试矩阵

- 领域层：Case/Flow 批次、稳定排序、AND 标签、200 条边界、安全项排除、风险确认和文件契约。
- 快照层：路径越界、符号链接、摘要篡改、项目身份不一致、执行中 YAML 变化和执行清单清理。
- 调度层：FIFO、队列满、排队/运行取消、超时、重启恢复、同 Credential 串行、不同 Credential 并行。
- 平台层：Session/用户/权限/项目授权/Scope 变化、Context 过期、Credential 版本刷新、系统快照固定及幂等重派。
- 结果层：多条继续执行、JUnit 精确映射、缺失结果失败、失败项 Retry、日志 task ID 和报告锁。
- Web 层：canonical/兼容路由、三模式切换、批量筛选、图片输入、队列位置、子项详情、键盘焦点、错误恢复和 Base Path 刷新。

## 14. 发布、回滚与观测

发布顺序固定为平台后端、接口自动化工具；两者健康后再开放 Web 验收。默认并发保持 `1`，仅自动化测试使用 `2` 验证隔离能力。回滚工具版本时，历史 V3 JSON 继续只读展示；不删除 pending/running 文件。若平台 dispatch 不可用，任务进入带稳定错误码的失败终态，不回退 `.env` 或本地 Secret。Dating Scope 可独立禁用，不影响 Truthy 与历史报告。
