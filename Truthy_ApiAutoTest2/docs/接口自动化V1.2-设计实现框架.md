# Gateway 接口自动化 V1.2 设计实现框架

## 1. 设计目标

在不改变现有单接口执行方式的基础上，增加两项能力：

1. 每次测试执行时，将请求、响应和异常同时输出到终端与 `logs/` 文件。
2. 使用通用执行器加载 Flow YAML 和同名 Scenario YAML，完成接口调用、变量提取、断言、固定等待和条件轮询。

设计原则：复用现有 `GatewayApi`、`RuntimeContext`、case YAML 和断言器，只增加必要模块。

## 2. 总体结构

```text
runtest.py
    ↓
pytest / test_gateway_flow.py
    ↓
flow_loader.py ── 加载并校验 Flow + Scenario
    ↓
flow_runner.py ── 按顺序执行 call / wait / upload / poll
    ↓
GatewayApi + RuntimeContext + assertions.py
    ↓
HttpClient
    ↓
终端日志 + logs/运行日志
```

## 4. 模块职责

### 4.1 `logger.py`

- 根据配置初始化日志级别。
- 同时添加终端 Handler 和文件 Handler。
- 每个 pytest 进程只创建一个日志文件。
- 文件名格式：`YYYYMMDD_HHMMSS_环境_进程号.log`。
- 重复初始化时不重复添加 Handler。

### 4.2 `http_client.py`

- 保留现有 POST 和 PUT 能力。
- 请求前记录方法、脱敏 URL、请求头和请求数据。
- 响应后记录 HTTP 状态、响应数据和耗时。
- 请求异常时记录脱敏请求和异常类型。
- 二进制 PUT 只记录文件大小，不记录文件内容。

### 4.3 `flow_loader.py`

- 扫描 `data/flows/*.yaml`。
- 按 Flow 文件名加载同名 `data/scenarios/*.yaml`。
- 按 `--flow` 过滤需要执行的流程。
- 校验步骤 ID、步骤动作、case 文件、Scenario step ID 和等待参数。
- 返回可以直接交给 FlowRunner 的 FlowCase 对象或字典。

### 4.4 `flow_runner.py`

- 每条 Flow 创建独立 `RuntimeContext`。
- 按 steps 顺序执行步骤。
- 加载并复制 case YAML，不修改原始对象。
- 合并 case 默认参数与 Scenario 步骤参数。
- 执行默认断言和场景断言。
- 将提取值写入当前 Flow 的 RuntimeContext。
- 处理固定等待、条件轮询和现有 COS 上传动作。
- 步骤失败后立即终止当前 Flow。

### 4.5 `test_gateway_flow.py`

- 不再写死 Flow 文件路径或具体执行步骤。
- 通过 FlowLoader 参数化加载全部 Flow。
- 每个 Flow/Scenario 配对生成一条 pytest 用例。
- 调用 FlowRunner 执行并把异常交给 pytest 展示。

### 4.6 `runtest.py`

- 保留 `--env`、`--module`、`--tag`。
- 新增 `--flow`，用于按 Flow 文件名筛选。
- 将参数透传给 pytest。

## 5. 日志设计

### 5.1 配置

```yaml
logging:
  level: INFO
  directory: logs
  console: true
  file: true
```

### 5.2 日志文件

```text
logs/20260717_153012_test_12345.log
```

一次执行只产生一个日志文件。单接口和多接口 Flow 都写入该文件。

### 5.3 单次请求日志

```text
Flow=AnonymousSessionMediaSearch
Scenario=图片与姓名联合搜索成功场景
Step=prepare_media (2/8)
Request=POST /gateway/invoke
Response=HTTP 200
Elapsed=235ms
```

请求和响应 JSON 紧随上下文信息输出。token、refresh token、Authorization 和签名 URL 参数继续使用现有脱敏规则。

## 6. Flow 与 Scenario 对应关系

```text
data/flows/AnonymousSessionMediaSearch.yaml
data/scenarios/AnonymousSessionMediaSearch.yaml
```

- 文件名必须一致。
- Flow 负责步骤顺序和控制。
- Scenario 负责业务输入和场景期望。
- case YAML 负责接口默认请求和默认断言。
- 一组 Flow + Scenario 对应一条 pytest 流程用例。

## 7. Flow YAML 最小格式

```yaml
name: 匿名会话媒体搜索流程
tags: [flow, media, search]
steps:
  - id: create_session
    call: CreateAnonymousSession.yaml

  - id: prepare_media
    call: PrepareMediaUpload.yaml
    extract:
      upload_url: $.upload_url
      upload_headers: $.upload_headers
      media_asset_id: $.media_asset_id

  - id: upload_media
    action: prepared_media_upload

  - id: create_task
    call: CreateIntentTask.yaml
    extract:
      task_id: $.task_id

  - id: poll_task
    call: GetTask.yaml
    until:
      path: $.status
      equals: SUCCEEDED
      interval_seconds: 2
      timeout_seconds: 120

  - id: wait_detail
    wait:
      seconds: 1

  - id: candidate_detail
    call: GetTaskCandidateDetail.yaml
```

每个步骤只能存在一种主动作：`call`、`action` 或 `wait`。

## 8. Scenario YAML 最小格式

```yaml
name: 图片与姓名联合搜索成功场景
variables:
  media_file: "${MEDIA_FILE}"
step_data:
  prepare_media:
    params:
      content_type: image/jpeg

  create_task:
    params:
      match_strategy: UNION
      clues:
        - type: FULL_NAME
          full_name_query:
            full_name: JOJO CCQQ MOCK
        - type: PHOTO
          photo_query:
            media_asset_id: "{{media_asset_id}}"
            photo_type_hint: face
    assert:
      data_equals:
        status: QUEUED
```

`step_data` 下的 key 必须是 Flow 中已经声明的 step ID。

## 9. 接口调用步骤

执行顺序：

1. 加载 `call` 指定的 case YAML。
2. 深拷贝 case，避免修改公共用例数据。
3. 使用 Scenario 的 `params` 覆盖 case 的默认 params。
4. 使用 RuntimeContext 解析 `{{变量名}}`。
5. 调用 `GatewayApi.execute()` 完成请求和默认断言。
6. 执行 Scenario 的 `data_equals` 断言。
7. 执行 Flow 步骤的 extract，将值写入 RuntimeContext。

参数合并只处理 `request.params`，不允许 Scenario 修改 `service_name` 和 `method_name`。

## 10. 断言设计

保留现有断言：

- `http_status`
- `gateway`
- `response`
- `data_fields`

增加场景断言：

```yaml
assert:
  data_equals:
    status: SUCCEEDED
    progress.stage: report_ready
```

- `data_fields` 调整为只检查字段存在，允许合法的空字符串、0、false 和空列表。
- `data_equals` 支持 `field.child` 和 `items[0].field` 路径。
- V1.2 不支持任意表达式、正则和脚本断言。

## 11. 固定等待与条件轮询

### 11.1 固定等待

```yaml
wait:
  seconds: 1
```

等待时间范围为 0～300 秒。

### 11.2 条件轮询

```yaml
until:
  path: $.status
  equals: SUCCEEDED
  interval_seconds: 2
  timeout_seconds: 120
```

- 重复执行当前步骤的接口。
- 每次先完成 HTTP、Gateway 和子响应基础断言。
- 条件满足后继续最终断言和变量提取。
- 超时后显示 step ID、调用次数、最后实际值和总耗时。

## 12. RuntimeContext 生命周期

```text
开始 Flow
  ↓
创建独立 RuntimeContext
  ↓
写入 Scenario 初始变量
  ↓
步骤请求引用变量 / 响应提取变量
  ↓
Flow 结束后释放
```

不同 Flow 不共享 `task_id`、`candidate_id` 等业务变量。自动会话仍复用现有创建和刷新逻辑。

## 13. 配置校验

发送请求前检查：

- Flow 与 Scenario 是否同名存在。
- Flow 是否包含 steps。
- step ID 是否重复。
- 每个步骤是否只有一种主动作。
- call 引用的 case 是否存在。
- Scenario 中的 step ID 是否存在于 Flow。
- extract、data_equals 和 until 路径是否合法。
- 等待与轮询参数是否合法。

配置错误直接让对应 pytest 用例失败，不发送请求。

## 17. 验收标准

1. 每次测试执行在 `logs/` 生成唯一日志文件，终端仍有日志。
2. 日志包含请求、响应、耗时和步骤信息，且不存在敏感凭证。
3. 新增同名 Flow/Scenario YAML 后无需修改 Python 即可被收集。
4. 前序接口提取值可以用于后续请求和断言。
5. 固定等待和条件轮询按配置运行，超时错误可定位。
6. 两条 Flow 的 RuntimeContext 相互隔离。
7. 现有单接口、自动会话、COS PUT 和命令行筛选能力无回归。
