# Gateway 接口自动化 V1.3 开发计划

## 1. 计划信息

| 项目 | 内容 |

| 需求依据 | `docs/接口自动化V1.3-PRD.md` |

## 2. 任务目标

完成接口定义与测试用例拆分，使单接口 Cases 和多接口 Flows 并列依赖 APIs，并支持一个接口维护多条独立单接口用例。

## 3. 成功标准

- 全部现有接口拥有独立 API 定义。
- 一个 case 集合可以被展开为多条 pytest 用例。
- Flow 只依赖 API 和对应 Scenario。
- 自动会话不依赖单接口 case。
- 迁移前后的有效请求参数、断言和流程顺序保持一致。
- 所有配置错误在发送请求前被发现。
- 全量自动化测试通过，真实环境验证按条件完成。

## 4. 交付物

- `data/apis/*.yaml`
- 5 个现有可独立执行接口对应的 V1.3 `data/cases/*.yaml`
- V1.3 格式的 Flow 和 Scenario
- API 定义加载器
- 单接口多 case 加载器
- 修改后的 Flow 加载器和执行器
- 修改后的会话管理和 pytest 入口
- V1.3 单元测试、集成测试
- 更新后的 README

## 5. 实施约束

1. 只实现 V1.3 PRD 已确认内容。
2. 不开发 Web、数据库、Allure、Jenkins 或通知能力。
3. 不维护 V1.2/V1.3 YAML 双格式兼容分支。
4. 不改变 Gateway 请求信封、HTTP 客户端和日志脱敏协议。
5. 新增和修改的 Python 代码使用清晰中文注释及 docstring。
6. 每个阶段先补测试或迁移校验，再修改正式实现。
7. 数据迁移只改变组织方式，不改变业务请求值和断言预期。

## 6. 当前基线

当前代码存在文件命名不一致：

- 真实 case 文件带 `01_`～`12_` 前缀。
- Flow、fixture 和部分测试引用无前缀文件名。

当前验证结果：

```text
python3 -m pytest -q
结果：收集失败
原因：Flow 引用的 CreateIntentTask.yaml 不存在

python3 -m pytest test_cases/test_framework.py test_cases/test_v12.py -q
结果：36 passed, 1 failed
原因：测试引用的 CreateAnonymousSession.yaml 不存在
```

该基线问题将在真实 YAML 一次性迁移阶段消除。开发完成后的全量测试必须由失败恢复为通过。

## 7. 分阶段计划

### 阶段 0：建立迁移基线

目标：在修改前固定现有接口数据和 Flow 实际合并行为，防止迁移遗漏。

工作项：

1. 记录 12 个现有 case 的文件名、接口名称、service、method、params、assert 和 extract。
2. 记录当前 Flow 的步骤顺序、case 引用、Scenario 覆盖参数、断言和提取。
3. 使用现有 `_deep_merge()` 规则计算每个 Flow API 步骤的最终 params 和 assert。
4. 将计算结果放入测试 fixture 或测试代码，不新建临时项目数据文件。
5. 保留当前全量收集失败信息，作为已知基线。

涉及文件：

- `test_cases/test_v13.py`（新增）
- 只读检查 `data/cases/*.yaml`
- 只读检查现有 Flow 和 Scenario

验证：

- 迁移快照覆盖全部 12 个接口。
- Flow 每个 API 步骤都有明确的最终 params 和 assert。
- 当前命名不一致问题可稳定复现。

完成条件：

- 后续迁移具备可自动比较的基准，而不是依赖人工逐字段检查。

### 阶段 1：实现 API 定义加载层

目标：提供 Cases、Flows 和会话共同使用的 API 注册表。

测试先行：

1. 正常加载多个 API。
2. API ID 与文件名不一致。
3. API ID 重复。
4. 必填字段缺失或类型错误。
5. API 出现 params、assert、extract、tags 等禁止字段。
6. 可执行 case 组装后不修改原对象。

实现：

1. 新增 `utils/custom/api_loader.py`。
2. 实现 `ApiConfigError`。
3. 实现 `load_api_definitions()`。
4. 实现 `build_execution_case()`。
5. 添加完整中文 docstring 和关键校验注释。

涉及文件：

- `utils/custom/api_loader.py`（新增）
- `test_cases/test_v13.py`

验证命令：

```bash
python3 -m pytest test_cases/test_v13.py -k api_loader -q
```

完成条件：

- API 注册表可以独立工作，不读取 Cases、Flows 或 Scenarios。

### 阶段 2：实现单接口多 case 加载层

目标：一个 case YAML 可展开多条独立 pytest 用例。

测试先行：

1. 一个文件展开两条以上 case。
2. 生成稳定 ID `ApiId::case_id`。
3. 每条 case 独立保留 tags、params、assert 和 extract。
4. 缺参和多参请求保持原样，不发生默认参数合并。
5. case ID 重复。
6. API 引用不存在。
7. 文件名与 API ID 不一致。
8. 空 cases、非法 params 和非法 tags。
9. 精确筛选存在或不存在的 case ID。

实现：

1. 新增 `utils/custom/case_loader.py`。
2. 实现 `CaseConfigError`。
3. 实现 `load_single_cases()`。
4. 调用 API Loader 组装 `execution_case`。
5. 所有返回对象使用深拷贝，避免 case 间污染。

涉及文件：

- `utils/custom/case_loader.py`（新增）
- `test_cases/test_v13.py`

验证命令：

```bash
python3 -m pytest test_cases/test_v13.py -k case_loader -q
```

完成条件：

- 临时测试目录中的 V1.3 case 集合可以正确展开和校验。

### 阶段 3：改造 Flow Loader

目标：Flow 在加载阶段只解析 API 引用，不读取 case 文件。

测试先行：

1. `api` 步骤正常加载。
2. 引用不存在 API 时失败。
3. V1.2 `call` 字段被明确拒绝。
4. API step 缺少 Scenario step_data、params 或 assert 时失败。
5. wait/action 错误配置 step_data 时失败。
6. extract、until 只能用于 API step。
7. 重复 step、孤立 Scenario、非法路径和未知 action 回归。
8. FlowCase 只携带当前流程引用的 API。

实现：

1. 修改 `_validate_flow()` 参数，由 cases 目录改为 API 注册表。
2. 主动作集合改为 `api`、`action`、`wait`。
3. 删除 case 文件存在性和 case extract 校验。
4. 增加 Scenario 完整步骤数据校验。
5. `load_flow_cases()` 调用 API Loader。
6. 返回当前 Flow 的 API 引用子集。

涉及文件：

- `utils/custom/flow_loader.py`
- `test_cases/test_v12.py`
- `test_cases/test_v13.py`

验证命令：

```bash
python3 -m pytest test_cases/test_v12.py test_cases/test_v13.py -k "flow_loader" -q
```

完成条件：

- Flow Loader 的代码和测试均不读取 `data/cases`。

### 阶段 4：改造 Flow Runner

目标：由 API 定义和 Scenario 完整数据直接执行 Flow。

测试先行：

1. API 路由与 Scenario params 正确组装。
2. params 不与任何 case 默认值合并。
3. 删除临时 `data/cases` 后 Flow 仍可执行。
4. params 和 assert 中的 RuntimeContext 变量可解析。
5. data_equals、extract 和后续步骤引用正常。
6. 固定等待、轮询成功、轮询超时和上下文隔离回归。
7. prepared_media_upload 回归。

实现：

1. 将步骤分支由 `call` 改为 `api`。
2. 删除 case YAML 读取。
3. 删除 `_deep_merge()`。
4. 使用 `build_execution_case()` 组装步骤对象。
5. 解析完整 params 和 assert。
6. extract 只读取 Flow step 配置。
7. 保留现有异常类型、日志、等待和上传逻辑。

涉及文件：

- `utils/custom/flow_runner.py`
- `test_cases/test_v12.py`
- `test_cases/test_v13.py`

验证命令：

```bash
python3 -m pytest test_cases/test_v12.py test_cases/test_v13.py -k "flow_runner or flow_isolation" -q
```

完成条件：

- Flow 执行路径中没有 `data/cases` 文件访问。

### 阶段 5：解除自动会话对 Cases 的依赖

目标：创建和刷新会话只依赖 API 定义及框架会话策略。

测试先行：

1. 临期 token 使用 RefreshSession API 定义。

4. 缺少会话 API 定义时错误包含 API ID。
5. 会话数据提取、上下文更新和 `.env` 持久化回归。

实现：

1. `GatewayApi.__init__()` 将 `session_cases` 调整为 `api_definitions`。
2. 添加最小内部会话请求组装策略。
3. `_execute_session_case()` 调整为基于 API ID 组装和调用。
4. 保留 session 字段、刷新阈值和失败回退逻辑。
5. 更新 fixture 和测试替身的构造参数。

涉及文件：

- `api/gateway_api.py`
- `test_cases/conftest.py`
- `test_cases/test_gateway_flow.py`
- `test_cases/test_framework.py`
- `test_cases/test_v13.py`

验证命令：

```bash

```

完成条件：

- 会话执行代码不再加载或接收单接口 case。

## 8. 测试矩阵

| 能力 | 单元测试 | 收集测试 | 真实请求 |
| --- | --- | --- | --- |
| API 定义加载 | 必须 | 必须 | 不需要 |
| 单接口多 case | 必须 | 必须 | 选定成功 case |
| 缺参/多参数据保持 | 必须 | 必须 | 后续按业务数据执行 |
| Flow 引用 API | 必须 | 必须 | 现有 Flow |
| Flow 与 Cases 隔离 | 必须 | 不需要 | 不需要 |
| RuntimeContext 传值 | 必须 | 不需要 | 现有 Flow |
| 自动会话 | 必须 | 不需要 | 选定真实接口 |
| 日志与脱敏 | 必须 | 不需要 | 抽查日志 |
| `--env`/`--tag`/`--flow` | 必须 | 必须 | 可选 |

## 9. 回滚方案

开发期间每个阶段保持改动边界清晰：

1. 加载器阶段只新增代码和临时目录测试，不修改真实 YAML。
2. Flow 和会话改造在迁移前通过构造数据单元测试。
3. 真实 YAML、pytest 入口和执行器在同一迁移阶段切换。
4. 如迁移验证失败，恢复该阶段涉及的 YAML 和入口代码，不修改 HTTP、日志或配置层。
5. 不使用破坏性 Git 命令，不覆盖用户与本任务无关的改动。
