## 一、概述

本文档描述产品 MVP 阶段的账号体系方案。MVP 阶段采用**无账号体系**设计，通过设备 UUID 标识用户身份，后续过渡到正式账号体系。

---

## 二、MVP 方案 —— 无账号体系

### 2.1 核心机制

MVP 阶段不引入传统注册/登录流程，而是通过**设备 UUID** 作为用户唯一标识：

| 环节           | 说明                                                            |
| ------------ | ------------------------------------------------------------- |
| **设备标识生成**   | App 第一次启动时，生成一个唯一的设备 UUID                                     |
| **免注册使用**    | 用户无需注册流程即可正常查询，生成历史记录                                         |
| **付费绑定**     | 付费时绑定 UUID，做收据校验                                              |
| **Token 签发** | 后端和 Apple 签发 `subscription_token`，关联设备 UUID + 收据 + 过期时间返回给客户端 |
| **请求校验**     | 客户端携带 token，后端校验有效性（适用于所有订阅拦截场景）                              |
| **数据存储**     | 历史记录存储在**后端数据库**                                              |

### 2.2 重装恢复

- 用户重装 App 后，**Keychain 中的 UUID 仍然存在**
- 调用 `restore` 接口重新激活订阅
- 无需用户手动操作，自动恢复

## 三、双端设备 ID 生成方案参考

#### 3.1 iOS 方案流程

```
App 首次启动
    │
    ▼
生成 device_uuid
    │
    ▼
存储到 Keychain（持久化）
    │
    ▼
后续启动：从 Keychain 读取 UUID
    │
    ├── App 卸载重装 → Keychain 数据保留 → UUID 不变 → 订阅状态恢复
    │
    └── 正常使用 → UUID 一致 → 正常校验
```

## 四、风险分析

### 4.1 风险一：订阅无法跨设备 / 重装丢失

| 项目       | 说明                               |
| -------- | -------------------------------- |
| **问题描述** | 用户换手机或卸载重装后，设备 ID 变化，之前购买的订阅找不回来 |
| **解法**   | 提供「恢复购买」按钮，通过商店收据重新绑定新设备 ID      |

### 4.2 风险二：无法防刷 / 成本失控

| 项目       | 说明                                                           |
| -------- | ------------------------------------------------------------ |
| **问题描述** | 没有账号体系，恶意用户可以不断重置设备 ID，反复利用免费试用或首周优惠，套取大量深度查询（每次查询都有 API 成本） |
| **解法**   | 限制同一设备 / 支付 ID 的权益次数                                         |
