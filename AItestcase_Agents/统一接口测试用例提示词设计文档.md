# 统一接口测试用例生成提示词 v2.0 设计文档

## 一、设计背景与目标

本次重新设计基于对现有提示词的系统性分析，结合项目中的两篇核心文档《1、怎么设计接口的测试用例_.md》和《3、对于接口的参数，你是怎么去做检查？.md》的最佳实践，完成了一次全面且可行的提示词重构。

原有提示词存在三个核心问题：概念定位模糊导致职责边界不清，规则过于繁琐限制了AI的创造性输出，测试场景设计过度偏向异常测试而忽视了探索式测试的本质需求。这些问题不是简单的参数调整能够解决的，而是需要重新思考提示词的设计哲学。

新的设计采用**单阶段生成模式**，直接根据接口文档生成完整的可执行测试用例，省略了原有的两阶段转换流程（基础用例→可执行用例），从根本上解决了信息损耗和上下文丢失的问题。同时，新设计明确了探索式测试的核心定位：测试的首要目标是了解接口的实际行为，而不是预设断言让AI去验证。

## 二、核心设计理念

### 2.1 探索式测试模式

新提示词遵循探索式测试的核心原则，强调三个关键点：首要目标是了解接口的实际行为，记录真实的响应数据供测试人员判断；不预设断言，让测试人员根据实际响应自行判断接口是否符合预期；测试驱动开发，先发现接口实际表现，再确定期望行为。

这种设计理念完全符合用户的使用场景——新上传的接口本身就没有既定的期望结果，测试人员需要的是先用起来，看看接口返回什么，再判断是否有问题。原有的断言设计在这个场景下确实是无根之木。

### 2.2 测试层次与类型分类体系

新提示词建立了一套完整的测试分类体系，解决了原有设计中测试点分类混乱的问题。测试层次按粒度从粗到细分为五级：

**L1-接口层测试**验证接口的基本功能和协议合规性，关注HTTP方法是否正确、URL路径和参数是否正确、Content-Type是否与请求体匹配、基础鉴权是否生效。这是所有接口测试的基线，确保接口能够正常访问。

**L2-参数层测试**验证参数的处理逻辑，覆盖必填参数校验、参数类型校验、参数格式校验、参数长度校验、边界值处理。这是新接口最容易出问题的地方，也是测试人员最需要关注的内容。

**L3-业务层测试**验证业务逻辑的正确性，包括参数间依赖关系、状态流转验证、权限控制检查、业务流程完整性。这部分需要结合具体的业务场景来设计。

**L4-安全层测试**验证接口的安全性，包括SQL注入尝试、XSS攻击尝试、路径遍历尝试、特殊字符处理、未授权访问。这部分仅对涉及用户输入的接口生成，不需要对所有接口都做安全测试。

**L5-异常层测试**验证异常情况的处理，包括错误参数组合、重复提交处理、并发请求处理、超时场景、网络异常。这部分根据接口特点选择性生成。

测试类型按目标分为四类：**T1-正向测试**验证正常场景下的功能正确性，使用有效参数发起请求，验证返回状态码为2xx，记录完整的响应数据结构。**T2-异常测试**验证异常输入的处理，包括缺失必填参数、参数类型错误、参数格式错误、空值和null值、错误的数据组合。**T3-边界测试**验证边界条件，包括数值边界、字符串长度边界、集合大小边界、时间边界。**T4-组合测试**验证多参数组合场景，包括多个参数同时异常、参数间存在依赖关系、状态相关的参数组合、跨接口的数据组合。

这种分类体系的好处是结构清晰、覆盖全面、便于评估测试覆盖的完整性。每个生成的测试用例都可以用"[层次]-[类型]"的格式命名，如L2-T2-参数缺失-用户名必填、L4-T4-SQL注入-字符串参数。

## 三、参数检查方法体系

### 3.1 与《参数检查》文档的结合

新提示词系统地整合了《3、对于接口的参数，你是怎么去做检查？.md》中提出的五大类检查方法：

**基础验证**部分包含必填参数检查，逐一置空每个必填参数进行验证；参数类型验证，注入错误类型的数据如期望字符串输入数字；空值处理测试，验证null和空字符串的处理逻辑和默认值生效情况。

**边界值分析**针对不同参数类型给出具体的测试值建议：整数类型测试0、±1、最大值、溢出等边界点；字符串类型测试0字符、1字符、最大长度、超长字符串；数组类型测试空数组、单元素、最大数量；特殊值如0、负数、科学计数法表示的数值。

**安全性考虑**覆盖了文档中强调的SQL注入、XSS攻击、路径遍历、特殊字符处理等场景，这是原有提示词中相对薄弱的部分，新设计进行了重点加强。

**业务逻辑检查**涵盖参数依赖关系如修改密码需要旧密码、状态约束如订单完成后不能修改、权限检查如只有管理员能删除数据、业务规则如用户名不能重复等。这些内容在原有设计中没有被明确提出。

**异常场景处理**包括错误参数组合、重复提交处理、并发请求处理如多线程重复提交同一接口同一参数，这些在原有设计中也是缺失的。

### 3.2 参数来源分析原则

新提示词明确了参数来源的四种渠道，这是生成高质量测试用例的关键：前置接口返回的参数需要在`preconditions.extract`中定义提取规则，主请求中用`${{变量名}}`引用；测试数据必须使用`${{变量名}}`形式引用，不能硬编码；动态生成的数据需要写在`setup_script`中，通过`test.save_test_env_variables`保存；敏感参数如密码必须从前置接口或动态生成，不能硬编码到代码中。

常见的依赖参数类型包括认证令牌（token、access_key、authorization）、资源ID（user_id、order_id、project_id、file_id）、状态标记（status、step、phase、progress）、关联对象（reference_id、parent_id、related_id）。

## 四、与《接口测试用例设计》文档的结合

### 4.1 继承的方法论

新提示词继承了《1、怎么设计接口的测试用例_.md》中提出的系统性测试思维，主要体现在三个方面：

首先是**单接口测试与多接口测试的结合**。单接口测试关注参数校验、正常功能、异常情况、边界值、幂等性；多接口测试关注正向业务流程、逆向/异常流程、并发场景、数据一致性。新提示词中的L1-L5层次分类实际上涵盖了这两个维度的内容。

其次是**测试点覆盖的全面性**。文档中强调的测试点在新提示词中都有对应的体现：正常请求对应T1正向测试、参数缺失对应L2-T2异常测试、参数格式错误对应L2-T2异常测试、边界值对应T3边界测试、未授权访问对应L4-T4安全测试、错误数据类型对应L2-T2异常测试、空字符串和null值对应L2-T2异常测试。

最后是**用例命名和描述的规范性**。文档中的面试回答框架强调用例要清晰、可追溯，新提示词要求用例命名采用`[层次]-[类型]-[场景]-[输入]`的格式，描述要包含测试目标、观察要点和探索点。

### 4.2 新增的内容

新提示词在继承的基础上也新增了文档中没有明确提到的内容，包括：明确的测试层次分类体系（L1-L5），让测试覆盖更有系统性；安全层测试（L4）的独立分类，这是文档中一笔带过但实际很重要的一部分；测试用例质量标准（独立性、可重复性、清晰性、可追溯性），确保生成的用例真正可用；覆盖率要求的具体量化指标，如L1接口层100%覆盖、L2参数层必填参数100%等。

## 五、预期交付成果

### 5.1 测试用例集结构

每个生成的测试用例包含以下字段：

`name`字段格式为`[层次]-[类型]-[场景]-[输入]`，例如`L2-T2-参数缺失-用户名必填`、`L4-T4-SQL注入-字符串参数`。这种命名方式让测试人员一眼就能看出用例的类型和测试目标。

`description`字段包含测试目标、观察要点和探索点三部分内容。测试目标说明验证什么、期望什么结果；观察要点告诉测试人员重点关注哪些方面；探索点引导测试人员思考可能存在的问题。

`interface`字段填写接口路径，与被测主接口对应。

`preconditions`数组定义前置依赖接口，每个依赖接口包含名称、完整请求配置、数据提取规则。这是正确处理接口依赖的关键。

`request`字段包含主接口的完整请求配置，包括接口ID、HTTP方法、URL、请求头、查询参数、请求体、文件上传、前置脚本、后置脚本。

### 5.2 用例质量标准

新提示词为生成的测试用例设定了四个质量标准：

**独立性**要求每个用例可单独执行，不依赖其他用例的执行结果。这通过正确配置`preconditions`来实现。

**可重复性**要求相同输入产生相同结果。这要求测试数据使用变量引用而不是硬编码。

**清晰性**要求命名和描述无歧义。`[层次]-[类型]-[场景]-[输入]`的命名格式和包含三要素的描述确保了这一点。

**可追溯性**要求与接口文档字段一一对应。提示词中明确要求检查每个参数是否在接口文档中有定义。

### 5.3 覆盖率要求

新提示词给出了具体的覆盖率要求：

L1接口层要求100%覆盖，确保每个接口都能正常访问。

L2参数层要求必填参数100%覆盖，可选参数80%覆盖。必填参数的遗漏是最常见的bug来源。

L3业务层要求核心业务流程100%覆盖。这部分需要人工确认哪些是核心流程。

L4安全层要求关键接口100%覆盖。哪些是关键接口需要根据业务判断。

L5异常层要求异常路径覆盖率≥60%。异常场景很多，不需要全部覆盖，但需要覆盖主要的异常路径。

## 六、生成策略

### 6.1 生成优先级

新提示词给出了明确的生成优先级指导：

首先**优先覆盖L1-T1正向测试**，确保核心功能可正常访问。这是所有测试的基础，如果正向测试都不通过，其他测试就没有意义。

其次**重点覆盖L2-T2和T3参数异常和边界**，这是新接口最容易出问题的地方。测试人员最需要关注的就是参数处理是否正确。

然后**选择性覆盖L4-T4安全**，仅对涉及用户输入的接口生成。不是所有接口都需要做安全测试，安全测试的成本也比较高。

接着**业务关联覆盖L3-T2**，根据依赖接口的业务逻辑生成。这部分需要结合具体的业务场景。

最后**探索性覆盖L5**，根据接口特点选择性生成。L5的内容可以作为补充，不需要全部覆盖。

### 6.2 生成数量建议

根据接口复杂度，给出以下生成数量建议：

简单接口（5个以下参数、无复杂依赖）建议生成5-8个用例，包括2-3个正向用例、2-3个参数异常用例、1-2个边界值用例。

中等复杂度接口（5-10个参数、有依赖关系）建议生成10-15个用例，包括3-4个正向用例、4-5个参数异常用例、2-3个边界值用例、1-2个业务逻辑用例、1个安全用例。

复杂接口（10个以上参数、多层依赖）建议生成15-25个用例，包括4-5个正向用例、6-8个参数异常用例、3-4个边界值用例、2-3个业务逻辑用例、2-3个安全用例、1-2个异常场景用例。

## 七、输出格式要求

### 7.1 JSON格式约束

新提示词对输出格式有以下约束：

输出必须是合法的JSON数据，不能带markdown格式标记如```json。

输出的用例字段不得遗漏或虚构新增。每个字段都有明确的定义，不能随意添加新字段。

格式必须严格遵循Schema定义，字段顺序和结构都要一致。

空对象和空数组必须显式写出，不能省略。

### 7.2 字段类型规范

各字段的类型规范如下：

name字段为string类型，格式为`[层次]-[类型]-[场景]-[输入]`。

description字段为string类型，包含测试目标、观察要点、探索点三部分。

interface字段为string类型，为接口路径字符串。

preconditions字段为array类型，元素为前置依赖接口对象。

request字段为object类型，包含完整的请求配置。

## 八、代码修改说明

### 8.1 新增文件

本次重新设计新增了以下文件：

**config/prompts/api_cases_work/unified_api_case_generator.py**是新的统一提示词文件，包含完整的提示词模板和输出格式定义。这个文件整合了原有的`base_case_generator.py`和`api_case_generator.py`的功能，采用单阶段生成模式。

**workflow/unified_testcase_workflow.py**是新的统一测试用例生成工作流，包含完整的生成、保存、输出逻辑。这个工作流替代了原有的两阶段工作流。

**config/prompts/api_cases_work/__init__.py**是提示词模块的初始化文件，导出了所有提示词模块供外部使用。

### 8.2 保留的原有文件

原有文件保留未做修改，以保证向后兼容：

**config/prompts/api_cases_work/base_case_generator.py**和**config/prompts/api_cases_work/api_case_generator.py**继续可用，用户可以选择使用原有流程或新流程。

**workflow/api_basecase_workflow.py**和**workflow/api_case_generator_main_workflow.py**继续可用，支持原有的两阶段生成流程。

### 8.3 使用新提示词的方法

用户可以在自己的代码中按以下方式使用新的统一提示词：

```python
from workflow.unified_testcase_workflow import UnifiedTestCaseGeneratorWorkflow

# 准备输入数据
input_data = {
    "api_doc": "接口文档内容...",
    "project_apis": [其他接口文档列表],
    "test_data": {"base_url": "http://example.com"},
    "files_list": ["可用文件列表"],
    "function_list": ["random_mobile()", "random_email()"],
    "additional_info": "补充说明",
    "interface_id": 12345
}

# 创建工作流
workflow = UnifiedTestCaseGeneratorWorkflow().create_workflow()

# 执行工作流
result = workflow.stream(input_data, stream_mode=["messages", "custom"])

# 处理结果
for chunk in result:
    if chunk[0] == "messages":
        print(chunk[1][0].content)
    elif chunk[0] == "custom":
        print(chunk[1])
```

## 九、与原有设计的对比

### 9.1 流程对比

原有设计采用两阶段生成流程：第一阶段由`base_case_generator.py`生成基础用例（测试步骤描述），第二阶段由`api_case_generator.py`将基础用例转换为可执行用例。这种设计的问题在于信息损耗（从步骤描述到完整请求，中间有大量信息需要AI推断）、两倍的成本（需要两次LLM调用）、更长的生成时间。

新设计采用单阶段生成流程，直接从接口文档生成完整的可执行测试用例。好处是信息不损耗、一次LLM调用、更快的生成速度。

### 9.2 测试分类对比

原有设计的测试点分类混乱，测试点之间存在交叉和重复。

新设计建立了清晰的L1-L5层次分类和T1-T4类型分类，覆盖全面且便于评估。

### 9.3 参数检查对比

原有设计对参数检查方法的描述较为分散，没有形成体系。

新设计系统地整合了五大类参数检查方法：基础验证、边界值分析、安全性考虑、业务逻辑、异常场景。

### 9.4 质量标准对比

原有设计没有明确的用例质量标准。

新设计明确了独立性、可重复性、清晰性、可追溯性四个质量标准，以及各层次的覆盖率要求。

## 十、后续优化建议

### 10.1 提示词的迭代优化

建议在正式使用过程中收集反馈，对提示词进行迭代优化。可能的优化方向包括根据实际生成的用例质量调整规则描述、根据业务特点增加特定领域的检查规则、根据测试人员的反馈优化用例命名和描述格式。

### 10.2 与现有系统的集成

新提示词可以与现有的数据库、测试执行框架集成。提示词中定义了`setup_script`和`teardown_script`的规范，这些规范与现有的`BaseTestCase`执行器完全兼容。

### 10.3 测试用例的管理

建议建立测试用例的版本管理机制，每次生成的新用例应该能够与历史用例进行对比，便于测试人员评估新增用例的质量和必要性。
