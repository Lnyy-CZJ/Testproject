# 检索系统评估方案

## 1. 评估目的

本方案用于回答六个核心问题：

1. 检索是否返回了候选人结果，即本次检索是“有候选人”还是“无候选人”；
    
2. 返回的候选人中是否包含已知的基准候选人，即检索是否成功；
    
3. 命中的基准候选人返回了多少已知信息，即信息完整度；
    
4. 命中的基准候选人所返回的信息有多少是正确的，即字段准确率；
    
5. 其他未命中基准候选人的同名候选人，各自返回了多少信息，即非命中候选人信息完整度；

6. 每次检索产生了多少 LLM 成本、第三方调用成本和总成本，检索耗时多久、是否调用
   PDL，以及100个人全部检索的累计成本、时长和PDL调用情况。
    

“有候选人结果”只表示系统返回了一个或多个候选人，不表示已经命中基准候选人。
只有检索结果不为空时，才继续对候选人进行命中判断、完整度和准确率计算。非命中候选人
也可能是其他用户真正想查询的人，因此不能只关注基准候选人。候选人置信度、成本、
检索时长和 PDL 调用用于辅助评估结果与资源消耗，但不参与候选人信息完整度和字段准确率
计算。

## 2. 核心概念

### 2.1 基准候选人

基准候选人是测试前已经掌握确切信息的目标人物。

例如，测试人物为 JOJO，测试前已经整理好 JOJO 在以下模块中的已知信息：

- `insights`
    
- `photos`
    
- `profile`
    
- `social`
    
- `summary`
    

这些已知信息共同构成 JOJO 的基准数据，用于判断检索结果中的某个候选人是不是 JOJO，以及候选人的信息是否完整、准确。

### 2.2 评估字段

本方案使用 `字段整理.md` 中整理的实际返回字段。该文件当前定义的是五个业务模块：

- `Insights`
    
- `Photos`
    
- `Profile`
    
- `Social`
    
- `Summary`
    

五个模块共有 26 个原始字段：

|   |   |
|---|---|
|模块|原始字段|
|Insights|insights_status、insights_description、insights_links|
|Photos|photos_status、photos_baseline_photo_url、photos_identity_match_rate、photos_authenticity_photos、photos_match_photos|
|Profile|profile_status、profile.Identity.Full Name、profile.Identity.Age、profile.Identity.Location、profile.Identity.Email、profile.Identity.Profile URL、profile.Career.Current Role、profile.Background.Education、profile.Career.Other Roles|
|Social|social_status、social_display_handles、social_platforms、social_urls|
|Summary|summary_avatar_url、summary_confidence_level、summary_primary_image_url、summary_social_links、summary_web_links|

评估字段可以来自不同模块，但需要满足以下条件：

- 字段在测试前已经有明确、可验证的基准值；
    
- 字段名称、数据格式和比较方法保持固定；
    
- 多值字段需要提前拆分出具体信息项；
    
- 所有正式评估阶段和检索条件使用相同的22个内容字段。
    

如果 social link 或照片 URL 被用作本次查询条件，系统对该输入值的直接回显不计入完整度或准确率；只有能够确认该信息来自实际检索结果时才参与评分。直接回显的字段按空值处理，避免查询条件自动增加完整度。

22个内容字段的来源路径、中文含义和内容格式以 `字段整理.md` 为准，本文不重复维护第二份字段路径定义。

候选人置信度、成本、检索时长、PDL调用情况和五个模块的证据来源属于独立公共字段，
不计入上述22个内容字段的完整度或准确率分子、分母。

### 2.3 候选人结果

检索 JOJO 后，系统可能不返回任何候选人，也可能返回多个名称相同或相似的候选人。
每个候选人都可以包含 `insights / photos / profile / social / summary` 等模块的数据。

评估时必须逐个候选人处理，不能把多个同名候选人的信息拼在一起计算：

- 无候选人结果：记录本次检索为 `NO_CANDIDATES`，检索成功记为0，候选人完整度和
  准确率记为“不适用”；

- 命中基准候选人：计算基准候选人信息完整度和字段准确率；
    
- 未命中基准候选人：计算该候选人自身的非空信息完整度，不计算准确率；
    
- 疑似基准候选人：当前统计时仍按未命中处理，并在复核说明中标记“疑似”。
    

### 2.4 独立公共字段

除候选人的22个内容字段外，每次检索还需要单独收集任务成本、检索时长、PDL调用情况、
候选人置信度和候选人证据来源。

#### 检索任务级字段

任务级字段按一次 `task_id` 记录一次，不能复制到每个候选人后重复累计：

|   |   |   |
|---|---|---|
|逻辑字段|含义|当前来源|
|llm_cost|本次检索产生的 LLM 成本|检索任务接口返回字段|
|third_party_cost|本次检索调用第三方服务产生的成本|检索任务接口返回字段|
|total_cost|本次检索产生的全部成本|检索任务接口返回字段|
|search_duration_ms|本次检索的检索时长，统一记录为毫秒|检索任务接口返回字段|
|pdl_called|本次检索是否调用 People Data Labs|检索任务接口返回字段|
|provider_summary|本次检索调用的数据提供方摘要|当前样例可见于 或 ListTaskCandidates 的 responses[0].data.provider_summary|

如果成本或检索时长字段缺失，本次记录应留空或标记“未返回”，不能按0处理。失败或
重试任务如果产生了成本和时长，也应按实际接口返回记录。

#### 候选人级公共字段

每个候选人单独记录：

|逻辑字段|含义|当前来源|
|---|---|---|
|candidate_confidence|检索系统对该候选人的置信度|候选人接口返回字段|

候选人置信度不计入22个内容字段，不参与完整度或准确率计算，作为候选人结果的辅助观察
数据保存。

#### 候选人模块证据来源字段

每个候选人按五个模块分别收集证据来源：

|   |   |   |
|---|---|---|
|逻辑字段|收集内容|当前可用来源|
|insights_evidence_sources|Insight事实对应的公开链接、标题、平台或provider|ui_sections.insights.data.items[].links|
|photos_evidence_sources|照片来源页、图片匹配来源和provider|authenticity_photos[].source_url、match_photos[]及详情顶层 evidence 中的图片证据|
|profile_evidence_sources|姓名、地区、职业、教育等Profile字段的来源|详情顶层 evidence 中的provider、URL、subject_profile_url等；待接口补充明确模块映射|
|social_evidence_sources|社交账号的来源provider及主页URL|详情顶层 social_accounts、evidence或后续接口专用字段|
|summary_evidence_sources|Summary所引用的社交链接、网页链接和主图来源|summary_social_links、summary_web_links、summary.data.primary_image.source|
|candidate_evidence_raw|无法可靠归属模块的原始证据|GetTaskCandidateDetail.responses[0].data.evidence完整对象|

证据来源字段用于支持人工核验和追溯，不增加候选人的信息完整度，也不直接参与字段准确率计算。无法明确归属模块的证据只保存在 `candidate_evidence_raw`，不能凭猜测分配给某个模块。

当前 `searchTool` 的成功结果主要保存 `ui_sections`，还需要完整保留候选人置信度、
任务级成本、第三方调用成本、检索时长、`provider_summary`、详情顶层 `evidence`
和 `social_accounts`，才能完成本方案中的统计。

### 2.5 基准数据来源调研与收集方法（讨论稿）

本节仅用于帮助产品、开发和测试初步了解可选的数据源，以及这些数据源大致能够为
基准候选人提供哪些信息。当前不在方案中展开具体采购、收集和数据治理流程。

#### 2.5.1 数据源的优缺点

|数据源|优点|缺点|初步定位|
|---|---|---|---|
|Diffbot Knowledge Graph|人物字段类型较丰富，可以同时提供职业、教育、多平台Social、图片、网页链接以及部分来源信息|普通人的公开信息不一定丰富，不保证每个人、每个字段都有数据；部分人物信息仍可能需要确认|较适合作为基准候选人及其综合信息的主要调研来源|
|Coresignal Multi-Source Employee Data|职业人物数据较强，工作经历、教育、地区、职位和职业主页等信息相对集中|主要覆盖有公开职业资料的人；多平台Social、个人图片和非职业信息通常弱于Diffbot|较适合作为职业、教育和地区信息的调研来源|
|Social Links / ShadowDragon|擅长跨平台账号、用户名、别名和图片线索的辅助调查，有助于判断不同账号或照片是否可能属于同一个人|更接近调查工具，而不是字段稳定、可批量购买的标准人物数据集；结果完整度和使用成本需要另行确认|适合作为Social账号和照片身份的辅助确认工具|
|用户历史检索候选人|可以直接取得真实用户已经搜索过的人物和系统实际返回字段，便于持续复测|候选人字段可能不完整，首次结果本身不能证明所有字段都准确|适合作为持续观察候选人字段完整度变化的基准样本|

以上结论属于初步调研判断，后续是否采用仍需要结合实际样例进行讨论。

#### 2.5.2 可以收集的基准候选人信息

|数据源|可以重点收集的信息|对应本方案的主要模块|
|---|---|---|
|Diffbot Knowledge Graph|姓名、公开年龄或出生日期、地区、当前及历史职位、教育经历、人物简介、Profile URL、个人主页、多平台Social URL或账号、头像及其他公开图片、相关网页链接、部分来源与更新时间|Profile、Social、Photos、Insights、Summary及证据来源|
|Coresignal Multi-Source Employee Data|姓名、地区、当前职位、工作经历、教育经历、职业简介、职业Profile URL、Profile头像以及记录更新时间|以Profile为主，可补充部分Photos、Summary和证据来源|

Social Links / ShadowDragon 主要用于补充跨平台Social账号、用户名、别名和照片线索，
不预期由它们提供一个候选人的全部六大模块数据。

#### 2.5.3 不要求每个基准候选人达到100%信息完整度

基准数据来自人物在公开网络中实际存在且能够确认的信息，因此单个基准候选人的字段
完整度通常不会达到100%。不同候选人的公开信息量不同，例如：

- 候选人A可能有完整的职业、教育和LinkedIn信息，但缺少其他Social和照片；
- 候选人B可能有多个Social账号和照片，但年龄、教育或历史工作经历为空；
- 候选人C可能只能确认姓名、地区、职位和一个Social Link。

因此，基准候选人不要求具有完全相同的字段。每个人应记录其已经确认的
`baseline_available_fields`，没有收集到或无法确认的字段不作为该候选人的基准字段。
后续计算命中候选人完整度时，以该候选人实际拥有且已确认的基准字段为分母。

同一个候选人在不同检索阶段和不同系统版本中，应继续使用同一组已确认基准字段进行
对比；不同候选人则按照各自的基准字段范围分别计算，避免因为原始公开信息量不同而
直接比较非空字段数量。

#### 2.5.4 使用用户历史检索候选人建立持续观察基准

后续可以从用户已经完成的历史检索中，拉取并固定一批可识别的候选人。将每个候选人
首次保存时已经返回的字段作为该候选人的初始基准，即使字段不全，也可以在系统优化后
再次检索同一个人，观察其候选人信息是否发生变化。

主要对比内容包括：

- 同一候选人返回的非空字段数量是否增加；
- Insights、Photos、Profile、Social、Summary各模块的字段是否变得更完整；
- 原来已有的字段是否仍然保留；
- 新增字段、减少字段和发生变化的字段分别有哪些。

这类历史候选人基准主要用于持续观察字段完整度变化。首次检索中没有返回的字段不能
直接认定为现实中不存在；系统优化后新增的字段也需要进一步确认后，才能用于字段准确率
评价。为保证前后比较的是同一个人，应保存稳定的候选人标识以及可以确认身份的Social
Link或照片等信息。

#### 2.5.5 待讨论事项

1. Diffbot与Coresignal实际样例中，哪一个更符合本次欧美普通人的基准数据需求；
2. 是否以一个数据源为主，另一个数据源只用于补充缺少的信息；
3. 每个候选人至少确认哪些身份信息后，才可以作为正式基准候选人；
4. Social Links / ShadowDragon是否只用于少量Social或照片难以确认的候选人；
5. 第一批从用户历史检索中选取多少候选人作为持续观察样本。

## 3. 三个评估阶段

本方案中的“阶段”改为检索系统的评估与优化周期，不再直接代表某一种检索条件。
为避免数据字段混淆：

- `evaluation_phase` 表示第一、第二或第三评估阶段；
- `query_stage` 继续表示 `FULL_NAME`、`FULL_NAME_SOCIAL`、
  `FULL_NAME_PHOTO` 等具体检索条件。

### 3.1 第一阶段：优化前的基础能力探索

第一阶段用于建立检索功能优化前的基线，回答“当前系统在没有优化时具备什么能力”。

|检索条件|执行要求|目的|
|---|---|---|
|全名（`FULL_NAME`）|必做|观察只提供姓名时能否找到基准候选人，以及返回信息的完整度和准确率|
|全名 + Link（`FULL_NAME_SOCIAL`）|待产品、开发与测试评审决定|如第一阶段执行，可同时建立带Link条件的优化前基线|

第一阶段是否加入“全名 + Link”必须在正式执行前确定，并冻结到本阶段Dataset中。
如果第一阶段不执行该条件，后续首次加入Link时只能评价“增加线索后的效果”，不能称为
“全名 + Link检索的优化前后提升”。

### 3.2 第二阶段：优化后复测与新增线索实验

第二阶段在检索功能完成一轮优化后执行，同时完成两类测试：

1. **同条件复测**：重新执行第一阶段已经执行过的全部检索条件，使用相同的
   `person_id + query_stage`、Query文本、基准数据和评分口径，与第一阶段进行
   一一配对，判断系统优化本身带来的变化。
2. **新增线索实验**：在优化后版本增加第一阶段未使用的Link或照片线索，观察增加
   线索后检索结果是否改善。

新增线索实验按以下情况选择：

- 第一阶段只有全名：第二阶段在复跑全名后，可新增“全名 + Link”；照片功能可用后，
  也可新增“全名 + 照片”；
- 第一阶段已经执行全名和全名 + Link：第二阶段必须复跑这两个条件；如照片功能已经
  完成并通过评审，可再新增“全名 + 照片”；
- 当前 `searchTool v1.3 MVP` 支持 `FULL_NAME` 和 `FULL_NAME_SOCIAL`，
  暂不支持 `FULL_NAME_PHOTO`。照片条件只有在功能完成、输入链路和回显规则确认后
  才能进入正式实验。

第二阶段报告必须把“同条件版本对比”和“优化后新增线索对比”分开。前者回答系统是否
优化，后者回答额外线索是否有帮助，不能将二者合并归因为检索功能优化。

### 3.3 第三阶段：根据报告确定下一轮测试

第三阶段不提前固定检索条件。先根据第一、第二阶段的配对报告，识别需要继续优化的
具体方面，再决定第三阶段测试什么。

第三阶段开始前必须形成一份简要测试定义，至少确定：

- 本轮要改善的问题，例如召回不足、错误Social Link、信息不完整、准确率下降、
  结果不稳定或成本过高；
- 对应的目标样本和典型失败案例；
- 需要回归的已有检索条件，以及需要新增的线索或场景；
- 沿用或更新的基准数据、字段配置和判定规则版本；
- 本轮成功标准和不允许发生的退化。

第三阶段仍需保留与上一阶段相同条件的回归组，新增测试只能作为补充组。只有相同条件、
相同样本和相同口径之间才能继续计算版本提升；临时新增的条件只能做同版本横向观察或
作为下一轮基线。

## 4. 如何判断候选人是否命中基准候选人

### 4.1 名字相同不能单独证明命中

因为检索条件本身包含 JOJO 的名字，而且结果中可能出现多个同名人物，所以名字相同只能用于初步筛选，不能单独用于确认身份。

### 4.2 Social link 强绑定规则

Social link 使用 `social_urls` 和 `summary_social_links` 中的链接，与基准候选人的已知 social links 进行比较。

比较前应对 URL 做统一处理，例如去除首尾空格、末尾 `/` 和不影响账号身份的跟踪参数，避免同一主页因格式不同被误判。

判定规则：

- 候选人至少有一个 social link 与基准候选人一致：可以判定为命中；
    
- 候选人与基准候选人存在同一个社交平台，但该平台 link 不一致：判定为不命中；
    
- 候选人的 social links 为空，或者没有可与基准平台比较的链接：social 规则无法判断，继续检查照片规则。
    

同平台 link 不一致属于明确身份冲突，优先级高于其他普通字段。即使姓名、地区、职位等字段一致，也不能覆盖该冲突。

### 4.3 照片相似度强绑定规则

照片使用 `photos_identity_match_rate` 判断。统一将返回值转换为百分比后：

```Plain
照片相似度 >= 80%：可以判定为命中
照片相似度 < 80%：不能通过照片判定为命中
照片相似度为空：照片规则无法判断
```

如果已经发现同平台 social link 不一致，则仍然判定为不命中，不再由照片相似度覆盖 social 冲突。

### 4.4 最终判断顺序

对每个同名候选人按以下顺序判断：

1. 如果存在同平台 social link 不一致，判定为不命中；
    
2. 否则，如果至少一个 social link 与基准候选人一致，判定为命中；
    
3. 否则，如果 `photos_identity_match_rate >= 80%`，判定为命中；
    
4. 如果 social links 和照片相似度都为空，即使其他字段全部或部分一致，也只能认为“疑似基准候选人”；当前统计时按不命中处理；
    
5. 其他情况判定为不命中。
    

可以将“疑似”写入人工复核说明，但检索成功字段仍记录为 `0`，不计入成功次数。

### 4.5 强绑定字段以外的信息如何使用

Profile、Insights、Summary 等其他字段不参与当前版本的命中判定，只在候选人命中后用于计算信息完整度和字段准确率。

因此，即使某个候选人有很多普通字段与 JOJO 一致，只要 social links 和照片都无法满足强绑定规则，当前仍按不命中处理，后续可以按疑似命中候选人处理。

## 5. 核心评估项的计算方法

### 5.1 检索有结果率与无结果率

首先判断一次检索是否实际返回候选人。结果状态统一分为：

```Plain
HAS_CANDIDATES：检索正常完成，候选人数大于或等于1
NO_CANDIDATES：检索正常完成，但候选人数为0
EXECUTION_FAILED：接口失败、超时或无法取得候选人列表
```

`EXECUTION_FAILED` 是执行异常，不等同于“正常检索但没有候选人”，需要单独统计。

按评估阶段、系统版本和检索条件汇总：

```Plain
有结果率 = HAS_CANDIDATES次数 / 可判定结果的检索次数 * 100%

无结果率 = NO_CANDIDATES次数 / 可判定结果的检索次数 * 100%

可判定结果的检索次数 = HAS_CANDIDATES次数 + NO_CANDIDATES次数
```

例如100次检索中，90次返回候选人、8次正常完成但没有候选人、2次执行失败：

```Plain
有结果率 = 90 / 98 * 100% = 91.84%
无结果率 = 8 / 98 * 100% = 8.16%
执行失败次数 = 2
```

有候选人结果不等于检索成功。返回的候选人还需要按第4章判断是否包含基准候选人。
无候选人结果一定无法命中基准候选人，因此该次 `retrieval_success = 0`；但不存在可计算
完整度和准确率的候选人，这些字段应记为“不适用”，不能记为0。

### 5.2 检索成功率

### 单次检索

对一次 JOJO 检索，检索成功是一个二元结果：

```Plain
返回结果中存在命中的基准候选人：成功，记为 1
返回结果中不存在命中的基准候选人：失败，记为 0
```

单次检索本身不需要计算“百分之多少成功”。只有汇总多个人物或多次检索后，才计算成功率。

### 多个人物或多次检索

```Plain
检索成功率 = 成功命中基准候选人的检索次数 / 总检索次数 * 100%
```

这里的总检索次数按本轮应执行的正式检索任务计算。`NO_CANDIDATES` 和
`EXECUTION_FAILED` 都不能命中基准候选人，因此 `retrieval_success` 均记为0；
同时在报告中分别展示无候选人数和执行失败数，不能把两类失败合并。

例如准备 100 个基准候选人，其中 82 个人的返回候选人中包含对应的基准候选人：

```Plain
检索成功率 = 82 / 100 * 100% = 82%
```

候选人返回了多少字段不决定检索成功率。只要能够确认该候选人就是基准候选人，本次检索就算成功；字段多少由完整度评价，字段真假由准确率评价。

### 5.3 命中基准候选人的信息完整度

### 不建议只计算非空字段数

直接使用下面的计算方式存在问题：

```Plain
非空字段数 / 需要收集的字段数
```

因为一个字段即使不为空，也可能返回了属于其他人物的错误信息。错误信息不应该让完整度变高。

因此，本方案使用“正确找回的基准信息”计算完整度。

### 单值字段

对于姓名、地区等只有一个基准值的字段：

```Plain
返回值与基准值一致：该字段完整度得分为 1
没有返回或返回错误：该字段完整度得分为 0
```

### 多值字段

对于 social links、照片、工作经历等可能包含多个已知值的字段：

```Plain
该字段完整度得分 = 正确找回的基准信息项数 / 基准信息项总数
```

例如 JOJO 已知有 4 个 social links，检索结果正确找回 3 个：

```Plain
social 字段完整度得分 = 3 / 4 = 0.75
```

### 候选人整体完整度

默认使用22个内容字段：

```Plain
命中候选人信息完整度 = 22个内容字段的完整度得分之和 / 22 * 100%
```

例如，22个内容字段中有11个字段正确找回，其余字段为空或错误：

```Plain
命中候选人信息完整度 = 11 / 22 * 100% = 50%
```

错误字段、无关字段和空字段都不会增加完整度。

### 5.4 非命中基准候选人的信息完整度

其他同名候选人没有可供比对的基准真值，因此无法判断其内容是否正确。对这些候选人只评价22个内容字段中有多少字段不为空。

单个非命中候选人的计算公式：

```Plain
非命中候选人信息完整度 = 非空内容字段数 / 22 * 100%
```

例如，某个非命中 JOJO 有8个内容字段不为空：

```Plain
非命中候选人信息完整度 = 8 / 22 * 100% = 36.36%
```

计算规则：

- 4个 `*_status` 状态字段不进入分子和分母；
    
- 单值字段非空记为1个完整字段；
    
- 多值字段只要至少有一个有效信息项，字段层面记为非空；
    
- 空字符串、空数组、空对象、`null` 和直接回显的查询条件按空值处理；
    
- 每个非命中候选人单独计算，不能把多个候选人的字段合并；
    
- 该完整度只表示“信息填充程度”，不代表信息真实或属于正确人物。
    

一次检索返回多个非命中候选人时，可以计算它们的平均值：

```Plain
非命中候选人平均完整度 = 所有非命中候选人信息完整度之和 / 非命中候选人数
```

如果本次检索没有非命中候选人，该项记为“不适用”，不记为0。

### 5.5 命中基准候选人的字段准确率

准确率只评价命中基准候选人实际返回的非空字段，不返回的字段由命中候选人信息完整度体现。非命中候选人因为没有基准真值，不计算字段准确率。

### 单值字段

```Plain
返回值与基准值一致：该字段准确率得分为 1
返回值与基准值不一致：该字段准确率得分为 0
```

### 多值字段或字段中包含多条内容

先将字段内容拆分成可以独立比较的信息项，再计算：

```Plain
该字段准确率得分 = 与基准数据一致的返回信息项数 / 该字段返回的信息项总数
```

例如某个 social 字段返回 3 个链接，其中 2 个属于 JOJO，1 个属于其他人：

```Plain
social 字段准确率得分 = 2 / 3 = 66.67%
```

对于 `summary` 或 `insights` 中的一段文字，应拆成可验证的事实点。例如公司、职位、地区分别作为事实点，再判断每个事实点是否与基准数据一致。

### 候选人整体准确率

先计算每个非空返回字段的准确率得分，再对这些字段取平均：

```Plain
字段准确率 = 所有非空返回字段的准确率得分之和 / 非空返回字段数 * 100%
```

例如候选人返回 6 个字段，其中 5 个字段完全正确，1 个字段完全错误：

```Plain
字段准确率 = (1 + 1 + 1 + 1 + 1 + 0) / 6 * 100%
           = 83.33%
```

如果第 6 个字段不是完全错误，而是返回 3 条内容，其中 2 条正确、1 条错误，则该字段得分为 `2/3`：

```Plain
字段准确率 = (1 + 1 + 1 + 1 + 1 + 2/3) / 6 * 100%
           = 94.44%
```

### 5.6 检索成本、检索时长与PDL调用统计

成本和检索时长按一次实际检索任务统计，与候选人数量无关。一个 `task_id` 即使返回
5个候选人，也只能累计一次任务成本和一次检索时长。

单次检索记录：

```Plain
本次 LLM 成本 = 接口返回的 llm_cost
本次第三方调用成本 = 接口返回的 third_party_cost
本次总成本 = 接口返回的 total_cost
本次检索时长 = 接口返回的 search_duration_ms
本次是否调用 PDL = 接口返回的 pdl_called
```

`total_cost` 按接口返回的本次全部成本直接统计。如果其中已经包含 `llm_cost` 和
`third_party_cost`，不能再次相加，否则会重复计算。

100个人各执行一次检索时：

```Plain
100人 LLM 总成本 = 100次检索的 llm_cost 之和
100人第三方调用总成本 = 100次检索的 third_party_cost 之和
100人检索总成本 = 100次检索的 total_cost 之和
平均检索时长 = 有时长数据任务的 search_duration_ms 之和 / 有时长数据的任务数
最长检索时长 = 所有有效 search_duration_ms 中的最大值
PDL 调用次数 = pdl_called 为 true 的检索次数
PDL 未调用次数 = 100 - PDL 调用次数
```

实际检索任务数由每个评估阶段最终执行的检索条件决定，不能固定按“三个阶段 =
300次任务”计算。例如第一阶段100人只执行全名，第二阶段100人复跑全名并新增
全名 + Link，则两个阶段共执行300次任务。应先按
`evaluation_phase + query_stage` 分组统计成本、检索时长和PDL调用次数，再汇总全部
实际任务。

重试任务和重复运行属于真实发生的额外检索，应单独记录并计入实际总成本和检索时长。
成本或时长字段缺失时必须同时报告缺失任务数，不能把缺失值当成0加入统计。

### 5.7 基准发布线与上线判断（讨论稿）

当前阶段只关注评估目的中的核心质量指标和检索成本。以下数值是第一版讨论参考线，
不是行业统一标准；第一阶段主要用于得到真实基线，即使没有达到参考线也可以完成评估，
后续准备上线时再根据实际结果确认最终标准。

|核心指标|第一版参考线|判断说明|
|---|---:|---|
|有结果率 / 无结果率|第一阶段统计后确定|用于判断检索能否返回候选人，但不能代替检索成功率|
|全名检索成功率|≥70%，建议达到80%|100人中至少70人能够命中对应基准候选人|
|全名 + Link检索成功率|≥85%，建议达到90%|第一阶段未执行该条件时，只展示本次结果，不计算优化前后提升|
|全名 + 照片检索成功率|待照片功能有真实结果后确定|当前不设置参考线|
|全名命中候选人完整度|≥60%，建议达到70%|按正确找回的基准信息计算|
|全名 + Link命中候选人完整度|≥70%，建议达到80%|按正确找回的基准信息计算|
|命中候选人字段准确率|≥95%，建议达到97%|所有正式检索条件分别统计|
|非命中候选人信息完整度|全名参考35%；全名 + Link参考40%|当前只有信息填充程度，主要用于观察，不单独决定是否上线|
|LLM成本、总成本|第一阶段建立实际成本基线|后续使用相同人数和检索条件比较成本增减|
|第三方调用成本|第一阶段建立实际成本基线|单独观察第三方服务带来的成本|
|每次成功命中的平均成本|第一阶段建立实际成本基线|用于判断质量提升是否伴随过高成本|
|平均检索时长、最长检索时长|第一阶段建立实际时长基线|后续使用相同人数和检索条件比较检索速度|
|PDL调用次数和调用率|暂不设置固定比例|展示实际调用情况及其成本|

简单上线判断：

- 核心成功率、命中完整度和字段准确率达到确认后的参考线，并且检索成本与检索时长
  可以接受，可以建议上线；
- 任一核心质量指标未达到参考线，继续优化对应能力后再评估；
- 质量有所提升但成本明显增加或检索明显变慢时，由产品和开发判断收益是否值得；
- 基准数据、检索结果、成本或检索时长字段不完整时，暂不能判断；
- 不把所有指标合成为一个总分，报告分别展示质量、成本和检索时长。

## 6. 同一检索条件重复执行时如何计算

对同一个检索条件，每次运行都单独保存结果并计算各项结果。

示例记录：

|运行次数|是否命中基准候选人|命中候选人置信度|命中完整度|命中准确率|非命中平均完整度|LLM成本|第三方成本|总成本|检索时长|调用PDL|
|---|---|---|---|---|---|---|---|---|---|---|
|第 1 次|否|不适用|不适用|不适用|45.45%|||||是/否|
|第 2 次|是||50%|100%|36.36%|||||是/否|
|第 3 次|是||50%|91.67%|40.91%|||||是/否|

三次运行的检索成功率为：

```Plain
检索成功率 = 2 / 3 * 100% = 66.67%
```

命中候选人的完整度和准确率只对成功运行计算。多次运行汇总时，对成功运行的对应得分取平均：

```Plain
命中候选人平均完整度 = 成功运行的命中候选人完整度之和 / 成功运行次数
命中候选人平均准确率 = 成功运行的命中候选人准确率之和 / 成功运行次数

非命中候选人平均完整度 = 所有运行中非命中候选人的完整度之和 / 所有运行中非命中候选人总数
```

疑似基准候选人当前按非命中候选人参与完整度汇总。

三次重复运行均是实际检索任务，因此三次的 LLM 成本、第三方调用成本、总成本和检索
时长都要分别保存，PDL调用次数按三次 `pdl_called` 分别统计，不能只保留最后一次运行。

### 新增错误信息时如何判断

假设第一次在22个内容字段中返回11个字段，11个都正确：

```Plain
命中候选人完整度 = 11 / 22 = 50%
命中候选人准确率 = 11 / 11 = 100%
```

第二次多返回 1 个字段，但新增字段与基准数据不一致：

```Plain
命中候选人完整度仍为 11 / 22 = 50%
命中候选人准确率变为 11 / 12 = 91.67%
```

因此，新增错误字段不会提高本方案中的完整度，但会降低准确率。

如果新增字段与基准数据一致：

```Plain
命中候选人完整度变为 12 / 22 = 54.55%
命中候选人准确率仍为 12 / 12 = 100%
```

## 7. 三个评估阶段如何统计与对比

### 7.1 按评估阶段和检索条件分别计算

一次统计记录必须同时保留 `evaluation_phase` 和 `query_stage`：

|基准候选人|评估阶段|系统版本|检索条件|结果状态|是否检索成功|命中完整度|命中准确率|非命中平均填充程度|
|---|---|---|---|---|---|---:|---:|---:|
|JOJO|第一阶段|优化前|全名|有候选人 / 无候选人 / 执行失败|是/否||||
|JOJO|第一阶段|优化前|全名 + Link（如执行）|有候选人 / 无候选人 / 执行失败|是/否||||
|JOJO|第二阶段|优化后|全名|有候选人 / 无候选人 / 执行失败|是/否||||
|JOJO|第二阶段|优化后|全名 + Link或照片|有候选人 / 无候选人 / 执行失败|是/否||||
|JOJO|第三阶段|下一优化版本|评审后确定|有候选人 / 无候选人 / 执行失败|是/否||||

每个指标按 `evaluation_phase + system_version + query_stage` 独立汇总，不能把同一
阶段内的全名、Link和照片任务混成一个总体成功率：

```Plain
分组有结果率 = 该分组HAS_CANDIDATES次数 / 该分组可判定结果的检索次数 * 100%

分组无结果率 = 该分组NO_CANDIDATES次数 / 该分组可判定结果的检索次数 * 100%

分组检索成功率 = 该分组成功人数 / 该分组参与统计人数 * 100%

分组命中候选人平均完整度 = 该分组命中候选人完整度之和 / 该分组成功人数

分组命中候选人平均准确率 = 该分组命中候选人准确率之和 / 该分组成功人数

分组非命中候选人平均填充程度 =
  该分组所有非命中候选人的非空填充程度之和 / 该分组非命中候选人总数

分组成本、检索时长和PDL = 该分组实际 task_id 对应数值的汇总
```

未命中基准候选人时，命中完整度和准确率记为“不适用”。报告必须同时展示成功人数、
执行失败、无候选人和待复核数量，避免只展示成功样本的高分。

### 7.2 第二阶段与第一阶段的两类比较

第二阶段报告必须分成两种比较，使用不同结论名称。

#### A. 同条件版本对比

只比较第一阶段与第二阶段都执行过的相同 `person_id + query_stage`：

1. 先看有结果率、无结果率和执行失败情况；
2. 再看检索成功率和新增命中、退化未命中人数；
3. 再看持续命中候选人的字段准确率是否下降；
4. 再看持续命中候选人的信息完整度是否提高；
5. 单独观察非命中候选人的信息填充程度；
6. 最后并列比较成本、检索时长和PDL调用情况。

该比较可以得出“优化后提升、退化或基本不变”的版本结论。

#### B. 优化后新增线索对比

Link或照片如果第一阶段没有执行，只能在第二阶段内部与优化后全名结果横向比较：

- 有结果率是否提高、无结果率是否下降；
- 成功率是否提高；
- 新增线索帮助了哪些原本未命中的人物；
- 命中准确率和完整度是否改善；
- 是否产生新的错误绑定、信息污染、成本增加或检索变慢。

该比较的结论应写为“增加Link/照片线索后改善或退化”，不能写成“系统优化提升”。
新增条件本次结果可以作为该条件下一轮版本对比的基线。

|观察结果|建议结论|
|---|---|
|同条件成功率提高，准确率不下降，完整度提高或不变|系统优化后整体改善|
|同条件成功率下降|系统在基础召回方面发生退化|
|成功率提高但准确率明显下降|召回增加但错误风险上升，不能直接判定更好|
|完整度提高但准确率下降|返回信息变多，但信息污染增加|
|新增线索条件优于优化后全名|新增线索具有增益，但不等于版本提升|
|所有同条件指标基本不变|本轮优化未观察到明确改善|

成本和检索时长不与成功率、完整度或准确率合成综合分。报告分别呈现质量、成本和时长
变化，由业务判断收益是否值得。

### 7.3 第三阶段如何确定

第三阶段不直接套用固定的“名字 + 某种线索”。第一、第二阶段报告完成后，按以下顺序
确定第三阶段：

1. 从新增命中、退化未命中、持续未命中和字段错误中选择主要问题；
2. 判断问题属于候选人召回、排序与身份绑定、信息补全、信息准确性、稳定性还是成本；
3. 选择对应样本，保留上一阶段同条件回归组，并增加针对性测试组；
4. 冻结第三阶段的系统版本、Query、样本、规则和成功标准后再执行；
5. 报告同时展示上一阶段回归结果和本轮专项结果。

例如第二阶段显示“全名召回改善，但错误Social Link增加”，第三阶段应优先验证
Social身份绑定和错误Link问题，而不是默认继续增加更多查询线索。

### 7.4 同一个人优化前后配对

优化前后必须使用相同的 `person_id + query_stage` 进行一一配对，不能只比较两轮100人的总体平均值。

配对前提：

- 使用同一批100个人；
    
- 全名查询文本完全相同；
    
- 全名 + link 使用同一个基准link；
    
- 命中规则、22个内容字段和计算公式不变；
    
- 记录优化前版本、优化后版本及执行时间。
    

每个人每种检索条件形成一行配对记录：

|person_id|检索条件|优化前命中|优化后命中|置信度变化|完整度变化|准确率变化|非命中完整度变化|成本变化|检索时长变化|变化结论|
|---|---|---|---|---|---|---|---|---|---|---|
|JOJO-001|全名|否|是||不适用|不适用||||未命中 -> 命中，检索改善|
|JOJO-002|全名 + link|是|是||+13.64个百分点|0||||持续命中且信息更完整|
|JOJO-003|全名|是|否||不适用|不适用||||命中 -> 未命中，属于退化|

100个人配对后，至少汇总以下四种变化数量：

```Plain
持续命中数 = 优化前命中、优化后仍命中的人数
新增命中数 = 优化前未命中、优化后命中的人数
退化未命中数 = 优化前命中、优化后未命中的人数
持续未命中数 = 优化前未命中、优化后仍未命中的人数
```

完整度和准确率变化只在“持续命中”的同一个基准候选人之间计算。由未命中变为命中或由命中变为未命中时，重点记录命中状态变化，不强行计算不存在的完整度、准确率差值。

如果第一阶段没有运行某个Link或照片条件，该条件在第二阶段只能与优化后同版本的
其他检索条件横向比较，不能称为该条件的优化前后提升。要评价该检索条件的版本提升，
必须从它首次正式执行时建立基线，并在后续阶段使用相同条件再次执行。

### 8.4 报告详情附加项的数据处理与统计

以下统计用于解释核心结果为什么变化，放在报告详情或附录，不作为主汇报重点，也不与核心指标合成综合分。

#### 1. 模块返回情况

利用 `insights_status`、`photos_status`、`profile_status` 和 `social_status` 统计各模块返回数据的候选人比例。Summary当前没有独立status字段，可按Summary内容字段是否至少一个非空判断模块是否返回。

```Plain
模块返回率 = 该模块有数据的候选人数 / 参与统计的候选人总数 * 100%
```

命中候选人与非命中候选人分开统计，避免大量非命中候选人改变基准候选人的模块表现。

#### 2. 单字段对比

对22个内容字段分别比较优化前后表现：

- 命中候选人：统计每个字段的完整度和准确率；
    
- 非命中候选人：只统计每个字段的非空比例；
    
- 按全名、全名 + link、全名 + 照片分别展示。
    

单字段结果用于定位总体变化具体来自年龄、地区、邮箱、职位、教育、social URL或其他字段。

#### 3. 模块完整度

将22个内容字段按 Insights、Photos、Profile、Social、Summary分组，分别计算模块内字段的平均完整度：

```Plain
命中候选人模块完整度 = 模块内各字段正确找回得分之和 / 模块内内容字段数

非命中候选人模块完整度 = 模块内非空内容字段数 / 模块内内容字段数
```

模块完整度用于解释总体完整度提升来自哪个模块。

#### 4. Social数据

Social详情附加项包括：

- 返回的社交平台数量；
    
- 返回的social link数量；
    
- 与基准候选人一致的link数量；
    
- 错误link数量；
    
- 同平台link冲突数量；
    
- 各平台的返回情况。
    

命中候选人的正确、错误link通过基准数据判断；非命中候选人没有真值时只统计平台数和link非空情况。

#### 5. Photos数据

Photos详情附加项包括：

- Photos模块是否返回；
    
- `photos_identity_match_rate` 的值；
    
- 相似度达到80%的候选人数；
    
- `photos_authenticity_photos` 信息项数量；
    
- `photos_match_photos` 信息项数量；
    
- 有照片来源页的候选人数。
    

照片相似度达到80%仍按第4章的强绑定规则使用，详情统计本身不改变命中判定。

#### 6. 候选人置信度

候选人置信度作为详情附加项，分别统计：

- 命中基准候选人的平均置信度；
- 非命中候选人的平均置信度；
- 置信度缺失的候选人数；
- 同一个候选人优化前后的置信度变化。

当前不设置置信度通过线，也不使用置信度自动替代命中判断。先保存真实数据，再观察
置信度与实际命中结果是否一致。

#### 7. 成本与检索时长

成本详情附加项包括：

```Plain
平均每次检索成本 = 检索总成本 / 实际检索任务数

每次成功命中的平均成本 = 检索总成本 / 成功命中次数

平均检索时长 = 有时长数据任务的检索时长之和 / 有时长数据的任务数
```

并分别展示：

- 全名、全名 + link、全名 + 照片的平均成本；

- LLM成本、第三方调用成本和总成本；

- 各检索条件的平均检索时长和最长检索时长；
    
- PDL调用任务与未调用任务的成功率、完整度、准确率和平均成本；
    
- 优化前后同一检索条件的成本变化；
    
- 重试和重复运行增加的实际成本。
    

当成功命中次数为0时，“每次成功命中的平均成本”记为不适用，不能进行除法。

## 9. 当前方案的最小执行流程

当前使用 `searchTool v1.3 MVP` 实现本方案时，采用“采集、处理、复核、计算、报告”分层执行。v1.3 负责把一次评测组织成可追溯的 `Evaluation / Run / Query / Task / Candidate` 数据链路；接口请求与评分后处理仍然保持分离。

### 9.1 v1.3 MVP执行范围

|        |                                                                                                 |
| ------ | ----------------------------------------------------------------------------------------------- |
| 项目     | v1.3 MVP执行方式                                                                                    |
| 检索条件   | 工具支持 FULL_NAME、FULL_NAME_SOCIAL；第一阶段必做FULL_NAME，是否同时执行FULL_NAME_SOCIAL由评审决定；暂不执行FULL_NAME_PHOTO |
| 数据进入   | 通过Web启动新检索，或导入历史JSONL、Excel                                                                     |
| 候选人范围  | 保存 ListTaskCandidates 实际返回的全部候选人；MVP不处理候选人分页                                                    |
| 原始数据   | 完整保存各接口业务响应、失败信息和采集时间，不被后处理覆盖                                                                   |
| 字段处理   | 按版本化 FieldSchema 提取、规范化和判断非空状态                                                                  |
| 人工复核   | 导入基准数据后，复核候选人身份和字段得分                                                                            |
| 指标报告   | 生成单Run报告或baseline/candidate配对报告，并可下钻到原始JSON                                                     |
| 成本、时长与PDL | 候选人置信度、第三方调用成本或检索时长字段未接入时显示“数据未接入”或缺失数，不按0计算                                           |

### 9.2 实现流程

```Plain
创建 Evaluation
  → 导入基准人物和 Query Dataset
  → 冻结 person_id + query_stage
  → 创建 Run，记录 system_version 和 run_label
  → Web启动 searchTool，或导入历史 JSONL / Excel
  → 保存 Query、Task、Candidate 和完整原始响应
  → 选择 schema_version 和处理规则版本
  → 提取结构化字段并生成待复核项
  → 人工完成候选人判定和字段复核
  → 自动计算 Query、Run 和版本配对指标
  → 生成 Web、Excel 或静态 HTML 报告
  → 从报告下钻到人物、Query、Candidate、字段和原始 JSON
```

各阶段的实现边界如下：

1. **准备数据**：为每个基准人物建立稳定的 `person_id`，导入姓名、已知
   Social Links、22个内容字段、基准版本和更新时间；必需生成 `FULL_NAME`
   Query，按本阶段已评审的范围决定是否生成 `FULL_NAME_SOCIAL` Query，
   保证 `input_id = query_id`。
    
2. **执行采集**：每次执行创建新的 `run_id`，按 `CreateIntentTask → GetTask → ListTaskCandidates → GetTaskCandidateDetail` 采集，同时保存候选人置信度、LLM成本、第三方调用成本、总成本、检索时长和PDL调用情况。重复运行、baseline和candidate不得覆盖旧Run。
    
3. **保存异常**：无候选人记录为 `NO_CANDIDATES`；单个Candidate Detail失败时 保留List基本信息并继续其他候选人，标记 `PARTIAL_DETAIL_FAILED`，不能把详情 获取失败伪装成字段为空。
    
4. **处理字段**：使用固定的 `schema_version + 基准数据版本 + 处理规则版本` 提取26个原始字段，以22个内容字段评分。处理失败只记录异常，不修改Raw； 同一份Raw可以使用新FieldSchema重新处理。
    
5. **复核候选人**：v1.3不使用照片规则自动判定。按“同平台Social冲突 → Social Link一致 → 无强字段时疑似”的顺序给出建议，再由测试人员确认 `HIT / NOT_HIT / SUSPECTED`。`SUSPECTED`在正式统计中仍按未命中处理。
    
6. **复核字段**：对命中候选人逐字段确认完整度、准确率和证据；对非命中 候选人只计算22个内容字段的非空填充程度。复核未完成时可以查看中间数据， 但不能生成最终结论。
    
7. **计算与报告**：按本方案第5至第8章生成核心指标和附加明细。报告必须同时 展示执行失败、无候选人、部分详情失败和待复核数量，避免把采集异常误认为 检索质量问题。
    

### 9.3 首次基线与优化后对比的执行方法

第一阶段建立优化前基线：

1. 创建 `Evaluation`，标记 `evaluation_phase = PHASE_1_BASELINE`；
2. 导入暂定100人的基准数据和必做的 `FULL_NAME` Query；
3. 评审决定是否同时加入 `FULL_NAME_SOCIAL`，决定后冻结Dataset；
4. 为优化前系统版本创建baseline Run，完成采集、处理和人工复核；
5. 生成第一阶段单Run报告，保存Raw、字段配置、基准版本、规则版本和报告快照。

第二阶段验证优化并增加线索：

1. 标记 `evaluation_phase = PHASE_2_POST_OPTIMIZATION`；
2. 在同一 `Evaluation` 下，使用相同Dataset为优化后版本创建candidate Run，
   先复跑第一阶段全部检索条件；
3. 另外建立新增线索Dataset：第一阶段未执行Link时可新增
   `FULL_NAME_SOCIAL`；照片功能正式可用后可新增 `FULL_NAME_PHOTO`；
4. 完成采集、处理和复核后，先生成同条件baseline/candidate配对结果，再单独生成
   优化后新增线索横向结果；
5. 汇总持续命中、新增命中、退化未命中和持续未命中，并下钻复核退化、疑似、
   失败和部分详情失败案例。

第三阶段根据报告立项：

1. 根据前两阶段结论确定下一轮优化问题和目标样本；
2. 创建 `PHASE_3_TARGETED_ITERATION` 的测试定义和Run；
3. 保留上一阶段同条件回归Dataset，再增加专项Dataset；
4. 冻结成功标准后执行，并生成“回归结果 + 专项结果”报告。

只有 `query_stage`、Dataset、字段配置、基准版本和规则版本兼容的Run才能进行正式
版本对比。新增线索Dataset必须单独标记，不能混入同条件配对结果。若使用新
FieldSchema重新处理历史Raw，应生成新的 `ProcessResult`和报告，旧处理结果与旧报告
保持不变。

## 10. 产品、开发与测试评审

本方案正式执行前，应由产品、开发和测试共同评审。评审目标不是增加更多指标，而是确认接口行为、字段含义和判定规则能够真实落地。

### 10.1 必须讨论的特别注意问题

“全名 + link”和“全名 + 照片”存在循环判断风险：

- link既是输入条件，又是命中判断字段；
    
- 照片URL既是输入条件，又可能被返回到 `photos_baseline_photo_url`；
    
- 如果系统只是把请求参数原样复制到候选人结果中，会导致虚假的命中、完整度和准确率提升。
    

v1.3 MVP已经确认Social Link不会回显，返回Link可以参与候选人判定和字段评分。

正式执行前仍需用接口原始响应完成一次验收并记录结果。照片检索未进入v1.3

MVP，其回显和相似度计算口径仍需在后续开发前确认。

评审与验收需要明确：

1. 返回的social link确实来自检索结果并绑定到具体 `candidate_id`，不存在请求参数回显；
    
2. 是否有provider或evidence能够证明link属于该候选人；
    
3. `photos_identity_match_rate` 是否由基准照片与候选人检索照片实际计算；

## 11. 第一版评估报告结构

第一版报告采用“主报告 + 详情附录”。主报告用于汇报结论，建议控制在4至6页；详情附录用于测试、产品和开发追查具体字段。

报告模板按评估阶段逐步启用：

- 第一阶段报告：展示优化前全名基线；全名 + Link仅在评审决定执行时加入；

### 11.7 汇报展示原则

- 主报告只展示评估目的中的核心结果，不在首页堆放22个字段；
    
- 所有百分比同时显示分子和分母，例如 `82/100，82%`；
    
- 提升和下降使用统一方向符号，如 `↑`、`↓`、`→`；
    
- 颜色只用于辅助：提升用绿色、退化用红色、无变化用灰色；
    
- 每张图表标题直接写结论，例如“全名检索成功率提升5个百分点”，不要只写“成功率对比”；
    
- 任何总体结论都能够下钻到具体 `person_id`、候选人、字段和证据来源；

- 核心指标同时展示参考线、实际值和是否达到；
    
- 照片没有优化前基线时必须显著标注，避免错误归因。
    

## 12. 后续可考虑的指标建议

以下内容不纳入当前核心方案。先把有结果率与无结果率、检索成功率、命中候选人信息完整度、非命中候选人信息完整度、字段准确率和成本统计跑通后，再根据实际分析需要决定是否增加。

### 12.1 命中候选人的排名

同名候选人很多时，即使成功命中了 JOJO，JOJO 排第 1 和排第 20 的使用效果并不相同。后续可以增加“命中排名”或 Top 1/Top 5 命中情况。

### 12.2 更细的结果一致性分析

当前阶段不把结果一致性设置为发布门槛。后续可以根据实际需要增加命中状态一致率、
候选人集合重合率、排名变化、字段值变化和provider变化，用于进一步区分检索逻辑变化
与外部数据源波动。

### 12.3 错误类型记录

可以给错误结果增加简单原因，例如：命中其他同名人物、错误 social link、错误照片、信息过期或多人信息混合。该内容主要用于定位问题，不一定需要计算成新的分数。

现阶段建议先不增加这些指标，先使用当前核心评估内容完成第一轮真实数据评估，再根据第一轮暴露的问题决定是否扩展。
