# 检索系统评估方案

## 1. 评估目的

本方案用于回答五个核心问题：

1. 检索结果中是否包含已知的基准候选人，即检索是否成功；
2. 命中的基准候选人返回了多少已知信息，即信息完整度；
3. 命中的基准候选人所返回的信息有多少是正确的，即字段准确率；
4. 其他未命中基准候选人的同名候选人，各自返回了多少信息，即非命中候选人信息完整度；
5. 每次检索产生了多少 LLM 成本和总成本、是否调用 PDL，以及100个人全部检索的累计成本和 PDL 调用情况。

非命中候选人也可能是其他用户真正想查询的人，因此不能只关注基准候选人。成本和 PDL 调用用于评估检索资源消耗，但不参与候选人信息完整度和字段准确率计算。

`searchTool` 只负责通过接口批量执行检索并保存候选人的完整结果。候选人识别、基准数据比对和评估项计算在结果收集完成后进行。

## 2. 核心概念

### 2.1 基准候选人

基准候选人是测试前已经掌握确切信息的目标人物。

例如，测试人物为 JOJO，测试前已经整理好 JOJO 在以下模块中的已知信息：

- `insights`
- `photos`
- `profile`
- `social`
- `summary`

这些已知信息共同构成 JOJO 的基准数据，用于判断检索结果中的某个候选人是不是 JOJO，以及候选人的信息是否完整、准确。

### 2.2 评估字段

本方案使用 [`字段整理.md`](../字段整理.md) 中整理的实际返回字段。该文件当前定义的是五个业务模块：

- `Insights`
- `Photos`
- `Profile`
- `Social`
- `Summary`

五个模块共有 26 个原始字段：

| 模块       | 原始字段                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Insights | `insights_status`、`insights_description`、`insights_links`                                                                                                                                                                                          |
| Photos   | `photos_status`、`photos_baseline_photo_url`、`photos_identity_match_rate`、`photos_authenticity_photos`、`photos_match_photos`                                                                                                                        |
| Profile  | `profile_status`、`profile.Identity.Full Name`、`profile.Identity.Age`、`profile.Identity.Location`、`profile.Identity.Email`、`profile.Identity.Profile URL`、`profile.Career.Current Role`、`profile.Background.Education`、`profile.Career.Other Roles` |
| Social   | `social_status`、`social_display_handles`、`social_platforms`、`social_urls`                                                                                                                                                                          |
| Summary  | `summary_avatar_url`、`summary_confidence_level`、`summary_primary_image_url`、`summary_social_links`、`summary_web_links`                                                                                                                             |


评估字段可以来自不同模块，但需要满足以下条件：

- 字段在测试前已经有明确、可验证的基准值；
- 字段名称、数据格式和比较方法保持固定；
- 多值字段需要提前拆分出具体信息项；
- 所有检索次数和三个检索阶段使用相同的22个内容字段。

如果 social link 或照片 URL 被用作本次查询条件，系统对该输入值的直接回显不计入完整度或准确率；只有能够确认该信息来自实际检索结果时才参与评分。直接回显的字段按空值处理，避免查询条件自动增加完整度。

22个内容字段的来源路径、中文含义和内容格式以 `字段整理.md` 为准，本文不重复维护第二份字段路径定义。

成本、PDL调用情况和五个模块的证据来源属于独立公共字段，不计入上述22个内容字段的完整度或准确率分子、分母。

### 2.3 候选人结果

检索 JOJO 后，系统可能返回多个名称相同或相似的候选人。每个候选人都可以包含 `insights / photos / profile / social / summary` 等模块的数据。

评估时必须逐个候选人处理，不能把多个同名候选人的信息拼在一起计算：

- 命中基准候选人：计算基准候选人信息完整度和字段准确率；
- 未命中基准候选人：计算该候选人自身的非空信息完整度，不计算准确率；
- 疑似基准候选人：当前统计时仍按未命中处理，并在复核说明中标记“疑似”。

### 2.4 独立公共字段

除候选人的22个内容字段外，每次检索还需要单独收集任务成本、PDL调用情况和候选人证据来源。

#### 检索任务级字段

任务级字段按一次 `task_id` 记录一次，不能复制到每个候选人后重复累计：

| 逻辑字段               | 含义                        | 当前来源                                                                   |
| ------------------ | ------------------------- | ---------------------------------------------------------------------- |
| `llm_cost`         | 本次检索产生的 LLM 成本            | 待接口提供正式字段路径                                                            |
| `total_cost`       | 本次检索产生的全部成本               | 待接口提供正式字段路径                                                            |
| `cost_currency`    | 成本币种                      | 待接口提供；所有任务必须统一币种后再汇总                                                   |
| `pdl_called`       | 本次检索是否调用 People Data Labs | 待接口提供；是否包含 `people_data_labs`                                          |
| `provider_summary` | 本次检索调用的数据提供方摘要            | 当前样例可见于  或 `ListTaskCandidates` 的 `responses[0].data.provider_summary` |

如果成本字段缺失，本次记录应留空或标记“未返回”，不能按0处理。失败或重试任务如果产生了成本，也应按实际接口返回记录。

#### 候选人模块证据来源字段

每个候选人按五个模块分别收集证据来源：

| 逻辑字段                        | 收集内容                            | 当前可用来源                                                                         |
| --------------------------- | ------------------------------- | ------------------------------------------------------------------------------ |
| `insights_evidence_sources` | Insight事实对应的公开链接、标题、平台或provider | `ui_sections.insights.data.items[].links`                                      |
| `photos_evidence_sources`   | 照片来源页、图片匹配来源和provider           | `authenticity_photos[].source_url`、`match_photos[]`及详情顶层 `evidence` 中的图片证据     |
| `profile_evidence_sources`  | 姓名、地区、职业、教育等Profile字段的来源        | 详情顶层 `evidence` 中的provider、URL、`subject_profile_url`等；待接口补充明确模块映射              |
| `social_evidence_sources`   | 社交账号的来源provider及主页URL           | 详情顶层 `social_accounts`、`evidence`或后续接口专用字段                                     |
| `summary_evidence_sources`  | Summary所引用的社交链接、网页链接和主图来源       | `summary_social_links`、`summary_web_links`、`summary.data.primary_image.source` |
| `candidate_evidence_raw`    | 无法可靠归属模块的原始证据                   | `GetTaskCandidateDetail.responses[0].data.evidence`完整对象                        |

证据来源字段用于支持人工核验和追溯，不增加候选人的信息完整度，也不直接参与字段准确率计算。无法明确归属模块的证据只保存在 `candidate_evidence_raw`，不能凭猜测分配给某个模块。

当前 `searchTool` 的成功结果主要保存 `ui_sections`，尚未完整保留任务级成本、`provider_summary`、详情顶层 `evidence` 和 `social_accounts`。本方案先定义收集与统计口径；后续接口字段确定后，需要再让采集结果保留这些独立公共字段，才能完成实际统计。

## 3. 三个检索阶段

对同一个基准候选人依次执行三类检索：

| 阶段 | 检索条件 | 目的 |
| --- | --- | --- |
| 第一阶段 | JOJO 名字 | 观察只有名字时能否找到基准候选人 |
| 第二阶段 | JOJO 名字 + 已知 social links | 观察增加社交线索后，检索结果是否改善 |
| 第三阶段 | JOJO 名字 + 已知照片 URL | 观察增加照片线索后，检索结果是否改善 |

三个阶段应使用同一份基准数据、同一套评估字段和同一套计算规则。

## 4. 如何判断候选人是否命中基准候选人

### 4.1 名字相同不能单独证明命中

因为检索条件本身包含 JOJO 的名字，而且结果中可能出现多个同名人物，所以名字相同只能用于初步筛选，不能单独用于确认身份。

### 4.2 Social link 强绑定规则

Social link 使用 `social_urls` 和 `summary_social_links` 中的链接，与基准候选人的已知 social links 进行比较。

比较前应对 URL 做统一处理，例如去除首尾空格、末尾 `/` 和不影响账号身份的跟踪参数，避免同一主页因格式不同被误判。

判定规则：

- 候选人至少有一个 social link 与基准候选人一致：可以判定为命中；
- 候选人与基准候选人存在同一个社交平台，但该平台 link 不一致：判定为不命中；
- 候选人的 social links 为空，或者没有可与基准平台比较的链接：social 规则无法判断，继续检查照片规则。

同平台 link 不一致属于明确身份冲突，优先级高于其他普通字段。即使姓名、地区、职位等字段一致，也不能覆盖该冲突。

### 4.3 照片相似度强绑定规则

照片使用 `photos_identity_match_rate` 判断。统一将返回值转换为百分比后：

```text
照片相似度 >= 80%：可以判定为命中
照片相似度 < 80%：不能通过照片判定为命中
照片相似度为空：照片规则无法判断
```

如果已经发现同平台 social link 不一致，则仍然判定为不命中，不再由照片相似度覆盖 social 冲突。

### 4.4 最终判断顺序

对每个同名候选人按以下顺序判断：

1. 如果存在同平台 social link 不一致，判定为不命中；
2. 否则，如果至少一个 social link 与基准候选人一致，判定为命中；
3. 否则，如果 `photos_identity_match_rate >= 80%`，判定为命中；
4. 如果 social links 和照片相似度都为空，即使其他字段全部或部分一致，也只能认为“疑似基准候选人”；当前统计时按不命中处理；
5. 其他情况判定为不命中。

可以将“疑似”写入人工复核说明，但检索成功字段仍记录为 `0`，不计入成功次数。

### 4.5 强绑定字段以外的信息如何使用

Profile、Insights、Summary 等其他字段不参与当前版本的命中判定，只在候选人命中后用于计算信息完整度和字段准确率。

因此，即使某个候选人有很多普通字段与 JOJO 一致，只要 social links 和照片都无法满足强绑定规则，当前仍按不命中处理。

## 5. 核心评估项的计算方法

### 5.1 检索成功率

### 单次检索

对一次 JOJO 检索，检索成功是一个二元结果：

```text
返回结果中存在命中的基准候选人：成功，记为 1
返回结果中不存在命中的基准候选人：失败，记为 0
```

单次检索本身不需要计算“百分之多少成功”。只有汇总多个人物或多次检索后，才计算成功率。

### 多个人物或多次检索

```text
检索成功率 = 成功命中基准候选人的检索次数 / 总检索次数 * 100%
```

例如准备 100 个基准候选人，其中 82 个人的返回候选人中包含对应的基准候选人：

```text
检索成功率 = 82 / 100 * 100% = 82%
```

候选人返回了多少字段不决定检索成功率。只要能够确认该候选人就是基准候选人，本次检索就算成功；字段多少由完整度评价，字段真假由准确率评价。

### 5.2 命中基准候选人的信息完整度

### 不建议只计算非空字段数

直接使用下面的计算方式存在问题：

```text
非空字段数 / 需要收集的字段数
```

因为一个字段即使不为空，也可能返回了属于其他人物的错误信息。错误信息不应该让完整度变高。

因此，本方案使用“正确找回的基准信息”计算完整度。

### 单值字段

对于姓名、地区等只有一个基准值的字段：

```text
返回值与基准值一致：该字段完整度得分为 1
没有返回或返回错误：该字段完整度得分为 0
```

### 多值字段

对于 social links、照片、工作经历等可能包含多个已知值的字段：

```text
该字段完整度得分 = 正确找回的基准信息项数 / 基准信息项总数
```

例如 JOJO 已知有 4 个 social links，检索结果正确找回 3 个：

```text
social 字段完整度得分 = 3 / 4 = 0.75
```

### 候选人整体完整度

默认使用22个内容字段：

```text
命中候选人信息完整度 = 22个内容字段的完整度得分之和 / 22 * 100%
```

例如，22个内容字段中有11个字段正确找回，其余字段为空或错误：

```text
命中候选人信息完整度 = 11 / 22 * 100% = 50%
```

错误字段、无关字段和空字段都不会增加完整度。

### 5.3 非命中基准候选人的信息完整度

其他同名候选人没有可供比对的基准真值，因此无法判断其内容是否正确。对这些候选人只评价22个内容字段中有多少字段不为空。

单个非命中候选人的计算公式：

```text
非命中候选人信息完整度 = 非空内容字段数 / 22 * 100%
```

例如，某个非命中 JOJO 有8个内容字段不为空：

```text
非命中候选人信息完整度 = 8 / 22 * 100% = 36.36%
```

计算规则：

- 4个 `*_status` 状态字段不进入分子和分母；
- 单值字段非空记为1个完整字段；
- 多值字段只要至少有一个有效信息项，字段层面记为非空；
- 空字符串、空数组、空对象、`null` 和直接回显的查询条件按空值处理；
- 每个非命中候选人单独计算，不能把多个候选人的字段合并；
- 该完整度只表示“信息填充程度”，不代表信息真实或属于正确人物。

一次检索返回多个非命中候选人时，可以计算它们的平均值：

```text
非命中候选人平均完整度 = 所有非命中候选人信息完整度之和 / 非命中候选人数
```

如果本次检索没有非命中候选人，该项记为“不适用”，不记为0。

### 5.4 命中基准候选人的字段准确率

准确率只评价命中基准候选人实际返回的非空字段，不返回的字段由命中候选人信息完整度体现。非命中候选人因为没有基准真值，不计算字段准确率。

### 单值字段

```text
返回值与基准值一致：该字段准确率得分为 1
返回值与基准值不一致：该字段准确率得分为 0
```

### 多值字段或字段中包含多条内容

先将字段内容拆分成可以独立比较的信息项，再计算：

```text
该字段准确率得分 = 与基准数据一致的返回信息项数 / 该字段返回的信息项总数
```

例如某个 social 字段返回 3 个链接，其中 2 个属于 JOJO，1 个属于其他人：

```text
social 字段准确率得分 = 2 / 3 = 66.67%
```

对于 `summary` 或 `insights` 中的一段文字，应拆成可验证的事实点。例如公司、职位、地区分别作为事实点，再判断每个事实点是否与基准数据一致。

### 候选人整体准确率

先计算每个非空返回字段的准确率得分，再对这些字段取平均：

```text
字段准确率 = 所有非空返回字段的准确率得分之和 / 非空返回字段数 * 100%
```

例如候选人返回 6 个字段，其中 5 个字段完全正确，1 个字段完全错误：

```text
字段准确率 = (1 + 1 + 1 + 1 + 1 + 0) / 6 * 100%
           = 83.33%
```

如果第 6 个字段不是完全错误，而是返回 3 条内容，其中 2 条正确、1 条错误，则该字段得分为 `2/3`：

```text
字段准确率 = (1 + 1 + 1 + 1 + 1 + 2/3) / 6 * 100%
           = 94.44%
```

### 5.5 检索成本与PDL调用统计

成本按一次实际检索任务统计，与候选人数量无关。一个 `task_id` 即使返回5个候选人，也只能累计一次任务成本。

单次检索记录：

```text
本次 LLM 成本 = 接口返回的 llm_cost
本次总成本 = 接口返回的 total_cost
本次是否调用 PDL = 接口返回的 pdl_called
```

`total_cost` 表示本次检索的全部成本时，不能再与 `llm_cost` 相加，否则会重复计算。

100个人各执行一次检索时：

```text
100人 LLM 总成本 = 100次检索的 llm_cost 之和
100人检索总成本 = 100次检索的 total_cost 之和
PDL 调用次数 = pdl_called 为 true 的检索次数
PDL 未调用次数 = 100 - PDL 调用次数
```

如果100个人分别执行名字、名字 + social links、名字 + 照片 URL三个阶段，则实际是300次检索任务。应先按阶段分别统计100次检索的成本和PDL调用次数，再计算300次任务的总计。

重试任务和重复运行属于真实发生的额外检索，应单独记录并计入实际总成本。成本字段缺失时必须同时报告缺失任务数，不能把缺失值当成0加入总成本。

## 6. 同一检索条件重复执行时如何计算

对同一个检索条件，每次运行都单独保存结果并计算各项结果。

示例记录：

| 运行次数 | 是否命中基准候选人 | 命中候选人完整度 | 命中候选人准确率 | 非命中候选人平均完整度 | LLM成本 | 总成本 | 调用PDL |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 第 1 次 | 是 | 50% | 100% | 36.36% |  |  | 是/否 |
| 第 2 次 | 是 | 50% | 91.67% | 40.91% |  |  | 是/否 |
| 第 3 次 | 否 | 不适用 | 不适用 | 45.45% |  |  | 是/否 |

三次运行的检索成功率为：

```text
检索成功率 = 2 / 3 * 100% = 66.67%
```

命中候选人的完整度和准确率只对成功运行计算。多次运行汇总时，对成功运行的对应得分取平均：

```text
命中候选人平均完整度 = 成功运行的命中候选人完整度之和 / 成功运行次数
命中候选人平均准确率 = 成功运行的命中候选人准确率之和 / 成功运行次数

非命中候选人平均完整度 = 所有运行中非命中候选人的完整度之和 / 所有运行中非命中候选人总数
```

疑似基准候选人当前按非命中候选人参与完整度汇总。

三次重复运行均是实际检索任务，因此三次的 LLM 成本和总成本全部相加，PDL调用次数按三次 `pdl_called` 分别统计，不能只保留最后一次运行。

### 新增错误信息时如何判断

假设第一次在22个内容字段中返回11个字段，11个都正确：

```text
命中候选人完整度 = 11 / 22 = 50%
命中候选人准确率 = 11 / 11 = 100%
```

第二次多返回 1 个字段，但新增字段与基准数据不一致：

```text
命中候选人完整度仍为 11 / 22 = 50%
命中候选人准确率变为 11 / 12 = 91.67%
```

因此，新增错误字段不会提高本方案中的完整度，但会降低准确率。

如果新增字段与基准数据一致：

```text
命中候选人完整度变为 12 / 22 = 54.55%
命中候选人准确率仍为 12 / 12 = 100%
```

## 7. 三个检索阶段如何统计与对比

### 7.1 每个阶段分别计算

对每个基准候选人，在三个阶段分别执行检索并记录：

| 基准候选人 | 检索阶段 | 是否检索成功 | 命中候选人完整度 | 命中候选人准确率 | 非命中候选人平均完整度 |
| --- | --- | --- | ---: | ---: | ---: |
| JOJO | 名字 | 是/否 |  |  |  |
| JOJO | 名字 + social links | 是/否 |  |  |  |
| JOJO | 名字 + 照片 URL | 是/否 |  |  |  |

准备多个人物后，分别汇总每个阶段：

```text
阶段检索成功率 = 该阶段成功人数 / 该阶段总检索人数 * 100%

阶段命中候选人平均完整度 = 该阶段所有命中候选人的完整度之和 / 该阶段成功人数

阶段命中候选人平均准确率 = 该阶段所有命中候选人的准确率之和 / 该阶段成功人数

阶段非命中候选人平均完整度 = 该阶段所有非命中候选人的完整度之和 / 该阶段非命中候选人总数

阶段 LLM 总成本 = 该阶段所有实际检索任务的 llm_cost 之和

阶段检索总成本 = 该阶段所有实际检索任务的 total_cost 之和

阶段 PDL 调用次数 = 该阶段 pdl_called 为 true 的任务数
```

未命中基准候选人时，命中候选人完整度和准确率记为“不适用”；但仍然逐个计算所有非命中候选人的信息完整度。报告中必须同时展示成功人数，避免出现“只成功少数人，但成功候选人的平均分很高”而被误解为整体效果很好。

### 7.2 如何判断第二阶段比第一阶段更好

比较顺序建议保持简单：

1. 先看检索成功率是否提高；
2. 再看成功候选人的字段准确率是否下降；
3. 最后看命中候选人的信息完整度是否提高；
4. 单独观察非命中候选人的平均完整度是否提高；
5. 最后并列比较三个阶段的 LLM 成本、总成本和 PDL 调用次数。

可以按以下方式得出结论：

| 对比结果 | 结论 |
| --- | --- |
| 成功率提高，准确率不下降，命中候选人完整度提高或不变 | 第二阶段更好 |
| 成功率不变，准确率不下降，命中候选人完整度提高 | 第二阶段更好 |
| 成功率下降 | 第二阶段在“能否找到人”方面变差 |
| 成功率提高，但准确率明显下降 | 有收益也有风险，不能直接判断为更好 |
| 命中候选人完整度提高，但准确率下降 | 返回得更多但错误也更多，属于混合结果 |
| 非命中候选人完整度提高 | 说明其他同名候选人的信息更丰富，但不代表基准候选人检索能力变好 |
| 所有评估项都不变 | 第二阶段没有观察到改善 |

第三阶段与第一阶段、第二阶段的比较使用同样的方法，不需要额外设计一套指标。

成本不与成功率、完整度或准确率合成一个综合分。报告应分别呈现质量变化和成本变化，例如“成功率提高5个百分点，同时100人总成本增加20%”，由业务再判断收益是否值得。

### 7.3 单个人物的阶段对比例子

| 阶段 | 是否成功 | 命中候选人完整度 | 命中候选人准确率 | 非命中候选人平均完整度 | 结论 |
| --- | --- | ---: | ---: | ---: | --- |
| 名字 | 是 | 50% | 100% | 36.36% | 基线 |
| 名字 + social links | 是 | 68.18% | 100% | 40.91% | 找到同一个人，且命中与非命中候选人的信息都更丰富 |
| 名字 + 照片 URL | 是 | 81.82% | 75% | 45.45% | 信息更多但错误增加，不能简单判断为更好 |

### 7.4 同一个人优化前后配对

优化前后必须使用相同的 `person_id + query_stage` 进行一一配对，不能只比较两轮100人的总体平均值。

配对前提：

- 使用同一批100个人；
- 全名查询文本完全相同；
- 全名 + link 使用同一个基准link；
- 命中规则、22个内容字段和计算公式不变；
- 记录优化前版本、优化后版本及执行时间。

每个人每种检索条件形成一行配对记录：

| person_id | 检索条件 | 优化前命中 | 优化后命中 | 完整度变化 | 准确率变化 | 非命中完整度变化 | 成本变化 | 变化结论 |
| --- | --- | --- | --- | ---: | ---: | ---: | ---: | --- |
| JOJO-001 | 全名 | 否 | 是 | 不适用 | 不适用 |  |  | 未命中 -> 命中，检索改善 |
| JOJO-002 | 全名 + link | 是 | 是 | +13.64个百分点 | 0 |  |  | 持续命中且信息更完整 |
| JOJO-003 | 全名 | 是 | 否 | 不适用 | 不适用 |  |  | 命中 -> 未命中，属于退化 |

100个人配对后，至少汇总以下四种变化数量：

```text
持续命中数 = 优化前命中、优化后仍命中的人数
新增命中数 = 优化前未命中、优化后命中的人数
退化未命中数 = 优化前命中、优化后未命中的人数
持续未命中数 = 优化前未命中、优化后仍未命中的人数
```

完整度和准确率变化只在“持续命中”的同一个基准候选人之间计算。由未命中变为命中或由命中变为未命中时，重点记录命中状态变化，不强行计算不存在的完整度、准确率差值。

如果优化前没有运行“全名 + 照片”，优化后的照片检索只能与优化后同版本的全名、全名 + link比较，不能称为照片检索的优化前后提升。若要评价照片检索的版本提升，需要优化前后都运行相同的照片查询。

### 8.4 报告详情附加项的数据处理与统计

以下统计用于解释核心结果为什么变化，放在报告详情或附录，不作为主汇报重点，也不与核心指标合成综合分。

#### 1. 模块返回情况

利用 `insights_status`、`photos_status`、`profile_status` 和 `social_status` 统计各模块返回数据的候选人比例。Summary当前没有独立status字段，可按Summary内容字段是否至少一个非空判断模块是否返回。

```text
模块返回率 = 该模块有数据的候选人数 / 参与统计的候选人总数 * 100%
```

命中候选人与非命中候选人分开统计，避免大量非命中候选人改变基准候选人的模块表现。

#### 2. 单字段对比

对22个内容字段分别比较优化前后表现：

- 命中候选人：统计每个字段的完整度和准确率；
- 非命中候选人：只统计每个字段的非空比例；
- 按全名、全名 + link、全名 + 照片分别展示。

单字段结果用于定位总体变化具体来自年龄、地区、邮箱、职位、教育、social URL或其他字段。

#### 3. 模块完整度

将22个内容字段按 Insights、Photos、Profile、Social、Summary分组，分别计算模块内字段的平均完整度：

```text
命中候选人模块完整度 = 模块内各字段正确找回得分之和 / 模块内内容字段数

非命中候选人模块完整度 = 模块内非空内容字段数 / 模块内内容字段数
```

模块完整度用于解释总体完整度提升来自哪个模块。

#### 4. Social数据

Social详情附加项包括：

- 返回的社交平台数量；
- 返回的social link数量；
- 与基准候选人一致的link数量；
- 错误link数量；
- 同平台link冲突数量；
- 各平台的返回情况。

命中候选人的正确、错误link通过基准数据判断；非命中候选人没有真值时只统计平台数和link非空情况。

#### 5. Photos数据

Photos详情附加项包括：

- Photos模块是否返回；
- `photos_identity_match_rate` 的值；
- 相似度达到80%的候选人数；
- `photos_authenticity_photos` 信息项数量；
- `photos_match_photos` 信息项数量；
- 有照片来源页的候选人数。

照片相似度达到80%仍按第4章的强绑定规则使用，详情统计本身不改变命中判定。

#### 6. 成本效果

成本详情附加项包括：

```text
平均每次检索成本 = 检索总成本 / 实际检索任务数

每次成功命中的平均成本 = 检索总成本 / 成功命中次数
```

并分别展示：

- 全名、全名 + link、全名 + 照片的平均成本；
- PDL调用任务与未调用任务的成功率、完整度、准确率和平均成本；
- 优化前后同一检索条件的成本变化；
- 重试和重复运行增加的实际成本。

当成功命中次数为0时，“每次成功命中的平均成本”记为不适用，不能进行除法。

## 9. 当前方案的最小执行流程

1. 产品、开发和测试先完成第10章评审，确认回显、命中、成本、PDL和证据来源口径。
2. 选择一批已经掌握确切信息的人物，并为每个人建立基准候选人数据。
3. 按 `字段整理.md` 提取26个原始字段，保留4个状态字段，并用22个内容字段进行评分。
4. 冻结 `person_id + query_stage` 配对查询集，优化前后不得临时更换人物或查询条件。
5. 分别生成名字、名字 + social links、名字 + 照片 URL 三组 `searchTool` 输入。
6. 通过接口运行 `searchTool`，保留每次运行的全部候选人原始结果、任务成本、provider摘要及详情顶层证据。
7. 按“social 冲突 -> social 命中 -> 照片80% -> 疑似/不命中”的顺序逐个判断候选人。
8. 对命中的候选人逐字段比较，计算命中候选人信息完整度和字段准确率。
9. 对每个非命中候选人计算非空信息完整度，疑似候选人也按非命中计算。
10. 为每个候选人分别整理 Insights、Photos、Profile、Social、Summary五个模块的证据来源，并保留无法归类的原始证据。
11. 同一条件重复运行时，分别计算每次结果，再汇总成功率、命中候选人平均完整度、平均准确率和非命中候选人平均完整度。
12. 按每个 `task_id` 统计 LLM 成本、总成本和PDL调用情况，不能按候选人重复累计。
13. 优化后按相同 `person_id + query_stage` 与优化前逐人配对，记录新增命中、退化未命中和持续命中变化。
14. 分别汇总三个检索阶段，先比较基准候选人的成功率、准确率和完整度，再观察非命中候选人的信息完整度及各阶段成本。
15. 完成100个人后，汇总 LLM 总成本、检索总成本、PDL调用次数和未调用次数；三个阶段全部执行时再汇总300次任务总计。
16. 按第11章生成主报告，将模块、字段、Social、Photos和成本效果细项放入附录。

## 10. 产品、开发与测试评审

本方案正式执行前，应由产品、开发和测试共同评审。评审目标不是增加更多指标，而是确认接口行为、字段含义和判定规则能够真实落地。

### 10.1 必须讨论的特别注意问题

“全名 + link”和“全名 + 照片”存在循环判断风险：

- link既是输入条件，又是命中判断字段；
- 照片URL既是输入条件，又可能被返回到 `photos_baseline_photo_url`；
- 如果系统只是把请求参数原样复制到候选人结果中，会导致虚假的命中、完整度和准确率提升。

评审必须明确：

1. 返回的social link是否由数据提供方实际检索并绑定到具体 `candidate_id`，还是请求参数回显；
2. 是否有provider或evidence能够证明link属于该候选人；
3. `photos_identity_match_rate` 是否由基准照片与候选人检索照片实际计算；
4. `photos_baseline_photo_url` 是否只是输入照片回显；
5. 直接回显字段如何在采集结果中标记，并从完整度、准确率计算中排除。

在以上问题未确认前，“全名 + link”或“全名 + 照片”的命中率不能作为正式结论。

### 10.2 其他评审确认项

| 评审项 | 需要确认的内容 |
| --- | --- |
| Social判定 | URL规范化规则、同平台link冲突优先级、多个link同时匹配和冲突时如何处理 |
| 照片判定 | 80%阈值的数据格式、计算对象、无可比照片时的返回值 |
| 成本字段 | `llm_cost`、`total_cost`、币种、`total_cost`是否已经包含LLM成本 |
| PDL调用 | `pdl_called`表示实际调用、缓存命中还是候选人来源；专用字段路径 |
| 证据来源 | 五个模块的证据字段路径及顶层 `evidence` 如何映射模块 |
| 失败与重试 | 失败任务是否产生费用，重试是否生成新 `task_id` |
| 字段口径 | 22个内容字段、空值、多值和直接回显的处理规则 |
| 版本对比 | 优化前后使用相同100人、相同查询文本和相同基准数据 |

### 10.3 评审交付结果

评审完成后应确认并记录：

- 最终字段路径和接口响应样例；
- 命中判断流程；
- 成本和PDL统计口径；
- 证据来源收集规则；
- 优化前后版本号及查询集；
- 第一版报告模板；
- 尚未解决的问题及负责人。

## 11. 第一版评估报告结构

第一版报告采用“主报告 + 详情附录”。主报告用于汇报结论，建议控制在4至6页；详情附录用于测试、产品和开发追查具体字段。

报告模板分两种使用方式：

- 首次运行只有当前版本数据：主报告展示当前全名、全名 + link的能力差异、100人结果和成本，不展示不存在的优化前后列；
- 后续优化版本：启用完整的优化前、优化后和同人配对页面，并沿用首次报告的字段与计算口径。

首次报告的主要作用是建立基线。后续报告在相同位置增加优化后数据和变化列，方便汇报人员直接复用版式。

### 11.1 第1页：执行摘要

第1页只回答“当前能力怎么样、优化后是否变好、成本是否可接受”。

基本信息：

| 项目 | 内容 |
| --- | --- |
| 样本 | 100个基准候选人 |

### 11.7 汇报展示原则

- 主报告只展示评估目的中的核心结果，不在首页堆放22个字段；
- 所有百分比同时显示分子和分母，例如 `82/100，82%`；
- 提升和下降使用统一方向符号，如 `↑`、`↓`、`→`；
- 颜色只用于辅助：提升用绿色、退化用红色、无变化用灰色；
- 每张图表标题直接写结论，例如“全名检索成功率提升5个百分点”，不要只写“成功率对比”；
- 任何总体结论都能够下钻到具体 `person_id`、候选人、字段和证据来源；
- 照片没有优化前基线时必须显著标注，避免错误归因。

## 12. 后续可考虑的指标建议

以下内容不纳入当前核心方案。先把检索成功率、命中候选人信息完整度、非命中候选人信息完整度、字段准确率和成本统计跑通后，再根据实际分析需要决定是否增加。

### 12.1 命中候选人的排名

同名候选人很多时，即使成功命中了 JOJO，JOJO 排第 1 和排第 20 的使用效果并不相同。后续可以增加“命中排名”或 Top 1/Top 5 命中情况。

### 12.2 相同条件下的结果一致性

如果同一个条件重复检索时结果经常变化，可以增加结果一致性指标，用于区分检索能力变化和外部数据源波动。

### 12.3 错误类型记录

可以给错误结果增加简单原因，例如：命中其他同名人物、错误 social link、错误照片、信息过期或多人信息混合。该内容主要用于定位问题，不一定需要计算成新的分数。

现阶段建议先不增加这些指标，先使用当前核心评估内容完成第一轮真实数据评估，再根据第一轮暴露的问题决定是否扩展。
