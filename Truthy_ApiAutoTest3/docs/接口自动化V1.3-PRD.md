# Gateway 接口自动化 V1.3 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.3 |
| 日期 | 2026-07-26 |
| 技术栈 | Python + pytest + requests + PyYAML |
| 核心目标 | 拆分接口定义与测试用例，解除多接口 Flow 对单接口用例的依赖 |
| 文档状态 | 待 Review |

## 2. 背景

V1.2 已具备单接口执行、日志记录、运行时变量传递、响应提取、断言、等待和多接口 Flow 编排能力。

当前 `data/cases/*.yaml` 同时保存以下内容：

- 接口的 `service_name`、`method_name`。
- 一组具体请求参数。
- 对应断言和响应提取规则。
- Flow 调用时复用的接口信息。

这种方式适合快速完成首个版本，但会产生两个问题：

1. 一个接口增加成功、缺参、多参、异常值等用例时，接口信息会与多组测试数据混在一起。
2. Flow 依赖单接口 case 文件。流程出现新接口时，必须先补一份可独立执行的单接口用例，才能进行流程编排。

V1.3 将“接口是什么”与“怎样测试接口”拆开，并让单接口 Cases 和多接口 Flows 成为并列的测试方式。

## 3. V1.3 目标

### 3.1 核心目标

1. 新增独立的接口定义层，只保存接口身份和调用路由信息。
2. 单接口用例引用接口定义，并允许一个接口配置多条独立测试用例。
3. 多接口 Flow 直接引用接口定义，不再依赖单接口 case。
4. 单接口 Cases 与多接口 Flows 互不依赖，分别管理自己的请求数据、断言和提取规则。
5. 保留 V1.2 的 Gateway 请求、日志、变量、断言、等待、轮询和统一执行入口能力。

### 3.2 成功标准

- 一个接口定义可被多条单接口用例复用。
- 同一个单接口 YAML 可管理成功、缺参、多参和异常参数等多条用例。
- 新接口只创建接口定义后，即可被 Flow 使用，不要求同时创建单接口用例。
- 修改单接口用例数据不会改变 Flow 的请求数据和执行结果。
- 修改 Flow 场景数据不会改变单接口用例。
- pytest 能分别收集并执行每一条单接口用例和每一条 Flow。

## 4. 核心依赖关系

```text
                  ┌── 单接口 Cases
接口定义 APIs ────┤
                  └── 多接口 Flows
```

依赖规则：

- APIs 是 Cases 和 Flows 共同依赖的基础定义。
- Cases 不依赖 Flows。
- Flows 不依赖 Cases。
- 接口定义不保存具体测试场景的数据和断言。
- 测试用例之间不通过修改 YAML 或共享全局业务变量传递数据。

## 5. 范围

### 5.1 V1.3 包含

- 新增 `data/apis/` 接口定义目录。
- 将接口定义与单接口测试数据拆分。
- 一个接口对应一个 case 集合，一个 case 集合支持多条用例。
- 每条单接口用例拥有独立的名称、标签、请求参数、断言和可选提取配置。
- Flow 步骤直接引用 API，不再引用 case YAML。
- Flow 与同名 Scenario 继续一一对应。
- Scenario 独立保存 Flow 各步骤的请求参数和场景断言。
- 加载阶段校验 API 引用、case ID、Flow step ID 和 YAML 必填字段。
- 支持按模块、标签、环境、Flow 名称继续运行测试。
- 保持请求和响应日志、脱敏、运行时变量、固定等待及条件轮询能力。

### 5.2 V1.3 不包含

- Web 管理页面、用户系统和权限管理。
- 数据库存储及 YAML 与数据库同步。
- 在线编辑、调试和执行接口用例。
- Allure、Jenkins、飞书等第三方集成。
- 并发步骤、条件分支、循环和任意 Python 脚本。
- 参数组合自动生成、模糊测试和数据驱动笛卡尔积。
- OpenAPI、Swagger 或其他接口文档自动导入。
- 新增复杂断言类型；V1.3 继续使用现有断言能力。

Web 平台化想法统一记录在 `docs/接口自动化需求池.md`，不进入 V1.3 的开发和验收范围。

## 6. 数据目录规划

```text
data/
├── api/
│   └── gateway_invoke.yaml               # Gateway 固定 HTTP 地址等传输配置
├── apis/
│   ├── CreateAnonymousSession.yaml        # 接口定义
│   ├── CreateIntentTask.yaml
│   └── GetTask.yaml
├── cases/
│   ├── CreateAnonymousSession.yaml        # 单接口用例集合
│   ├── CreateIntentTask.yaml
│   └── GetTask.yaml
├── flows/
│   └── AnonymousSessionMediaSearch.yaml   # 多接口步骤编排
└── scenarios/
    └── AnonymousSessionMediaSearch.yaml   # 对应流程的业务数据和断言
```

目录职责：

| 目录 | 职责 | 不保存 |
| --- | --- | --- |
| `data/api/` | Gateway HTTP 地址和公共传输配置 | 业务接口和测试数据 |
| `data/apis/` | `service_name`、`method_name` 等接口定义 | 测试参数、断言、流程顺序 |
| `data/cases/` | 单接口的多条测试用例 | 接口路由、流程步骤 |
| `data/flows/` | 多接口调用顺序、提取、等待和轮询 | 单接口用例引用、具体业务输入 |
| `data/scenarios/` | Flow 各步骤的请求数据和场景断言 | 接口路由、Python 执行逻辑 |

## 7. 接口定义模型

### 7.1 最小格式

```yaml
id: CreateIntentTask
name: 创建并启动线索搜索任务
request:
  service_name: tool.people_insight.SearchService
  method_name: CreateIntentTask
```

### 7.2 字段规则

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 接口唯一标识，建议与文件名一致 |
| `name` | 是 | 接口中文名称 |
| `request.service_name` | 是 | Gateway 业务服务名称 |
| `request.method_name` | 是 | Gateway 业务方法名称 |

接口定义不保存 `params`、`assert`、`extract` 或 `tags`。这些字段都属于具体测试用例或流程场景。

## 8. 单接口用例模型

### 8.1 一个接口配置多条用例

```yaml
api: CreateIntentTask
cases:
  - id: create_task_success
    name: 创建搜索任务成功
    tags: [smoke, search, positive]
    request:
      params:
        client_request_id: "{{client_request_id}}"
        match_strategy: UNION
        clues:
          - type: FULL_NAME
            full_name_query:
              full_name: JOJO CCQQ MOCK
        additional_details: []
    assert:
      http_status: 200
      gateway:
        code: 0
        message: ok
      response:
        id: req_0
        success: true
        code: 0
        message: ok
      data_fields:
        - status
        - task_id
    extract:
      task_id: $.task_id

  - id: create_task_missing_clues
    name: 缺少 clues 时创建失败
    tags: [search, negative]
    request:
      params:
        client_request_id: "{{client_request_id}}"
        match_strategy: UNION
        additional_details: []
    assert:
      http_status: 200
      gateway:
        code: 0
      response:
        id: req_0
        success: false
```

### 8.2 用例规则

- `api` 引用 `data/apis` 中的接口 ID，不直接重复 `service_name` 和 `method_name`。
- `cases` 必须是非空列表。
- 同一文件内的 `case.id` 必须唯一。
- 每条 case 的 `request.params` 表示该次请求的完整业务参数，不与其他 case 合并。
- 缺参用例通过不声明目标参数实现，不需要额外的删除语法。
- 多参用例直接在当前 case 的 `request.params` 中增加参数。
- 每条 case 独立保存断言，成功用例与失败用例互不继承断言。
- `extract` 为可选字段，只在该 case 自身需要保存响应字段时使用。
- pytest 将 `cases` 中的每个元素收集为一条独立测试用例。
- 单条 case 失败不影响其他 case 继续执行，除非用户使用 pytest 的中断参数。

## 9. 多接口 Flow 模型

### 9.1 Flow 直接引用接口定义

```yaml
name: 搜索流程
tags: [flow, media, search]
steps:
  - id: create_task
    api: CreateIntentTask
    extract:
      task_id: $.task_id

  - id: poll_task
    api: GetTask
    until:
      path: $.status
      equals: SUCCEEDED
      interval_seconds: 2
      timeout_seconds: 120

  - id: list_candidates
    api: ListTaskCandidates
    extract:
      candidate_id: $.items[0].candidate_id

  - id: candidate_detail
    api: GetTaskCandidateDetail
```

原 `call: CreateIntentTask.yaml` 调整为 `api: CreateIntentTask`。Flow 只依赖接口定义，不读取单接口 case 的默认参数、断言或提取配置。

### 9.2 Scenario 保存完整步骤数据

```yaml
name: 姓名搜索成功场景
step_data:
  create_task:
    params:
      client_request_id: "{{client_request_id}}"
      match_strategy: UNION
      clues:
        - type: FULL_NAME
          full_name_query:
            full_name: JOJO CCQQ MOCK
      additional_details: []
    assert:
      http_status: 200
      gateway:
        code: 0
        message: ok
      response:
        id: req_0
        success: true
        code: 0
        message: ok
      data_equals:
        status: QUEUED

  poll_task:
    params:
      task_id: "{{task_id}}"
    assert:
      http_status: 200
      gateway:
        code: 0
      response:
        id: req_0
        success: true
      data_equals:
        status: SUCCEEDED
```

Scenario 规则：

- 普通接口步骤应在 `step_data.<step_id>.params` 中提供该步骤的完整业务参数。
- Flow 场景断言不继承单接口 case 断言，应在 Scenario 中独立声明。
- 前序步骤的响应值继续通过 `extract` 写入当前 Flow 的 `RuntimeContext`。
- 后续步骤通过 `{{变量名}}` 使用已提取的值。
- 不同 Flow 的运行时变量保持隔离。
- Flow 和 Scenario 文件继续使用同名配对规则。

## 10. 执行规则

### 10.1 单接口执行

1. 扫描 `data/cases/*.yaml`。
2. 校验 case 文件引用的 API 是否存在。
3. 将 API 的 `service_name`、`method_name` 与当前 case 的 `request.params` 组合为执行数据。
4. 解析运行时变量并发送 Gateway 请求。
5. 执行当前 case 自己的断言和可选提取。
6. 以 `接口ID::case.id` 作为 pytest 用例标识。

### 10.2 Flow 执行

1. 加载同名 Flow 和 Scenario。
2. 校验每个接口步骤引用的 API 是否存在。
3. 将 API 的路由信息与 Scenario 对应步骤的完整 `params` 组合。
4. 解析当前 Flow 的运行时变量并发送 Gateway 请求。
5. 执行 Scenario 中当前步骤的断言。
6. 执行 Flow 声明的提取、等待或轮询。
7. 任一步骤失败后立即终止当前 Flow。

### 10.3 数据优先级

V1.3 不在 API、case 和 Scenario 之间合并默认业务参数：

```text
接口路由：API 定义
单接口参数：当前 case.request.params
流程参数：当前 Scenario 的 step_data.<step_id>.params
动态数据：RuntimeContext 解析 {{变量名}}
```

这种规则保证缺参用例表达直接，也避免 Flow 因单接口默认参数变化而发生隐式变化。

## 11. 配置校验与失败策略

在发送第一个请求前，至少完成以下校验：

- API 文件根节点为对象，必填字段完整。
- API ID 在全部接口定义中唯一。
- API ID 与文件名一致。
- case 文件根节点为对象，`api` 引用存在，`cases` 非空。
- 同一 case 文件中的 case ID 唯一。
- case 的 `request.params` 为对象或空对象。
- Flow 与 Scenario 文件同名且一一对应。
- Flow 步骤 ID 唯一，步骤引用的 API 存在。
- Scenario 的 `step_data` 只引用 Flow 中已存在的 step ID。
- 请求、断言、提取、等待和轮询字段符合现有格式。

失败信息至少包含文件名、API ID、case ID 或 Flow step ID，确保可以直接定位问题。配置校验失败时不得发送请求。

## 12. 兼容与迁移要求

V1.3 的数据结构变化涉及现有全部 case 和 Flow 文件，实施时采用一次性数据迁移：

1. 从现有 `data/cases` 提取 `service_name` 和 `method_name`，生成对应 API 定义。
2. 将现有单接口 YAML 转换为包含一条 case 的 case 集合，原请求参数和断言保持不变。
3. 将 Flow 的 `call` 引用改为 `api` 引用。
4. 将 Flow 当前依赖的 case 默认参数和断言复制到对应 Scenario；流程需要的提取规则移入对应 Flow step，保证迁移后流程行为一致。
5. 迁移完成后，执行器只识别 V1.3 格式，不长期维护 V1.2/V1.3 双格式分支。

迁移期间不得改变现有接口的业务参数、断言预期、调用顺序和变量名称。

## 13. 验收标准

### 13.1 接口定义

1. 每个业务接口只维护一份 API 定义。
2. API 定义不包含测试参数、断言、标签或提取规则。
3. 引用不存在或重复的 API 时，在发送请求前给出明确错误。

### 13.2 单接口用例

1. 同一接口 YAML 至少可配置并收集两条独立 case。
2. 成功、缺参、多参和异常值用例可分别声明完整参数与断言。
3. 修改其中一条 case 不会改变同文件其他 case。
4. pytest 输出中可以通过 API ID 和 case ID 唯一定位用例。
5. 现有标签、环境选择、日志和变量替换能力继续有效。

### 13.3 多接口 Flow

1. Flow 只引用 API，不读取 `data/cases`。
2. 仅创建 API 定义后即可在 Flow 中使用新接口。
3. Flow 每个步骤的参数和断言均来自对应 Scenario。
4. 单接口 case 的新增、删除或修改不影响 Flow。
5. 前序响应提取和后续步骤变量引用继续正常工作。
6. 固定等待、条件轮询、日志及失败即停止能力继续有效。

### 13.4 回归

1. 现有单接口成功用例迁移后请求与断言行为不变。
2. 现有 `AnonymousSessionMediaSearch` 流程迁移后调用顺序和结果不变。
3. 自动会话、Gateway 请求封装、COS PUT、日志脱敏和统一执行入口回归通过。

## 14. 测试策略

- API 定义加载、重复 ID、缺失字段和不存在引用测试。
- 单接口多 case 收集、ID 唯一性和独立执行测试。
- 成功、缺参、多参及异常参数的 YAML 解析测试。
- API 路由与 case 参数组合测试。
- Flow 不读取 case 文件的隔离性测试。
- Flow API 引用、Scenario 完整参数及运行时变量传递测试。
- V1.2 数据迁移后的请求对象和断言配置对比测试。
- 运行全部现有测试，确认日志、会话、等待、轮询和 COS PUT 无回归。

## 15. 交付物

- 独立的 API 定义及加载能力。
- 支持多 case 的单接口 YAML 结构及通用执行入口。
- 直接引用 API 的 Flow YAML 结构及执行能力。
- 完成迁移的现有接口、单接口用例、Flow 和 Scenario 数据。
- 配置校验和对应自动化测试。
- 更新后的使用说明与 YAML 示例。
